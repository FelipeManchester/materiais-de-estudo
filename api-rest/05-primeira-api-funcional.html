Material de estudo — API REST — Parte 5

Primeira API funcional

Este material explica como uma API REST é construída na prática — as peças que toda stack tem, só com nomes diferentes. Não assume Node, Python, Java ou qualquer outra linguagem: os conceitos aqui valem antes de você escrever a primeira linha de código na stack escolhida.

1. Por que este material é independente de stack

A parte 4 comparou as opções de mercado, mas não fixou uma — a escolha final é sua, e pode até mudar no futuro (sua ou de quem mais ler este material). O que não muda ao trocar de stack são os conceitos: toda API HTTP, em qualquer linguagem, resolve os mesmos problemas — receber uma requisição, decidir o que fazer com ela, validar entrada, buscar/alterar dado, devolver uma resposta.

O que muda de stack pra stack é só a sintaxe e o nome que cada framework dá pra essas peças. Depois de decidir a stack, a tradução desses conceitos pro código real é rápida — e aí sim vale conversar/pesquisar as particularidades da ferramenta escolhida.

2. As camadas de uma API, em qualquer stack

Praticamente toda API minimamente organizada separa responsabilidades em camadas. Os nomes variam (controller/handler, service/use case, repository/DAO), mas o papel de cada uma é o mesmo:

RoteamentoRecebe a requisição HTTP, identifica método + URI, decide qual handler chamar
↓
Handler / ControllerLê dados da requisição (params, query, body), chama a lógica de negócio, monta a resposta
↓
ValidaçãoConfere se o que chegou é válido antes de prosseguir (formato, campos obrigatórios, tipos)
↓
Lógica de negócio / ServiceRegras da aplicação: "não pode cancelar pedido já entregue", "e-mail precisa ser único"
↓
Acesso a dados / RepositoryFala com o banco de dados (ou outro armazenamento) — é a única camada que sabe que existe um banco

Por que separar em camadas, e não escrever tudo dentro de uma função só: cada camada muda por um motivo diferente. Trocar de banco de dados só deveria afetar a camada de acesso a dados. Mudar uma regra de negócio não deveria exigir mexer no roteamento. Isso é o mesmo princípio de separação de responsabilidades da restrição Client-Server que você viu na parte 1, só que aplicado dentro do servidor.

Numa API pequena de estudo, tudo bem misturar camadas no começo pra não travar em arquitetura antes de ter algo funcionando. O importante é reconhecer essas responsabilidades — separar em arquivos/pastas vem depois, naturalmente, quando o código começar a doer.

3. Roteamento: da URI ao handler

Todo framework web tem um mecanismo que mapeia método + padrão de URI para uma função que trata aquela requisição. Conceito, independente de sintaxe:

GET    /pedidos          ->  função "listarPedidos"
GET    /pedidos/:id      ->  função "buscarPedido"     (:id = parte variável da URI)
POST   /pedidos          ->  função "criarPedido"
PATCH  /pedidos/:id      ->  função "atualizarPedido"
DELETE /pedidos/:id      ->  função "removerPedido"

Repare que esse mapeamento é exatamente o desenho de URIs da parte 3 — o roteamento é onde aquele design vira código de verdade. Cada framework tem sua sintaxe pra declarar isso (arquivo de rotas, decorators, convenção de pastas), mas a estrutura por trás é sempre essa tabela método+padrão → função.

Parâmetros de rota vs. query string

Vale reforçar a diferença, porque os dois chegam de formas diferentes no handler:

  • Parâmetro de rota (/pedidos/501): parte obrigatória da URI, identifica qual recurso. Framework extrai isso e entrega como algo tipo params.id = "501".
  • Query string (/pedidos?status=pago): parte opcional, geralmente filtro/paginação/ordenação (parte 3). Framework entrega separado, tipo query.status = "pago".

4. O objeto de requisição e o de resposta

Todo handler, em qualquer stack, recebe (de alguma forma) acesso a duas coisas:

Do lado da requisiçãoDo lado da resposta
Método HTTP usadoCódigo de status a devolver (parte 2)
Parâmetros de rota (:id)Headers a devolver (ex: Location num 201)
Query string (filtros, paginação)Body da resposta (o JSON com o resultado)
Headers recebidos (Authorization, Content-Type)
Body recebido (dado enviado em POST/PUT/PATCH)

O trabalho de um handler, resumido: ler o que precisar do lado "requisição", processar, e preencher o lado "resposta" — nessa ordem, sempre.

5. Persistência: onde os dados realmente vivem

Pra ter uma API "funcional" de verdade, o dado precisa sobreviver além de uma única execução do processo. Três níveis, do mais simples ao mais realista:

  1. Em memória (array/objeto na aplicação): mais simples possível pra aprender roteamento/handlers sem se preocupar com banco ainda. Problema: dado some toda vez que o servidor reinicia. Bom só pra um primeiro protótipo de estudo.
  2. Arquivo local (JSON, SQLite): sobrevive a reinícios, ainda simples de configurar, sem precisar instalar um banco separado. Passo intermediário razoável.
  3. Banco de dados de verdade (PostgreSQL, MySQL, MongoDB...): o que uma API real usa em produção. Introduz um novo conceito importante: ORM (Object-Relational Mapper) ou query builder — uma biblioteca que traduz chamadas no código pra comandos SQL (ou equivalente), evitando escrever SQL cru toda vez. Cada stack tem os seus (ex: no ecossistema Node existem múltiplas opções de ORM; em outras linguagens, o padrão costuma vir embutido no framework, como visto na parte 4).

Sugestão de progressão pra essa parte da trilha: comece em memória pra validar que os endpoints respondem certo (métodos, status codes, formato de resposta — tudo que as partes 2 e 3 ensinaram), depois evolua pra um banco de verdade. Trocar a camada de persistência depois não deveria exigir tocar no roteamento nem nos handlers, se as camadas da seção 2 estiverem bem separadas — esse é o teste real de uma boa separação.

6. Validação de entrada

Toda API precisa desconfiar do que chega — nunca assumir que o cliente mandou o formato certo. Duas categorias de validação:

  • Validação de forma (schema): campo existe? é do tipo certo (string, número, data)? está dentro de um formato esperado (e-mail válido, data no formato certo)? Isso é mecânico e várias stacks têm bibliotecas prontas pra declarar o formato esperado e validar automaticamente.
  • Validação de regra de negócio: mesmo com formato correto, faz sentido no contexto? ("cliente existe?", "quantidade não pode ser negativa", "não pode cancelar pedido já entregue"). Essa fica na camada de lógica de negócio (seção 2), não na validação de schema.

Onde isso se conecta com o que você já viu: validação de schema que falha devolve 400 Bad Request; validação de regra de negócio que falha geralmente devolve 422 Unprocessable Entity ou 409 Conflict — ver a tabela de status codes da parte 2.

7. Tratamento de erros centralizado

Erro comum de quem está começando: colocar um try/catch (ou equivalente) repetido dentro de cada handler, cada um decidindo na mão qual status code devolver. Funciona, mas duplica lógica e é fácil esquecer um caso.

Praticamente toda stack madura oferece um mecanismo de tratamento de erro centralizado: um ponto único (um handler especial, um middleware de erro, um interceptor) que captura qualquer erro não tratado nos handlers individuais e decide o status code + formato da resposta de erro, de forma consistente pra API inteira.

Handler de "criar pedido" lança erro "produto não encontrado"
                    ↓
     (framework intercepta o erro automaticamente)
                    ↓
Tratador central de erros decide:
  - erro é "não encontrado" -> 404
  - erro é "validação"      -> 400
  - erro é "regra de negócio" quebrada -> 422
  - erro não reconhecido    -> 500 (e loga pra investigar depois)

Formato de resposta de erro consistente também importa — definir um "contrato de erro" (ex: sempre { "erro": { "mensagem": "...", "codigo": "..." } }) que toda a API segue, pra quem consome não precisar tratar cada endpoint de erro de um jeito diferente.

8. Middlewares / interceptors: o conceito

Quase toda stack tem algum mecanismo de função que roda no meio do caminho, entre a requisição chegar e o handler final processar — geralmente chamado de middleware (Node, Python) ou interceptor/filter (Java, .NET). Serve pra lógica que se repete em vários endpoints:

  • Checar se existe um token válido no header Authorization antes de deixar a requisição continuar (autenticação — assunto da próxima parte da trilha)
  • Logar toda requisição que chega (método, URI, tempo de resposta)
  • Tratamento de erro centralizado, como visto na seção anterior, geralmente é implementado como um middleware especial
  • Parsing do body da requisição (transformar o JSON cru recebido em um objeto que o handler consegue usar)

Ideia central: em vez de repetir a mesma checagem em cada handler, você registra uma função que roda automaticamente antes (ou depois) de qualquer rota — ou só das rotas que você escolher.

9. Estrutura de projeto sugerida

Nomes de pasta variam por convenção de stack, mas a divisão conceitual costuma seguir as camadas da seção 2:

projeto/
├── rotas/         (ou routes/)      -> mapeamento URI -> handler
├── handlers/      (ou controllers/) -> lê requisição, chama lógica, monta resposta
├── servicos/      (ou services/)    -> regras de negócio
├── dados/         (ou repositories/) -> acesso à persistência
├── validacao/     (ou schemas/)     -> definição do formato esperado de cada entrada
└── middlewares/                     -> funções que rodam no meio do caminho

Não existe uma estrutura "oficial" — cada framework tem convenções próprias (algumas impõem essa estrutura, como vimos na parte 4 sobre frameworks opinativos; outras deixam livre). O que importa é reconhecer essas responsabilidades quando for organizar o código, independente de como as pastas acabam se chamando na prática.

10. Testando manualmente antes de qualquer front-end

Antes de conectar um front-end, teste a API isoladamente — isso isola problemas: se algo não funciona, você sabe que é a API, não uma interação complicada entre duas aplicações.

Ferramentas comuns pra isso, nenhuma delas específica de stack:

  • curl: linha de comando, vem pré-instalado na maioria dos sistemas. Rápido pra testar um endpoint isolado.
  • Postman / Insomnia: interface gráfica, permite salvar coleções de requisições, reutilizar token de autenticação entre chamadas, ver resposta formatada.
  • Extensão de cliente HTTP no editor (ex: arquivos .http no VS Code): fica junto do código, versionável no git.
# Exemplo com curl, testando o ciclo completo de um recurso
curl -X POST http://localhost:3000/pedidos \
  -H "Content-Type: application/json" \
  -d '{"produto": "livro", "quantidade": 2}'

curl http://localhost:3000/pedidos/501

curl -X PATCH http://localhost:3000/pedidos/501 \
  -H "Content-Type: application/json" \
  -d '{"status": "pago"}'

curl -X DELETE http://localhost:3000/pedidos/501

Checklist mínimo pra considerar um endpoint "funcional": responde com o status code certo (parte 2), responde no formato esperado (JSON consistente), lida com entrada inválida sem quebrar (400/422, não 500), e recurso criado/alterado realmente persiste entre requisições diferentes.

11. Erros conceituais comuns

  1. "Preciso decidir a arquitetura perfeita antes de escrever a primeira rota" — Não. Comece simples (até com tudo num arquivo só), separe em camadas conforme o código for crescendo e a mistura começar a atrapalhar.
  2. "Sem banco de dados não é uma API de verdade" — Não pro estágio de aprendizado. Uma API em memória que responde certo nos métodos, status codes e formato já validou os conceitos das partes 2 e 3. Banco entra depois, como camada de persistência isolada.
  3. "Validação e regra de negócio são a mesma coisa" — Não, ver seção 6. Formato errado é um tipo de problema (400); dado com formato certo mas que viola uma regra do domínio é outro (422/409).
  4. "Preciso testar direto pelo front-end pra saber se a API funciona" — Não, e isso dificulta debugar. Testar a API isolada (seção 10) primeiro elimina uma camada inteira de possíveis problemas.

12. O que vem a seguir

Com os conceitos de estrutura, roteamento, persistência e tratamento de erro entendidos, a trilha segue para:

  1. Autenticação e autorização (JWT, API keys, OAuth — visão geral).
  2. Boas práticas de produção: versionamento, tratamento de erros, validação, documentação (OpenAPI/Swagger).

Este material ficou no nível de conceito, de propósito — independente da stack que você (ou quem mais estiver lendo) escolheu na parte 4. As nuances de sintaxe e ferramentas específicas da stack escolhida valem a pena conversar separadamente, fora deste arquivo, pra este material continuar servindo de referência não importa a tecnologia usada.
