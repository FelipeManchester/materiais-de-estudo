Design de recursos e URIs

Parte 1 explicou a teoria, parte 2 explicou o protocolo. Agora é a parte que você mais vai usar no dia a dia: como nomear endpoints pra que qualquer pessoa (ou você, 6 meses depois) entenda a API só de olhar a URI.

1. Recursos, não ações

A regra mãe, de onde todas as outras derivam: URI identifica uma coisa (recurso), não uma ação. A ação já está no verbo HTTP (parte 2). Repetir a ação na URI é redundante e é o sinal mais claro de uma API "RPC disfarçada de REST".

Evitar

GET /getPedidos POST /criarPedido POST /deletarPedido/501 POST /pedidos/501/atualizar

Preferir

GET /pedidos POST /pedidos DELETE /pedidos/501 PATCH /pedidos/501

Na coluna da direita, o verbo já diz "criar", "deletar", "atualizar" — repetir isso no caminho é ruído. A URI só precisa dizer qual recurso.

2. Regras de nomeação de URIs

  • Substantivos, sempre no plural: /pedidos, não /pedido. Mesmo pra buscar um item único (/pedidos/501), a coleção continua no plural — só muda o que vem depois.
  • Minúsculo, sem acentuação: /produtos, não /Produtos ou /prodútos. URIs são tecnicamente case-sensitive; minúsculo evita ambiguidade e bugs bobos.
  • kebab-case pra palavras compostas: /itens-pedido, não /itensPedido nem /itens_pedido. Convenção de mercado predominante em URIs (diferente de JSON, onde camelCase é comum nos nomes de campo).
  • Sem barra no final: /pedidos, não /pedidos/. Escolha uma forma e seja consistente — servidores tratam as duas como coisas diferentes por padrão.
  • Sem extensão de arquivo: /relatorios/3, não /relatorios/3.json. Formato se negocia pelo header Accept (parte 2), não pela URI.
  • Identificador do recurso é opaco: cliente não deveria precisar "decodificar" ou montar lógica em cima do formato do ID (seja número sequencial, UUID, o que for) — trata como string opaca.

3. Coleção vs. item

Já apresentado na parte 1, vale reforçar o padrão de URI:

GET    /pedidos        <- coleção: lista de pedidos
POST   /pedidos        <- cria um novo pedido dentro da coleção
GET    /pedidos/501    <- item: um pedido específico
PUT    /pedidos/501    <- substitui esse item
PATCH  /pedidos/501    <- atualiza parte desse item
DELETE /pedidos/501    <- remove esse item

Padrão: coleção nunca recebe PUT/PATCH/DELETE diretamente (não faz sentido "substituir todos os pedidos de uma vez" na maioria dos casos) — essas operações agem sobre um item.

4. Aninhamento de recursos

Quando um recurso só existe no contexto de outro (relação de posse/composição), aninha na URI:

GET /pedidos/501/itens       <- itens do pedido 501
GET /pedidos/501/itens/7     <- item específico desse pedido

Mas cuidado com aninhamento profundo demais — fica ilegível e acopla URIs a uma hierarquia rígida:

Evitar (aninhamento excessivo)

/clientes/42/pedidos/501/itens/7/avaliacoes/3

Preferir (achatar a partir de 2 níveis)

/pedidos/501/itens/7 /avaliacoes/3

Regra prática de mercado: aninha 1 nível quando o recurso filho não existe fora do pai (item só existe dentro de um pedido). A partir daí, se o recurso tem identidade própria e pode ser acessado/referenciado sozinho, trata como recurso de primeiro nível e relaciona via campo no body ou query string, não aninhamento.

5. Ações que não são CRUD puro

Nem tudo é criar/ler/atualizar/deletar um registro. Coisas como "cancelar pedido", "fazer login", "reenviar e-mail de confirmação" são ações de negócio, não um CRUD direto sobre um campo.

Convenção de mercado predominante: modela como um sub-recurso no plural, verbo no infinitivo, ou substantivo que representa a ação como "coisa", sempre via POST:

POST /pedidos/501/cancelamento   <- cria "o cancelamento" como recurso
POST /sessoes                    <- login = criar uma sessão
DELETE /sessoes/atual            <- logout = remover a sessão

<- variação mais pragmática, muito comum na prática:
POST /pedidos/501/cancelar
POST /pedidos/501/reenviar-confirmacao

Não existe consenso 100% "puro" aqui — mesmo APIs bem desenhadas de mercado misturam os dois estilos. O importante é: continua sendo POST (não é seguro, não é idempotente por padrão), e o nome da URI ainda descreve uma coisa (o cancelamento, a sessão) ou pelo menos um verbo claro, não uma chamada de função genérica tipo /processar.

6. Filtros e busca

Filtro não é recurso novo — é query string em cima da coleção:

GET /pedidos?status=pago
GET /pedidos?status=pago&cliente_id=42
GET /pedidos?criado_apos=2026-01-01

Erro comum: criar endpoint separado pra cada combinação de filtro (/pedidos-pagos, /pedidos-por-cliente/42). Isso multiplica endpoints à toa — o recurso continua sendo "pedidos", o filtro é só um parâmetro de consulta sobre a mesma coleção.

7. Paginação

Coleção grande nunca deveria voltar inteira numa resposta só. Dois estilos comuns:

Offset/limit (mais simples, mais comum em APIs pequenas/médias)

GET /pedidos?offset=40&limit=20

{
  "dados": [ ... 20 pedidos ... ],
  "total": 187,
  "offset": 40,
  "limit": 20
}

Simples de implementar, mas degrada em tabelas muito grandes (banco ainda precisa "pular" as linhas anteriores) e pode duplicar/pular itens se dados forem inseridos/removidos entre uma página e outra.

Cursor-based (mais robusto, comum em APIs de alto volume)

GET /pedidos?limit=20&cursor=eyJpZCI6NTIwfQ

{
  "dados": [ ... 20 pedidos ... ],
  "proximo_cursor": "eyJpZCI6NTQwfQ"
}

Cursor é um ponteiro opaco pra "onde parei" (geralmente baseado no último ID/timestamp visto), não um número de posição. Evita os problemas de offset em dados que mudam constantemente. Custo: não dá pra "pular direto pra página 8" como no offset.

8. Ordenação

Também via query string, convenção comum usando prefixo - pra ordem decrescente:

GET /pedidos?sort=criado_em        <- crescente
GET /pedidos?sort=-criado_em       <- decrescente
GET /pedidos?sort=status,-total    <- múltiplos critérios

9. Erros conceituais comuns

  1. "URI precisa refletir a estrutura do banco de dados" — Não. URI reflete o modelo do domínio exposto pra fora, não as tabelas internas. Podem (e costumam) ser diferentes.
  2. "Todo filtro precisa virar rota nova" — Não, ver seção 6. Query string existe exatamente pra isso.
  3. "Verbo no nome do endpoint deixa mais claro" — Geralmente o oposto: se o verbo HTTP já diz a ação, repetir na URI (/getPedidos) é sinal de design RPC, não REST (ver seção 1 e Nível 2 vs Nível 0 da parte 1).
  4. "Singular ou plural, tanto faz" — Tecnicamente funciona dos dois jeitos, mas misturar (/pedido aqui, /produtos ali) quebra previsibilidade. Escolher plural sempre e manter consistente é a convenção dominante de mercado.

10. O que vem a seguir

Este documento cobriu como desenhar o "vocabulário" da API. A partir daqui a trilha sai da teoria/convenção e vai pra prática de construção:

  1. Escolha de stack: qual linguagem/framework vamos usar pra construir (reaproveitar JavaScript no back-end via Node.js está em aberto).
  2. Primeira API funcional: colocar a mão na massa.
  3. Autenticação e autorização (JWT, API keys, OAuth — visão geral).
  4. Boas práticas de produção: versionamento, tratamento de erros, validação, documentação (OpenAPI/Swagger).

Quando terminar de ler este arquivo, volte com suas dúvidas. Perguntas do tipo "quando vale a pena aninhar 2 níveis?" ou "por que cursor é melhor que offset em produção?" são o tipo de coisa que vale esclarecer antes de escolher a stack e começar a codar.
