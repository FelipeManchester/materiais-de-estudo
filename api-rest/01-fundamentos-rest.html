Material de estudo — API REST — Parte 1

Fundamentos de API REST

Teoria e contexto histórico. Antes de escrever uma linha de código, o objetivo aqui é você entender o problema que REST resolve, de onde ele veio e como pensar em termos de recursos. Isso muda completamente como você desenha uma API depois.

1. O que é uma API, antes de falar de REST

API (Application Programming Interface) é um contrato: um conjunto de regras que permite que dois sistemas de software conversem entre si sem que um precise conhecer os detalhes internos do outro.

Você já consome APIs há tempos no front-end: quando faz fetch('/api/users'), está seguindo um contrato que alguém definiu no back-end. A pergunta que este material responde é: quem define esse contrato, e por quê da forma que é definido?

REST é um estilo de arquitetura para desenhar esse contrato quando a comunicação acontece pela web, usando HTTP. Não é um protocolo, não é uma biblioteca, não é um framework. É um conjunto de restrições (constraints) que, se seguidas, trazem propriedades desejáveis ao sistema (escalabilidade, simplicidade, independência entre cliente e servidor).

2. Contexto histórico: de onde veio o REST

2.1 O problema em 1999-2000

No fim dos anos 90, a web já era grande, mas ainda era usada majoritariamente para servir páginas HTML estáticas ou geradas no servidor (CGI, ASP). Ao mesmo tempo, a indústria de software corporativo (Microsoft, IBM, etc.) estava empurrando SOAP (Simple Object Access Protocol) e arquiteturas RPC (Remote Procedure Call) como forma de fazer sistemas distribuídos conversarem — geralmente com XML pesado, contratos rígidos (WSDL) e muita complexidade de infraestrutura.

Havia uma pergunta em aberto: a própria arquitetura da web (HTTP, URIs, hipertexto) já não era, por si só, um jeito eficiente de construir sistemas distribuídos em larga escala? Afinal, a web já escalava para milhões de usuários todos os dias.

2.2 Roy Fielding e a tese de doutorado

Em 2000, Roy Fielding publicou sua tese de doutorado na UC Irvine, intitulada:

"Architectural Styles and the Design of Network-based Software Architectures"

Fielding não era um acadêmico qualquer estudando a web de fora: ele foi um dos autores das especificações HTTP/1.0, HTTP/1.1 e URI, e cofundador do projeto Apache HTTP Server. Ou seja, ele ajudou a construir a própria infraestrutura que a web usa, e sua tese é, em grande parte, uma explicação retroativa e formalizada de por que a web funciona tão bem em escala — e como generalizar esses princípios para desenhar outros sistemas.

No Capítulo 5 dessa tese, ele nomeia esse estilo arquitetural de REST — Representational State Transfer.

Ponto importante: REST não foi inventado do zero. Ele foi extraído e formalizado a partir de padrões que já existiam informalmente na arquitetura da web (HTTP, cache de navegador/proxy, URLs, links). Fielding deu nome, formalizou as regras e explicou o "porquê" arquitetural por trás de decisões que já existiam.

2.3 O nome "Representational State Transfer"

O nome é estranho à primeira vista, mas faz sentido decomposto:

  • Resource (Recurso): tudo que a API expõe é modelado como um "recurso" — um usuário, um pedido, um produto. Não é uma "função para chamar", é uma "coisa que existe".
  • Representation (Representação): o cliente nunca recebe o recurso "de verdade" (o registro cru do banco de dados). Ele recebe uma representação desse recurso em um formato (JSON, XML, HTML) em um dado momento.
  • State Transfer (Transferência de estado): cada interação transfere o estado necessário para o cliente entender ou modificar o recurso, sem que o servidor precise "lembrar" de conversas anteriores (chegamos nisso: statelessness).

3. Qual problema o REST resolve, na prática

Antes de aceitar as regras do REST, é importante entender os problemas reais que essas regras evitam:

ProblemaComo REST resolve
Cliente e servidor evoluindo juntos demais, cada mudança em um quebra o outroSeparação Cliente-Servidor: contrato é a interface (URIs + HTTP + formato), não a implementação interna
Servidor não escala porque guarda sessão/estado de cada cliente em memóriaStateless: cada requisição carrega tudo que o servidor precisa saber; servidor não guarda "conversa"
Toda requisição repetida bate no banco de novoCacheable: respostas podem se declarar cacheáveis, evitando processamento redundante
Cada API tem verbos/nomes de ação diferentes (getUser, fetchUser, retrieveUserById...)Uniform Interface: mesmo vocabulário sempre — GET, POST, PUT, DELETE sobre recursos identificados por URI
Sistemas gigantes de proxies, gateways e balanceadores não conseguem inspecionar/otimizar tráfegoLayered System: camadas intermediárias (proxy, cache, gateway, load balancer) podem existir de forma transparente porque a interface é uniforme e sem estado

O fio condutor: tudo isso já eram problemas resolvidos pela própria arquitetura da web (HTTP + URI + cache de navegador). REST é basicamente dizer: "pare de reinventar RPC customizado, use os mecanismos que a web já oferece."

4. As 6 restrições arquiteturais do REST

Isso é o núcleo técnico da tese de Fielding. Uma API só é "verdadeiramente RESTful" se seguir estas restrições (as 5 primeiras são obrigatórias, a 6ª é opcional):

4.1 Client-Server (Cliente-Servidor)

Separação de responsabilidades. Cliente cuida de interface/experiência do usuário. Servidor cuida de dados/lógica de negócio/armazenamento. Um pode evoluir sem o outro, desde que o contrato (a interface) não mude.

Isso já é natural pra você: seu front-end em React não sabe (nem precisa saber) se o back-end é Node, Python ou Java.

4.2 Stateless (Sem estado)

Esta é a restrição mais mal-entendida e mais importante.

Cada requisição do cliente para o servidor deve conter toda a informação necessária para o servidor entendê-la e processá-la. O servidor não guarda contexto de sessão do cliente entre requisições.

Isso não significa "a aplicação não tem estado" (um carrinho de compras claramente tem estado). Significa que esse estado vive no cliente ou em um armazenamento explícito (banco/cache), e é enviado a cada requisição (via token, parâmetros, headers) — o servidor não mantém uma "memória de conversa" atrelada a uma conexão específica.

Por que isso importa: um servidor stateless pode responder a requisição de qualquer instância de um cluster, sem precisar que seja "a mesma instância que atendeu a última vez". Isso é o que permite escalar horizontalmente (adicionar mais servidores) com facilidade.

4.3 Cacheable (Cacheável)

Toda resposta deve, implícita ou explicitamente, se rotular como cacheável ou não (headers como Cache-Control, ETag). Isso permite que clientes e intermediários evitem refazer requisições desnecessárias, melhorando performance e reduzindo carga no servidor.

4.4 Uniform Interface (Interface Uniforme)

A restrição que mais define "a cara" de uma API REST. Se divide em 4 sub-princípios:

  1. Identificação de recursos via URI: /users/42 identifica o usuário 42, não "a função que busca usuário".
  2. Manipulação de recursos através de representações: você não manda "delete o usuário", você envia uma requisição DELETE para a representação do recurso /users/42.
  3. Mensagens auto-descritivas: a requisição/resposta carrega informação suficiente para ser entendida sozinha (método HTTP, Content-Type, códigos de status).
  4. HATEOAS (Hypermedia as the Engine of Application State): a resposta deveria conter links para as próximas ações possíveis, assim como uma página HTML tem links. Esse é o princípio menos seguido na prática pela indústria — a maioria das "APIs REST" do mundo real ignora HATEOAS (falamos disso na seção 6).

4.5 Layered System (Sistema em Camadas)

O cliente não precisa saber se está falando diretamente com o servidor final, ou com um proxy, gateway de API, load balancer, ou camada de cache no meio do caminho. Cada camada só enxerga a camada imediatamente adjacente.

4.6 Code on Demand (opcional)

O servidor pode estender a funcionalidade do cliente enviando código executável (ex: JavaScript). É a única restrição opcional — e ironicamente é o que o seu navegador faz o tempo todo ao carregar JS de uma página. Raramente é discutida no contexto de "APIs REST" de back-end porque normalmente falamos de APIs que retornam dados (JSON), não código.

5. REST vs. outros estilos (contexto pra você situar)

EstiloIdeia centralQuando você provavelmente já viu
SOAPProtocolo rígido, baseado em XML, com contrato formal (WSDL), geralmente sobre HTTP mas não depende de seus verbosSistemas corporativos/bancários legados
RPC / JSON-RPC / gRPCCliente chama uma "função remota" diretamente (createUser(), deleteOrder()) — modela ações, não recursosgRPC é comum em comunicação interna entre microsserviços (alta performance, contratos via Protobuf)

Ponto importante que vamos aprofundar mais pra frente: a maioria das APIs que o mercado chama de "REST" hoje não são 100% RESTful no sentido estrito da tese (particularmente por ignorarem HATEOAS). Isso é tão comum que existe um modelo pra classificar "o quão RESTful" uma API realmente é — é o assunto da próxima seção.

6. Richardson Maturity Model (Modelo de Maturidade de Richardson)

Criado por Leonard Richardson (não confundir com Fielding), esse modelo classifica APIs em 4 níveis de "quão REST" elas realmente são:

  • Nível 0 — The Swamp of POX ("o pântano de XML puro"): um único endpoint, um único método HTTP (geralmente POST), tudo resolvido pelo corpo da requisição. É basicamente RPC disfarçado de HTTP. Ex: tudo passa por POST /api com um campo "action": "getUser" no corpo.
  • Nível 1 — Recursos: introduz múltiplos endpoints, um por recurso (/users, /orders), mas ainda usando só um método HTTP pra tudo.
  • Nível 2 — Verbos HTTP: usa os métodos HTTP corretamente (GET, POST, PUT, DELETE) com o significado semântico correto, e os códigos de status HTTP corretos. Isso é onde a esmagadora maioria das "APIs REST" do mundo real está — inclusive a que você provavelmente vai construir primeiro.
  • Nível 3 — HATEOAS: respostas incluem links de navegação para os próximos estados/ações possíveis, exatamente como uma página HTML tem links <a>. Muito raro na prática fora de exemplos acadêmicos e alguns poucos casos (ex: PayPal API, algumas APIs bancárias).

Por que isso importa pra você agora: não se cobre para chegar no Nível 3 logo de cara. O mercado, majoritariamente, opera e considera "aceitável" uma API que está no Nível 2. Nosso objetivo prático quando formos codar será atingir um bom Nível 2 — bem desenhado — antes de sequer considerar HATEOAS.

7. Conceitos-chave que vamos usar o tempo todo

Só pra fixar vocabulário antes da parte de código:

  • Recurso: a "coisa" que a API expõe (ex: um usuário, um post, um pedido). Geralmente representa uma entidade ou coleção.
  • Coleção vs. item único: /users (coleção de usuários) vs /users/42 (um usuário específico).
  • Representação: o formato em que o recurso é entregue — quase sempre JSON hoje em dia.
  • Verbo HTTP (Método): GET, POST, PUT, PATCH, DELETE — cada um com significado semântico específico (próximo material vai detalhar cada um).
  • Código de status HTTP: número que indica o resultado da requisição (200, 201, 404, 500...).
  • Idempotência: uma operação é idempotente se fazer ela 1 vez ou 100 vezes seguidas produz o mesmo resultado final no servidor. (GET, PUT, DELETE deveriam ser idempotentes; POST normalmente não é.) Conceito crítico pra desenhar bem uma API — vamos voltar nisso.
  • Statelessness (já visto acima): servidor não guarda estado de sessão do cliente entre requisições.

8. Erros conceituais comuns (pra você já sair evitando)

  1. "REST = JSON sobre HTTP" — Não. Dá pra fazer REST com XML, e dá pra fazer HTTP sem ser REST (SOAP roda sobre HTTP). REST é sobre a arquitetura/restrições, não sobre o formato de dado.
  2. "Toda API que usa GET/POST/PUT/DELETE é REST" — Tecnicamente é REST "nível 2", não REST completo (falta HATEOAS pra ser Nível 3), mas na prática do mercado isso é aceito como "API REST". O importante é você saber a diferença e não se confundir quando ler material mais purista.
  3. "REST é um protocolo" — Não. HTTP é o protocolo. REST é um estilo arquitetural que normalmente é implementado usando HTTP.
  4. "Stateless significa que a aplicação não pode ter estado (ex: carrinho de compras, sessão de usuário)" — Não. Significa que esse estado não fica "preso" na memória de uma instância específica do servidor entre requisições; ele é persistido (banco, token, cache) e enviado quando necessário.

9. O que vem a seguir

Este documento cobriu teoria, história e princípios. Os próximos materiais (que vamos criar conforme avançamos) vão cobrir, nesta ordem:

  1. HTTP na prática: métodos, códigos de status, headers relevantes, o ciclo requisição/resposta.
  2. Design de recursos e URIs: como nomear endpoints bem, convenções de mercado, aninhamento de recursos, filtros/paginação/ordenação.
  3. Escolha de stack: qual linguagem/framework vamos usar pra construir (a decisão de reaproveitar seu conhecimento de JavaScript no back-end via Node.js está em aberto).
  4. Primeira API funcional: colocar a mão na massa.
  5. Autenticação e autorização (JWT, API keys, OAuth — visão geral).
  6. Boas práticas de produção: versionamento, tratamento de erros, validação, documentação (OpenAPI/Swagger).

Quando terminar de ler este arquivo, volte com suas dúvidas. Perguntas do tipo "por que idempotência importa pra DELETE?" ou "por que servidor não pode guardar estado?" são exatamente o tipo de coisa que vale a pena esclarecer antes de ir pro código.
