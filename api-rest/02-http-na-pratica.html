Material de estudo — API REST — Parte 2

HTTP na prática

A parte 1 explicou por que REST usa HTTP. Agora vamos entender como o protocolo funciona por dentro: o ciclo requisição/resposta, os métodos e seu significado semântico, os códigos de status e os headers que você vai usar toda vez que desenhar um endpoint.

1. O ciclo requisição/resposta

HTTP é um protocolo request-response: o cliente sempre inicia a conversa mandando uma requisição, o servidor sempre responde. Não existe o servidor "chamando" o cliente do nada (isso é outro problema, resolvido por WebSocket/SSE, fora do escopo de REST clássico).

Fluxo básico:

Cliente                                  Servidor
   |                                          |
   |--- GET /pedidos/123 HTTP/1.1 --------->  |
   |    Host: api.exemplo.com                 |
   |    Authorization: Bearer xyz             |
   |                                          |  (processa, consulta banco)
   |<-- HTTP/1.1 200 OK --------------------  |
   |    Content-Type: application/json        |
   |    { "id": 123, "status": "pago" }       |
   |                                          |

Cada requisição é, como vimos na parte 1, independente (stateless): essa troca acima não sabe nada sobre a próxima. Tudo que o servidor precisa pra entender veio dentro dela mesma.

2. Anatomia de uma requisição HTTP

Toda requisição tem 3 partes:

GET /pedidos/123?incluir=itens HTTP/1.1        <- linha de requisição (método + caminho + versão)
Host: api.exemplo.com                          <- headers
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
Accept: application/json

                                                <- linha em branco separa headers do body
(sem body em GET)
  • Linha de requisição: método (GET), caminho do recurso (/pedidos/123), query string opcional (?incluir=itens), versão do protocolo.
  • Headers: metadados sobre a requisição — quem está autenticado, que formato o cliente aceita de volta, etc.
  • Body: dados enviados junto (comum em POST/PUT/PATCH, ausente em GET/DELETE na prática usual).

Exemplo com body, criando um recurso:

POST /pedidos HTTP/1.1
Host: api.exemplo.com
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
Content-Type: application/json

{
  "produto": "livro",
  "quantidade": 2
}

3. Anatomia de uma resposta HTTP

HTTP/1.1 201 Created                           <- linha de status (versão + código + texto)
Content-Type: application/json                 <- headers
Location: /pedidos/501

{
  "id": 501,
  "produto": "livro",
  "quantidade": 2,
  "status": "pendente"
}                                                <- body
  • Linha de status: código numérico (201) + texto legível (Created).
  • Headers: metadados da resposta — formato do body, onde achar o recurso recém-criado (Location), regras de cache, etc.
  • Body: a representação do recurso (quase sempre JSON no seu caso).

4. Métodos HTTP em detalhe

Cada verbo tem um significado semântico esperado. Seguir esse significado é o que separa Nível 2 (bem feito) de uma API que só usa métodos como rótulo aleatório.

GET — buscar

Busca uma representação do recurso. Não deve alterar nada no servidor. Sem body na requisição (na prática, alguns clientes/servidores nem suportam body em GET).

GET /pedidos          <- lista de pedidos (coleção)
GET /pedidos/123      <- um pedido específico (item)
GET /pedidos?status=pago&limit=20   <- filtros via query string

POST — criar (ou executar ação sem recurso próprio)

Uso mais comum: criar um novo recurso dentro de uma coleção. Servidor decide o identificador do novo recurso e normalmente devolve onde ele ficou (header Location).

POST /pedidos
{ "produto": "livro", "quantidade": 2 }

→ 201 Created
Location: /pedidos/501

Uso secundário, comum na prática: ações que não mapeiam bem pra um recurso CRUD, tipo POST /pedidos/123/cancelar ou POST /sessoes (login). Não é "puro" no sentido de recurso, mas é aceito amplamente no mercado.

PUT — substituir por completo

Substitui o recurso inteiro no endereço indicado pelo body enviado. Se um campo não vier no body, a expectativa é que ele seja removido/resetado — porque é uma substituição total, não uma atualização parcial.

PUT /pedidos/501
{ "produto": "livro", "quantidade": 3, "status": "pago" }

→ 200 OK (ou 204 No Content)

PATCH — atualizar parcialmente

Atualiza só os campos enviados, mantém o resto como está. É o que a maioria das pessoas realmente quer quando pensa em "editar um recurso", mas PUT ainda é mais usado por hábito/simplicidade em várias APIs do mercado.

PATCH /pedidos/501
{ "status": "pago" }

→ 200 OK   (quantidade e produto continuam como estavam)

DELETE — remover

Remove o recurso identificado pela URI. Corpo de resposta geralmente vazio.

DELETE /pedidos/501

→ 204 No Content

HEAD e OPTIONS — menos comuns, mas existem

  • HEAD: igual GET, mas servidor devolve só os headers, sem body. Útil pra checar se recurso existe ou pegar metadados (tamanho, ETag) sem baixar o conteúdo inteiro.
  • OPTIONS: pergunta "quais métodos esse endpoint aceita?". Usado bastante nos bastidores por navegadores em requisições preflight de CORS — você provavelmente já viu isso no DevTools sem saber o porquê.

5. Safety vs. Idempotência

Dois conceitos parecidos, mas diferentes. Idempotência já foi apresentada na parte 1 (repetir N vezes = mesmo estado final). Safety (segurança, no sentido HTTP) é mais restrito: método seguro não modifica o servidor de jeito nenhum — nem na primeira chamada.

MétodoSeguro (não altera nada)IdempotenteCacheável por padrão
GETsimsimsim
HEADsimsimsim
OPTIONSsimsimnão
PUTnãosimnão
DELETEnãosimnão
PATCHnãodependenão
POSTnãonãodepende

PATCH "depende" porque o resultado varia com o que está sendo aplicado: {"status": "pago"} é idempotente (repetir dá o mesmo resultado), mas {"quantidade": "+1"} (incremento relativo) não é — cada chamada muda o estado de novo.

Por que isso importa na prática: navegadores, proxies e bibliotecas HTTP retentam automaticamente métodos seguros/idempotentes quando a conexão falha, sem perguntar. Um POST nunca é retentado automaticamente por padrão — é por isso que formulário duplicado / compra duplicada é um problema clássico de POST, e não de GET.

6. Códigos de status HTTP

Organizados em 5 categorias pelo primeiro dígito:

FaixaCategoriaSignificado geral
1xxInformationalRequisição recebida, processo continua (raramente aparece no seu dia a dia de API REST)
2xxSuccessDeu certo
3xxRedirectionRecurso está em outro lugar, siga o novo endereço
4xxClient ErrorO cliente errou (dado inválido, não autenticado, recurso não existe)
5xxServer ErrorO servidor errou (bug, banco fora do ar, etc.) — cliente fez tudo certo

Os que você vai realmente usar o tempo todo:

CódigoNomeQuando usar
200OKSucesso genérico com body de resposta (GET, PUT, PATCH bem-sucedidos)
201CreatedPOST que criou um recurso novo. Vem acompanhado do header Location
204No ContentSucesso sem body de resposta (comum em DELETE, às vezes PUT)
400Bad RequestBody/parâmetros malformados ou inválidos — erro de quem enviou
401UnauthorizedNão autenticado — token ausente, inválido ou expirado
403ForbiddenAutenticado, mas sem permissão pra essa ação (autorização, não autenticação)
404Not FoundRecurso não existe nesse caminho
409ConflictRequisição conflita com o estado atual (ex: criar recurso com identificador que já existe)
422Unprocessable EntitySintaxe do body ok, mas dado semanticamente inválido (ex: e-mail sem @, campo obrigatório vazio)
500Internal Server ErrorErro genérico não tratado no servidor — bug, exceção não capturada
503Service UnavailableServidor temporariamente fora (deploy, sobrecarga, manutenção)

401 vs 403, erro comum de confundir: 401 = "eu não sei quem você é" (falta login/token válido). 403 = "eu sei quem você é, mas você não pode fazer isso" (ex: usuário comum tentando acessar rota de admin).

HeaderDireçãoPra que serve
Content-Typerequisição e respostaFormato do body (application/json, multipart/form-data, etc.)
AcceptrequisiçãoCliente diz que formato(s) aceita de volta (application/json)
AuthorizationrequisiçãoCredencial — Bearer <token>, como visto na parte 1 sobre statelessness

Cache-ControlrespostaRegras de cache: no-store, max-age=3600, etc. — a restrição Cacheable da parte 1, na prática

8. Erros conceituais comuns

  1. "200 pra tudo que deu certo, 500 pra tudo que deu errado" — Não. Erro de validação do cliente é 4xx, não 500. Reservar 5xx só pra falha real do servidor ajuda muito na hora de debugar (log de 5xx = "meu código quebrou", log de 4xx = "cliente mandou algo errado").
  2. "PUT e PATCH são a mesma coisa" — Não. PUT substitui o recurso inteiro (campo ausente = removido); PATCH altera só o que foi enviado.
  3. "DELETE precisa devolver o recurso deletado no body" — Não é obrigatório. 204 No Content sem body é o mais comum e correto.
  4. "401 é pra qualquer erro de permissão" — Não, ver distinção 401 vs 403 acima.
