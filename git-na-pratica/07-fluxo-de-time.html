Material de estudo — Git na prática — Parte 7

Fluxo de time: branch, Pull Request, code review

Esta é a aula mais próxima do que você vai fazer no primeiro dia de trabalho. Comando novo de Git tem pouco aqui — a maior parte já apareceu nas aulas 4 e 6. O que muda é o processo em volta: quem pode mexer no quê, quem revisa, o que trava o merge e por quê. Vale um lembrete da aula 1: Pull Request não é Git — não existe git pull-request. É um recurso do GitHub construído em cima do Git, e por isso muda de nome entre plataformas.

1. Por que ninguém commita na main

Nas aulas anteriores você commitou direto na main à vontade. Em time, isso não acontece — e não é burocracia.

A main de um projeto real costuma ser o que está em produção, ou o que vai pra produção no próximo deploy. Commitar direto nela significa:

  • Ninguém olhou seu código antes. O erro que outra pessoa acharia em trinta segundos vai pro ar.
  • Nada garante que ainda funciona. Sem uma etapa entre você e a main, não há onde rodar teste automatizado antes.
  • Trabalho pela metade quebra o de todo mundo. Quem puxar a main nos próximos minutos leva junto o seu meio-caminho.
  • Não há registro da decisão. Some o "por que fizemos assim" que o PR guarda.

O fluxo com branch e Pull Request cria um portão: todo código passa por um lugar onde dá pra olhar, discutir, testar e recusar antes de virar oficial. A aula 4 já tinha a mecânica; aqui ela ganha o processo.

Isso é imposto por ferramenta, não por confiança. Na seção 11 você vai configurar o GitHub pra recusar push direto na main — inclusive o seu, inclusive sendo dono do repositório. Times sérios não deixam essa regra na memória das pessoas.

2. O ciclo, de ponta a ponta

É este o ciclo que se repete por tarefa, todo dia, em qualquer time que use GitHub:

1

Atualize a main

git switch main e git pull. Partir de código velho é a causa número um de conflito.

2

Crie a branch da tarefa

git switch -c feat/nome-da-tarefa, com o nome na convenção do time (seção 3).

3

Trabalhe em commits pequenos

O ciclo das aulas 2 e 3, sem novidade.

4

Publique a branch

git push -u origin feat/nome-da-tarefa.

5

Abra o Pull Request

No GitHub, descrevendo o que mudou e por quê.

6

Espere review e CI

Alguém revisa; os testes automatizados rodam. Você responde, corrige, empurra mais commits.

7

Merge e limpeza

Aprovado e verde, faz merge pelo botão do GitHub, apaga a branch e atualiza a main local.

Compare com o ciclo da aula 4, seção 12: os passos 1 a 3 são idênticos. O que entrou foi o portão — publicar, ser revisado, e só então integrar.

3. Nome de branch

Repositório de time tem dezenas de branches abertas ao mesmo tempo. Nome bom é o que permite saber, sem abrir, o que é aquilo e de quem é.

A convenção mais comum usa prefixo por tipo:

feat/exportar-relatorio-csv
fix/login-aceita-email-com-maiuscula
docs/atualiza-instrucoes-de-setup
refactor/extrai-servico-de-email
chore/atualiza-dependencias

Em empresa com Jira ou similar, é muito comum entrar o número do ticket, porque ele liga a branch à tarefa:

feat/PROJ-1234-exportar-relatorio-csv
PROJ-1234-exportar-relatorio

Regras práticas que valem em qualquer convenção:

  • Tudo minúsculo, palavras separadas por hífen. Sem espaço, sem acento.
  • Descritivo, mas curto. Você vai digitar esse nome várias vezes.
  • Uma tarefa por branch. Nome que precisa de "e" no meio é sinal de PR grande demais.
  • Evite minha-branch, teste, felipe, correcoes.
Ao entrar num time

Não invente convenção. Rode git branch -a e git log --oneline -30 e copie o que já está lá. Convenção é decisão coletiva; chegar impondo a sua é ruído.

4. Conventional Commits

Na aula 2 ficou pendente: existe uma convenção com nome pra mensagem de commit, e é a mais adotada do mercado.

tipo(escopo opcional): descrição no imperativo
feat: adiciona exportacao de relatorio em CSV
fix(login): aceita email com letra maiuscula
docs: atualiza instrucoes de setup no README
refactor(email): extrai envio para servico proprio
test: cobre caso de matricula duplicada
chore: atualiza dependencias
TipoQuando usar
featFuncionalidade nova
fixCorreção de bug
docsSó documentação
refactorMuda o código sem mudar o comportamento
perfMelhora de performance
testAdiciona ou corrige teste
buildBuild, empacotamento, dependências
ciConfiguração de pipeline
choreManutenção que não se encaixa acima
styleFormatação sem efeito no código. Raro hoje — formatador resolve

Mudança que quebra compatibilidade leva ! ou um rodapé:

feat!: remove endpoint /v1/usuarios

BREAKING CHANGE: clientes devem migrar para /v2/usuarios

4.1 Por que existe

Não é estética: a mensagem vira legível por máquina. Com isso, ferramentas geram changelog sozinhas e decidem a próxima versão automaticamente — fix sobe o número de correção, feat sobe o de funcionalidade, ! sobe o principal.

Sendo honesto sobre a adoção: é padrão de fato no ecossistema JavaScript e em bibliotecas open source, mas não é universal. Kernel do Linux, Google e muitos times de produto usam outra coisa — com frequência o número do ticket como prefixo. E onde o time usa squash (seção 10), os commits da branch viram um só e a convenção passa a valer no título do PR, não em cada commit. Se o time não automatiza nada com isso, o padrão vira só disciplina de leitura — o que já é bom, mas não é o motivo principal dele existir.

5. Abrindo o Pull Request

Vamos fazer um de verdade, usando as duas pastas da aula 6.

cd ~/projetos/guia-de-cafes
git switch main
git pull
git switch -c feat/secao-de-moagem

Alterar index.html — depois do </ul>, acrescente a seção nova:

  </ul>
  <h2>Moagem</h2>
  <p>Cada método pede uma moagem diferente: fina para espresso,
  média para coado, grossa para prensa francesa.</p>
  <footer>
git commit -am "feat: adiciona secao de moagem na pagina"
git push -u origin feat/secao-de-moagem

Repare no fim da saída do push:

remote: Create a pull request for 'feat/secao-de-moagem' on GitHub by visiting:
remote:      https://github.com/seuusuario/guia-de-cafes/pull/new/feat/secao-de-moagem

O GitHub já oferece o link. Abra, ou vá pelo site — ele mostra um banner "Compare & pull request" por alguns dias após o push.

5.1 Preenchendo

Na tela do PR, confira antes de tudo a linha do topo: base: main ← compare: feat/secao-de-moagem. É a direção do merge — trazer a sua branch para a main. Errar isso acontece, principalmente quando o time tem outras branches longas.

Depois, título e descrição. Uma descrição que presta responde três perguntas:

## O que muda
Adiciona uma seção explicando qual moagem cada método pede.

## Por quê
A lista de métodos não dizia nada sobre preparo, e moagem é a
dúvida mais comum de quem está começando.

## Como testar
Abrir o index.html no navegador; a seção aparece depois da lista
e antes do rodapé.

Duas coisas úteis na mesma tela:

  • Draft pull request — abre o PR marcado como rascunho. Serve pra mostrar trabalho em andamento e rodar o CI sem pedir review ainda. O botão de merge fica bloqueado até você marcar como pronto.
  • Ligar a uma issue — escrever Closes #12 na descrição faz o GitHub fechar a issue 12 automaticamente quando o PR for mergeado.

Criado o PR, explore as abas: Conversation (discussão), Commits (os commits da branch) e Files changed (o diff completo — aquele mesmo formato da aula 3, seção 3.1).

6. O que faz um PR bom

Uma variável domina todas as outras:

Tamanho

PR pequeno é revisado. PR grande é aprovado sem ser lido.

Um PR de 50 linhas recebe comentários específicos e úteis. Um de 2000 recebe "LGTM" de alguém que rolou até o fim. O segundo dá a impressão de ter passado por revisão, o que é pior do que não ter revisão nenhuma.

O resto decorre disso:

PráticaPor quê
Um assunto por PRMisturar correção com refatoração impede aprovar uma e recusar a outra
Título que descreve o efeitoÉ o que aparece na lista de PRs e, com squash, vira a mensagem do commit
Descrição com o "por quê"O diff mostra o que mudou; só você sabe o motivo
Revisar o próprio diff antes de pedir reviewMetade dos comentários que você receberia, você mesmo acha na aba "Files changed"
Não deixar aberto por semanasQuanto mais tempo, mais a main anda e mais conflito acumula (aula 5)

7. Do outro lado: ser revisor

Metade do tempo gasto com PR num time é revisando o de outra pessoa. É trabalho, conta como trabalho, e costuma ser o que forma opinião sobre você mais rápido do que o próprio código.

7.1 O que o GitHub oferece

Na aba Files changed, clicando no + ao lado de uma linha, você comenta naquela linha. Ao terminar, o botão Review changes pede um veredito:

VereditoSignifica
CommentObservações, sem aprovar nem barrar
ApprovePode ir. Em repositório protegido, é isso que libera o merge
Request changesTem coisa que precisa mudar antes. Bloqueia o merge até você revisar de novo

Há ainda o suggestion: um comentário com bloco de sugestão que o autor aplica com um clique, virando commit. Ótimo pra correção pequena — melhor que três parágrafos descrevendo uma vírgula.

No seu repositório de estudo, dá pra abrir o PR, ver o diff e comentar em linha normalmente. O que o GitHub não deixa é aprovar o próprio PR — Approve exige outra conta. Em time real é justamente esse o ponto; aqui, basta saber que o botão existe e o que ele libera.

7.2 O que procurar

Em ordem de importância — e sim, nessa ordem:

  1. Faz o que diz que faz? O código resolve o problema descrito.
  2. Casos que faltaram. Lista vazia, valor nulo, usuário sem permissão, dois cliques rápidos.
  3. Segurança e dados. Entrada não validada, credencial no código, log com dado pessoal.
  4. Legibilidade. Alguém entende isso em seis meses?
  5. Estilo. Por último, e só o que a ferramenta automática não pega.

7.3 Como comentar

Review é conversa entre colegas sobre código, não avaliação de pessoa. Duas coisas mudam muito o tom:

Evite

Isso está errado.
Por que você fez assim?
Ninguém escreve mais desse jeito.

Prefira

Se a lista vier vazia, isso quebra na linha 12.
Dá pra usar X aqui? Fica mais simples de ler.
Nit: nome no plural deixa mais claro que é coleção.

Fale do código, não de quem escreveu ("essa função quebra se...", não "você esqueceu de..."), e separe o obrigatório do opinativo. A convenção mais usada pra isso é o prefixo nit: (de nitpick), que significa "detalhe pequeno, pode ignorar". Sem essa marcação, o autor não sabe o que precisa mudar pra destravar o merge.

8. Respondendo ao review

Chegaram comentários. O fluxo é simples: você corrige na mesma branch e empurra mais commits.

git switch feat/secao-de-moagem
# ... corrige ...
git commit -am "fix: corrige exemplo de moagem para prensa"
git push

O PR se atualiza sozinho. Não se abre PR novo pra cada correção: enquanto a branch é a mesma, os commits entram no PR existente, e o revisor consegue ver só o que mudou desde a última revisão.

Sobre as conversas: cada comentário vira um fio que pode ser marcado como Resolved. Convenção comum e sensata — quem abriu o comentário é quem resolve, depois de conferir a correção. Autor resolvendo os próprios encerra a conversa antes do revisor concordar.

E responder "não vou mudar" é resposta legítima, desde que com motivo. Review é discussão técnica; se o revisor não sabia de um contexto, explicar resolve.

Não reescreva histórico com PR aberto. commit --amend ou reset numa branch já publicada trocam os hashes (aula 3), o revisor perde a referência dos comentários e o push é rejeitado. Faça commits normais de correção — se o time usar squash, eles somem no merge de qualquer forma.

9. O CI travando o merge

Repositório de time costuma ter integração contínua: um serviço que roda automaticamente a cada push — testes, verificação de estilo, build. No GitHub isso é o GitHub Actions.

O resultado aparece no fim do PR, como uma lista de checks:

EstadoSignifica
verdePassou. Merge liberado (se houver aprovação)
amareloRodando. Espere
vermelhoFalhou. Merge bloqueado

Vermelho não se contorna: é o próprio PR dizendo que o código não está pronto. Clique em "Details" pra ver o log e descobrir qual teste quebrou. Corrija na branch, empurre, e o CI roda de novo sozinho.

Duas coisas que vale saber desde já:

  • CI que falha por motivo alheio existe — teste instável, serviço externo fora do ar. Nesses casos se re-roda o job. Mas "deve ser instabilidade" é a desculpa mais cara do desenvolvimento: confira antes de reexecutar.
  • Rodar o teste localmente antes de abrir o PR é o que evita o ciclo lento de empurrar, esperar cinco minutos e descobrir um erro de digitação.

Configurar o CI em si é assunto de outra trilha — aqui interessa o efeito: ele é parte do portão.

10. As três formas de merge

Com aprovação e CI verde, o botão libera. E ele tem três opções, que produzem históricos bem diferentes na main.

10.1 Create a merge commit

Traz todos os commits da branch e cria um merge commit por cima — o merge da aula 4, seção 9.

*   Merge pull request #3 from usuario/feat/secao-de-moagem
|\
| * fix: corrige exemplo de moagem para prensa
| * feat: adiciona secao de moagem na pagina
|/
* commit anterior da main

Preserva tudo, inclusive os commits de correção do review. Histórico fiel e mais poluído.

10.2 Squash and merge

Junta todos os commits da branch em um só, aplicado na main:

* feat: adiciona secao de moagem na pagina (#3)
* commit anterior da main

É a opção mais usada hoje em time de produto, e a lógica é: a unidade que importa no histórico da main é o PR, não cada passo do trabalho. Os "corrige typo", "responde review" e "wip" desaparecem.

Detalhe prático que fecha a seção 4: com squash, a mensagem do commit final vem do título do PR. É por isso que muitos times cobram Conventional Commits ali, e não em cada commit da branch.

10.3 Rebase and merge

Reaplica os commits da branch um a um no topo da main, sem merge commit:

* fix: corrige exemplo de moagem para prensa
* feat: adiciona secao de moagem na pagina
* commit anterior da main

Histórico linear preservando cada commit. Exige commits bem feitos na branch — o mecanismo do rebase é a aula 8.

10.4 Comparando

 Merge commitSquashRebase
Commits na mainTodos + o mergeUm sóTodos, sem merge
HistóricoRamificadoLinearLinear
Reverter o PR inteiroUm comandoUm comandoCommit a commit
Preserva os passos do trabalhoSimNãoSim
Bom quandoSe quer rastrear a ramificaçãoCommits da branch são bagunçadosCada commit tem valor próprio

Não existe escolha certa — é decisão do time, e normalmente já está configurada no repositório quando você chega. Faça o merge do seu PR agora com Squash and merge, que é o caso mais provável de encontrar por aí.

11. Branch protection

Nada até aqui impede alguém de dar git push direto na main e pular o processo inteiro. É o GitHub que impede, se configurado.

No seu repositório: Settings → Branches → Add branch protection rule (nas contas mais novas, aparece como Rules → Rulesets). Aplique à main e marque:

RegraEfeito
Require a pull request before mergingPush direto na main é recusado. A regra central
Require approvalsExige N aprovações no PR. Normalmente 1 ou 2
Require status checks to passCI vermelho bloqueia o merge de fato
Require branches to be up to dateObriga atualizar com a main antes de mergear
Require linear historyProíbe merge commit — força squash ou rebase
Do not allow bypassingVale também para administradores. Sem isso, quem tem permissão pula tudo

Com isso ligado, tentar empurrar direto:

git push
remote: error: GH006: Protected branch update failed for refs/heads/main.
remote: error: Changes must be made through a pull request.

Vale ligar no seu repositório de estudo pra ver o erro acontecer. Ele é comum no primeiro dia de trabalho, e reconhecer a mensagem evita achar que quebrou alguma coisa.

Force push também é bloqueado por essa configuração, o que é metade do motivo dela existir. É o que impede alguém de reescrever a história compartilhada — o assunto da aula 8.

12. Depois do merge

O PR foi mergeado no GitHub. Sua máquina ainda não sabe:

git switch main
git pull
git branch -d feat/secao-de-moagem
git fetch --prune

Os quatro passos: voltar pra main, trazer o que foi mergeado, apagar a branch local e limpar a referência à branch remota — que o GitHub já apagou, se você usou o botão "Delete branch" que ele oferece depois do merge.

Se o time usa squash, o git branch -d pode reclamar que a branch "não foi mergeada". Faz sentido: os commits originais dela não existem na main — o que existe é um commit novo com o conteúdo deles. Nesse caso, e só depois de confirmar que o PR foi mergeado no GitHub, use git branch -D.

Esse bloco de quatro comandos é o começo de toda tarefa nova. Vale virar reflexo.

13. Os modelos de fluxo com nome

O que você fez nesta aula tem nome, e vai ouvir esses nomes numa entrevista ou no primeiro dia. São três os que aparecem.

13.1 GitHub Flow

O mais simples e o mais comum. Uma branch permanente só — a main, sempre pronta pra ir pra produção. Toda tarefa vira branch curta, PR, review, merge, deploy.

main ──┬──> feat/x ──┐
       │              ├──> merge
       └──> fix/y ────┘

É exatamente o ciclo da seção 2. Serve para a maioria dos produtos web, que fazem deploy a qualquer momento.

13.2 GitFlow

Bem mais estruturado, com duas branches permanentes — main (o que está em produção) e develop (o que vai na próxima versão) — mais três famílias temporárias: feature/*, release/* e hotfix/*.

main    ──────●───────────────●──   (versões publicadas)
               \             /
release         ●───────────●
               /
develop ──●───●───●───●───●──
           \     /     \   /
feature     ●───●       ●─●

Faz sentido em software com versões numeradas e lançamentos programados — desktop, mobile com ciclo de loja, produto que mantém várias versões ao mesmo tempo. Em produto web com deploy contínuo, costuma ser peso morto: o próprio autor publicou em 2020 uma nota dizendo que o modelo não foi pensado para esse cenário.

13.3 Trunk-based development

O oposto do GitFlow. Branches vivem horas, não dias — e às vezes se commita direto na main. Funcionalidade incompleta vai pra produção desligada por feature flag.

main ──●──●──●──●──●──●──●──  (integração várias vezes ao dia)

Exige CI forte, boa cobertura de teste e disciplina. Comum em times grandes e maduros, e é o modelo que a pesquisa sobre desempenho de times de engenharia costuma apontar como o de melhor resultado.

13.4 Comparando

 GitHub FlowGitFlowTrunk-based
Branches permanentesmainmain + developmain
Vida de uma branchDiasSemanasHoras
ComplexidadeBaixaAltaBaixa (no Git)
ExigePR e reviewDisciplina de processoCI forte e feature flags
Bom paraProduto web, maioria dos timesVersões numeradas, releases programadasTimes grandes com automação madura

Você não escolhe o modelo ao entrar num time — herda. O que importa é reconhecer qual é, e a pergunta que resolve isso no primeiro dia é direta: "qual é o fluxo de branch aqui?". Ninguém estranha ela; estranha-se quem passa duas semanas errando o processo sem perguntar.

14. Erros comuns nesta fase

  1. PR gigante. O erro mais caro de todos: não recebe revisão de verdade. Quebre em PRs menores, mesmo que dê trabalho.
  2. Branch criada a partir de main desatualizada. Conflito garantido. Sempre git pull antes do switch -c.
  3. Abrir PR novo pra cada correção do review. Basta empurrar na mesma branch.
  4. Reescrever histórico com PR aberto. amend/reset quebram a referência dos comentários e o push.
  5. Merge com CI vermelho. Se o repositório permite, alguém vai tentar. É como o código quebrado chega na main.
  6. Aprovar sem ler. "LGTM" em PR de 1500 linhas é pior do que não revisar: cria a ilusão de que passou por revisão.
  7. Esquecer de atualizar a main local depois do merge. A próxima branch nasce velha, e o ciclo recomeça.
  8. Levar review pro pessoal. Dos dois lados. Comentário é sobre código.

15. Checklist antes de seguir

  • Você abriu um Pull Request de verdade, com título e descrição decentes
  • Navegou pelas abas Conversation, Commits e Files changed
  • Comentou numa linha específica do diff
  • Empurrou um commit novo na branch e viu o PR se atualizar sozinho
  • Fez merge pelo botão do GitHub e limpou as branches local e remota
  • Sabe explicar a diferença entre merge commit, squash e rebase merge
  • Ligou branch protection e viu o push direto na main ser recusado
  • Sabe dizer, em uma frase, o que distingue GitHub Flow, GitFlow e trunk-based
  • Sabe o que perguntar no primeiro dia sobre o fluxo do time

16. O que vem a seguir

Você já consegue trabalhar num time sem quebrar nada. As duas últimas aulas cuidam de histórico limpo e rede de segurança.

  1. Rebase e histórico limpo — o mecanismo por trás do pull --rebase e do "Rebase and merge", rebase -i pra reorganizar commits antes do PR (squash, reword, drop, fixup), o conflito durante rebase — que se resolve diferente do da aula 5 —, a regra de ouro de não reescrever histórico compartilhado e o force push feito direito com --force-with-lease.
  2. Rede de segurança — stash, reflog, recuperar o que sumiu, cherry-pick e o caso do segredo commitado.
  3. Git no dia a dia — cenários reais de ponta a ponta e a colinha final.

Vale repetir o ciclo desta aula duas ou três vezes antes de seguir, usando a pasta clonada como "outra pessoa": abra um PR de lá, revise pela interface, comente numa linha, corrija e mergeie. É o único jeito de o fluxo virar automático antes de ele valer dinheiro — e é literalmente o que você vai fazer todo dia.
