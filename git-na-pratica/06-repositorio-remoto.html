Material de estudo — Git na prática — Parte 6

Repositório remoto: GitHub

Até agora tudo aconteceu dentro da sua máquina. Esta aula tira o projeto de lá. A ideia central vem da aula 1 e vale repetir antes de começar: o repositório no GitHub não é especial — é mais um clone, igual ao seu. Ele é a fonte de verdade porque as pessoas combinaram que é, não porque a ferramenta obriga. Todo o resto da aula fica mais simples com isso em mente.

1. O que muda com um remoto

Um remote é um repositório em outro lugar, com o qual o seu troca commits. Ter um resolve três coisas de uma vez:

  • Backup. Sua máquina morre e o trabalho continua existindo.
  • Colaboração. Outras pessoas conseguem pegar o seu trabalho e mandar o delas.
  • Portfólio. Em vaga de programação, o link do GitHub costuma ser olhado antes do currículo.

O que não muda: todo o ciclo das aulas 2 a 5 continua idêntico. add, commit, branch, merge seguem sendo locais e instantâneos. O remoto acrescenta dois verbos ao vocabulário — enviar (push) e trazer (fetch/pull) — e mais nada.

Git ≠ GitHub, de novo. Nada nesta aula é exclusivo do GitHub: os mesmos comandos funcionam com GitLab, Bitbucket ou um servidor da própria empresa. O que muda entre eles é o site, não o Git.

2. Conta e repositório no GitHub

2.1 A conta

Se ainda não tem, crie em github.com/signup. Duas recomendações que economizam dor de cabeça:

  • Nome de usuário profissional. Ele vira parte da URL dos seus projetos e aparece em processo seletivo.
  • Ative 2FA. Autenticação em dois fatores é obrigatória no GitHub para quem contribui com código, e uma conta comprometida significa código alheio comprometido junto.

Momento de voltar ao pendente da aula 1: em Settings → Emails, marque "Keep my email addresses private" e copie o endereço noreply que aparece ali. Depois:

git config --global user.email "12345678+seuusuario@users.noreply.github.com"

Assim os commits daqui pra frente não expõem seu e-mail pessoal. Os commits antigos continuam com o endereço antigo — reescrever isso não vale o esforço num projeto de estudo.

2.2 O repositório

No GitHub, botão New repository. Preencha:

CampoValor
Repository nameguia-de-cafes
DescriptionOpcional
Public / PrivateQualquer um serve. Público é bom pra portfólio
Add a README fileNÃO marque
Add .gitignoreNÃO marque
Choose a licenseNÃO marque

Por que não marcar nada: essas opções fazem o GitHub criar um commit inicial no repositório remoto. Como o seu repositório local já tem commits próprios, você ficaria com duas histórias sem ancestral em comum — e o primeiro pull falharia com fatal: refusing to merge unrelated histories.

A regra: repositório local já existe? Crie o remoto vazio. As opções acima só fazem sentido quando o projeto começa no GitHub e você vai cloná-lo.

Depois de criar, o GitHub mostra uma tela com instruções e duas URLs. Guarde a página aberta.

3. Autenticação: SSH ou HTTPS

Antes de enviar qualquer coisa, o GitHub precisa saber que é você. Senha da conta não funciona — o GitHub removeu essa possibilidade em 2021, justamente porque senha reusada em várias ferramentas é um risco ruim de conter.

Restam dois caminhos:

 SSHHTTPS + token
URLgit@github.com:usuario/repo.githttps://github.com/usuario/repo.git
Como funcionaPar de chaves criptográficasToken que substitui a senha
ConfiguraçãoUma vez por máquinaUma vez, mas o token expira
Passa em rede corporativa restritivaÀs vezes bloqueadaQuase sempre passa
Recomendado paraSua máquina de trabalhoAmbiente onde SSH é bloqueado

A recomendação é SSH: configura uma vez e nunca mais pede nada.

3.1 Configurando SSH

Veja se já existe uma chave na máquina:

ls -la ~/.ssh

Procure por um par id_ed25519 e id_ed25519.pub. Se não houver, gere:

ssh-keygen -t ed25519 -C "seu@email.com"

Ele faz três perguntas:

  • Local do arquivo — aceite o padrão, Enter.
  • Passphrase — uma senha que protege a chave. Recomendada: se alguém copiar sua chave privada, ela sozinha não serve.
  • Confirmação da passphrase.

Isso cria dois arquivos, e a diferença entre eles é o ponto inteiro:

ArquivoO que é
id_ed25519Chave privada. Nunca sai da sua máquina, nunca é enviada a ninguém, nunca entra num repositório
id_ed25519.pubChave pública. Essa sim vai pro GitHub. Pode ser vista por qualquer um sem problema

A chave privada é uma credencial. Quem tiver o arquivo id_ed25519 consegue agir como você em todo repositório onde a chave está autorizada. Não copie pra outra máquina por e-mail ou chat, não coloque em pasta sincronizada na nuvem, e não commite por acidente — se isso acontecer, gere um par novo e remova o antigo do GitHub imediatamente.

Copie o conteúdo da chave pública:

cat ~/.ssh/id_ed25519.pub

No GitHub: Settings → SSH and GPG keys → New SSH key. Título livre (o nome da máquina ajuda), cole o conteúdo, salve.

Teste:

ssh -T git@github.com
Hi seuusuario! You've successfully authenticated, but GitHub does not provide shell access.

Essa mensagem — inclusive a parte do "does not provide shell access" — é sucesso.

3.2 A alternativa: HTTPS com token

Se o SSH estiver bloqueado na sua rede, use token. Em Settings → Developer settings → Personal access tokens, gere um token com escopo repo e prazo de validade.

Ele aparece uma única vez. Ao dar push, o Git pede usuário e senha: informe seu usuário e cole o token no lugar da senha.

O token é equivalente à sua senha para efeitos de acesso a repositório. Trate como tal: não cole em chat, não coloque dentro de arquivo do projeto, não deixe em variável commitada. Prefira sempre o menor escopo e o menor prazo que resolvam o seu caso, e revogue quando não precisar mais.

Pra não digitar a cada push, configure um gerenciador de credenciais do sistema (no Linux, libsecret; no macOS, o Keychain; no Windows, o gerenciador que vem com o Git). Evite credential.helper store, que grava o token em texto puro num arquivo comum.

Atalho: o GitHub CLI resolve autenticação num comando — gh auth login — e configura tudo sozinho. Vale conhecer; ele volta na aula 10.

4. git remote add

Agora é ligar o repositório local ao remoto:

cd ~/projetos/guia-de-cafes
git remote add origin git@github.com:seuusuario/guia-de-cafes.git

Decompondo: remote add registra um remoto novo, origin é o apelido que você dá a ele, e o resto é o endereço.

Sobre o nome "origin"

origin não é palavra reservada do Git — é só uma convenção, tão forte que todo mundo usa. É o apelido do remoto principal. Você poderia chamar de github ou casa; não faça isso sem motivo, porque todo material e todo colega vai assumir origin.

Confira:

git remote -v
origin	git@github.com:seuusuario/guia-de-cafes.git (fetch)
origin	git@github.com:seuusuario/guia-de-cafes.git (push)

Duas linhas porque o Git permite endereços diferentes para buscar e para enviar. Na prática, são sempre iguais.

Comandos relacionados, pra quando precisar:

git remote set-url origin nova-url    # troca o endereço (ex: migrar de HTTPS pra SSH)
git remote remove origin              # desconecta
git remote rename origin upstream     # renomeia

5. git push -u: o primeiro envio

git push -u origin main
Enumerating objects: 34, done.
Counting objects: 100% (34/34), done.
Writing objects: 100% (34/34), 3.21 KiB | 3.21 MiB/s, done.
To github.com:seuusuario/guia-de-cafes.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.

Atualize a página do GitHub: seus arquivos estão lá, com todo o histórico — cada commit das aulas anteriores, com mensagem, autor e data.

Lendo o comando por partes: push envia, origin é pra onde, main é qual branch. E o -u:

O que -u faz

-u (ou --set-upstream) estabelece um vínculo permanente entre a sua branch local e a do remoto. Depois dele, git push e git pull sem argumento nenhum já sabem para onde ir.

Usa-se uma vez por branch, no primeiro push dela. Depois, só git push.

Faça um commit e teste a forma curta:

echo "" >> README.md
git commit -am "Ajusta README"
git push

6. Branch de rastreamento

Aquele vínculo criou uma coisa nova no seu repositório. Veja:

git branch -a
* main
  remotes/origin/main

origin/main é uma branch de rastreamento remoto. Entender o que ela é resolve metade das confusões com remoto:

O que origin/main é

Um ponteiro local, dentro do seu .git, que registra onde a main do remoto estava na última vez que você se comunicou com ele.

Não é o remoto. É a sua última foto conhecida do remoto — e ela só é atualizada quando você roda fetch, pull ou push. Entre uma comunicação e outra, ela pode estar desatualizada sem você saber.

É por isso que o Git consegue dizer "sua branch está 2 commits à frente de origin/main" sem acessar a rede: ele compara dois ponteiros locais.

git status
On branch main
Your branch is ahead of 'origin/main' by 1 commit.
  (use "git push" to publish your local commits)

Vocabulário que aparece o tempo todo:

MensagemSignificaO que fazer
ahead of 'origin/main' by NVocê tem N commits que o remoto não temgit push
behind 'origin/main' by NO remoto tem N commits que você não temgit pull
diverged, N and M different commitsOs dois lados andaramgit pull, resolver, git push
up to dateIguais na última foto conhecidaNada

Para ver os vínculos de todas as branches:

git branch -vv

7. git clone: simulando um colega

Pra entender o resto da aula de verdade, é preciso ter duas cópias conversando com o mesmo remoto — que é a situação real de um time. Vamos criar a segunda:

cd ~/projetos
git clone git@github.com:seuusuario/guia-de-cafes.git guia-de-cafes-colega
Cloning into 'guia-de-cafes-colega'...
remote: Enumerating objects: 36, done.
Receiving objects: 100% (36/36), done.

O último argumento é opcional — sem ele, a pasta ganha o nome do repositório. Aqui damos outro nome só pra conviver com a original.

Daqui em diante, trate essa pasta como se fosse a máquina de outra pessoa. É exatamente o mesmo que acontece quando alguém entra no seu time e clona o projeto.

Repare no que o clone fez sozinho:

cd ~/projetos/guia-de-cafes-colega
git log --oneline | head -3
git remote -v
git branch -vv
  • Baixou todo o histórico, não só os arquivos atuais — é o "distribuído" da aula 1 na prática.
  • Configurou o remoto origin automaticamente.
  • Criou a main local já vinculada a origin/main. Não precisa de -u no primeiro push.

8. fetch e pull

Faça o "colega" mandar um commit:

cd ~/projetos/guia-de-cafes-colega
echo "<!-- revisado pelo colega -->" >> index.html
git commit -am "Marca revisao no index"
git push

Agora volte pra sua pasta original, que não sabe desse commit:

cd ~/projetos/guia-de-cafes
git status
On branch main
Your branch is up to date with 'origin/main'.

Mentira — e é a mentira mais instrutiva desta aula. O Git está comparando com origin/main, a foto antiga da seção 6. Ele não vai à rede pra responder git status.

8.1 fetch: baixar sem mexer

git fetch
remote: Enumerating objects: 5, done.
From github.com:seuusuario/guia-de-cafes
   a1b2c3d..e4f5g6h  main       -> origin/main

O fetch baixa os commits novos e atualiza a foto (origin/main). Ele não encosta na sua branch nem nos seus arquivos. Abra o index.html: o comentário do colega não está lá.

git status
On branch main
Your branch is behind 'origin/main' by 1 commit, and can be fast-forwarded.
  (use "git pull" to update your local branch)

Agora sim a informação é real. Dá pra inspecionar antes de aceitar:

git log --oneline main..origin/main    # o que veio que eu não tenho
git diff main origin/main              # o que muda no código

fetch é sempre seguro. Ele nunca altera seu trabalho, nunca gera conflito, nunca perde nada. Pode rodar a qualquer momento.

8.2 pull: baixar e integrar

git pull
Updating a1b2c3d..e4f5g6h
Fast-forward
 index.html | 1 +
 1 file changed, 1 insertion(+)

Agora o comentário está no seu arquivo.

A relação entre os dois

git pull = git fetch + git merge origin/main

Não é comando novo: é a composição de dois que você já conhece. E, sendo um merge, ele pode gerar conflito — o mesmo conflito da aula 5, resolvido do mesmo jeito.

Repare que este pull foi fast-forward: sua branch não tinha andado, então bastou mover o ponteiro (aula 4, seção 8). É o caso feliz.

9. pull --rebase

O caso não-feliz é quando os dois lados andaram. Provoque:

# na pasta do colega
cd ~/projetos/guia-de-cafes-colega
echo "Contribuicoes sao bem-vindas." >> README.md
git commit -am "Convida contribuicoes no README"
git push
# na sua pasta, sem puxar antes
cd ~/projetos/guia-de-cafes
echo "<!-- rascunho de seçao de moagem -->" >> index.html
git commit -am "Anota rascunho de moagem"

Cada lado tem um commit que o outro não tem. Um git pull comum resolve isso com um merge, e o histórico ganha uma linha estranha:

Merge branch 'main' of github.com:seuusuario/guia-de-cafes

Esse commit não representa decisão nenhuma — é só o registro de que duas pessoas trabalharam ao mesmo tempo. Num time ativo, ele aparece dezenas de vezes por semana e polui o histórico sem informar nada.

A alternativa:

git pull --rebase

Em vez de criar merge commit, o Git pega os seus commits locais e reaplica em cima do que veio do remoto, deixando a história em linha reta:

Com pull comum:
──> colega ──┐
             ├──> Merge branch 'main'
──> seu    ──┘

Com pull --rebase:
──> colega ──> seu (recriado em cima)

Como isso reescreve seus commits locais — que ganham hashes novos —, vale a ressalva da aula 3: só é seguro porque esses commits ainda não tinham sido publicados. O mecanismo completo do rebase, incluindo o que fazer quando ele dá conflito no meio, é a aula 8.

Muita gente adota como padrão:

git config --global pull.rebase true

Com isso, git pull passa a se comportar como git pull --rebase sempre. É configuração comum em time que preza histórico linear — e é decisão coletiva, não individual: vale combinar antes.

Se você nunca configurou nada, o Git 2.27+ imprime um aviso no primeiro pull divergente pedindo pra você escolher entre merge, rebase ou fast-forward only. Não é erro: é ele pedindo uma decisão que não quer tomar por você.

10. Push rejeitado

Este é o erro mais comum de quem começa a trabalhar com remoto. Provoque de propósito — ainda com a divergência da seção anterior, se você não fez o pull:

git push
To github.com:seuusuario/guia-de-cafes.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com:seuusuario/guia-de-cafes.git'
hint: Updates were rejected because the remote contains work that you do
hint: not have locally. This is usually caused by another repository pushing
hint: to the same ref. You may want to first integrate the remote changes
hint: (e.g., 'git pull ...') before pushing again.

Traduzindo: o remoto tem commits que você não tem. Aceitar o seu push apagaria o trabalho da outra pessoa, então o Git recusa.

Isso é o non-fast-forward — o mesmo conceito da aula 4, do outro lado. O push só é aceito quando ele consegue simplesmente arrastar o ponteiro do remoto pra frente. Se as histórias divergiram, não dá.

A solução, sempre

Puxe antes de empurrar. git pull (ou git pull --rebase), resolva conflito se houver, e então git push.

git pull --rebase
git push

O que você vai ver na internet — e não deve fazer: a resposta rápida pra esse erro costuma ser git push --force. Ele funciona, e funciona porque sobrescreve o remoto com a sua versão, apagando os commits que estavam lá. Em repositório compartilhado, é assim que se apaga o trabalho de um colega — sem aviso, e sem que ele saiba antes de perceber que sumiu.

Existe uso legítimo pra force push, e existe uma variante bem menos perigosa (--force-with-lease). As duas coisas são assunto da aula 8, depois que o rebase estiver entendido. Até lá: diante de push rejeitado, a resposta é pull.

11. Branches no remoto

Branch local é sua e ninguém vê. Pra outras pessoas acessarem, precisa ser publicada:

git switch -c metodos-quentes
# ... commits ...
git push -u origin metodos-quentes

De novo o -u: primeira vez de cada branch. Depois disso, git push sozinho.

Do outro lado, quem clonou vê a branch nova depois de um fetch:

cd ~/projetos/guia-de-cafes-colega
git fetch
git branch -a
* main
  remotes/origin/main
  remotes/origin/metodos-quentes

E cria uma cópia local pra trabalhar:

git switch metodos-quentes

Não precisa de -c: quando existe uma branch remota com esse nome, o switch cria a local já vinculada. É atalho de conveniência que você vai usar toda semana.

11.1 Apagando branch remota

Deletar a local (aula 4) não mexe no remoto. São dois comandos:

git branch -d metodos-quentes            # apaga a local
git push origin --delete metodos-quentes # apaga a do remoto

Na prática, quem faz o segundo é o próprio GitHub: o botão de merge do Pull Request oferece apagar a branch junto (aula 7).

11.2 Limpando referências mortas

Quando alguém apaga uma branch no remoto, sua lista local continua mostrando origin/aquela-branch — a foto antiga, de novo. Para limpar:

git fetch --prune

Remove as referências a branches que não existem mais no remoto. Não apaga nada seu.

12. Erros comuns nesta fase

  1. Criar o repositório no GitHub com README marcado tendo repositório local. Dá refusing to merge unrelated histories. Solução preventiva: criar vazio (seção 2.2).
  2. Achar que git status consulta o remoto. Não consulta. Rode git fetch antes se quiser informação atual.
  3. Esquecer o -u no primeiro push da branch. Não quebra nada: o Git responde com o comando completo pra copiar.
  4. Responder a push rejeitado com --force. Apaga trabalho alheio. A resposta é pull.
  5. Commitar credencial. Token, chave privada e .env não entram no repositório — ainda mais em repositório público. Se acontecer, rotacione a credencial (revogue o token, gere outra chave): removê-la do histórico não desfaz o vazamento. Aula 9.
  6. Trabalhar um dia inteiro sem dar push. Perde o backup e aumenta a chance de divergir do time. Push ao menos uma vez por dia.

13. Checklist antes de seguir

  • ssh -T git@github.com responde com seu usuário (ou o token HTTPS funciona)
  • O guia-de-cafes está no GitHub com todo o histórico visível
  • Existe a segunda pasta clonada, e as duas conversam com o mesmo remoto
  • Você sabe explicar o que origin/main é, e por que pode estar desatualizado
  • Sabe a diferença entre fetch e pull em uma frase
  • Provocou um push rejeitado e resolveu com pull
  • Sabe o que -u faz e quando usar
  • Sabe por que git push --force é perigoso em repositório compartilhado

14. O que vem a seguir

Você tem tudo que é preciso pra trabalhar sozinho com um remoto. Falta o que transforma isso em trabalho de time.

  1. Fluxo de time: branch, Pull Request, code review — por que ninguém commita direto na main, como abrir um PR, como revisar o PR de outra pessoa, as três formas de merge do GitHub (merge commit, squash, rebase), branch protection, o CI travando o merge, convenções de nome de branch e commit, e os modelos de fluxo com nome: GitHub Flow, GitFlow e trunk-based.
  2. Rebase e histórico limpo — o mecanismo por trás do pull --rebase, rebase -i e o force push feito direito.
  3. Rede de segurança — stash, reflog e recuperação.

Mantenha as duas pastas — guia-de-cafes e guia-de-cafes-colega — até o fim da trilha. Elas são o jeito mais barato de praticar sozinho tudo que normalmente exigiria outra pessoa: push rejeitado, conflito vindo do remoto, revisar código de terceiro, branch aparecendo do nada. A partir da aula 7 elas passam a ser usadas o tempo todo.
