Material de estudo — Git na prática — Parte 3

Navegando o histórico e desfazendo

Você já sabe criar histórico. Esta aula é a outra metade: consultar o que foi feito e voltar atrás quando algo sai errado. É a aula que mais gera pergunta em time real — não porque os comandos sejam difíceis, mas porque são parecidos, e escolher o errado num repositório compartilhado dá trabalho pra todo mundo. A ideia aqui é você sair com um critério de decisão, não com uma lista de comandos decorada.

1. Ponto de partida

Tudo nesta aula acontece no guia-de-cafes da aula 2. Entre na pasta e confira onde você está:

cd ~/projetos/guia-de-cafes
git log --oneline
git status

Você deve ver alguns commits e working tree clean. Os hashes dos exemplos desta aula serão diferentes dos seus — sempre são. Troque pelos que aparecerem no seu terminal.

Antes de começar, uma boa notícia: quase nada no Git se perde de verdade. Commit que "sumiu" costuma continuar guardado, alcançável pelo git reflog por semanas. A aula 9 é inteira sobre isso. Vale saber disso agora pra experimentar esta aula sem medo — o único comando desta aula que destrói trabalho de forma realmente irrecuperável está sinalizado na seção 9, e ele destrói apenas o que nunca foi commitado.

2. git log com filtros

Na aula 2 o log apareceu na forma crua. Em projeto real, o histórico tem milhares de commits, e o que se faz é procurar. Os filtros abaixo se combinam livremente.

2.1 Quantidade e formato

git log --oneline -5              # os 5 mais recentes, uma linha cada
git log --stat -3                 # mostra quais arquivos mudaram e quanto
git log -p -1                     # mostra o conteúdo da mudança (o diff) do último commit

O --stat é o meio-termo mais útil: dá o resumo sem despejar o diff inteiro.

git log --stat -1
commit 9c4d7e15a2b8f3c6d9e0a1b2c3d4e5f6a7b8c9d0 (HEAD -> main)
Author: Seu Nome <seu@email.com>
Date:   Thu Aug 28 14:32:10 2025 -0300

    Explica o proposito do projeto no README

 README.md | 2 ++
 1 file changed, 2 insertions(+)

2.2 Filtros de busca

ComandoEncontra
git log --author="Felipe"Commits de uma pessoa. Casa por pedaço do nome ou e-mail
git log --grep="prensa"Commits cuja mensagem contém o termo
git log -S "espresso"Commits que adicionaram ou removeram esse texto no código. Diferente do --grep: procura na mudança, não na mensagem
git log --since="2 weeks ago"Por data. Também aceita --until, e datas como 2025-08-01
git log -- index.htmlSó commits que tocaram nesse arquivo. Os dois hífens separam "isto é caminho, não branch"

O -S merece atenção: é o comando de "quando essa linha entrou no código, e em qual commit?". Numa investigação de bug, costuma achar em segundos o que a leitura manual não acha.

git log --oneline --author="Felipe" --since="1 month ago" -- index.html

Traduzindo: commits do Felipe, do último mês, que mexeram no index.html.

2.3 O formato que a maioria dos times usa

git log --oneline --graph --decorate --all

Quatro flags que andam juntas: --graph desenha as linhas do grafo, --decorate mostra os nomes de branch e tag, --all inclui todas as branches, não só a atual. Com um histórico linear como o seu agora, o resultado é modesto — a partir da aula 4 ele vira a forma padrão de enxergar o repositório.

Isso vira um atalho depois. Ninguém digita essas quatro flags todo dia; se cria um alias. Fica pra aula 10, junto com o resto da configuração de conforto.

3. git show: abrindo um commit

O log lista. O show abre um commit e mostra tudo dele — metadados e a mudança completa:

git show 64a8889
commit 64a888952c1e4a7b0c3d6e9f2a5b8c1d4e7f0a3b
Author: Seu Nome <seu@email.com>
Date:   Thu Aug 28 14:28:44 2025 -0300

    Adiciona coado e prensa francesa na lista

diff --git a/index.html b/index.html
index 3a5f1c2..8b9d4e7 100644
--- a/index.html
+++ b/index.html
@@ -8,6 +8,8 @@
   <ul>
     <li>Espresso</li>
+    <li>Coado</li>
+    <li>Prensa francesa</li>
   </ul>

Sem argumento, git show mostra o commit mais recente. Também dá pra pedir um arquivo específico dentro de um commit:

git show 64a8889:index.html      # o arquivo inteiro como estava naquele commit

3.1 Lendo um diff

Essa saída aparece no show, no diff, no code review do GitHub e no conflito de merge da aula 5. Vale decodificar de vez:

LinhaSignifica
--- a/index.htmlVersão antiga do arquivo
+++ b/index.htmlVersão nova
@@ -8,6 +8,8 @@Cabeçalho do trecho: a partir da linha 8, antes eram 6 linhas, agora são 8
Linha com +Adicionada
Linha com -Removida
Linha sem sinalContexto — não mudou, está ali só pra você se localizar

Uma linha alterada aparece como um - seguido de um +. O Git não tem conceito de "linha editada": ele vê remoção mais adição.

4. git diff: as três comparações

Aqui mora uma confusão clássica. git diff compara duas versões, e o resultado muda completamente dependendo de quais duas. Como existem três áreas (aula 2), existem três comparações possíveis.

Faça uma mudança pra ter o que comparar:

Alterar index.html — dentro do <ul>, acrescente uma linha:

    <li>Prensa francesa</li>
    <li>Aeropress</li>
  </ul>

4.1 Working directory vs staging

git diff

Sem argumento nenhum, o diff responde: "o que eu mudei e ainda não coloquei na caixa?" — working directory contra staging.

diff --git a/index.html b/index.html
--- a/index.html
+++ b/index.html
@@ -10,6 +10,7 @@
     <li>Prensa francesa</li>
+    <li>Aeropress</li>
   </ul>

Agora coloque no staging e rode de novo:

git add index.html
git diff

Saída vazia. Não é bug: não há mais diferença entre o working directory e o staging — as duas áreas estão iguais. É exatamente aqui que a maioria trava na primeira vez.

4.2 Staging vs último commit

git diff --staged

Responde: "o que vai entrar se eu commitar agora?" — staging contra o último commit. A linha do Aeropress reaparece.

--cached é sinônimo de --staged; você vai ver os dois por aí.

O hábito que separa

Rodar git diff --staged imediatamente antes de todo git commit. É a última chance de ver exatamente o que está sendo gravado — e é assim que se pega o console.log esquecido, a senha coladinha por engano e o arquivo que entrou junto sem querer.

4.3 Comparando commits

git diff 49413d5 4e993b8           # entre dois commits
git diff 49413d5                   # de um commit até o estado atual
git diff HEAD~2 HEAD -- index.html # só um arquivo, entre dois pontos

A ordem importa: o primeiro argumento é o "antes", o segundo é o "depois". Inverter mostra o diff de cabeça pra baixo.

4.4 Resumindo as três

ComandoComparaPergunta que responde
git diffWorking directory × stagingO que mudei e ainda não adicionei?
git diff --stagedStaging × último commitO que vai entrar no commit?
git diff HEADWorking directory × último commitTudo que mudei desde o último commit, adicionado ou não
git diff A BCommit A × commit BO que mudou entre esses dois pontos da história?

Finalize o ciclo antes de seguir:

git commit -m "Adiciona aeropress na lista"

5. Como apontar para um commit

Os comandos de desfazer precisam que você diga até onde voltar. Existem três formas de nomear um commit, e a segunda é a que se usa no dia a dia:

FormaExemploObservação
Hash4e993b8Os 7 primeiros caracteres bastam. Preciso, mas você precisa ir buscar no log
Relativo a HEADHEAD~1"Um commit antes de onde estou". HEAD~3 = três antes. É a forma mais usada
Nome de branchmainAponta pro commit mais recente daquela branch (aula 4)

Lembrando da aula 2: HEAD é "onde eu estou agora", normalmente o commit mais recente da sua branch. Então:

HEAD      # commit atual
HEAD~1    # o anterior
HEAD~2    # dois antes
HEAD~5    # cinco antes

Sobre o ^: você vai encontrar HEAD^ por aí, e nesta situação ele é igual a HEAD~1. Os dois só se diferenciam em commit de merge, que tem dois pais — assunto da aula 4. Por ora, use ~ e não se preocupe.

6. Os cinco níveis de desfazer

Antes dos comandos, o mapa. "Desfazer" no Git não é uma coisa só: depende de onde a mudança está. São cinco situações, da mais inofensiva pra mais delicada:

1

Editei o arquivo e quero jogar fora

A mudança está só no working directory. git restore

2

Fiz add e quero tirar da caixa

A mudança está no staging. git restore --staged

3

Commitei e quero corrigir o último commit

Errei a mensagem ou esqueci um arquivo. git commit --amend

4

Quero apagar um ou mais commits

Só serve se ainda não foram compartilhados. git reset

5

Quero desfazer um commit que já foi publicado

Apagar não é opção. git revert

Repare no critério que separa o 4 do 5: o commit já saiu da sua máquina? Volta na seção 11.

7. Nível 1 e 2: restore

7.1 Descartar mudança não commitada

Estrague um arquivo de propósito:

Alterar README.md — apague tudo e escreva qualquer bobagem:

asdasdasd
git status
Changes not staged for commit:
  (use "git restore <file>..." to discard changes in working directory)
	modified:   README.md

O próprio Git sugere a saída. Aceite:

git restore README.md

Abra o arquivo: voltou ao conteúdo do último commit. Para descartar tudo de uma vez, git restore ..

Este comando destrói trabalho sem rede de segurança. A mudança descartada nunca esteve num commit, então o reflog da aula 9 não recupera. É o único ponto desta aula onde o Git realmente apaga algo pra sempre — e ele não pergunta se você tem certeza. Antes de rodar git restore ., confira com git diff o que está prestes a sumir.

7.2 Tirar do staging

git add README.md      # supondo que você adicionou por engano
git restore --staged README.md

A flag --staged muda o alvo: em vez de mexer no arquivo, ela tira da caixa. A alteração continua no seu arquivo, intacta — só saiu do próximo commit. Este comando é seguro: não perde nada.

ComandoEfeito no arquivoPerde trabalho?
git restore arquivoVolta ao conteúdo do último commitSim
git restore --staged arquivoNenhum. Só sai do stagingNão

Os dois juntos desfazem tudo que ainda não virou commit: git restore --staged arquivo seguido de git restore arquivo.

8. Nível 3: commit --amend

Duas situações resolvidas pelo mesmo comando, e as duas acontecem toda semana.

8.1 Errei a mensagem

git commit --amend -m "Adiciona aeropress na lista de metodos"

O commit anterior é substituído por um novo, com a mensagem corrigida e o mesmo conteúdo.

8.2 Esqueci um arquivo

Você commitou e percebeu que faltou algo que fazia parte da mesma mudança:

git add arquivo-esquecido.html
git commit --amend --no-edit

O --no-edit diz "mantenha a mensagem como está". O que estava no staging entra no commit anterior, que continua sendo um commit só — em vez de virar um segundo commit "esqueci um arquivo", que polui o histórico.

O --amend não edita o commit: ele cria outro. Da aula 1, seção 6.3 — o hash é calculado a partir do conteúdo, então qualquer alteração produz um commit diferente, com hash novo. O antigo deixa de fazer parte da história.

Consequência prática: só use --amend em commit que ainda não foi enviado pro remoto. Se já foi, o commit que você acabou de reescrever continua existindo na cópia das outras pessoas, e o Git vai recusar seu push. A regra completa está na seção 11.

9. Nível 4: reset

O reset move o ponteiro da branch pra trás. Os commits que ficaram pra frente saem da história.

git log --oneline
4e993b8 (HEAD -> main) Explica o proposito do projeto no readme
64a8889 Adiciona coado e prensa francesa
49413d5 Cria estrutura inicial

Rodar git reset 49413d5 faz a main voltar a apontar pro primeiro commit. Os outros dois somem do log.

A pergunta que sobra é: e as alterações que estavam neles? É isso que as três flags decidem.

9.1 As três formas

ComandoCommitsStagingSeus arquivos
git reset --soft <commit>SomemAlterações ficam aquiPreservados
git reset --mixed <commit>SomemLimpoPreservados
git reset --hard <commit>SomemLimpoDescartados

--mixed é o padrão: git reset HEAD~1 sem flag nenhuma faz isso.

Traduzindo pra situação real:

  • --soft — "esses commits não deviam ser separados". As mudanças voltam pro staging, prontas pra virar um commit só. É o jeito mais simples de juntar três commits pequenos em um antes de mostrar pra alguém.
  • --mixed — "quero refazer esses commits do zero, escolhendo melhor o que entra em cada um". As mudanças ficam na pasta, fora do staging.
  • --hard — "esse trabalho todo foi um erro, quero o estado daquele commit e mais nada".

9.2 Exemplo prático: juntando dois commits

Faça dois commits bobos, um depois do outro:

echo "<!-- rascunho -->" >> index.html
git commit -am "Comeca rascunho"
echo "<!-- rascunho 2 -->" >> index.html
git commit -am "Continua rascunho"

Dois commits que deveriam ser um. Junte:

git reset --soft HEAD~2
git status
Changes to be committed:
	modified:   index.html

Os dois commits sumiram, e as alterações dos dois estão no staging, juntas. Agora vira um commit só:

git commit -m "Adiciona comentarios de rascunho no index"

Isso é a versão manual do "squash" que a aula 8 automatiza com rebase -i.

9.3 O --hard

Comando destrutivo — leia antes de rodar. git reset --hard descarta, sem confirmação:

  • os commits à frente do ponto escolhido;
  • tudo que estiver no staging;
  • todas as alterações não commitadas nos seus arquivos.

Os commits são recuperáveis pelo git reflog (aula 9) por cerca de 30 dias. As alterações não commitadas não são recuperáveis por nada.

Antes de rodar: git status e confirme working tree clean.

Com essa ressalva feita, o uso legítimo:

git status                    # confirme: working tree clean
git reset --hard HEAD~2       # descarta os 2 últimos commits

Um jeito barato de trabalhar sem risco enquanto você não tem intimidade com o comando: antes do reset, rode git branch backup. Isso deixa uma marca no commit atual, e você volta pra ela quando quiser. Branch é assunto da aula 4, mas o comando funciona hoje.

10. Nível 5: revert

O revert resolve o mesmo problema por um caminho oposto: em vez de apagar o commit, ele cria um commit novo que aplica o inverso do que o outro fez.

git log --oneline
a7b3c91 (HEAD -> main) Adiciona comentarios de rascunho no index
9c4d7e1 Adiciona aeropress na lista
4e993b8 Explica o proposito do projeto no readme

Desfaça o commit de rascunho:

git revert a7b3c91

O Git abre o editor com uma mensagem já pronta (Revert "Adiciona comentarios de rascunho no index"). Salve e feche — ou use --no-edit pra aceitar direto.

git log --oneline
f2e8d40 (HEAD -> main) Revert "Adiciona comentarios de rascunho no index"
a7b3c91 Adiciona comentarios de rascunho no index
9c4d7e1 Adiciona aeropress na lista
4e993b8 Explica o proposito do projeto no readme

Os comentários de rascunho sumiram do arquivo, mas o histórico cresceu em vez de encolher. Os dois commits — o original e o que o desfez — continuam lá, e é possível ver que a mudança existiu e foi revertida.

Para reverter vários, liste do mais novo pro mais antigo:

git revert --no-edit HEAD HEAD~1

A ordem importa: reverter de trás pra frente aplica os inversos na sequência correta e evita conflito.

Reverter um revert funciona. Como o revert é só mais um commit, dá pra revertê-lo e trazer a mudança de volta. Acontece de verdade: desfaz-se uma funcionalidade que quebrou produção, corrige-se com calma, e ela volta.

11. A pergunta que decide entre os dois

reset e revert chegam ao mesmo estado de código. A escolha não é de gosto:

O critério

O commit já saiu da sua máquina?

Não (só local, nunca deu push) — reset é livre. Ninguém mais viu aqueles commits, então apagá-los não afeta pessoa nenhuma.

Sim (já foi pro remoto, outras pessoas podem ter puxado) — use revert. Sempre.

O motivo é o hash, de novo. Quando você apaga commits que outras pessoas já baixaram, a história delas e a sua deixam de bater. Elas vão puxar, o Git vai tentar reconciliar duas versões diferentes do mesmo passado, e os commits que você apagou voltam — trazidos pela cópia delas. O resultado é um histórico embaralhado que alguém vai ter que arrumar na mão.

Isso tem nome — a regra de ouro: não reescreva histórico compartilhado — e vale pro reset, pro --amend e pro rebase da aula 8, que é onde o assunto é fechado.

Commit ainda local

git reset --soft HEAD~2
git commit -m "mensagem melhor"

Histórico limpo, ninguém foi afetado.

Commit já publicado

git reset --hard HEAD~2
git push --force

Reescreve a história de todo mundo. Em time, é assim que se apaga o trabalho de um colega sem perceber.

Enquanto o repositório é só seu e local — o caso do guia-de-cafes até a aula 6 — nenhum comando desta aula tem consequência pra outra pessoa. Experimente à vontade agora; é justamente pra isso que o projeto de estudo existe.

13. Por que a internet manda usar checkout

Ao procurar qualquer coisa desta aula fora daqui, você vai achar respostas com git checkout:

git checkout -- arquivo.txt      # equivale a git restore arquivo.txt
git checkout abc1234             # navegar até um commit antigo

Não está errado — funciona até hoje. É que o checkout era um comando sobrecarregado: trocava de branch, restaurava arquivo, navegava pra um commit, criava branch. Coisas sem relação, com uma sintaxe em que dois hífens fora do lugar mudavam completamente o efeito.

Na versão 2.23 (2019), o Git separou as responsabilidades:

AntesHojeFaz
git checkout -- arquivogit restore arquivoMexe em arquivo
git checkout branchgit switch branchMexe em branch (aula 4)

Use restore e switch: são mais claros e mais difíceis de usar errado. Mas saiba ler checkout, porque ele está em toda resposta antiga de fórum, em documentação de projeto e no dedo de quem aprendeu Git antes de 2019 — e não vai sumir tão cedo.

14. Erros comuns nesta fase

  1. Rodar git diff depois do add e achar que a mudança sumiu. Ela está no staging. Use git diff --staged.
  2. Usar --hard como reflexo. A maioria dos casos quer --soft ou --mixed. O --hard é o único que apaga arquivo, e quase nunca é o que se precisa.
  3. reset em commit já publicado. Funciona na sua máquina e quebra pro time. É revert.
  4. --amend depois do push. Mesmo problema: o commit já está na mão dos outros.
  5. Entrar em pânico e apagar a pasta. Quase tudo é recuperável (aula 9). Apagar o .git é o único jeito garantido de perder de verdade.
  6. Confundir revert com "voltar pra um commit antigo". git revert abc123 desfaz aquele commit específico, não tudo que veio depois dele.

15. Checklist antes de seguir

  • Você sabe dizer o que git diff e git diff --staged comparam, sem consultar
  • Consegue achar todos os commits que tocaram no index.html
  • Sabe ler um diff: +, -, contexto e o cabeçalho @@
  • Sabe o que HEAD~2 significa
  • Já usou git restore e git restore --staged e sabe qual dos dois perde trabalho
  • Já juntou dois commits com git reset --soft
  • Já fez um git revert e viu o histórico crescer em vez de encolher
  • Sabe responder, em uma frase, quando usar reset e quando usar revert

16. O que vem a seguir

Tudo até aqui aconteceu numa linha reta de commits, numa branch só. A partir da próxima aula, o histórico deixa de ser uma linha.

  1. Branches: trabalhar em paralelo — por que branch é só um ponteiro (e por que isso a torna barata), o que HEAD significa de verdade, git switch -c, git branch, as duas formas de merge (fast-forward e merge commit) e quando deletar uma branch.
  2. Conflitos de merge — provocar um de propósito no guia-de-cafes e resolver na mão.
  3. Repositório remoto — o projeto sai da sua máquina e vai pro GitHub.

Esta é a aula que mais compensa praticar antes de seguir, porque os comandos são parecidos e a diferença entre eles só fica clara com o dedo. Sugestão: faça três ou quatro commits bobos no guia-de-cafes e desfaça cada um de um jeito diferente — um com --amend, um com reset --soft, um com revert — conferindo o git log --oneline depois de cada um. Enquanto o repositório for só seu, errar aqui não custa nada.
