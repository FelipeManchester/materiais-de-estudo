Conflitos de merge

Todos os merges da aula 4 deram certo sozinhos — as mudanças estavam em arquivos e linhas diferentes, de propósito. Esta aula quebra isso. Conflito é a parte do Git que mais assusta quem está começando, e o motivo é quase sempre o mesmo: a pessoa nunca viu um de propósito, num lugar onde errar não custa nada. É o que vamos fazer aqui. No fim você vai ver conflito como o que ele é — uma pergunta que o Git faz porque não tem como adivinhar a resposta.

1. Por que conflito acontece

Quando o Git faz um merge, ele não compara só as duas pontas. Ele olha três versões do arquivo:

A base comumO último commit em que as duas branches eram iguais — onde elas se separaram
Sua versãoComo o arquivo ficou na branch que está recebendo
A outra versãoComo o arquivo ficou na branch que está vindo

Com essas três em mãos, ele resolve sozinho a maioria dos casos, porque consegue responder "o que cada lado mudou em relação à base":

  • Só um lado mexeu num trecho? Aplica a mudança desse lado.
  • Os dois mexeram, mas em partes distantes do arquivo? Aplica as duas.
  • Os dois fizeram exatamente a mesma alteração? Aplica uma vez.

O merge automático da aula 4 foi isso. Impressiona: dois arquivos, mudanças independentes, resolvido sem você.

Quando ele desiste

Conflito acontece quando as duas branches alteraram a mesma linha do mesmo arquivo de formas diferentes. Aí não existe resposta técnica: as duas mudanças são válidas, e escolher qual vale é decisão de quem escreveu o código. O Git para e pergunta.

Reformulando o mais importante: conflito não é erro, e não é sinal de que você fez algo errado. É o Git se recusando a adivinhar. A alternativa — escolher sozinho — seria muito pior: ele descartaria em silêncio o trabalho de alguém.

2. Provocando um conflito

Vamos fabricar um. Comece limpo:

cd ~/projetos/guia-de-cafes
git switch main
git status

2.1 A branch

git switch -c titulo-descritivo

Alterar index.html — na linha do <h1>, troque o texto do título:

<body>
-  <h1>Guia de Cafés</h1>
+  <h1>Guia de Cafés: métodos e preparo</h1>
  <ul>
git commit -am "Deixa o titulo mais descritivo"

2.2 A mesma linha, na main

git switch main

Alterar index.html — a mesma linha do <h1>, com um texto diferente:

<body>
-  <h1>Guia de Cafés</h1>
+  <h1>O Guia do Café</h1>
  <ul>
git commit -am "Encurta o titulo da pagina"

Pronto: duas branches, duas versões diferentes da mesma linha. Exatamente o que acontece quando duas pessoas de um time mexem no mesmo trecho na mesma semana.

2.3 O merge

git merge titulo-descritivo
Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.

Conflito. Leia a mensagem com calma, porque ela já diz tudo: qual arquivo (index.html), que tipo (content) e o que fazer (resolver e commitar).

3. O Git travou. E agora?

Primeira coisa, sempre:

git status
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   index.html

no changes added to commit (use "git add" and/or "git commit -a")

Três informações importantes aí:

  • You have unmerged paths — o repositório está num estado especial, no meio de um merge. Ele fica assim até você concluir ou abortar.
  • both modified — a categoria nova do status, além das três da aula 2. Lista os arquivos que precisam da sua decisão.
  • As duas saídas possíveis, sugeridas pelo próprio Git: resolver e commitar, ou git merge --abort.

Não há pressa e não há risco. Nesse estado, nada foi perdido: as duas versões estão guardadas nos commits de cada branch. Dá pra sair pra almoçar no meio de um conflito. O git status vai lembrar você de onde parou.

Um detalhe que ajuda: no meio do conflito o seu prompt do terminal pode mudar, mostrando algo como (main|MERGING). É o shell avisando o estado. Se o seu não mostra, o git status diz a mesma coisa.

4. Lendo os marcadores

O Git editou o index.html e escreveu as duas versões dentro dele. Abra o arquivo:

<body>
<<<<<<< HEAD
  <h1>O Guia do Café</h1>
=======
  <h1>Guia de Cafés: métodos e preparo</h1>
>>>>>>> titulo-descritivo
  <ul>

Isso é texto comum dentro do seu arquivo — nada mágico. Anatomia:

MarcadorSignifica
<<<<<<< HEADComeça aqui a versão da branch em que você está (a que recebe)
=======Divisória entre as duas versões
>>>>>>> titulo-descritivoTermina aqui a versão da branch que está vindo. O nome dela aparece no marcador

O trecho entre <<<<<<< e ======= é o seu lado. Entre ======= e >>>>>>> é o lado que veio.

Se houver vários trechos em conflito no mesmo arquivo, cada um vem com seu próprio conjunto de marcadores. Todos precisam ser resolvidos.

O arquivo, nesse estado, está quebrado. É HTML com lixo no meio; se fosse código, não compilaria. Isso é intencional — é praticamente impossível não perceber que existe conflito pendente. O acidente clássico é justamente commitar com os marcadores dentro; a seção 12 mostra como evitar.

5. Resolvendo na mão

Resolver significa uma coisa só: deixar o arquivo do jeito que ele deve ficar, e apagar os marcadores. Não existe comando que decida por você — a decisão é editorial.

Três saídas possíveis, e as três são legítimas:

1

Fica a sua versão

Apaga o outro lado e os três marcadores.

2

Fica a versão que veio

Mesma coisa, ao contrário.

3

Fica uma terceira coisa

Você combina as duas, ou escreve algo novo que resolve o que os dois lados queriam. É o caso mais comum em código de verdade.

Vamos pela terceira, que é a mais realista:

Alterar index.html — apague as duas versões e os três marcadores, deixando só a linha final:

<body>
  <h1>O Guia do Café: métodos e preparo</h1>
  <ul>

Confira que não sobrou marcador nenhum no arquivo:

grep -n "<<<<<<<\|=======\|>>>>>>>" index.html

Sem saída significa limpo.

5.1 Marcando como resolvido

git add index.html

Aqui o add tem um significado extra: além de colocar no staging, ele declara ao Git que aquele arquivo está resolvido. Era isso que o status dizia com "use git add <file>... to mark resolution".

git status
On branch main
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)

Changes to be committed:
	modified:   index.html

5.2 Concluindo

git commit

Sem -m: o Git abre o editor com a mensagem de merge já preenchida, listando os arquivos que tiveram conflito. Aceite como está — mensagem de merge é uma das poucas em que o padrão do Git é melhor que o improviso. Salve e feche.

git log --oneline --graph -4
*   8f3c204 (HEAD -> main) Merge branch 'titulo-descritivo'
|\
| * b1e7d59 (titulo-descritivo) Deixa o titulo mais descritivo
* | 6a2f8c3 Encurta o titulo da pagina
|/
* e5b1f77 Merge branch 'rodape'

Um merge commit normal, igual ao da aula 4 — com dois pais. Do ponto de vista do histórico, não sobra registro de que houve conflito: o merge commit apenas guarda o resultado que você decidiu.

Limpe a branch:

git branch -d titulo-descritivo

Alternativa ao git commit: git merge --continue faz exatamente a mesma coisa e é mais explícito sobre o que está acontecendo. Os dois existem; use o que preferir. O --continue volta na aula 8, no conflito durante rebase, onde ele não é opcional.

6. merge --abort: desistir no meio

Nem todo conflito precisa ser resolvido na hora. Às vezes ele é maior do que se esperava, ou você percebe que mergeou a branch errada, ou simplesmente quer entender melhor antes de decidir.

git merge --abort

Isso desfaz o merge inteiro e devolve o repositório exatamente ao estado anterior ao comando git merge: sem marcadores nos arquivos, sem estado de merge, sem nada pela metade. É seguro e reversível — dá pra tentar o merge de novo depois.

Vale experimentar agora pra ver funcionando: refaça um conflito qualquer e aborte. Saber que essa saída existe muda a relação com conflito — nenhuma situação de merge é sem volta.

Uma ressalva: o --abort descarta também as edições que você tiver feito nos arquivos em conflito durante a resolução. Se você passou vinte minutos resolvendo um arquivo grande e abortar, esse trabalho vai junto. Ele desfaz o merge por completo, não só a parte automática.

7. ours e theirs

Quando o conflito é do tipo "quero um lado inteiro, sem editar nada", existem atalhos:

git checkout --ours index.html      # fica a versão da branch atual
git checkout --theirs index.html    # fica a versão da branch que veio
git add index.html
Qual é qual

ours = a branch em que você está, a que recebe o merge. theirs = a branch que você mandou vir, no git merge <nome>.

Regra prática: ours é sempre o lado que aparece sob <<<<<<< HEAD.

Esses nomes confundem porque dependem de onde você está, não de quem escreveu o código. Se você está na main mergeando a branch de um colega, ours é a main — mesmo que o código dela tenha sido escrito por outra pessoa.

Use com parcimônia. Descartar um lado inteiro joga fora o trabalho de alguém sem ler. Faz sentido em arquivo gerado automaticamente, ou quando você tem certeza absoluta. Em código escrito à mão, o normal é abrir e decidir trecho por trecho.

8. Vendo a versão original também

Com dois lados na tela e nenhuma referência, às vezes falta a informação mais útil: como aquilo era antes de os dois mexerem. Saber isso costuma deixar óbvio qual lado mudou o quê.

O Git sabe mostrar, mas não vem ligado por padrão:

git config --global merge.conflictStyle zdiff3

Com isso, o conflito passa a ter três partes:

<<<<<<< HEAD
  <h1>O Guia do Café</h1>
||||||| base
  <h1>Guia de Cafés</h1>
=======
  <h1>Guia de Cafés: métodos e preparo</h1>
>>>>>>> titulo-descritivo

O trecho entre ||||||| e ======= é a base comum — o original de onde os dois lados partiram. Agora dá pra ver que um lado encurtou e o outro acrescentou complemento.

É uma das configurações que mais valem a pena e quase ninguém conhece. zdiff3 exige Git 2.35 ou superior; em versões mais antigas, use diff3.

9. Resolvendo pelo editor

Na prática, quase ninguém resolve conflito apagando marcador na mão — o editor faz isso melhor. No VS Code, um arquivo em conflito mostra botões acima de cada trecho:

BotãoEquivale a
Accept Current Changeours — o lado do HEAD
Accept Incoming Changetheirs — o lado que veio
Accept Both ChangesMantém os dois, um depois do outro
Compare ChangesAbre os dois lado a lado

Os botões só apagam os marcadores e deixam o que você escolheu — o resultado é idêntico a editar na mão. E, mesmo usando o editor, o git add continua sendo necessário pra marcar como resolvido, e o commit pra concluir.

Cuidado com "Accept Both". Ele empilha as duas versões, o que quase nunca é o que se quer — no nosso exemplo, resultaria em dois <h1> na página. É rápido e por isso tentador; leia o resultado antes de seguir.

Existe ainda git mergetool, que abre uma ferramenta gráfica de três painéis configurada à parte. Vale saber que existe; o editor resolve na esmagadora maioria dos casos.

10. Outros tipos de conflito

"Mesma linha" é o caso mais comum, mas não é o único. Os outros aparecem menos e assustam mais, porque não trazem marcadores:

SituaçãoComo o Git mostraComo resolver
Um lado editou o arquivo, o outro deletoudeleted by them ou deleted by usDecidir se o arquivo fica: git add arquivo pra manter, git rm arquivo pra apagar
Os dois criaram um arquivo com o mesmo nomeboth addedIgual ao conflito de conteúdo: marcadores dentro do arquivo
Um lado renomeou, o outro editouAviso de rename/modifyO Git costuma acertar sozinho; confira o resultado antes de commitar

Em todos, o caminho é o mesmo: git status pra ver a categoria, decidir, git add (ou git rm) pra marcar, e commitar.

11. O que reduz conflito num time

Conflito não se elimina — onde há duas pessoas no mesmo código, ele vai acontecer. O que se controla é a frequência e, principalmente, o tamanho. Um conflito de três linhas se resolve em um minuto; um de trezentos vira meio dia de trabalho e risco real de apagar coisa sem querer.

1

Branch curta

A medida mais eficaz, de longe. Uma branch que vive dois dias diverge pouco. Uma que vive três semanas acumula todas as mudanças que o resto do time fez nesse período — e cobra tudo de uma vez no merge.

2

Atualizar a branch com frequência

Trazer a main pra dentro da sua branch periodicamente (git merge main estando nela) resolve os conflitos aos poucos, enquanto são pequenos, em vez de deixar tudo pro fim.

3

Commits pequenos e focados

Aquilo da aula 2 sobre staging. Commit que mexe em uma coisa só gera conflito localizado e fácil de entender.

4

Combinar quem mexe onde

Simples e subestimado. Duas pessoas reescrevendo o mesmo arquivo na mesma semana é problema de organização, não de ferramenta. Uma conversa de trinta segundos evita horas.

5

Formatação automática combinada

Metade dos conflitos gigantes em time é formatação: seu editor reindenta o arquivo inteiro, e cada linha vira conflito. Ferramenta de formatação com configuração versionada no projeto elimina essa categoria inteira.

Os dois primeiros itens só ficam completos com o remoto, na aula 6 — atualizar a branch pressupõe ter de onde puxar novidade.

12. Erros comuns nesta fase

  1. Commitar com os marcadores dentro. O erro mais frequente, e chega a produção com <<<<<<< no meio do arquivo. Prevenção: rodar git diff --staged antes do commit (aula 3, seção 4.2) — os marcadores saltam aos olhos.
  2. Resolver um trecho e esquecer os outros. Arquivo grande pode ter vários blocos em conflito. O git status continua acusando enquanto sobrar algum.
  3. Apagar o marcador e esquecer o git add. O arquivo está certo, mas o Git ainda considera não resolvido. O add é o que marca a resolução.
  4. Entrar em pânico e apagar a pasta do projeto. Sempre há git merge --abort. Nada está perdido durante um conflito.
  5. Aceitar um lado inteiro sem ler. --ours/--theirs ou "Accept Current Change" por pressa descartam trabalho alheio em silêncio. Ninguém percebe até faltar a funcionalidade.
  6. Resolver conflito e não testar. O resultado é código que nunca existiu antes — a combinação de duas mudanças. Compila? Funciona? Rode o projeto antes de dar por encerrado.

13. Checklist antes de seguir

  • Você provocou um conflito de propósito e resolveu até o commit final
  • Sabe explicar por que o Git resolve alguns merges sozinho e outros não
  • Identifica os três marcadores e sabe qual lado é qual
  • Sabe que git add é o que marca um arquivo como resolvido
  • Já rodou git merge --abort e viu o repositório voltar ao normal
  • Sabe dizer o que são ours e theirs sem hesitar
  • Consegue citar duas práticas que reduzem conflito num time

14. O que vem a seguir

Metade da trilha. Você já sabe versionar, consultar, desfazer, trabalhar em paralelo e resolver conflito — tudo dentro da sua máquina. A partir da próxima aula o projeto sai daqui.

  1. Repositório remoto: GitHub — criar conta e repositório, SSH vs HTTPS com token, remote add, push, clone, a diferença entre fetch e pull, o push rejeitado por non-fast-forward e o que é uma branch de rastreamento.
  2. Fluxo de time — Pull Request, code review, e os modelos de fluxo que os times usam.
  3. Rebase — a outra forma de integrar branches, e o conflito durante rebase, que se resolve de um jeito diferente do desta aula.

Vale provocar mais dois ou três conflitos no guia-de-cafes antes de seguir, resolvendo cada um de um jeito: um ficando com o seu lado, um com o outro, um combinando os dois — e um abortando no meio só pra ver o repositório voltar ao normal. Conflito deixa de assustar quando vira rotina, e este é o único momento da sua vida em que ele não custa nada.
