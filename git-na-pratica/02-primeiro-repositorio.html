Primeiro repositório: o ciclo básico

Aqui começa o comando de verdade. Você cria o projeto guia-de-cafes do zero, transforma ele em repositório e roda o ciclo editar → status → add → commit algumas vezes, até ele virar automático. No meio do caminho, entende por que existe uma área intermediária entre seu arquivo e o histórico — a parte que confunde quem vem de outras ferramentas — e sai com um .gitignore funcionando, incluindo o caso em que ele parece ignorado.

1. Criando o projeto

Antes do Git, o projeto. Lembrando da aula 1: ele mora fora deste repositório de estudo, pra não criar repositório dentro de repositório.

mkdir -p ~/projetos/guia-de-cafes
cd ~/projetos/guia-de-cafes

No Windows com Git Bash, ~ aponta pra sua pasta de usuário do mesmo jeito. Confira onde você está com pwd — daqui em diante, todo comando desta aula roda de dentro dessa pasta.

Criar index.html — arquivo novo, na raiz do projeto:

<!DOCTYPE html>
<html lang="pt-BR">
<head>
  <meta charset="UTF-8">
  <title>Guia de Cafés</title>
</head>
<body>
  <h1>Guia de Cafés</h1>
  <ul>
    <li>Espresso</li>
  </ul>
</body>
</html>

Criar README.md — arquivo novo, na raiz do projeto:

# Guia de Cafés

Lista de métodos e tipos de café.

Pode criar pelo editor de texto ou pelo terminal, tanto faz. A pasta agora tem dois arquivos e nenhum controle de versão — é só uma pasta comum.

2. git init: virando repositório

git init

Saída:

Initialized empty Git repository in /home/voce/projetos/guia-de-cafes/.git/

Um comando, e a pasta virou repositório. O que mudou de concreto: apareceu uma subpasta oculta .git. Confira:

ls -a
.  ..  .git  index.html  README.md

Essa pasta .git é o repositório. Todo o histórico, todos os commits, todas as branches, a configuração local: tudo mora ali. Seus arquivos de trabalho continuam sendo arquivos normais na pasta, sem nada de especial.

Duas consequências que valem gravar:

Apagar a pasta .git apaga todo o histórico e devolve uma pasta comum, com os arquivos na versão atual. Não existe lixeira. É a operação mais destrutiva desta aula, e ninguém pergunta se você tem certeza.

Copiar a pasta do projeto leva o histórico junto, porque o .git vai junto. É por isso que um clone (aula 6) tem a história completa.

Não é preciso abrir o .git nem entender o formato dele — isso é o "plumbing" que a trilha declarou fora de escopo. Basta saber que é ali que o Git guarda tudo.

3. As três áreas do Git

Este é o conceito central da aula. Em ferramentas mais simples, salvar uma versão é um passo só. No Git são dois, e existe uma área intermediária entre o seu arquivo e o histórico:

Working directoryOs arquivos como estão na pasta agora. Onde você edita.
git add ↓
Staging areaTambém chamada de index. O rascunho do próximo commit: o que você já escolheu incluir.
git commit ↓
RepositórioO histórico, dentro de .git. Commits gravados, com hash e mensagem.

3.1 Por que existe o staging

A pergunta natural é: por que dois passos, se eu quase sempre quero commitar tudo que mudei?

Porque "tudo que mudei" e "uma mudança" raramente são a mesma coisa. Na prática, uma sessão de trabalho fica assim:

  • Você foi implementar uma funcionalidade nova.
  • No caminho, corrigiu um erro de digitação num outro arquivo.
  • E mexeu num arquivo de configuração só pra testar uma coisa — que não deveria ir pro histórico.

Sem staging, isso vira um commit só, com três assuntos misturados. Com staging, você monta o commit escolhendo o que entra: primeiro a funcionalidade, depois o erro de digitação em outro commit, e a alteração de teste fica de fora. O histórico resultante é legível — e reverter uma coisa não desfaz as outras (aula 3).

Modelo mental que ajuda: o staging é a caixa onde você vai colocando o que quer mandar. git add põe na caixa, git commit fecha e etiqueta a caixa. Enquanto não fechou, dá pra tirar coisa de dentro.

Um detalhe importante e não óbvio: o add captura o arquivo como ele está naquele instante. Se você faz git add arquivo.txt, edita o arquivo de novo e commita, o commit leva a versão do add — não a mais recente. O git status avisa disso mostrando o mesmo arquivo nas duas listas. Acontece com frequência quando se trabalha rápido.

4. git status: o comando mais usado

Rode agora:

git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md
	index.html

nothing added to commit but untracked files present (use "git add" to track)

Vale ler linha por linha, porque essa saída vai te acompanhar todo dia:

LinhaO que diz
On branch mainVocê está na branch main — resultado do init.defaultBranch configurado na aula 1
No commits yetO repositório existe, mas o histórico está vazio
Untracked filesArquivos que o Git enxerga mas não versiona. Ele não assume nada: arquivo novo só entra no histórico se você pedir
A linha entre parêntesesO Git sugerindo o próximo comando. Ele faz isso o tempo todo — é a documentação mais útil que existe

"Rastreado" (tracked) é vocabulário que volta sempre: arquivo rastreado é aquele que o Git já conhece, porque entrou em algum commit ou está no staging. O resto é untracked.

Hábito: rodar git status antes e depois de qualquer coisa. É rápido, é local, não altera nada e responde "onde eu estou e o que está pendente". Quem usa Git bem roda esse comando dezenas de vezes por dia.

5. git add: preparando o commit

Coloque os dois arquivos no staging:

git add index.html README.md

Nenhuma saída — no Git, silêncio quase sempre significa sucesso. Confira o efeito:

git status
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   README.md
	new file:   index.html

Os arquivos saíram de "untracked" e viraram "Changes to be committed" — estão na caixa, esperando o commit.

5.1 As formas de usar o add

ComandoO que adiciona
git add arquivo.txtUm arquivo específico
git add pasta/Tudo dentro de uma pasta
git add *.htmlTodos os arquivos que casam com o padrão
git add .Tudo que mudou a partir da pasta atual
git add -ATudo que mudou no repositório inteiro, esteja você em que pasta estiver

Cuidado com git add . — é o comando mais usado e a origem mais comum de acidente: ele arrasta junto arquivos que você não pretendia versionar (arquivo temporário, credencial, pasta de dependências gigante). Não é proibido usar, mas o hábito seguro é rodar git status antes e conferir a lista. A seção 10 resolve boa parte disso de forma permanente com o .gitignore.

6. git commit: o primeiro ponto salvo

git commit -m "Cria estrutura inicial do guia de cafes"
[main (root-commit) 3f8a1c2] Cria estrutura inicial do guia de cafes
 2 files changed, 12 insertions(+)
 create mode 100644 README.md
 create mode 100644 index.html

Lendo a saída:

  • main — branch onde o commit entrou.
  • root-commit — marca que aparece só no primeiro commit do repositório: é o único sem commit pai (aula 1, seção 6.2).
  • 3f8a1c2 — os 7 primeiros caracteres do hash. O seu vai ser diferente do exemplo, sempre. O Git mostra a forma curta porque ela já basta pra identificar o commit.
  • O resumo de arquivos e linhas.

A flag -m passa a mensagem direto. Sem ela, o Git abre o editor configurado na aula 1 — útil pra mensagem longa, tratada na seção 9.

Confira o estado agora:

git status
On branch main
nothing to commit, working tree clean

working tree clean é o estado que você quer ver antes de trocar de branch, atualizar o projeto ou parar de trabalhar: significa que não há nada pendente — tudo que está na pasta já está gravado no histórico.

7. O ciclo completo, de novo

Um commit não ensina o ciclo. Faça mais dois, com uma mudança de verdade em cada.

Alterar index.html — dentro do <ul>, adicione duas linhas depois do Espresso:

  <ul>
    <li>Espresso</li>
    <li>Coado</li>
    <li>Prensa francesa</li>
  </ul>

Veja como o Git descreve isso:

git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   index.html

no changes added to commit (use "git add" and/or "git commit -a")

Repare na diferença: o arquivo aparece como modified, não new file, e a seção agora é "Changes not staged for commit" — mudou no working directory, mas ainda não foi pro staging. São as três seções possíveis do status:

Seção do statusSignificaOnde está
Untracked filesGit não versiona esse arquivoSó no working directory
Changes not staged for commitArquivo rastreado, alterado, fora da caixaWorking directory
Changes to be committedVai entrar no próximo commitStaging

Complete o ciclo:

git add index.html
git commit -m "Adiciona coado e prensa francesa na lista"

Agora o terceiro commit, num arquivo diferente:

Alterar README.md — acrescente uma linha no fim:

# Guia de Cafés

Lista de métodos e tipos de café.

Projeto usado para estudar Git.
git add README.md
git commit -m "Explica o proposito do projeto no README"

Atalho que você vai ver por aí: git commit -am "mensagem" faz add e commit num passo só. A pegadinha: ele só pega arquivos já rastreados — arquivo novo continua sendo ignorado, e a pessoa jura que commitou. Além disso, ele pula justamente a etapa de escolher o que entra, que é o motivo do staging existir. Conheça, mas não faça dele o padrão.

8. git log: lendo o histórico

git log
commit 9c4d7e15a2b8f3c6d9e0a1b2c3d4e5f6a7b8c9d0 (HEAD -> main)
Author: Seu Nome <seu@email.com>
Date:   Thu Aug 28 14:32:10 2025 -0300

    Explica o proposito do projeto no README

commit 5b3a9f2c8d1e4a7b0c3d6e9f2a5b8c1d4e7f0a3b
Author: Seu Nome <seu@email.com>
Date:   Thu Aug 28 14:28:44 2025 -0300

    Adiciona coado e prensa francesa na lista

commit 3f8a1c2b5d8e1f4a7c0d3e6f9a2b5c8d1e4f7a0b
Author: Seu Nome <seu@email.com>
Date:   Thu Aug 28 14:21:03 2025 -0300

    Cria estrutura inicial do guia de cafes

Está tudo aqui: o hash completo de 40 caracteres, o autor vindo do git config da aula 1, a data e a mensagem. Do mais recente para o mais antigo, de cima pra baixo.

Repare no (HEAD -> main) no primeiro. Traduzindo: a branch main está apontando pro commit mais novo, e HEAD — que significa "onde eu estou agora" — está em main. Esse par volta com força na aula 4.

Se o histórico for longo, o Git abre a saída num paginador: navegue com as setas e saia com q.

8.1 A forma que se usa no dia a dia

git log --oneline
9c4d7e1 (HEAD -> main) Explica o proposito do projeto no README
5b3a9f2 Adiciona coado e prensa francesa na lista
3f8a1c2 Cria estrutura inicial do guia de cafes

Um commit por linha, hash curto e mensagem. É assim que se lê histórico na prática — e é aqui que fica evidente por que mensagem ruim custa caro: essa lista é o que outra pessoa (ou você em três meses) vai usar pra achar alguma coisa.

Duas variações úteis agora, sem entrar nos filtros da aula 3:

git log --oneline -3          # só os 3 últimos
git log --oneline --graph     # desenha o grafo (fica interessante com branches, aula 4)

9. Mensagem de commit que presta

Da aula 1: a mensagem é a única parte do commit que o Git não consegue deduzir sozinho. Ela é o porquê, e é o que o mercado avalia quando lê seu histórico num code review.

Mensagens ruins

ajustes
correções
wip
teste
alterado index.html
asdf

Mensagens boas

Adiciona coado e prensa francesa na lista
Corrige acento no titulo da pagina
Remove metodo duplicado do guia
Explica o proposito do projeto no README

O que separa as duas colunas:

  • Diz o que a mudança faz, não o arquivo que foi tocado. "alterado index.html" o git log já sabe sozinho; o que ele não sabe é por quê.
  • Verbo no início, no imperativo ("Adiciona", "Corrige", "Remove"). É a convenção do próprio Git e da maioria dos projetos — a mensagem completa a frase "este commit ___".
  • Primeira linha curta, até uns 50 caracteres. É ela que aparece no --oneline e na interface do GitHub.
  • Sem ponto final na primeira linha. Convenção, não regra.

Quando a explicação não cabe numa linha, use corpo: rode git commit sem -m, escreva o título, deixe uma linha em branco e escreva o resto. A linha em branco é obrigatória — é ela que o Git usa pra separar título de corpo.

Remove prensa francesa da lista principal

O metodo exige moagem grossa e a pagina ainda nao explica
moagem. Volta quando a secao de moagem existir.

Existe convenção com nome pra isso. Muitos times exigem o padrão Conventional Commits (feat:, fix:, docs:...), que torna a mensagem legível por máquina. Fica pra aula 7, junto com o resto das convenções de time — por enquanto, escrever mensagem clara em português já resolve.

10. .gitignore: o que não versionar

Nem tudo que aparece na pasta do projeto deve entrar no histórico. Três categorias, sempre as mesmas:

CategoriaExemplosPor quê
Segredo.env, chave de API, certificado, senhaVira público quando o repositório vai pro GitHub, e continua no histórico depois de apagado (aula 9)
Gerado ou baixadonode_modules/, dist/, build/, *.logReproduzível a partir do código. Versionar incha o repositório e gera conflito sem sentido
Local, da sua máquina.DS_Store, .vscode/, anotações pessoaisNão diz respeito ao projeto nem ao resto do time

O jeito de excluir isso é um arquivo chamado .gitignore, versionado junto com o projeto — assim a regra vale pra todo mundo que clonar.

Criar .gitignore — arquivo novo, na raiz do projeto:

# Sistema operacional
.DS_Store
Thumbs.db

# Editor
.vscode/
.idea/

# Segredos
.env

# Logs
*.log

Sintaxe, que é curta:

PadrãoEfeito
# comentárioLinha ignorada pelo próprio arquivo
arquivo.txtIgnora esse arquivo, em qualquer pasta do projeto
*.logIgnora por extensão ou padrão
pasta/A barra no fim indica pasta: ignora ela e todo o conteúdo
/arquivo.txtA barra no início prende na raiz: ignora só o da raiz, não os de subpastas
!importante.logA exclamação abre exceção a uma regra anterior

Commite o .gitignore — ele faz parte do projeto:

git add .gitignore
git commit -m "Adiciona gitignore com arquivos locais e segredos"

Não escreva do zero em projeto real. Existe uma coleção oficial de .gitignore por linguagem em github.com/github/gitignore, e o GitHub oferece o arquivo pronto na hora de criar o repositório (aula 6). Para um projeto Node, por exemplo, o arquivo pronto já cobre node_modules/ e uma dúzia de casos que ninguém lembra sozinho.

11. Quando o .gitignore "não funciona"

Este é um dos tropeços mais comuns do Git, e é melhor viver ele agora, de propósito, num projeto de estudo — do que na primeira semana de trabalho.

11.1 Provocando o problema

Crie um arquivo de anotações pessoais e commite por descuido, com o git add . que a seção 5 avisou:

echo "senha do wifi da cafeteria: 12345678" > notas-pessoais.txt
git add .
git commit -m "Atualiza guia"

Pronto: um arquivo que não devia estar no histórico, está. Você percebe e faz o movimento intuitivo — acrescenta no .gitignore:

Alterar .gitignore — acrescente no fim:

# Logs
*.log

# Anotações locais
notas-pessoais.txt

Agora edite o arquivo pra ver se o Git ignora mesmo:

echo "outra anotacao" >> notas-pessoais.txt
git status
On branch main
Changes not staged for commit:
	modified:   notas-pessoais.txt

O Git continua acompanhando o arquivo, mesmo com ele listado no .gitignore.

11.2 Por que acontece

A regra

O .gitignore só decide sobre arquivos untracked. Ele quer dizer "não comece a rastrear isto", e não "pare de rastrear isto". Assim que um arquivo entra num commit, ele passa a ser rastreado, e o .gitignore deixa de ter qualquer efeito sobre ele.

Faz sentido quando se pensa no contrário: se o .gitignore pudesse remover arquivos já versionados, adicionar uma linha nele apagaria arquivos do projeto de todo mundo no próximo pull.

11.3 A solução

É preciso dizer ao Git, explicitamente, pra parar de rastrear:

git rm --cached notas-pessoais.txt
rm 'notas-pessoais.txt'

A flag --cached é a parte importante: ela remove o arquivo do rastreamento do Git, mas mantém ele na sua pasta. Sem a flag, git rm apagaria o arquivo do disco também.

Para uma pasta inteira, acrescente -r (recursivo): git rm -r --cached node_modules/.

git status
On branch main
Changes to be committed:
	deleted:    notas-pessoais.txt

Isso precisa de commit, como qualquer outra mudança:

git commit -m "Para de versionar anotacoes pessoais"

Confira que o arquivo continua no disco e agora é ignorado de verdade:

ls
git status
index.html  notas-pessoais.txt  README.md

On branch main
nothing to commit, working tree clean

O arquivo está lá, e o Git não vê mais.

Ponto de segurança, e ele é sério: o que você fez remove o arquivo dos commits futuros. O conteúdo continua no histórico, nos commits antigos — git log ainda alcança. Num projeto de estudo local, sem problema.

Se fosse uma credencial real num repositório já publicado, isso não seria suficiente: qualquer pessoa que clonou já tem a credencial em mãos, e apagá-la do histórico depois não muda esse fato. A resposta correta nesse caso é rotacionar a credencial — trocar a senha, revogar a chave, gerar outro token. A aula 9 trata desse cenário inteiro.

12. Erros comuns nesta fase

  1. "Commitei mas o arquivo novo não foi junto." Quase sempre é git commit -am: ele ignora arquivo untracked. Use git add antes.
  2. "Fiz add, editei de novo, e o commit foi com a versão velha." O add fotografa o arquivo no instante em que roda. Se editou depois, rode add de novo.
  3. git init na pasta errada. Rodar na home por engano cria um repositório que engole tudo. Confira com pwd antes; se aconteceu, apague o .git criado por engano — e só ele.
  4. Um commit gigante no fim do dia. Funciona, mas joga fora o principal benefício do histórico: reverter ou entender um pedaço isolado depois.
  5. Ignorar a saída de erro e ir direto pro Google. Da aula 1: a mensagem do Git costuma trazer o comando exato da solução.

13. Checklist antes de seguir

  • A pasta ~/projetos/guia-de-cafes existe e tem uma subpasta .git
  • git log --oneline mostra pelo menos 5 commits, com mensagens legíveis
  • git status mostra working tree clean
  • Existe um .gitignore versionado, e notas-pessoais.txt está no disco sem aparecer no status
  • Você sabe explicar por que o Git tem staging em vez de commitar direto
  • Você sabe dizer a diferença entre "Changes not staged for commit" e "Changes to be committed"
  • Você sabe por que o .gitignore não afeta arquivo já rastreado, e qual comando resolve

14. O que vem a seguir

Você já sabe criar histórico. Falta a outra metade: consultar e desfazer.

  1. Navegando o histórico e desfazendo — log com filtros, show, as três comparações do diff, e o conjunto de comandos do "quero voltar atrás": restore, restore --staged, commit --amend, reset nas três formas e revert. Com uma tabela de "quero desfazer X, use Y".
  2. Branches — trabalhar em paralelo, o que HEAD significa de verdade, merge.
  3. Conflitos de merge — provocar um de propósito e resolver.

Antes de seguir, vale fazer mais dois ou três commits no guia-de-cafes por conta própria — acrescente métodos na lista, mexa no README. O ciclo status / add / commit precisa estar automático, porque a partir da aula 3 ele deixa de ser o assunto e passa a ser só o meio.
