Branches: trabalhar em paralelo

Até aqui seu histórico foi uma linha reta. Esta aula quebra a linha. Branch é o recurso que o Git fez ser barato de propósito (lembra do requisito de 2005, na aula 1) e é a base de tudo que vem depois — Pull Request, code review, o fluxo de time inteiro. O truque pra entender branch sem decoreba é aceitar uma frase: branch não é uma cópia do projeto, é um ponteiro para um commit. Tudo o mais decorre daí.

1. O problema que branch resolve

Você está no meio de uma mudança grande no guia-de-cafes. Metade feita, nada funcionando direito. Aí chega o pedido: "corrige o erro de digitação no título, é urgente".

Sem branch, as opções são todas ruins: commitar o trabalho pela metade só pra tirar da frente, ou fazer a correção urgente misturada com o trabalho inacabado, ou copiar a pasta inteira pra outro lugar — o projeto-v2-final-AGORA-VAI da aula 1.

Com branch, cada linha de trabalho fica isolada. A correção urgente sai de uma base limpa, e sua mudança pela metade continua exatamente onde estava, esperando.

Em time, o motivo é ainda mais direto: várias pessoas mexendo no mesmo projeto ao mesmo tempo, sem que o trabalho inacabado de uma apareça no de outra. É o assunto da aula 7.

2. Branch é um ponteiro

Vem de outras ferramentas a ideia de que branch é uma cópia do projeto. No Git, não é — e a diferença explica por que criar branch aqui é instantâneo enquanto no SVN era uma operação cara (aula 1, seção 2.2).

A definição

Uma branch é um arquivo de texto com o hash de um commit dentro. Nada além disso. Criar uma branch é escrever 41 bytes em disco — por isso é instantâneo, independente do tamanho do projeto.

Dá pra ver com os próprios olhos:

cat .git/refs/heads/main
f2e8d40c1a9b3e5d7f0a2c4e6b8d0f2a4c6e8b0d

É esse o conteúdo inteiro da sua branch main: o hash do commit mais recente dela.

Lembrando da aula 1: cada commit aponta pro anterior. Então o ponteiro da branch, apontando pro commit mais recente, alcança toda a história a partir dali:

49413d5 ──> 64a8889 ──> 4e993b8 ──> f2e8d40
                                        ↑
                                      main

E quando você faz um commit novo, o ponteiro anda pra frente sozinho:

49413d5 ──> 64a8889 ──> 4e993b8 ──> f2e8d40 ──> a1c9e33
                                                    ↑
                                                  main

É só isso que uma branch faz. Ter duas branches é ter dois ponteiros para pontos diferentes do mesmo grafo de commits.

3. HEAD: onde você está

HEAD apareceu na aula 2 traduzido como "onde eu estou agora". Agora dá pra ser preciso: HEAD é um ponteiro para a branch em que você está — um ponteiro para um ponteiro.

cat .git/HEAD
ref: refs/heads/main

Ele não guarda um hash: guarda o nome da branch atual. É isso que o (HEAD -> main) do git log vem dizendo desde a aula 2.

Com isso, dá pra descrever o que um commit faz em uma frase exata: o commit é criado apontando pro commit atual, e a branch para a qual o HEAD aponta anda pra frente. Trocar de branch é mudar para onde o HEAD aponta — e o Git trocar os arquivos da sua pasta pra corresponder.

4. Criando e trocando de branch

Confira o ponto de partida:

cd ~/projetos/guia-de-cafes
git status
git branch
* main

git branch sem argumento lista as branches. O asterisco marca em qual você está. Por enquanto só existe uma.

4.1 O comando do dia a dia

git switch -c metodos-frios
Switched to a new branch 'metodos-frios'

Duas coisas num comando: -c (de create) cria a branch, e o switch move o HEAD pra ela. Confira:

git branch
  main
* metodos-frios

E o estado do grafo agora:

49413d5 ──> 64a8889 ──> 4e993b8 ──> f2e8d40
                                        ↑
                                  main, metodos-frios
                                        ↑
                                      HEAD

As duas branches apontam pro mesmo commit. Nenhum arquivo mudou, nada foi copiado — só existe um ponteiro novo. É por isso que criar branch não tem custo.

4.2 As variações

ComandoFaz
git branchLista as branches locais
git branch nomeCria a branch, mas não troca pra ela
git switch nomeTroca para uma branch existente
git switch -c nomeCria e troca. O mais usado
git switch -Volta pra branch anterior. Atalho ótimo pra vai-e-volta
git switch -c nome abc1234Cria a branch a partir de um commit específico, não do atual
git branch -vLista mostrando o último commit de cada uma

Sobre checkout: como visto na aula 3, seção 13, o mesmo se faz com git checkout -b nome. Funciona e você vai ver muito por aí. Prefira switch — foi criado justamente pra separar "trocar de branch" de "restaurar arquivo".

Sobre o nome da branch: por enquanto use algo descritivo e sem espaço. Times têm convenção própria (feature/, fix/, número do ticket) — isso é assunto da aula 7.

5. Trabalhando na branch

Estando em metodos-frios, o ciclo é o mesmo de sempre:

Alterar index.html — dentro do <ul>, acrescente duas linhas no fim da lista:

    <li>Aeropress</li>
    <li>Cold brew</li>
    <li>Café gelado batido</li>
  </ul>
git add index.html
git commit -m "Adiciona metodos frios na lista"

Agora o grafo se separou de verdade:

4e993b8 ──> f2e8d40 ──> b7d2a10
                ↑            ↑
              main    metodos-frios
                             ↑
                           HEAD

main ficou parada onde estava. Ela só anda quando você commita estando nela.

Veja isso desenhado pelo próprio Git — é aqui que aquelas quatro flags da aula 3 finalmente valem a pena:

git log --oneline --graph --decorate --all
* b7d2a10 (HEAD -> metodos-frios) Adiciona metodos frios na lista
* f2e8d40 (main) Revert "Adiciona comentarios de rascunho no index"
* a7b3c91 Adiciona comentarios de rascunho no index

6. O que acontece ao trocar de branch

Volte pra main e abra o index.html:

git switch main
Switched to branch 'main'

Cold brew e café gelado sumiram do arquivo. Não foram perdidos: estão no commit b7d2a10, que continua existindo, alcançável pelo ponteiro metodos-frios. O que o Git fez foi reescrever os arquivos da sua pasta pra corresponder ao commit que a main aponta.

Volte e confira que reaparecem:

git switch metodos-frios

Essa é a parte que impressiona no começo: uma pasta só, que muda de conteúdo conforme a branch. Não existem duas cópias em disco.

6.1 Trocar com trabalho pendente

Se você tentar trocar de branch com alterações não commitadas que conflitam com o destino, o Git recusa:

error: Your local changes to the following files would be overwritten by checkout:
	index.html
Please commit your changes or stash them before you switch branches.

É proteção, não erro: trocar sobrescreveria seu trabalho. As saídas são as da mensagem — commitar, ou guardar temporariamente com git stash (aula 9).

Detalhe que confunde: quando a alteração pendente não conflita com o destino, o Git deixa trocar e leva a alteração junto pra outra branch. Não é bug — é conveniência. Mas é fonte de "commitei na branch errada", o erro mais comum desta aula. Hábito que resolve: git status antes de trocar, e trocar só com working tree clean.

7. Detached HEAD: o aviso que assusta

Na aula 3 apareceu git checkout abc1234 pra navegar até um commit antigo. Se você fizer isso, o Git imprime um texto longo começando com:

You are in 'detached HEAD' state.

Traduzindo com o que você já sabe: normalmente o HEAD aponta pra uma branch. Aqui ele está apontando direto pra um commit, sem branch no meio. Está "solto".

Isso não quebrou nada. Você pode olhar arquivos, rodar o projeto, investigar como as coisas eram. O risco é só um: commits feitos nesse estado não pertencem a branch nenhuma. Ao trocar de branch depois, eles ficam sem ponteiro — e somem da vista (recuperáveis pelo reflog da aula 9, mas o susto é grande).

Como sair:

git switch main                    # só olhei, quero voltar
git switch -c nome-da-branch       # commitei aqui e quero manter o trabalho

O segundo comando cria uma branch apontando pro commit onde você está — os commits soltos ganham dono e param de correr risco.

8. Merge fast-forward

Trabalho pronto na branch, hora de trazer pra main. O merge sempre segue a mesma lógica: vá para a branch que vai receber, e mande vir.

git switch main
git merge metodos-frios
Updating f2e8d40..b7d2a10
Fast-forward
 index.html | 2 ++
 1 file changed, 2 insertions(+)

Repare no Fast-forward. Ele acontece numa situação específica: a main não andou nada desde que a branch nasceu. Não há o que combinar — os commits da branch já continuam a história da main em linha reta.

Então o Git faz a coisa mais simples possível: arrasta o ponteiro da main pra frente. Nenhum commit novo é criado.

Antes:
4e993b8 ──> f2e8d40 ──> b7d2a10
                ↑            ↑
              main    metodos-frios

Depois:
4e993b8 ──> f2e8d40 ──> b7d2a10
                             ↑
                    main, metodos-frios

Histórico continua linear. Olhando o log depois, não há sinal de que uma branch existiu.

9. Merge commit

O outro caso é o que acontece de verdade em time: a main andou enquanto você trabalhava na sua branch. As duas histórias divergiram, e aí é preciso combinar.

9.1 Provocando a divergência

Crie uma branch nova e faça um commit nela:

git switch -c rodape

Alterar index.html — antes do </body>, acrescente o rodapé:

  </ul>
  <footer>Guia mantido para estudo de Git.</footer>
</body>
git commit -am "Adiciona rodape na pagina"

Agora vá pra main e faça um commit lá também, em outro arquivo:

git switch main

Alterar README.md — acrescente uma linha no fim:

Projeto usado para estudar Git.

Cada metodo tera sua propria pagina no futuro.
git commit -am "Anota plano de paginas por metodo no README"

O grafo bifurcou:

                    ┌──> c3f8e21 (rodape)
b7d2a10 ──> ────────┤
                    └──> d9a4b60 (main) ←── HEAD

Por que arquivos diferentes: as duas mudanças foram feitas de propósito em arquivos separados, então o Git resolve a combinação sozinho. Quando as duas branches mexem na mesma linha do mesmo arquivo, ele não consegue decidir e para pedindo ajuda — isso é conflito, e é a aula 5 inteira.

9.2 O merge

git merge rodape

Desta vez o Git abre o editor com uma mensagem pronta (Merge branch 'rodape'). Salve e feche.

Merge made by the 'recursive' strategy.
 index.html | 1 +
 1 file changed, 1 insertion(+)

Não é mais fast-forward. Como as duas histórias divergiram, o Git precisou criar um commit novo pra unir as duas pontas:

                    ┌──> c3f8e21 ──┐
b7d2a10 ──> ────────┤               ├──> e5b1f77 (main)
                    └──> d9a4b60 ──┘

Esse é o merge commit, e ele tem uma característica única: dois pais, um de cada branch. Todos os outros commits têm um só.

É aqui que fecha o detalhe pendente da aula 3, seção 5: HEAD~1 e HEAD^ são iguais em commit normal, mas num merge commit existem dois pais — HEAD^1 é o primeiro (a branch que recebeu), HEAD^2 é o segundo (a que veio).

Confira o desenho:

git log --oneline --graph
*   e5b1f77 (HEAD -> main) Merge branch 'rodape'
|\
| * c3f8e21 (rodape) Adiciona rodape na pagina
* | d9a4b60 Anota plano de paginas por metodo no README
|/
* b7d2a10 Adiciona metodos frios na lista

9.3 Os dois tipos, lado a lado

 Fast-forwardMerge commit
Quando aconteceA branch de destino não andouAs duas andaram
Cria commit?Não, só move o ponteiroSim, com dois pais
Histórico ficaLinearCom bifurcação visível
Registra que houve branch?NãoSim
Pode dar conflito?NuncaSim (aula 5)

Você não escolhe entre os dois: o Git decide pela situação. O que dá pra fazer é forçar o segundo — próxima seção.

10. Forçando merge commit com --no-ff

git merge --no-ff metodos-frios

A flag --no-ff ("no fast-forward") manda criar merge commit mesmo quando o atalho seria possível.

Motivo de existir: preservar no histórico o registro de que aquele conjunto de commits foi uma unidade de trabalho. Com fast-forward, os commits da branch se misturam à linha principal e some a informação de que pertenciam à mesma tarefa. Com merge commit, dá pra ver o agrupamento — e reverter a tarefa inteira de uma vez.

O custo é um histórico mais poluído: um merge commit por tarefa, muitos deles sem conteúdo próprio.

Não existe consenso de mercado — é decisão de time, e cada lado tem argumento honesto:

Prefere --no-ff

"Quero ver no histórico onde cada tarefa começou e terminou, e poder reverter uma tarefa inteira num comando."

Prefere fast-forward

"Merge commit sem conteúdo é ruído. Quero o log legível como uma lista de mudanças reais."

Na prática do dia a dia, quem decide isso é a configuração do GitHub no repositório do time — as três opções de merge de um Pull Request, assunto da aula 7.

11. Deletando branch

Depois do merge, a branch cumpriu o papel. Os commits dela já estão na main; o ponteiro sobrando só polui a lista.

git branch -d rodape
Deleted branch rodape (was c3f8e21).
O que deletar uma branch faz

Apaga o ponteiro, não os commits. Se a branch foi mergeada, seus commits continuam alcançáveis pela main — nada se perde. É só remover a etiqueta de um trabalho concluído.

11.1 -d e -D

O -d minúsculo é seguro: ele recusa apagar uma branch cujos commits ainda não estão em lugar nenhum.

git branch -d experimento
error: The branch 'experimento' is not fully merged.
If you are sure you want to delete it, run 'git branch -D experimento'.

Isso é o Git avisando: "esses commits só existem aqui, apagar o ponteiro deixa eles órfãos".

O -D maiúsculo apaga assim mesmo, sem perguntar. Use só quando a intenção for realmente jogar o trabalho fora — uma tentativa que não deu certo, por exemplo. Os commits ficam recuperáveis pelo git reflog por algumas semanas (aula 9), mas nenhum ponteiro aponta mais pra eles.

Comandos úteis pra fazer essa faxina:

git branch --merged      # branches já incorporadas: seguras de apagar
git branch --no-merged   # branches com trabalho ainda não mergeado

Deletar branch mergeada é hábito de higiene. Repositório de time com 60 branches velhas na lista é atrito puro na hora de procurar a certa.

12. O ciclo completo, resumido

É este o ciclo que se repete o dia inteiro em qualquer time. Vale memorizar a forma, não os detalhes:

1

Parta de uma base limpa

git switch main e confirme working tree clean.

2

Crie a branch da tarefa

git switch -c nome-da-tarefa. Uma branch por tarefa, sempre.

3

Trabalhe e commite ali

O ciclo da aula 2, sem mudança nenhuma. Vários commits pequenos.

4

Traga pra main

git switch main e git merge nome-da-tarefa.

5

Limpe

git branch -d nome-da-tarefa.

A partir da aula 6 esse ciclo ganha o remoto no meio, e na aula 7 o passo 4 deixa de ser um merge na sua máquina e passa a ser um Pull Request revisado por outra pessoa. A forma continua a mesma.

13. Erros comuns nesta fase

  1. Commitar na branch errada. O mais comum de todos, quase sempre commitando na main sem perceber. Prevenção: git status antes de commitar — a primeira linha diz a branch. Correção: git reset --soft HEAD~1 (aula 3), trocar de branch e commitar de novo.
  2. Mergear na direção errada. git merge traz a outra branch pra dentro da atual. Estar na branch de feature e rodar git merge main não publica sua feature — traz a main pra sua branch. Regra: vá para quem recebe.
  3. Criar branch a partir de uma branch desatualizada. Se você não voltou pra main antes de switch -c, a branch nova nasce em cima da anterior, herdando commits que não têm relação com a tarefa.
  4. Deixar branch viver semanas. Quanto mais tempo separada da main, mais as duas divergem e maior o conflito no fim. Branch curta é a principal medida preventiva contra conflito (aula 5).
  5. Pânico com detached HEAD. Não quebrou nada. git switch main resolve; se houver commit a salvar, git switch -c nome antes.
  6. Achar que deletar branch apaga commits. Se foi mergeada, não apaga nada — só o ponteiro.

14. Checklist antes de seguir

  • Você consegue explicar, em uma frase, o que uma branch é fisicamente
  • Sabe dizer a diferença entre HEAD e o nome de uma branch
  • Criou branch, commitou nela, voltou pra main e viu os arquivos mudarem
  • Fez um merge fast-forward e sabe por que ele foi fast-forward
  • Fez um merge que gerou merge commit e sabe por que esse precisou de commit
  • Consegue ler a saída de git log --oneline --graph --all
  • Sabe a diferença entre git branch -d e -D
  • Sabe em qual branch precisa estar antes de rodar git merge

15. O que vem a seguir

Todos os merges desta aula deram certo sozinhos, de propósito — as mudanças estavam em arquivos ou linhas diferentes. A próxima aula quebra isso.

  1. Conflitos de merge — provocar um conflito de verdade no guia-de-cafes, ler os marcadores <<<<<<< no arquivo, resolver na mão, e git merge --abort pra desistir no meio. Mais o que reduz a frequência de conflito num time.
  2. Repositório remoto: GitHub — o projeto sai da sua máquina.
  3. Fluxo de time — branch e merge viram Pull Request e code review.

Se alguma coisa aqui ficou nebulosa, quase sempre é o modelo do ponteiro. Vale repetir o exercício olhando o grafo a cada passo: git log --oneline --graph --decorate --all depois de criar branch, depois de commitar, depois de trocar, depois de mergear. Ver o desenho mudar a cada comando resolve em minutos o que a explicação em texto leva páginas.
