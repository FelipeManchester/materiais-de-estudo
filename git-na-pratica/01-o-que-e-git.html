Material de estudo — Git na prática — Parte 1

O que é Git e por que ele existe

Nesta primeira aula não se digita nenhum comando de versionamento. O objetivo é você entender qual problema o Git resolve, por que ele foi feito do jeito que foi e como ele pensa internamente — porque quase toda confusão com Git mais adiante vem de um modelo mental errado, não de comando esquecido. No fim, você deixa a ferramenta instalada e configurada.

1. O problema, antes da ferramenta

Antes de qualquer definição, vale reconhecer o problema. Você provavelmente já resolveu ele na mão:

projeto/
projeto-v2/
projeto-v2-final/
projeto-v2-final-AGORA-VAI/
projeto-backup-antes-de-mexer/

Isso é controle de versão manual. Funciona mal, e falha em pontos específicos:

  • Não dá pra saber o que mudou entre duas versões. Só abrindo as duas pastas e comparando arquivo por arquivo.
  • Não dá pra saber por que mudou. A pasta guarda o resultado, não a intenção. Três meses depois, ninguém lembra por que aquela linha virou aquilo.
  • Não dá pra voltar só um pedaço. Ou você volta a pasta inteira, ou copia trechos na mão e reza.
  • Não escala pra mais de uma pessoa. Dois desenvolvedores mexendo na mesma pasta compartilhada sobrescrevem o trabalho um do outro em silêncio — o pior tipo de erro, porque não gera mensagem nenhuma.

Um sistema de controle de versão (VCS, Version Control System) existe pra resolver exatamente esses quatro pontos: registrar o que mudou, por que mudou, quem mudou e quando, permitindo voltar a qualquer ponto anterior e combinar o trabalho de várias pessoas de forma controlada.

Reformulando: o Git não é uma ferramenta de "salvar backup". Ele é uma ferramenta de registrar história. Backup guarda o estado atual; história guarda a sequência de decisões que levou até ele. É essa diferença que faz o Git valer o esforço de aprender.

2. Controle de versão: as três gerações

O Git não apareceu do nada. Ele é a terceira geração de uma ideia, e entender as duas anteriores explica várias escolhas dele.

2.1 Local (anos 80)

Ferramentas como o RCS guardavam as versões de um arquivo numa base local, na mesma máquina. Resolvia o "voltar a versão anterior" de um arquivo só, para uma pessoa só. Não resolvia colaboração.

2.2 Centralizado (anos 90 e 2000)

CVS e depois SVN (Subversion) trouxeram um servidor central que guarda todo o histórico do projeto. Cada desenvolvedor tem na máquina apenas uma cópia de trabalho — os arquivos na versão atual, sem o histórico. Para ver o log, comparar versões ou salvar uma alteração, é preciso falar com o servidor.

Isso resolveu colaboração, e por muitos anos foi o padrão da indústria. Mas trouxe limitações duras:

  • Servidor fora do ar = ninguém trabalha. Sem rede, não dá para salvar uma versão nem consultar o histórico.
  • Servidor perdido = história perdida. O histórico existe num lugar só. Se o backup falhar, acabou.
  • Criar branch é caro. No SVN, uma branch é uma operação no servidor, lenta em projeto grande. Consequência cultural: as pessoas evitavam criar branch. Todo mundo trabalhava no mesmo lugar, e as integrações eram raras, grandes e dolorosas.

2.3 Distribuído (2005 em diante)

Git, Mercurial e outros inverteram a premissa: cada pessoa tem uma cópia completa do repositório, com todo o histórico, na própria máquina. O servidor deixa de ser a fonte única de verdade e vira apenas um ponto de encontro combinado entre as pessoas.

 Centralizado (SVN)Distribuído (Git)
Onde fica o históricoSó no servidorEm cada clone, completo

3. De onde veio o Git

O Git foi escrito em 2005 por Linus Torvalds — o mesmo criador do Linux — e a história explica o desenho da ferramenta.

O kernel do Linux é desenvolvido por milhares de pessoas espalhadas pelo mundo, sem empresa única no comando, com um volume enorme de mudanças propostas por e-mail. Até 2005, o projeto usava um sistema distribuído proprietário chamado BitKeeper, cedido gratuitamente ao projeto. Nesse ano, a licença gratuita foi retirada após um desentendimento entre a empresa dona e parte da comunidade, e o kernel ficou de uma hora para outra sem ferramenta de versionamento.

Nenhuma alternativa da época atendia. Torvalds escreveu a própria, com um conjunto de requisitos declarados que valem ser lidos, porque cada um deles ainda está visível no Git de hoje:

Requisito de 2005Como isso aparece hoje
Ser rápido, mesmo com projeto gigantegit log e git status respondem na hora, porque tudo é local
Suportar desenvolvimento distribuído em larga escalaTodo clone é um repositório completo e autônomo
Ter branch e merge baratosÉ cultura no Git criar uma branch para cada tarefa — algo impensável no SVN
Garantir integridade: história não pode ser corrompida em silêncioTodo conteúdo é identificado por um hash criptográfico do próprio conteúdo

A primeira versão utilizável nasceu em poucos dias, e o kernel do Linux passou a usá-la ainda em 2005. Sobre o nome: Torvalds descreveu de forma bem-humorada como "gíria britânica para pessoa desagradável", dizendo que costuma nomear projetos em homenagem a si mesmo.

Por que essa história importa pra você: o Git não foi desenhado para uma pessoa versionar um projeto pessoal. Foi desenhado para milhares de pessoas que não confiam totalmente umas nas outras colaborarem sem um servidor central mandando. É por isso que ele parece ter mais poder do que você precisa — e por isso o mercado inteiro conseguiu adotar ele para times de 3 ou de 3000 pessoas.

4. O que "distribuído" muda no seu dia

Fora da teoria, ser distribuído tem quatro consequências práticas que você vai sentir já nas próximas aulas:

1

Quase tudo funciona sem internet

Registrar uma versão, ver o histórico, comparar, criar branch, voltar no tempo: tudo local. Só trocar trabalho com outras pessoas (as aulas 06 em diante) precisa de rede.

2

Salvar uma versão é barato, então salve com frequência

Não existe motivo para acumular um dia de trabalho antes de registrar. Versões pequenas e frequentes são mais fáceis de entender, de reverter e de resolver conflito depois. Este é provavelmente o hábito que mais separa quem usa Git bem de quem sofre com ele.

3

Você tem uma cópia inteira do histórico da empresa na sua máquina

Ao clonar o repositório de um time, você baixa toda a história do projeto, não só os arquivos atuais. Isso é ótimo para investigar ("quem mudou essa linha e por quê"), e é também o motivo de um segredo commitado ser um problema sério: quem clonou já tem. Voltamos a isso na aula 09.

4

O "servidor" é só uma convenção

Do ponto de vista do Git, o repositório no GitHub não tem poder nenhum de especial — é mais um clone. Ele é a fonte de verdade porque o time combinou que é, não porque a ferramenta impõe.

5. Git não é GitHub

Essa confusão é a mais comum de todas em quem está começando, e atrapalha porque mistura duas coisas com responsabilidades diferentes.

Git

  • Programa que roda na sua máquina
  • Gratuito e de código aberto
  • Funciona sem internet e sem conta em lugar nenhum
  • Faz o versionamento: commits, branches, merges, histórico
  • Criado em 2005 por Linus Torvalds

GitHub

  • Site/empresa que hospeda repositórios Git
  • Serviço comercial (hoje da Microsoft), com plano gratuito
  • Precisa de internet e de conta
  • Acrescenta o que o Git não tem: Pull Request, code review, issues, permissões, CI
  • Lançado em 2008 — três anos depois do Git

Uma analogia que ajuda: Git está para GitHub assim como um editor de texto está para o Google Drive. O editor cria e edita o arquivo; o Drive hospeda, compartilha e deixa outras pessoas comentarem. Dá para usar o editor sem o Drive; o Drive sozinho não escreve nada.

Concorrentes diretos do GitHub são o GitLab e o Bitbucket. Todos hospedam o mesmo Git — o que muda é a interface e os recursos ao redor. Trocar de plataforma não exige reaprender Git, só reaprender o site.

Perceba o que essa separação implica: Pull Request não é um conceito do Git. Não existe comando git pull-request. PR é um recurso inventado pelo GitHub em cima do Git, e por isso muda de nome entre plataformas (no GitLab chama-se Merge Request). Isso volta em detalhe na aula 07.

6. O modelo mental: commits são fotografias

Esta seção é a mais importante da aula. Quase todo problema difícil com Git — nas aulas 03, 08 e 09, principalmente — fica simples quando este modelo está certo na cabeça, e fica impossível quando está errado.

6.1 Snapshot, não lista de alterações

A maioria dos sistemas anteriores guardava o histórico como uma lista de diferenças: o arquivo original mais um conjunto de alterações aplicadas em cima, uma após a outra.

O Git faz diferente. Cada versão salva é um snapshot do projeto inteiro naquele instante — como uma fotografia de todos os arquivos, não um bilhete dizendo "mudei a linha 12". Arquivo que não mudou não é duplicado: o Git guarda apenas uma referência ao conteúdo que já existia. Mas, conceitualmente, cada ponto do histórico é um estado completo do projeto.

Consequência prática: voltar a um ponto do histórico não é "desfazer alterações em ordem inversa". É apontar para uma fotografia que já está guardada inteira. Por isso operações que parecem drásticas no Git são rápidas — e por isso quase nada se perde de verdade (aula 09).

6.2 O que é um commit

Esse snapshot salvo tem um nome: commit. Você vai criar o primeiro na próxima aula; aqui interessa saber o que ele carrega:

Parte do commitPara que serve
O snapshot do projetoO estado completo dos arquivos naquele momento
Autor e dataQuem fez e quando — vem do git config que você faz na seção 8
MensagemO porquê da mudança. A única parte que o Git não consegue deduzir sozinho, e por isso a que mais depende de você
Referência ao commit anterior (o "pai")É o que transforma commits soltos numa história encadeada
Um identificador (hash)Código de 40 caracteres calculado a partir de todo o resto, ex.: a1b2c3d...

Como cada commit aponta para o anterior, o histórico do Git é uma corrente — e, quando há branches, um grafo. Nas aulas você vai ver isso desenhado assim, com o commit mais recente à direita:

a1b2c3d ──> e4f5g6h ──> 9i8j7k6   (cada um aponta para o anterior)
"cria a      "adiciona      "corrige o
 página"      o rodapé"      título"

6.3 Por que o identificador é um hash

Aquele código de 40 caracteres não é um número sequencial: é o resultado de uma função criptográfica (SHA-1) aplicada sobre o conteúdo do commit — arquivos, autor, data, mensagem e o hash do commit pai.

Isso tem um efeito importante: mudar qualquer coisa em um commit muda o hash dele, o que muda o hash de todos os commits seguintes, porque cada um inclui o hash do pai. Não existe alterar o passado em silêncio. Era exatamente o requisito de integridade da tabela da seção 3 — num projeto com milhares de contribuidores desconhecidos, é preciso poder confiar que a história recebida não foi adulterada no caminho.

Guarde isso, porque explica um comportamento que assusta muita gente na aula 08: quando você reescreve o histórico (com rebase), os commits não são "editados" — são recriados com hashes novos. E é por isso que reescrever histórico que outras pessoas já baixaram causa problema.

6.4 Vocabulário mínimo

Termos que aparecem daqui em diante. Não é preciso decorar agora; cada um ganha sua aula.

  • Repositório (ou "repo"): a pasta do projeto mais todo o histórico dela. Fica guardado numa subpasta oculta .git.
  • Commit: um ponto salvo do histórico, como descrito acima.
  • Branch: uma linha de trabalho paralela. Na prática, um ponteiro que anda para frente conforme você faz commits (aula 04).
  • Merge: juntar o trabalho de duas branches (aula 04).
  • Conflito: quando o Git não consegue juntar sozinho porque duas pessoas mudaram a mesma linha (aula 05).
  • Remote: um repositório em outro lugar, geralmente no GitHub, com o qual o seu troca commits (aula 06).
  • Clone: baixar um repositório inteiro, com histórico, para a sua máquina (aula 06).
  • Push / Pull: enviar seus commits para o remote / trazer os commits dele (aula 06).

7. Instalando o Git

Antes de instalar, verifique se já existe — em muitas máquinas de desenvolvimento já vem:

git --version

Se responder algo como git version 2.43.0, está instalado. Qualquer versão 2.30 ou superior serve para toda esta trilha. Se der "comando não encontrado", instale conforme o seu sistema.

7.1 Linux (Ubuntu/Debian)

sudo apt update
sudo apt install git

Em Fedora, sudo dnf install git. Em Arch, sudo pacman -S git.

7.2 macOS

Com o Homebrew:

brew install git

Sem o Homebrew, rodar git --version no Terminal faz o macOS oferecer a instalação das ferramentas de linha de comando do Xcode, que incluem o Git. Funciona, mas costuma trazer uma versão mais antiga.

7.3 Windows

Baixe o instalador em git-scm.com/download/win e siga o assistente. Os padrões sugeridos servem. Duas observações:

  • Ele instala junto o Git Bash, um terminal com comandos no estilo Linux. Use ele para acompanhar a trilha — os comandos ficam idênticos aos do material.
  • Se estiver usando WSL (Linux dentro do Windows), instale pelo apt dentro do WSL, e trate como Linux.

Depois de instalar, feche e abra o terminal, e confirme com git --version.

8. Configuração inicial

O Git recém-instalado ainda não sabe quem é você. Como cada commit registra autor, essa configuração é obrigatória antes do primeiro commit — que acontece na próxima aula.

8.1 Os três níveis de configuração

O Git lê configuração de três lugares, do mais amplo para o mais específico. O mais específico vence:

NívelFlagVale para
Sistema--systemTodos os usuários da máquina. Raramente usado.
Global--globalTodos os seus repositórios. É o que você vai usar.
Local(nenhuma flag)Só o repositório atual. Útil para usar outro e-mail num projeto específico.

8.2 Identidade

Rode os dois comandos, trocando pelos seus dados:

git config --global user.name "Seu Nome"
git config --global user.email "seu@email.com"

Esse par vai ficar gravado em todo commit que você fizer, para sempre. Use o nome pelo qual quer ser identificado profissionalmente — não é apelido de usuário, é o nome que aparece no histórico e no code review.

Sobre o e-mail, um ponto de privacidade: o endereço fica gravado dentro do commit e, quando você publicar o repositório (aula 06), fica visível publicamente para qualquer pessoa. Não dá para remover depois sem reescrever todo o histórico.

Se preferir não expor seu e-mail pessoal, o GitHub oferece um endereço de encaminhamento no formato id+usuario@users.noreply.github.com, disponível em Settings → Emails depois que você criar a conta. É o e-mail que se usa aqui, e o GitHub continua associando os commits a você normalmente. Como a conta só é criada na aula 06, deixe o e-mail pessoal por enquanto ou volte neste ponto depois — os commits das primeiras aulas ficam na sua máquina.

8.3 Nome da branch inicial

git config --global init.defaultBranch main

Todo repositório começa com uma branch. Historicamente ela se chamava master; desde 2020, a indústria migrou para main, e é o padrão do GitHub e da maioria das empresas hoje. Sem essa configuração, o Git ainda cria master e imprime um aviso a cada repositório novo.

Vale saber que as duas são apenas nomes de branch, sem nada de especial na ferramenta. Você vai encontrar projetos antigos usando master, e isso não muda comando nenhum.

8.4 Editor de texto

Em algumas operações o Git abre um editor para você escrever ou revisar texto — mensagem de commit longa, resolução de merge, rebase interativo. O padrão em Linux e macOS costuma ser o Vim, que trava quem não conhece (para sair: Esc, depois :q!, depois Enter).

Se você usa VS Code, vale trocar:

git config --global core.editor "code --wait"

A flag --wait é essencial: sem ela, o VS Code devolve o controle ao Git na hora, e o Git entende que você fechou o editor sem escrever nada. Alternativas mais simples: "nano" em Linux/macOS, ou "notepad" no Windows.

8.5 Conferindo o resultado

git config --global --list

Deve sair algo assim:

user.name=Seu Nome
user.email=seu@email.com
init.defaultbranch=main
core.editor=code --wait

Tudo isso está gravado em texto puro num arquivo chamado ~/.gitconfig (no Windows, C:\Users\SeuUsuario\.gitconfig). Dá para abrir e editar na mão — os comandos acima são só uma forma conveniente de escrever nesse arquivo. Para consultar um valor específico:

git config --global user.email

9. Como pedir ajuda ao próprio Git

Ninguém decora Git. O que separa quem se vira de quem trava é saber consultar rápido — e o Git traz a documentação completa junto com a instalação, sem internet:

git help commit        # manual completo, abre como página de manual
git commit -h          # resumo curto das opções, direto no terminal

O primeiro abre um documento longo; navegue com as setas e saia com q. O segundo cabe na tela e resolve a maioria das dúvidas do tipo "qual era a flag mesmo?".

Hábito que vale desde já: quando um comando de Git der erro, leia a mensagem inteira antes de procurar no Google. As mensagens de erro do Git são incomumente boas: na maior parte dos casos elas dizem o que aconteceu e sugerem o comando exato para resolver. Copiar a sugestão sem ler é a origem da maioria dos acidentes com Git.

10. O projeto que vamos usar na trilha

A partir da próxima aula, tudo é feito em cima de um projeto único, construído do zero: um site estático simples chamado guia-de-cafes, com um index.html e um README.md.

O conteúdo dele é deliberadamente banal. Aqui se estuda Git, não HTML — e um projeto simples deixa provocar um conflito de merge de propósito (aula 05) numa linha de texto, sem ter que depurar código junto.

Onde criar: o projeto vai numa pasta fora deste repositório de estudo, por exemplo ~/projetos/guia-de-cafes.

O motivo é concreto: este material de estudo já é um repositório Git. Criar outro repositório dentro dele faz o Git de fora enxergar a pasta interna de um jeito estranho, e comandos como git status e git log passam a mostrar informação que não corresponde ao que a aula descreve — bem no momento em que você ainda não tem repertório para desconfiar da saída.

11. Checklist antes de seguir

Confira cada item no terminal. Se algum falhar, resolva antes da aula 02 — a próxima aula começa criando o repositório e assume tudo isto pronto.

  • git --version responde com versão 2.30 ou superior
  • git config --global user.name devolve o seu nome
  • git config --global user.email devolve o seu e-mail
  • git config --global init.defaultBranch devolve main
  • git commit -h mostra a lista de opções (confirma que a ajuda embutida funciona)
  • Você sabe explicar, com suas palavras, a diferença entre Git e GitHub
  • Você consegue dizer o que um commit guarda além dos arquivos

12. O que vem a seguir

Esta aula cobriu contexto, modelo mental e preparação do ambiente. A próxima entra no comando de verdade.

  1. Primeiro repositório: o ciclo básico — criar o guia-de-cafes, git init, os três estados de um arquivo (working directory, staging e repositório) e por que o staging existe, status, add, commit, log, e o .gitignore — incluindo por que ele parece não funcionar quando o arquivo já estava sendo rastreado.
  2. Navegando o histórico e desfazendo — a aula do "socorro, quero voltar atrás".
  3. Branches — trabalhar em paralelo sem pisar no trabalho de ninguém.

Se ficou alguma dúvida conceitual aqui — por exemplo "por que o hash muda quando eu edito um commit antigo?" ou "se todo clone tem o histórico completo, quem manda afinal?" — vale esclarecer agora. São exatamente as perguntas que voltam a aparecer nas aulas 08 e 09, e resolvê-las cedo economiza confusão depois.
