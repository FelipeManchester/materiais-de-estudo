Projeto Studio Fit — Trilha Node + Express — Parte 5

CRUD completo: Instrutor e Aula

A parte 4 validou o caminho ponta a ponta com alunos, tudo num arquivo só. Agora o projeto cresce — duas entidades novas, uma delas (aulas) com regra de negócio de verdade (Regra 3: conflito de agenda). Hora de sair do arquivo único e organizar em camadas, como a parte 5 da trilha API REST descreveu em teoria.

1. Por que separar em camadas agora

A parte 5 da trilha API REST (seção 2) já avisou: "numa API pequena, tudo bem misturar camadas no começo... separar vem depois, quando o código começar a doer". Esse momento chegou — com 3 entidades, o index.js ficaria com centenas de linhas, rotas de recursos diferentes misturadas, difícil de navegar.

A separação que vamos aplicar segue exatamente as camadas já descritas naquele material:

  • Rotas (routes/): mapeia método + URI pro handler certo (parte 5, "Roteamento").
  • Repository (repositories/): isola todo acesso ao banco — é a única camada que escreve SQL.

Ainda não vamos criar uma camada de "service" separada da rota — as regras de negócio (Regra 3, por exemplo) vão morar dentro do handler da rota por enquanto. Com só duas entidades novas e regras simples, uma camada a mais adicionaria abstração sem ganho real ainda. Se o projeto crescer mais, essa extração vira natural.

Um arquivo de rota e um de repository por entidade — fácil de achar onde mexer quando for dar manutenção em aulas, por exemplo, sem precisar ler o projeto inteiro.

3. Centralizando a conexão: db/pool.js

Até agora o Pool era criado direto no index.js. Com 3 repositories precisando consultar o banco, cada um teria que criar seu próprio Pool — desperdício de conexões, e cada um se conectando com config potencialmente diferente. Centraliza num único módulo:

// db/pool.js
const { Pool } = require('pg');

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
});

module.exports = pool;

Qualquer arquivo que precisar consultar o banco importa esse mesmo pool — uma única instância compartilhada em todo o projeto (o próprio Pool já gerencia múltiplas conexões internamente, como visto na parte 4, seção 3; não precisa de mais de um Pool por processo).

4. Express Router: dividindo rotas por recurso

express.Router() cria um "mini-app" — um agrupador de rotas que depois se conecta no app principal. Em vez de app.get('/alunos', ...) direto no index.js, cada arquivo de rota declara suas rotas relativas:

// routes/alunos.js (esqueleto)
const express = require('express');
const router = express.Router();

router.get('/', async (req, res) => { /* ... */ });   // vira GET /alunos
router.post('/', async (req, res) => { /* ... */ });  // vira POST /alunos

module.exports = router;

E no index.js, o prefixo é definido na hora de "montar" o router:

const alunosRouter = require('./routes/alunos');
app.use('/alunos', alunosRouter);

router.get('/') dentro de alunos.js + app.use('/alunos', ...) no index.js = GET /alunos de verdade. router.get('/:id') viraria GET /alunos/:id. O arquivo de rota nem precisa saber que está "dentro" de /alunos — só declara o que vem depois desse prefixo.

5. Refatorando alunos pro novo padrão

Primeiro, migra o que já existe e funciona — sem mudar comportamento, só organização:

// repositories/alunosRepository.js
const pool = require('../db/pool');

async function listar() {
  const resultado = await pool.query('SELECT * FROM alunos ORDER BY id');
  return resultado.rows;
}

async function criar({ nome, email, data_nascimento }) {
  const resultado = await pool.query(
    'INSERT INTO alunos (nome, email, data_nascimento) VALUES ($1, $2, $3) RETURNING *',
    [nome, email, data_nascimento]
  );
  return resultado.rows[0];
}

module.exports = { listar, criar };
// routes/alunos.js
const express = require('express');
const alunosRepository = require('../repositories/alunosRepository');

const router = express.Router();

router.get('/', async (req, res) => {
  const alunos = await alunosRepository.listar();
  res.json(alunos);
});

router.post('/', async (req, res) => {
  const { nome, email, data_nascimento } = req.body;

  if (!nome || !email || !data_nascimento) {
    return res.status(400).json({
      erro: 'nome, email e data_nascimento são obrigatórios',
    });
  }

  const alunoCriado = await alunosRepository.criar({ nome, email, data_nascimento });
  res.status(201).location(`/alunos/${alunoCriado.id}`).json(alunoCriado);
});

module.exports = router;

Repara a diferença de responsabilidade: rota lê o corpo da requisição, valida forma, monta a resposta. Repository só sabe escrever SQL e devolver linha — não sabe o que é req/res, não sabe HTTP existe. Isso é a separação de camadas da parte 5 (trilha API REST) virando código real.

6. CRUD de Instrutor

Instrutor não tem regra de negócio própria — mas tem um detalhe importante: outras tabelas dependem dele (aulas.instrutor_id, com ON DELETE RESTRICT, decidido na parte 3). Isso aparece na hora de deletar.

Repository

// repositories/instrutoresRepository.js
const pool = require('../db/pool');

async function listar() {
  const resultado = await pool.query('SELECT * FROM instrutores ORDER BY id');
  return resultado.rows;
}

async function buscarPorId(id) {
  const resultado = await pool.query('SELECT * FROM instrutores WHERE id = $1', [id]);
  return resultado.rows[0]; // undefined se não existir
}

async function criar({ nome, especialidade }) {
  const resultado = await pool.query(
    'INSERT INTO instrutores (nome, especialidade) VALUES ($1, $2) RETURNING *',
    [nome, especialidade]
  );
  return resultado.rows[0];
}

async function atualizar(id, { nome, especialidade }) {
  const resultado = await pool.query(
    `UPDATE instrutores
     SET nome = COALESCE($1, nome),
         especialidade = COALESCE($2, especialidade)
     WHERE id = $3
     RETURNING *`,
    [nome, especialidade, id]
  );
  return resultado.rows[0]; // undefined se o id não existir
}

async function remover(id) {
  const resultado = await pool.query('DELETE FROM instrutores WHERE id = $1 RETURNING *', [id]);
  return resultado.rows[0]; // undefined se o id não existir
}

module.exports = { listar, buscarPorId, criar, atualizar, remover };

Cuidado com undefined em query parametrizada: a biblioteca pg lança erro se você passar undefined num dos parâmetros — precisa ser null quando o valor "não veio". Por isso, na rota (a seguir), campos não enviados no PATCH são convertidos com nome ?? null antes de chegar aqui.

COALESCE($1, nome): se o parâmetro vier null, usa o valor que já estava na coluna — é assim que o UPDATE vira parcial (semântica de PATCH, parte 2 da trilha API REST) mesmo escrevendo um único UPDATE que sempre define as duas colunas.

Rotas

// routes/instrutores.js
const express = require('express');
const instrutoresRepository = require('../repositories/instrutoresRepository');

const router = express.Router();

router.get('/', async (req, res) => {
  const instrutores = await instrutoresRepository.listar();
  res.json(instrutores);
});

router.get('/:id', async (req, res) => {
  const instrutor = await instrutoresRepository.buscarPorId(req.params.id);

  if (!instrutor) {
    return res.status(404).json({ erro: 'Instrutor não encontrado' });
  }

  res.json(instrutor);
});

router.post('/', async (req, res) => {
  const { nome, especialidade } = req.body;

  if (!nome || !especialidade) {
    return res.status(400).json({ erro: 'nome e especialidade são obrigatórios' });
  }

  const instrutorCriado = await instrutoresRepository.criar({ nome, especialidade });
  res.status(201).location(`/instrutores/${instrutorCriado.id}`).json(instrutorCriado);
});

router.patch('/:id', async (req, res) => {
  const { nome, especialidade } = req.body;

  const instrutorAtualizado = await instrutoresRepository.atualizar(req.params.id, {
    nome: nome ?? null,
    especialidade: especialidade ?? null,
  });

  if (!instrutorAtualizado) {
    return res.status(404).json({ erro: 'Instrutor não encontrado' });
  }

  res.json(instrutorAtualizado);
});

router.delete('/:id', async (req, res, next) => {
  try {
    const instrutorRemovido = await instrutoresRepository.remover(req.params.id);

    if (!instrutorRemovido) {
      return res.status(404).json({ erro: 'Instrutor não encontrado' });
    }

    res.status(204).send();
  } catch (err) {
    if (err.code === '23503') {
      return res.status(409).json({
        erro: 'Não é possível remover: existem aulas cadastradas com este instrutor',
      });
    }
    next(err);
  }
});

module.exports = router;
Padrão: 404 sem consulta extra

Repara que PATCH e DELETE não fazem um SELECT pra "checar se existe" antes de agir — só rodam o UPDATE/DELETE direto (ambos com RETURNING *) e olham se veio alguma linha de volta. Se resultado.rows[0] vier undefined, o id não existia — devolve 404. Uma consulta a menos por requisição, sem perder a checagem.

O código de erro 23503

23503 é o código padrão do Postgres (SQLSTATE) pra foreign_key_violation — é o que a biblioteca pg expõe em err.code quando um DELETE esbarra na restrição ON DELETE RESTRICT (decidida na parte 3, seção 6, tabela aulas). Sem esse try/catch, essa exclusão bloqueada cairia no middleware de erro genérico da parte 4 e devolveria 500 — tecnicamente funciona, mas 500 significa "o servidor quebrou", quando na verdade o servidor está funcionando certinho, só recusando uma operação inválida. 409 Conflict é a resposta correta (parte 2 da trilha API REST, seção 6): a requisição conflita com o estado atual do sistema.

7. CRUD de Aula

Aqui entra a Regra 3 do projeto (parte 2): "um instrutor não pode ter duas aulas cadastradas no mesmo horário". A parte 3 (schema) já deixou claro que essa validação não ficaria no banco — fica aqui.

Regra 3: detectando conflito de agenda com OVERLAPS

Postgres tem um operador nativo pra comparar dois intervalos e saber se eles se cruzam: OVERLAPS. Recebe dois pares (início, fim) e devolve true/false:

SELECT (TIME '09:00', TIME '10:00') OVERLAPS (TIME '09:30', TIME '10:30');
-- true: os dois intervalos se cruzam entre 09:30 e 10:00

SELECT (TIME '09:00', TIME '10:00') OVERLAPS (TIME '10:00', TIME '11:00');
-- false: um termina exatamente quando o outro começa, não há sobreposição real

Como a tabela aulas guarda hora_inicio + duracao_minutos (não um "fim" pronto), calculamos o horário de término somando um intervalo — hora_inicio + (duracao_minutos * INTERVAL '1 minute'):

// repositories/aulasRepository.js (trecho)
async function existeConflito({ instrutor_id, dia_semana, hora_inicio, duracao_minutos, ignorarId = null }) {
  const resultado = await pool.query(
    `SELECT EXISTS (
       SELECT 1 FROM aulas
       WHERE instrutor_id = $1
         AND dia_semana = $2
         AND id IS DISTINCT FROM $5
         AND (hora_inicio, hora_inicio + (duracao_minutos * INTERVAL '1 minute'))
             OVERLAPS
             ($3::time, $3::time + ($4::int * INTERVAL '1 minute'))
     ) AS conflito`,
    [instrutor_id, dia_semana, hora_inicio, duracao_minutos, ignorarId]
  );
  return resultado.rows[0].conflito; // true ou false
}

Dois detalhes que valem explicação:

  • SELECT EXISTS (...): em vez de trazer as linhas conflitantes pro Node e checar .length > 0, pede pro próprio Postgres devolver direto um booleano — mais eficiente, e o código em JS fica só com true/false.
  • id IS DISTINCT FROM $5: usado só quando atualizando uma aula existente (parâmetro ignorarId) — sem isso, checar conflito de uma aula contra ela mesma sempre daria "conflito" (ela obviamente se sobrepõe ao próprio horário). IS DISTINCT FROM é como um != que funciona corretamente mesmo quando o valor é NULL (na criação, ignorarId é null, e um != comum se comportaria de forma inesperada com NULL em SQL — IS DISTINCT FROM evita essa armadilha clássica).

Repara que atualizar aqui não usa COALESCE como em instrutoresRepository — grava os 6 campos diretamente. A mesclagem "campo não veio, mantém o valor antigo" acontece na rota desta vez (seção seguinte), porque a rota já precisa buscar a aula existente mesmo, pra rodar a checagem de conflito com os valores efetivos. Duas estratégias válidas pra a mesma necessidade (mesclar dado parcial) — a escolhida depende de já ter ou não a linha em mãos por outro motivo.

Rotas

// routes/aulas.js
const express = require('express');
const aulasRepository = require('../repositories/aulasRepository');
const instrutoresRepository = require('../repositories/instrutoresRepository');

const router = express.Router();

router.get('/', async (req, res) => {
  const aulas = await aulasRepository.listar({ instrutor_id: req.query.instrutor_id });
  res.json(aulas);
});

router.get('/:id', async (req, res) => {
  const aula = await aulasRepository.buscarPorId(req.params.id);

  if (!aula) {
    return res.status(404).json({ erro: 'Aula não encontrada' });
  }

  res.json(aula);
});

router.post('/', async (req, res) => {
  const { nome, instrutor_id, dia_semana, hora_inicio, duracao_minutos, capacidade_maxima } = req.body;

  if (!nome || !instrutor_id || !dia_semana || !hora_inicio || !duracao_minutos || !capacidade_maxima) {
    return res.status(400).json({
      erro: 'nome, instrutor_id, dia_semana, hora_inicio, duracao_minutos e capacidade_maxima são obrigatórios',
    });
  }

  const instrutorExiste = await instrutoresRepository.buscarPorId(instrutor_id);
  if (!instrutorExiste) {
    return res.status(422).json({ erro: 'instrutor_id não corresponde a nenhum instrutor existente' });
  }

  const temConflito = await aulasRepository.existeConflito({
    instrutor_id, dia_semana, hora_inicio, duracao_minutos,
  });
  if (temConflito) {
    return res.status(422).json({ erro: 'Instrutor já tem aula cadastrada nesse horário' });
  }

  const aulaCriada = await aulasRepository.criar({
    nome, instrutor_id, dia_semana, hora_inicio, duracao_minutos, capacidade_maxima,
  });
  res.status(201).location(`/aulas/${aulaCriada.id}`).json(aulaCriada);
});

router.patch('/:id', async (req, res) => {
  const aulaExistente = await aulasRepository.buscarPorId(req.params.id);

  if (!aulaExistente) {
    return res.status(404).json({ erro: 'Aula não encontrada' });
  }

  const dadosAtualizados = {
    nome: req.body.nome ?? aulaExistente.nome,
    instrutor_id: req.body.instrutor_id ?? aulaExistente.instrutor_id,
    dia_semana: req.body.dia_semana ?? aulaExistente.dia_semana,
    hora_inicio: req.body.hora_inicio ?? aulaExistente.hora_inicio,
    duracao_minutos: req.body.duracao_minutos ?? aulaExistente.duracao_minutos,
    capacidade_maxima: req.body.capacidade_maxima ?? aulaExistente.capacidade_maxima,
  };

  const temConflito = await aulasRepository.existeConflito({
    instrutor_id: dadosAtualizados.instrutor_id,
    dia_semana: dadosAtualizados.dia_semana,
    hora_inicio: dadosAtualizados.hora_inicio,
    duracao_minutos: dadosAtualizados.duracao_minutos,
    ignorarId: aulaExistente.id,
  });

  if (temConflito) {
    return res.status(422).json({ erro: 'Instrutor já tem aula cadastrada nesse horário' });
  }

  const aulaAtualizada = await aulasRepository.atualizar(req.params.id, dadosAtualizados);
  res.json(aulaAtualizada);
});

router.delete('/:id', async (req, res) => {
  const aulaRemovida = await aulasRepository.remover(req.params.id);

  if (!aulaRemovida) {
    return res.status(404).json({ erro: 'Aula não encontrada' });
  }

  res.status(204).send();
});

module.exports = router;
Por que DELETE de aula não precisa de try/catch

Diferente do instrutor, deletar uma aula não esbarra em restrição nenhuma — a tabela matriculas foi definida com ON DELETE CASCADE em aula_id (parte 3, seção 7): apagar a aula remove as matrículas dependentes automaticamente, sem bloquear. Duas tabelas, duas decisões de ON DELETE diferentes, dois comportamentos diferentes de API — a escolha feita no schema se reflete direto em quanto código de tratamento de erro cada rota precisa.

GET /aulas?instrutor_id=3 já aplica o filtro por query string (parte 3 da trilha API REST, seção 6) — instrutor_id não vira rota nova, é parâmetro sobre a mesma coleção.

8. index.js final

// index.js
require('dotenv').config();

const express = require('express');

const alunosRouter = require('./routes/alunos');
const instrutoresRouter = require('./routes/instrutores');
const aulasRouter = require('./routes/aulas');

const app = express();

app.use(express.json());

app.use('/alunos', alunosRouter);
app.use('/instrutores', instrutoresRouter);
app.use('/aulas', aulasRouter);

app.use((err, req, res, _next) => {
  console.error(err);
  res.status(500).json({ erro: 'Erro interno no servidor' });
});

const PORT = process.env.PORT || 3000;
app.listen(PORT, () => {
  console.log(`Servidor rodando em http://localhost:${PORT}`);
});

Comparado à parte 4: o arquivo principal encolheu bastante — agora só monta as peças (routers) e cuida do que é realmente global (JSON parsing, tratamento de erro, subir o servidor). Cada entidade vive isolada no seu par rota/repository.

10. Erros comuns

  1. Esquecer de exportar o router (module.exports = router) — index.js recebe undefined no lugar do router, app.use('/alunos', undefined) lança erro na inicialização.
  2. Montar o router com prefixo errado — se em routes/aulas.js você escrever router.get('/aulas', ...) (repetindo o prefixo) e ainda montar com app.use('/aulas', aulasRouter) no index.js, a rota final vira /aulas/aulas por engano. Dentro do arquivo de rota, os caminhos são sempre relativos ao prefixo já montado.
  3. Passar undefined em vez de null num parâmetro de query — biblioteca pg lança erro imediatamente. Ver aviso da seção 6.
  4. Esquecer o ::time/::int nos parâmetros do OVERLAPS — sem o cast explícito, o Postgres às vezes não consegue inferir o tipo do parâmetro ($3, $4) sozinho, e a query falha com erro de tipo ambíguo.
  5. Confundir 422 com 400 — campo ausente/mal formatado é 400 (seção 6 da parte 2 da trilha API REST); dado com formato certo mas que viola regra de negócio (conflito de agenda, instrutor inexistente) é 422. As rotas desta parte já seguem essa distinção.

11. O que vem a seguir

Com Aluno, Instrutor e Aula todos com CRUD completo, falta a peça mais rica do projeto: a Matrícula, que liga tudo.

  1. Matrícula e suas regras: Regra 1 (capacidade máxima, validada no código, contando matrículas confirmadas), Regra 2 (já resolvida pelo índice único parcial do banco, parte 3), Regra 4 (cancelamento via PATCH de status, nunca DELETE).
  2. Autenticação: login de aluno, proteção das rotas de matrícula.

Refatorar em camadas dá trabalho uma vez e paga o resto do projeto — repara como aulas, a entidade mais complexa até agora, ficou isolada num par de arquivos, sem misturar com a lógica de instrutores ou alunos. Quando terminar de testar, volta com dúvidas — principalmente se o OVERLAPS se comportar diferente do esperado em algum horário testado manualmente.
