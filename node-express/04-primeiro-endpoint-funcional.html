Projeto Studio Fit — Trilha Node + Express — Parte 4

Primeiro endpoint funcional

Schema criado (parte 3), Postgres no ar. Agora o Express entra em cena: um servidor de verdade, respondendo GET e POST em /alunos, lendo e gravando na tabela real. Primeiro recorte funcional do projeto Studio Fit.

1. O que vamos construir

Só dois endpoints, aplicando o que as partes 2, 3 e 5 da trilha API REST já ensinaram — agora em código de verdade:

RotaO que fazConceitos aplicados
GET /alunosLista todos os alunos cadastradosMétodo seguro/idempotente, 200 OK
POST /alunosCria um aluno novoValidação de forma, 201 Created + header Location

Ainda num único arquivo, sem separar em camadas (rotas/handlers/repository) — o callout da parte 5 (seção 2) já justificou essa escolha: separar em camadas cedo demais, antes de ter algo funcionando, atrapalha mais do que ajuda. Isso vem na próxima parte, quando o projeto crescer pras outras entidades.

2. O arquivo principal: index.js

Na pasta do projeto (a mesma do docker-compose.yml e do db/schema.sql), cria um arquivo index.js na raiz. É o ponto de entrada — o arquivo que o comando npm run dev (configurado no guia de ambiente) executa.

3. Conectando no Postgres com pg

A biblioteca pg (instalada no guia de ambiente) oferece uma classe chamada Pool — não conecta diretamente, mantém um conjunto de conexões reutilizáveis com o banco.

const { Pool } = require('pg');

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
});

Por que Pool e não uma conexão única: cada requisição que chega no Express pode rodar ao mesmo tempo que outra (Node lida com várias requisições concorrentes). Se todas dividissem uma única conexão com o banco, ficariam na fila umas atrás das outras. O Pool mantém várias conexões abertas prontas, empresta uma pra cada consulta, devolve pro conjunto quando termina — sem você precisar gerenciar isso na mão.

process.env.DATABASE_URL vem do arquivo .env criado no guia de ambiente (postgresql://postgres:senha123@localhost:5432/estudo) — por isso o dotenv precisa ser carregado antes de qualquer outra coisa no arquivo, seção 9.

4. Lendo JSON do corpo da requisição

Por padrão, o Express não interpreta o corpo de uma requisição automaticamente. Sem avisar isso, req.body viria undefined mesmo que o cliente tenha mandado um JSON certinho.

app.use(express.json());

Esse é o "parsing do body" mencionado na parte 5 da trilha API REST (seção 8) — um middleware que roda antes de qualquer rota, transformando o JSON cru recebido em objeto JavaScript acessível via req.body.

5. Rota GET /alunos

app.get('/alunos', async (req, res) => {
  const resultado = await pool.query('SELECT * FROM alunos ORDER BY id');
  res.json(resultado.rows);
});

pool.query(...) envia o SQL, devolve uma promise — por isso o handler é async e usa await. O resultado (resultado.rows) é um array de objetos JavaScript, um por linha da tabela. res.json(...) já cuida de: definir Content-Type: application/json, serializar o array, e — por não chamar res.status(...) antes — usa o padrão do Express, que é 200 OK.

Tabela vazia? resultado.rows vem como array vazio ([]), e a resposta é 200 com [] — não é erro, é uma coleção sem itens (mesma ideia da parte 3 da trilha API REST: coleção existe, só não tem itens ainda).

6. Rota POST /alunos

app.post('/alunos', async (req, res) => {
  const { nome, email, data_nascimento } = req.body;

  if (!nome || !email || !data_nascimento) {
    return res.status(400).json({
      erro: 'nome, email e data_nascimento são obrigatórios',
    });
  }

  const resultado = await pool.query(
    'INSERT INTO alunos (nome, email, data_nascimento) VALUES ($1, $2, $3) RETURNING *',
    [nome, email, data_nascimento]
  );

  const alunoCriado = resultado.rows[0];

  res
    .status(201)
    .location(`/alunos/${alunoCriado.id}`)
    .json(alunoCriado);
});

Passo a passo:

  • Validação de forma (parte 5, seção 6): confere se os 3 campos obrigatórios vieram, antes de tocar no banco. Falhando, devolve 400 Bad Request — nem chega perto de um INSERT.
  • RETURNING *: cláusula do Postgres que devolve a linha recém-inserida (com o id que o SERIAL gerou, e o criado_em que o DEFAULT NOW() preencheu) — sem isso, o INSERT não devolveria nada útil pro código.
  • res.status(201).location(...).json(...): encadeamento de métodos do Express. Define status 201 Created, o header Location apontando pro novo recurso (/alunos/42, por exemplo), e o body com o aluno criado — exatamente o que a parte 2 da trilha API REST (seção 3) descreveu como resposta correta de criação.

7. Por que usar $1, $2 em vez de concatenar string

Repara que o SQL usa $1, $2, $3 como marcadores de posição, e os valores reais vão num array separado — nunca direto dentro da string SQL:

Nunca fazer isso

pool.query(
  `INSERT INTO alunos (nome, email)
   VALUES ('${nome}', '${email}')`
)

Sempre fazer isso

pool.query(
  'INSERT INTO alunos (nome, email)
   VALUES ($1, $2)',
  [nome, email]
)

O motivo é segurança, não estilo: concatenar valor de entrada direto numa string SQL abre brecha pra SQL injection — se alguém mandar, no campo nome, algo como ' ); DROP TABLE alunos; --, a concatenação vira SQL válido e destrutivo executado no seu banco. Usando $1/$2 com array de valores separado (chamado de query parametrizada), a biblioteca pg trata qualquer coisa que vier do usuário como dado, nunca como comando SQL — não importa o que o valor contenha, ele nunca "escapa" pra virar instrução.

Isso não é opcional nem exagero: SQL injection está entre as vulnerabilidades mais exploradas historicamente em aplicações web. Toda consulta com valor vindo de fora (body, query string, params de rota) usa placeholder — sem exceção, mesmo em projeto de estudo.

8. Um tratamento de erro mínimo

Ainda não é o tratamento de erro centralizado completo da parte 5 (seção 7) — isso fica pra quando o projeto tiver mais de uma regra de negócio pra tratar (próxima parte). Por enquanto, um middleware de erro simples, no fim do arquivo, evita que qualquer falha (ex: tentar inserir e-mail duplicado, que o UNIQUE da parte 3 recusa) derrube o servidor sem resposta nenhuma pro cliente:

app.use((err, req, res, next) => {
  console.error(err);
  res.status(500).json({ erro: 'Erro interno no servidor' });
});

Middleware de erro se reconhece pela assinatura de 4 parâmetros (err, req, res, next) — é assim que o Express diferencia esse tipo de middleware dos outros. Precisa ser registrado por último, depois de todas as rotas.

Testando agora: se você tentar cadastrar dois alunos com o mesmo e-mail, o UNIQUE do banco (parte 3, seção 5) vai recusar o segundo INSERT, o pg lança um erro, e esse middleware captura — mas devolve 500 genérico, quando o certo seria 409 Conflict (parte 2, seção 6). Diferenciar "que tipo de erro de banco é esse" pra devolver o status certo é exatamente o assunto da próxima parte, quando o tratamento de erro for centralizado de verdade.

9. Código completo

// index.js
require('dotenv').config();

const express = require('express');
const { Pool } = require('pg');

const app = express();
const pool = new Pool({ connectionString: process.env.DATABASE_URL });

app.use(express.json());

app.get('/alunos', async (req, res) => {
  const resultado = await pool.query('SELECT * FROM alunos ORDER BY id');
  res.json(resultado.rows);
});

app.post('/alunos', async (req, res) => {
  const { nome, email, data_nascimento } = req.body;

  if (!nome || !email || !data_nascimento) {
    return res.status(400).json({
      erro: 'nome, email e data_nascimento são obrigatórios',
    });
  }

  const resultado = await pool.query(
    'INSERT INTO alunos (nome, email, data_nascimento) VALUES ($1, $2, $3) RETURNING *',
    [nome, email, data_nascimento]
  );

  const alunoCriado = resultado.rows[0];

  res
    .status(201)
    .location(`/alunos/${alunoCriado.id}`)
    .json(alunoCriado);
});

app.use((err, req, res, next) => {
  console.error(err);
  res.status(500).json({ erro: 'Erro interno no servidor' });
});

const PORT = process.env.PORT || 3000;
app.listen(PORT, () => {
  console.log(`Servidor rodando em http://localhost:${PORT}`);
});

10. Rodando o servidor

Com o Postgres no ar (docker compose up -d) e as dependências instaladas (guia de ambiente), roda:

npm run dev

Deve aparecer no terminal: Servidor rodando em http://localhost:3000. Como o script usa nodemon, qualquer alteração salva em index.js reinicia o servidor sozinho — não precisa parar e rodar de novo a cada mudança.

11. Testando com curl

# lista vazia no início
curl http://localhost:3000/alunos
# []

# cria um aluno
curl -X POST http://localhost:3000/alunos \
  -H "Content-Type: application/json" \
  -d '{"nome": "Ana Silva", "email": "ana@example.com", "data_nascimento": "1995-04-12"}'
# 201 Created, body com id, criado_em, e header Location: /alunos/1

# lista de novo, aluno aparece
curl http://localhost:3000/alunos

# validação: falta campo obrigatório
curl -X POST http://localhost:3000/alunos \
  -H "Content-Type: application/json" \
  -d '{"nome": "Sem email"}'
# 400 Bad Request

# UNIQUE do banco: tenta repetir o mesmo e-mail
curl -X POST http://localhost:3000/alunos \
  -H "Content-Type: application/json" \
  -d '{"nome": "Outro Ana", "email": "ana@example.com", "data_nascimento": "2000-01-01"}'
# 500 (esperado por enquanto — ver seção 8)

Confirma também direto no banco, fora da API:

docker compose exec db psql -U postgres -d estudo -c "SELECT * FROM alunos;"

12. Erros comuns

  1. req.body vem undefined — esqueceu app.use(express.json()), ou esqueceu o header Content-Type: application/json no curl.
  2. DATABASE_URL undefined, Pool tenta conectar em lugar errado — require('dotenv').config() precisa ser a primeira linha executada no arquivo, antes de qualquer outro require que dependa de variável de ambiente.
  3. Servidor não conecta no Postgres, erro ECONNREFUSED — confirma que o container está rodando (docker compose ps); se acabou de reiniciar o computador, precisa rodar docker compose up -d de novo (o guia de ambiente cobre isso).
  4. Concatenar valor direto na string SQL — ver seção 7. Sempre $1/$2 com array de valores.
  5. Servidor trava sem resposta numa requisição que dá erro — confirma que o middleware de erro (seção 8) está registrado depois de todas as rotas, não antes.

13. O que vem a seguir

Com o primeiro recorte funcionando de ponta a ponta (Express → Postgres → resposta), a trilha segue implementando o resto do projeto Studio Fit:

  1. CRUD completo de Instrutor e Aula, aplicando a Regra 3 (conflito de agenda) no código — e já separando em camadas (rotas/handlers/repository, parte 5 da trilha API REST), já que o projeto cresce demais pra um arquivo só.

Quando o GET e o POST estiverem respondendo certo (incluindo os casos de erro testados na seção 11), volte com dúvidas — principalmente se algo no pg se comportar diferente do esperado, ou se quiser entender melhor por que o e-mail duplicado ainda devolve 500 em vez de 409 por enquanto.
