Validação e erros de domínio

Cinco partes seguidas cuidaram de quem pode fazer o quê. Nenhuma delas olhou o que está sendo enviado: até agora, data_nascimento: "banana" atravessa a API inteira e só morre no Postgres, virando um 500 que culpa o servidor por um erro do cliente.

1. O que a API aceita hoje

Toda validação do projeto tem a mesma forma, desde a parte 4: if (!nome || !email). Isso responde uma pergunta só — "o campo veio?" — e nenhuma outra. Veja o que passa:

RequisiçãoO que deveria acontecerO que acontece hoje
{"data_nascimento": "banana"}400, data inválida500 — o Postgres rejeita, o erro sobe como falha interna
{"capacidade_maxima": -5}400, precisa ser positivo500 — estoura no CHECK da parte 3
{"email": "nao-e-email"}400, formato inválido201 — grava feliz, e esse aluno nunca vai conseguir recuperar senha
{"nome": " "}400, nome vazio201 — o if (!nome) só pega string vazia, não espaços
{"duracao_minutos": "60"} (string)aceitar, convertendo pra númerofunciona por acidente — o driver pg converte, e a comparação da parte 10 quebrou por causa disso
{"nome": "Ana", "nomee": "Ana"}400, campo desconhecido201 — o typo é ignorado em silêncio
{"senha": "1"}400, senha curta demais201 — todo o cuidado da parte 7 protegendo uma senha de um caractere
{"dia_semana": "sabadao"}400, valor fora da lista500 — o CHECK do banco recusa

Repare no padrão dos 500: em quase todos, o banco está fazendo o trabalho de validação. As constraints da parte 3 (CHECK, NOT NULL, tipos) seguram a integridade dos dados — e é ótimo que segurem, é a última linha de defesa. Mas elas não sabem responder HTTP: o erro chega como exceção genérica, o error handler devolve 500, e o cliente ouve "erro interno no servidor" quando o problema estava no que ele mandou. Status errado, mensagem inútil, e um log de erro seu poluído com problemas que não são seus.

2. Por que if (!campo) não escala

A reação natural é escrever mais if. Tente mentalmente, só pro POST /alunos: checar presença dos 4 campos, tipo de cada um, nome não-vazio depois de tirar espaços, tamanho máximo pra caber no VARCHAR(120), formato de email, data que existe de verdade (2026-02-31 não existe), senha com mínimo razoável, e nenhum campo estranho. São umas 20 linhas de if — numa rota que tem 8 linhas de lógica de verdade.

Multiplicado por 9 rotas de escrita, três problemas aparecem:

  • A regra fica espalhada. "Nome tem no máximo 120 caracteres" vira uma linha no POST e outra, quase igual, no PATCH. Uma hora as duas divergem.
  • As mensagens ficam inconsistentes. Cada rota inventa o próprio texto e o próprio formato de resposta — o cliente não consegue tratar erro de forma genérica.
  • O que não foi escrito não existe. Validação na mão é lista de casos lembrados. O caso esquecido não dá erro: ele passa.

A alternativa é declarar o formato esperado uma vez, num objeto, e deixar uma biblioteca conferir. Em vez de descrever como rejeitar, você descreve o que aceita.

3. Schema como contrato: por que Zod

As duas opções mais usadas em Node são Joi e Zod. As duas resolvem o problema; a escolha aqui é o Zod, por três motivos:

Zod escolhidoJoi
Escritaz.string().min(2) — encadeado, e o schema é um objeto JavaScript comum.Joi.string().min(2) — muito parecido, honestamente.
ErrosArray de issues com path, code e message — fácil de virar resposta por campo.Também estruturado, formato um pouco mais verboso.
TypeScriptO schema gera o tipo. Se um dia a trilha migrar pra TS, o trabalho já está feito.Tipagem é manual e separada.
IdiomaTraz traduções prontas, inclusive pt-BR (seção 4).Mensagens em inglês, tradução na mão.

Nenhum dos dois é errado. Se você herdar um projeto com Joi, não troque por trocar — o ganho está em ter um jeito de validar, não em qual dos dois.

5. O primeiro schema: aluno

Criar schemas/alunoSchema.js — o formato de um cadastro de aluno, campo a campo:

const { z } = require('zod');

const criarAlunoSchema = z.strictObject({
  nome: z.string().trim().min(2).max(120),
  email: z.email().max(160),
  data_nascimento: z.iso.date(),
  senha: z.string().min(8).max(72),
});

module.exports = { criarAlunoSchema };

Cada linha responde uma das falhas da seção 1:

RegraDe onde ela vem
.trim()Não é só validação — transforma. " Carla " vira "Carla" antes de chegar no banco, e " " vira "", que aí falha no .min(2).
.max(120)O VARCHAR(120) da tabela alunos (parte 3). Schema e banco precisam concordar, senão o erro só aparece no INSERT.
z.email()Formato de email. Não garante que o endereço existe — isso só um email de confirmação resolve — mas elimina o obviamente errado.
z.iso.date()Exige AAAA-MM-DD e uma data que exista de verdade: 2026-02-31 é rejeitado.
.min(8) na senhaRegra de negócio que a parte 7 deixou implícita. Sem ela, todo o bcrypt do mundo protege uma senha de um caractere.
.max(72) na senhaLimite técnico do bcrypt: ele ignora tudo além de 72 bytes. Recusar é mais honesto do que aceitar e truncar em silêncio.

6. Campo desconhecido é erro, não detalhe

Repare que o schema usa z.strictObject, não z.object. A diferença é o que acontece com um campo que você não declarou:

z.objectz.strictObject
Campo extra no bodyIgnorado em silêncio, some do resultado.400 — "Chave desconhecida".

Ignorar parece mais gentil, e é a escolha errada aqui. Pensa em quem manda {"nomee": "Ana", ...}: com z.object, a API responde 201, o aluno é criado sem nome... exceto que nome era obrigatório, então na verdade dá erro de campo faltando — e o cliente fica olhando pro payload dele jurando que mandou o nome. Pior ainda no PATCH, onde tudo é opcional: {"especialidadee": "yoga"} responderia 200 sem ter alterado nada.

Quando ignorar é a escolha certa

z.object faz sentido em API pública com muitos clientes antigos, onde alguém pode estar mandando um campo que você removeu há dois anos — recusar quebraria integrações que funcionavam. É o mesmo raciocínio de compatibilidade da parte 3 da trilha API REST. Num projeto onde você controla os dois lados, ser rígido é melhor: o erro aparece na hora, não vira dado silenciosamente perdido.

7. O middleware validar

O schema sozinho não faz nada — precisa rodar antes do handler. E como cada rota valida um schema diferente, o middleware precisa ser configurável: mesma estrutura do autorizar da parte 10, uma fábrica de middleware.

Criar middlewares/validar.js — ao lado do autenticar.js e do autorizar.js:

function validar(schemas) {
  return (req, res, next) => {
    for (const origem of ['body', 'params', 'query']) {
      const schema = schemas[origem];

      if (!schema) continue;

      const resultado = schema.safeParse(req[origem]);

      if (!resultado.success) {
        return res.status(400).json({
          erro: 'Dados inválidos',
          detalhes: resultado.error.issues.map((problema) => ({
            campo: problema.path.join('.') || origem,
            mensagem: problema.message,
          })),
        });
      }

      req[origem] = resultado.data;
    }

    next();
  };
}

module.exports = validar;

Três decisões dentro dessas linhas:

  • safeParse, não parse. O parse lança exceção; o safeParse devolve { success, data | error }. Como o erro de validação é um caminho esperado — cliente errando é rotina, não excepcional — tratar por retorno fica mais direto do que por try/catch.
  • req[origem] = resultado.data. A linha mais importante e a mais fácil de esquecer: ela substitui o dado cru pelo dado validado e transformado. Sem ela, o .trim() e as conversões de tipo não chegam no handler, e o schema vira só um porteiro.
  • O laço nas três origens. validar({ body: X }) valida só o body; validar({ params: Y, body: X }) valida os dois. Uma rota que não passa query nem paga o custo.

problema.path.join('.') monta o nome do campo — ['email'] vira "email". Quando o erro é do objeto inteiro (seção 11), path vem vazio e o || origem entra como reserva, resultando em "body".

8. O formato do 400

Toda resposta de erro da API, desde a parte 4, tem a forma { "erro": "mensagem" }. Validação precisa de mais: um POST pode errar cinco campos de uma vez, e mandar só o primeiro obriga o cliente a descobrir os problemas um por requisição.

Requisição

{
  "nome": "A",
  "email": "nao-e-email",
  "data_nascimento": "banana",
  "senha": "123"
}

Resposta 400

{
  "erro": "Dados inválidos",
  "detalhes": [
    { "campo": "nome",
      "mensagem": "Muito pequeno: ..." },
    { "campo": "email",
      "mensagem": "endereço de e-mail inválido" },
    { "campo": "data_nascimento",
      "mensagem": "data ISO inválido" },
    { "campo": "senha",
      "mensagem": "Muito pequeno: ..." }
  ]
}

O campo erro continua lá, então quem já tratava a API não quebra — detalhes é informação a mais, não formato novo. Um front-end usa isso pra pintar de vermelho exatamente os campos errados do formulário, em uma ida ao servidor.

10. Schemas de instrutor e aula

Criar schemas/instrutorSchema.js:

const { z } = require('zod');

const criarInstrutorSchema = z.strictObject({
  nome: z.string().trim().min(2).max(120),
  especialidade: z.string().trim().min(2).max(80),
  email: z.email().max(160).optional(),
  senha: z.string().min(8).max(72).optional(),
  papel: z.enum(['instrutor', 'admin']).optional(),
});

module.exports = { criarInstrutorSchema };

Os três .optional() vêm direto da decisão da parte 10: admin pode cadastrar um instrutor que ainda não loga, e o papel tem DEFAULT 'instrutor' no banco. Já o z.enum repete, no schema, exatamente a lista do CHECK da tabela — assim o valor errado vira 400 antes de virar 500.

Criar schemas/aulaSchema.js — o mais interessante dos três, porque a tabela aulas tem tipos que não são só texto:

const { z } = require('zod');

const DIAS = [
  'segunda',
  'terca',
  'quarta',
  'quinta',
  'sexta',
  'sabado',
  'domingo',
];

const criarAulaSchema = z.strictObject({
  nome: z.string().trim().min(2).max(120),
  instrutor_id: z.coerce.number().int().positive(),
  dia_semana: z.enum(DIAS),
  hora_inicio: z.iso.time(),
  duracao_minutos: z.coerce.number().int().positive().max(480),
  capacidade_maxima: z.coerce.number().int().positive().max(200),
});

module.exports = { criarAulaSchema, DIAS };
RegraPor quê
z.coerce.number()Aceita 3 e "3", entregando sempre 3 pro handler. Isso resolve na raiz a armadilha da parte 10: a comparação Number(instrutor_id) !== req.usuario.id existia porque o campo podia chegar como string. Depois do validar, não pode mais.
z.iso.time()Aceita "07:00" e "07:00:00", recusa "25:00" e "7:00". O tipo TIME do Postgres aceita as duas formas válidas.
.max(480) / .max(200)Tetos de sanidade que o banco não tem: o CHECK só exige > 0, então uma aula de 100 mil minutos passaria. Limite absurdo quase sempre é erro de digitação.

Alterar schemas/index.js — reexporte os dois schemas novos:

const { criarAlunoSchema } = require('./alunoSchema');

const { criarAulaSchema } = require('./aulaSchema');

module.exports = {
  criarAlunoSchema,
  criarInstrutorSchema,
  criarAulaSchema,
};

11. PATCH parcial e o corpo vazio

PATCH é atualização parcial (parte 2 da trilha API REST): manda só o que muda. O schema de criação exige todos os campos, então reaproveitá-lo direto quebraria a semântica — mas reescrever tudo de novo com .optional() em cada linha duplicaria as regras.

.partial() resolve: ele pega um schema e torna todos os campos opcionais, mantendo as validações de cada um.

Alterar schemas/aulaSchema.js — adicione o schema de atualização depois do criarAulaSchema, e inclua no module.exports:

const atualizarAulaSchema = criarAulaSchema
  .partial()
  .refine((dados) => Object.keys(dados).length > 0, {
    message: 'Envie ao menos um campo para atualizar',
  });

module.exports = { criarAulaSchema, DIAS };
module.exports = { criarAulaSchema, atualizarAulaSchema, DIAS };

O .refine cobre o caso que o .partial() abre: se tudo é opcional, {} é válido — e um PATCH com corpo vazio responderia 200 sem ter feito nada. Um 400 dizendo "envie ao menos um campo" é mais útil do que um sucesso que não aconteceu.

Esse erro não pertence a nenhum campo específico, então o Zod devolve path: []. É exatamente o caso que o || origem do middleware (seção 7) cobre: o cliente recebe { "campo": "body", "mensagem": "Envie ao menos um campo para atualizar" }.

Faça o mesmo par para instrutor, que também tem PATCH:

Alterar schemas/instrutorSchema.js — mesmo padrão, e ajuste o module.exports:

  .partial()
  .refine((dados) => Object.keys(dados).length > 0, {

12. Validando params e query

Body não é a única entrada. GET /alunos/abc/matriculas chega no repository com "abc" onde deveria ir um id, e GET /aulas?instrutor_id=xyz idem. Os dois viram erro do Postgres — 500 de novo.

Criar schemas/comumSchema.js — schemas pequenos que várias rotas reaproveitam:

const { z } = require('zod');

const idParamSchema = z.object({
  id: z.coerce.number().int().positive(),
});

const idsMatriculaParamSchema = z.object({
  id: z.coerce.number().int().positive(),
  matriculaId: z.coerce.number().int().positive(),
});

const listarAulasQuerySchema = z.object({
  instrutor_id: z.coerce.number().int().positive().optional(),
});

module.exports = {
  idParamSchema,
  idsMatriculaParamSchema,
  listarAulasQuerySchema,
};

Repare que aqui é z.object, não z.strictObject. Em params isso é indiferente (o Express só põe ali o que a rota declarou), mas em query a diferença importa: strictObject faria GET /aulas?utm_source=instagram responder 400. Parâmetro de rastreamento colado na URL por um link compartilhado é rotina — recusar a requisição por causa dele quebraria a navegação por um motivo que não é do usuário.

A coerção brilha aqui: req.params.id é sempre string (tudo que vem da URI é texto, como a parte 7 avisou), e depois do validar ele chega no handler como número. Aquela comparação Number(req.params.id) !== req.usuario.id da parte 10 pode virar só req.params.id !== req.usuario.id — mas cuidado: só nas rotas onde você aplicou o middleware. Enquanto a conversão não estiver em todas, manter o Number() é mais seguro do que remover pela metade.

13. Erros de domínio

Validação resolve "o dado tem o formato certo?". Sobra a outra família de erro: o dado está bem formado, mas a operação não pode acontecer — aula sem vaga, instrutor com conflito de agenda, aluno já matriculado. Essas são as regras das partes 5 e 6, e hoje cada uma responde assim:

if (totalConfirmadas >= aula.capacidade_maxima) {
  return res.status(409).json({ erro: 'Aula sem vagas disponíveis' });
}

Funciona, e tem dois incômodos. Primeiro, a regra de negócio fica amarrada ao res: se amanhã a checagem de capacidade descer pra uma camada de serviço (que não conhece HTTP), ela não pode mais responder assim. Segundo, cada rota decide sozinha o status — e nada impede que o mesmo erro vire 409 num lugar e 422 em outro.

A saída é um tipo de erro próprio, que carrega o status e é traduzido em HTTP num lugar só.

Criar errors/ErroDeDominio.js — diretório novo, uma classe pequena:

class ErroDeDominio extends Error {
  constructor(mensagem, status = 422) {
    super(mensagem);
    this.name = 'ErroDeDominio';
    this.status = status;
  }
}

module.exports = ErroDeDominio;

Herdar de Error é o que faz ele funcionar com throw, com instanceof e com o stack trace. O status é o que o diferencia de um erro qualquer: ele já sabe que HTTP responde a ele.

Alterar index.js — importe a classe no topo, junto dos outros require:

const cookieParser = require('cookie-parser');
const ErroDeDominio = require('./errors/ErroDeDominio');

Alterar index.js — no middleware de erro do fim do arquivo. A checagem nova entra antes das duas de err.type que a parte 9 adicionou:

app.use((err, req, res, _next) => {
  if (err instanceof ErroDeDominio) {
    return res.status(err.status).json({ erro: err.message });
  }

  if (err.type === 'entity.too.large') {
    return res.status(413).json({ erro: 'Corpo da requisição grande demais' });
  }

  if (err.type === 'entity.parse.failed') {
    return res.status(400).json({ erro: 'JSON inválido' });
  }

  console.error(err);
  res.status(500).json({ erro: 'Erro interno no servidor' });
});

Agora a regra pode simplesmente lançar. O Express 5 captura a rejeição de um handler async sozinho e entrega pro error handler — nada de try/catch em cada rota.

Alterar routes/aulas.js — importe a classe no topo, e converta a checagem de capacidade dentro de POST /:id/matriculas:

      throw new ErroDeDominio('Aula sem vagas disponíveis', 409);

Essa rota tem um try/catch em volta do matriculasRepository.criar (parte 6, pro código 23505). Confira onde você colocou o throw: se ele cair dentro do try, o catch vai pegá-lo, não vai achar err.code === '23505', e vai repassar com next(err) — que por sorte leva ao mesmo lugar. Funciona, mas por acidente. A checagem de capacidade vem antes do try, e é ali que o throw deve ficar.

Não converta tudo de uma vez. Os outros return res.status(...) espalhados pelas rotas continuam funcionando perfeitamente — 404 de recurso inexistente, 403 de posse, 422 de conflito de agenda. Trocar todos agora seria uma refatoração grande, arriscada e sem ganho imediato. O padrão está montado; use-o no código novo e converta o antigo quando estiver mexendo nele por outro motivo.

15. Erros comuns

  1. Esquecer req[origem] = resultado.data — a validação funciona, mas o handler recebe o dado cru: sem trim, sem conversão de tipo. O sintoma é sutil, porque nada dá erro.
  2. Validar antes de autenticar — a ordem correta é autenticar, autorizar, validar. Invertida, um estranho descobre o formato dos seus dados internos (seção 9).
  3. z.coerce.number() aceita string vazia — Number("") é 0, então "" vira 0 e passa. Por isso os schemas usam .positive() junto: sozinha, a coerção é mais permissiva do que parece.
  4. Usar strictObject na query — qualquer ?utm_source=... de link compartilhado vira 400 (seção 12).
  5. Deixar schema e banco divergirem — .max(120) no schema e VARCHAR(80) na tabela devolve 500 pra um valor que o schema aprovou. Sempre que mexer numa coluna, olhe o schema correspondente.
  6. Remover o Number() das comparações antes de aplicar validar em todas as rotas — a coerção só existe onde o middleware roda. Meia migração é pior que nenhuma.
  7. throw dentro de um try/catch existente — o catch intercepta o ErroDeDominio e o trata como erro inesperado (seção 13).
  8. Achar que validação substitui as constraints do banco — não substitui. O CHECK e o NOT NULL continuam necessários: eles protegem contra bug no código, migração manual e acesso direto pelo psql. Validação melhora a resposta; o banco garante a integridade.

16. O que vem a seguir

A API agora recusa entrada malformada com 400 e mensagem por campo, converte tipos antes de o handler ver o dado, e tem um jeito único de sinalizar erro de regra de negócio. Falta o terceiro item da categoria corretude e robustez, que é a próxima parte:

  1. Transações e concorrência — duas condições de corrida estão anotadas desde que apareceram, e são o mesmo problema: ler, decidir e escrever sem nada segurar a linha no meio. Na Regra 1 (parte 6), duas matrículas simultâneas na última vaga passam as duas pela checagem de capacidade. Na rotação de refresh (parte 8), duas requisições com o mesmo token são aceitas antes de qualquer uma revogar. Entram BEGIN/COMMIT, SELECT ... FOR UPDATE, e o truque de fazer o próprio UPDATE ... WHERE ... RETURNING * ser a checagem.

Depois dela, a ordem combinada segue: banco e dados (migrations — e aí os ALTER TABLE das partes 7, 8 e 10 viram arquivos versionados; limpeza de refresh tokens expirados; soft-delete de instrutor) → qualidade (Jest + supertest, CI) → contrato da API (paginação, OpenAPI — e a documentação sai quase de graça, porque os schemas desta parte descrevem o contrato de entrada) → produção (logging, health check, Dockerfile, deploy com HTTPS).

Fica registrado como dívida consciente: os return res.status(...) antigos continuam espalhados pelas rotas (seção 13), convertidos para ErroDeDominio só quando você estiver mexendo neles por outro motivo.

Ao testar, o mais satisfatório é repetir a tabela da seção 1 e ver cada 500 virar 400 com mensagem que explica o problema. Preste atenção especial no trim chegando no banco e na coerção de "1" pra 1 — são as duas transformações que provam que o req[origem] = resultado.data está no lugar. Volta com dúvidas, principalmente se alguma rota começar a responder 400 pra requisição que você considera válida.
