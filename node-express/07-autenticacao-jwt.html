Autenticação com JWT

Até agora, qualquer requisição podia matricular ou cancelar em nome de qualquer aluno — bastava passar um aluno_id diferente no body. Essa parte fecha essa brecha: o aluno faz login, recebe um token, e as rotas de matrícula passam a confiar só nesse token pra saber quem está pedindo.

1. O que vamos construir

Do que ficou planejado lá na parte 2 (seção "Autenticação, prevista, não agora"), o escopo é deliberadamente pequeno:

  • Aluno se autentica (login com email + senha) pra ver/cancelar as próprias matrículas.
  • Instrutor não precisa de login neste escopo — cadastro de instrutor continua sendo feito por quem administra o sistema, sem rota protegida.
  • Sem "papéis" complexos (admin, instrutor autenticado, etc.) — só autenticado vs. não autenticado, pras rotas que precisam identificar um aluno específico.

Concretamente, três coisas mudam: (1) cadastro de aluno passa a exigir uma senha, guardada com hash; (2) uma rota nova, POST /auth/login, troca email+senha por um token; (3) as rotas de matrícula passam a exigir esse token, e usam o aluno identificado nele — nunca mais um aluno_id vindo solto do body.

2. Autenticação vs. autorização

Dois conceitos parecidos, frequentemente confundidos, que esta parte implementa os dois:

ConceitoPergunta que respondeOnde aparece aqui
AutenticaçãoQuem é você?POST /auth/login — prova identidade com email + senha, recebe um token.
AutorizaçãoO que você pode fazer, sendo quem você é?Middleware de matrícula — aluno autenticado só pode cancelar/ver as próprias matrículas, não as de outro aluno.

Um sistema pode ter autenticação sem autorização refinada (todo mundo logado pode fazer tudo) ou, mais raro, autorização sem autenticação individual (uma chave de API compartilhada que libera um conjunto fixo de ações). Aqui os dois andam juntos: primeiro prova quem é (autenticação), depois cada rota decide se aquele "quem" pode fazer aquilo (autorização).

3. O que é JWT

JWT (JSON Web Token) é um formato de token auto-contido: carrega dentro dele mesmo a informação de quem é o usuário, sem o servidor precisar guardar nada em memória ou banco pra saber quem fez login. Um JWT é uma string com três partes separadas por ponto:

eyJhbGciOiJIUzI1NiJ9.eyJhbHVub19pZCI6M30.4f8a2c1e9b7d6a3f5e2c1b0a9d8e7f6c5b4a3d2e1f0

⬑ header ⬑ payload ⬑ signature
ParteConteúdoCodificação
HeaderQual algoritmo assinou o token (ex: HS256) e que é um JWT.Base64URL — só codificado, não é segredo.
PayloadAs claims: dados que você decide colocar. Aqui: aluno_id, mais iat (emitido em) e exp (expira em), adicionados automaticamente.Base64URL — também não é segredo, ver aviso abaixo.
SignatureUm HMAC do header + payload, calculado com um segredo que só o servidor conhece (JWT_SECRET).Garante integridade: se alguém alterar um byte do payload, a assinatura não bate mais.

JWT não é criptografado, só assinado. Header e payload são só Base64 — qualquer um pode rodar Buffer.from(parte, 'base64').toString() no Node (ou usar qualquer decodificador JWT online) e ler o conteúdo puro. A assinatura garante que ninguém alterou o payload sem o servidor perceber — não garante que o payload é secreto. Por isso: nunca coloque senha, dado sensível ou qualquer coisa que precise ficar confidencial dentro do payload de um JWT. Aqui, só vai aluno_id — um número que já é público (aparece nas URIs desde a parte 3 da trilha API REST).

Essa característica — o servidor não guarda nenhum estado de sessão, só verifica uma assinatura a cada requisição — conecta direto com a restrição stateless descrita na parte 1 da trilha API REST (tese de Fielding): cada requisição precisa conter tudo que o servidor precisa pra entendê-la, sem depender de contexto guardado de requisições anteriores. É o oposto do modelo clássico de sessão (cookie + tabela de sessões no servidor, que precisa ser consultada a cada requisição pra saber quem é o usuário). JWT é a forma mais comum de aplicar "stateless" à autenticação numa API REST — por isso a escolha aqui, e não sessões.

4. O fluxo completo, passo a passo

1

Login

Aluno manda POST /auth/login com email e senha.

2

Servidor confere e assina

Servidor busca o aluno pelo email, compara a senha recebida com o hash guardado. Se bater, gera um JWT assinado com JWT_SECRET e devolve no corpo da resposta.

3

Cliente guarda o token

Cabe ao cliente (front-end, app, ou o próprio curl nos nossos testes) guardar esse token em algum lugar — fora do escopo do backend, mas tipicamente localStorage ou memória da aplicação.

4

Cliente reenvia o token

Em toda requisição a uma rota protegida, o cliente manda o token no header Authorization: Bearer <token>.

5

Servidor verifica

Um middleware extrai o token do header, confere a assinatura e a validade (não expirou). Se ok, segue com a requisição sabendo quem é o aluno. Se não, 401 antes de chegar na rota.

5. Senhas: nunca em texto puro

Guardar a senha do jeito que o aluno digitou, direto na coluna do banco, é o tipo de erro que vira manchete quando o banco vaza. A prática correta é guardar um hash — o resultado de uma função que transforma a senha numa sequência que não dá pra reverter de volta pra senha original.

Vamos usar bcrypt, feito especificamente pra senhas (diferente de um hash genérico tipo SHA-256, que é rápido demais — bom pra checar integridade de arquivo, ruim pra senha, porque um atacante consegue testar bilhões de combinações por segundo). Duas características do bcrypt que importam:

  • Deliberadamente lento — tem um "custo" configurável (número de rounds) que controla quanto tempo de CPU cada hash consome. Lento pra você (uma vez por login) é lento também pro atacante testando senha por senha.
  • Salt embutido automaticamente — cada hash gerado é único, mesmo pra duas senhas idênticas. Isso impede um atacante de usar uma tabela pré-calculada (rainbow table) pra descobrir várias senhas de uma vez só.

Duas operações, nunca uma terceira: bcrypt.hash(senha, custo) no cadastro (gera o hash a guardar) e bcrypt.compare(senhaDigitada, hashGuardado) no login (confere se bate, sem nunca "desfazer" o hash — bcrypt é uma via de mão única, não existe bcrypt.decrypt).

6. Alterando o schema: coluna senha_hash

A tabela alunos (parte 3) não previa senha. Como a tabela já existe e já tem dados das partes anteriores, não dá pra simplesmente recriar o CREATE TABLE — usa ALTER TABLE pra adicionar a coluna:

ALTER TABLE alunos ADD COLUMN senha_hash VARCHAR(60);
Por que não NOT NULL aqui

Um hash bcrypt sempre tem 60 caracteres (por isso VARCHAR(60)), mas a coluna fica opcional por enquanto — se fosse NOT NULL, o ALTER TABLE falharia pros alunos que você já cadastrou nas partes anteriores (eles não têm valor pra essa coluna nova). Alunos antigos ficam com senha_hash igual a NULL e simplesmente não conseguem logar até você recriá-los (seção 15) ou fazer um UPDATE manual. Em produção isso seria resolvido com um fluxo de "defina sua senha" pros usuários existentes — fora do escopo de material de estudo.

Rode direto no psql (docker compose exec -T db psql -U postgres -d estudo, igual você já fez pra outras alterações) ou no DBeaver, do mesmo jeito que criou as tabelas na parte 3.

7. Instalando as dependências

npm install jsonwebtoken bcryptjs

bcryptjs, não bcrypt: mesma API, mas implementado em JavaScript puro, sem depender de compilar código nativo na instalação (o bcrypt original usa bindings em C++ via node-gyp, que às vezes dá dor de cabeça em máquinas sem as ferramentas de build certas). Pra estudo — e pra maioria dos projetos de porte pequeno/médio — a diferença de performance não justifica a complexidade extra de instalação.

Adicione o segredo do JWT no .env (já protegido pelo .gitignore desde a parte 1):

# .env
JWT_SECRET=cole_aqui_uma_string_aleatoria_grande

Pra gerar uma string aleatória forte, sem depender de nenhum site externo:

node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

O JWT_SECRET nunca deve estar escrito direto no código (só no .env, fora do controle de versão). Qualquer um que conheça esse segredo consegue forjar um token válido pra qualquer aluno_id — é literalmente a chave que garante que só o seu servidor emite tokens confiáveis.

8. Um lugar só pra hash: services/senhaService.js

bcrypt.hash e bcrypt.compare não têm nada de específico de aluno — são operações genéricas de senha, que qualquer entidade futura com login (um instrutor, por exemplo) vai precisar chamar do mesmo jeito. Em vez de importar bcryptjs direto dentro de cada arquivo de rota, isola numa camada nova, services/ — o mesmo nome de camada que a parte 5 já tinha cogitado e decidido adiar, só que agora com um caso concreto pra justificar:

// services/senhaService.js
const bcrypt = require('bcryptjs');

async function hashSenha(senha) {
  return bcrypt.hash(senha, 10);
}

async function compararSenha(senha, hash) {
  return bcrypt.compare(senha, hash);
}

module.exports = { hashSenha, compararSenha };
Por que isso é diferente de "criar camada de service agora"

Não é uma camada de negócio nova pro projeto inteiro — é só duas funções genéricas (hash e comparação de senha) que não pertencem a repositories/ (não é SQL) nem deveriam ficar repetidas dentro de cada routes/*.js que precisar de senha no futuro. Continua sem existir alunosService.js, authService.js ou qualquer coisa que já assuma como vai funcionar o login de outra entidade — isso fica pra quando (se) esse requisito aparecer de verdade. senhaService.js não sabe nem precisa saber o que é um "aluno".

O 10 passado pra bcrypt.hash é o custo (rounds) mencionado na seção 5 — fica escondido dentro do service, quem chama hashSenha não precisa saber (nem lembrar) desse detalhe.

9. Cadastro de aluno agora exige senha

POST /alunos (parte 4) passa a exigir senha no body, e guarda o hash — nunca a senha recebida:

// routes/alunos.js
const { hashSenha } = require('../services/senhaService');

router.post('/', async (req, res) => {
  const { nome, email, data_nascimento, senha } = req.body;

  if (!nome || !email || !data_nascimento || !senha) {
    return res.status(400).json({
      erro: 'nome, email, data_nascimento e senha são obrigatórios',
    });
  }

  const senha_hash = await hashSenha(senha);

  const alunoCriado = await alunosRepository.criar({
    nome,
    email,
    data_nascimento,
    senha_hash,
  });

  res.status(201).location(`/alunos/${alunoCriado.id}`).json(alunoCriado);
});
Por que a resposta não devolve senha_hash

alunoCriado vem do RETURNING * do repository, então tecnicamente inclui senha_hash. Deixar isso vazar na resposta JSON — mesmo sendo um hash, não a senha original — é prática ruim: dá material de sobra pra um atacante tentar quebrar offline. A repository fica igual (retorna a linha inteira, é a forma mais simples), mas voltaremos nisso na seção 14 pra remover o campo antes de responder.

10. Repository: buscarPorEmail

Login busca o aluno pelo email (não tem outro jeito de saber o id antes de autenticar). Adiciona em alunosRepository.js:

// repositories/alunosRepository.js
async function buscarPorEmail(email) {
  const query = 'SELECT * FROM alunos WHERE email = $1';
  const resultado = await pool.query(query, [email]);

  return resultado.rows[0];
}

E o criar passa a receber e gravar senha_hash:

// repositories/alunosRepository.js
async function criar({ nome, email, data_nascimento, senha_hash }) {
  const query =
    'INSERT INTO alunos (nome, email, data_nascimento, senha_hash) VALUES ($1, $2, $3, $4) RETURNING *';
  const resultado = await pool.query(query, [nome, email, data_nascimento, senha_hash]);

  return resultado.rows[0];
}

11. Rota de login: POST /auth/login

Arquivo novo, routes/auth.js:

// routes/auth.js
const express = require('express');
const jwt = require('jsonwebtoken');
const { compararSenha } = require('../services/senhaService');
const alunosRepository = require('../repositories/alunosRepository');

const router = express.Router();

router.post('/login', async (req, res) => {
  const { email, senha } = req.body;

  if (!email || !senha) {
    return res.status(400).json({ erro: 'email e senha são obrigatórios' });
  }

  const aluno = await alunosRepository.buscarPorEmail(email);
  if (!aluno) {
    return res.status(401).json({ erro: 'email ou senha inválidos' });
  }

  const senhaValida = await compararSenha(senha, aluno.senha_hash);
  if (!senhaValida) {
    return res.status(401).json({ erro: 'email ou senha inválidos' });
  }

  const token = jwt.sign({ aluno_id: aluno.id }, process.env.JWT_SECRET, {
    expiresIn: '2h',
  });

  res.json({ token });
});

module.exports = router;
Por que a mesma mensagem de erro nos dois casos

"Email não existe" e "senha errada" devolvem o mesmo 401 com a mesma mensagem genérica. De propósito: se as mensagens fossem diferentes ("email não encontrado" vs. "senha incorreta"), alguém tentando invadir contas conseguiria descobrir, testando emails em sequência, quais estão cadastrados no sistema (enumeração de usuários) — mesmo sem nunca acertar a senha. Mensagem genérica fecha esse vazamento de informação.

jwt.sign(payload, segredo, opções) monta e assina o token. expiresIn: '2h' adiciona automaticamente a claim exp no payload — depois de 2 horas, jwt.verify (próxima seção) passa a rejeitar esse token mesmo com assinatura válida, obrigando novo login. Sem expiração, um token vazado uma vez seria válido pra sempre.

12. Middleware de autenticação

Arquivo novo, middlewares/autenticar.js — um middleware "de guarda", que roda antes do handler da rota e decide se deixa passar:

// middlewares/autenticar.js
const jwt = require('jsonwebtoken');

function autenticar(req, res, next) {
  const authHeader = req.headers.authorization;

  if (!authHeader) {
    return res.status(401).json({ erro: 'Token não enviado' });
  }

  const [tipo, token] = authHeader.split(' ');

  if (tipo !== 'Bearer' || !token) {
    return res.status(401).json({ erro: 'Formato de token inválido' });
  }

  try {
    const payload = jwt.verify(token, process.env.JWT_SECRET);
    req.alunoId = payload.aluno_id;
    next();
  } catch {
    return res.status(401).json({ erro: 'Token inválido ou expirado' });
  }
}

module.exports = autenticar;

Authorization: Bearer <token> é a convenção padrão (RFC 6750) pra mandar esse tipo de token — "Bearer" (portador) indica que quem carrega o token tem acesso, sem verificação extra de identidade além da assinatura. authHeader.split(' ') separa a palavra Bearer do token em si.

jwt.verify faz duas coisas de uma vez: confere se a assinatura bate com o JWT_SECRET (ninguém adulterou o payload) e se o token não expirou. Qualquer uma das duas falhando, ele lança uma exceção — por isso o try/catch, diferente da maioria dos middlewares desta trilha que só retornam valores.

Por que catch sem parênteses aqui

Repare que é catch {, não catch (err) { como no POST /aulas/:id/matriculas da parte 6. Lá, o erro era usado — precisávamos ler err.code pra distinguir a violação de unicidade (23505) de qualquer outro problema. Aqui, não interessa qual das falhas aconteceu: assinatura errada, token adulterado ou prazo vencido, a resposta é a mesma 401. Declarar uma variável que ninguém lê é ruído, e o ESLint configurado na parte 4 reclama disso ('err' is defined but never used). O JavaScript permite omitir o parâmetro inteiro desde 2019 — chama-se optional catch binding, e diz explicitamente "sei que deu erro, não preciso saber qual".

Detalhe que pega muita gente: renomear pra _err não silencia o aviso. O argsIgnorePattern: "^_" que configuramos vale só pra argumentos de função — parâmetro de catch tem opção própria (caughtErrorsIgnorePattern), que não configuramos. Omitir de vez resolve sem mexer em configuração nenhuma.

Se tudo bater, o middleware guarda o aluno_id do payload em req.alunoId e chama next() — a rota protegida usa req.alunoId, nunca mais precisa (nem deve) confiar em algo vindo do body ou da URI pra saber quem é o aluno autenticado.

13. Protegendo as rotas de matrícula

Um middleware só roda numa rota se for passado como argumento dela. Adiciona autenticar nas três rotas que precisam saber quem é o aluno:

// routes/aulas.js
const autenticar = require('../middlewares/autenticar');

router.post('/:id/matriculas', autenticar, async (req, res, next) => {
  const aula = await aulasRepository.buscarPorId(req.params.id);
  if (!aula) {
    return res.status(404).json({ erro: 'Aula não encontrada' });
  }

  const totalConfirmadas = await matriculasRepository.contarConfirmadas(aula.id);
  if (totalConfirmadas >= aula.capacidade_maxima) {
    return res.status(409).json({ erro: 'Aula sem vagas disponíveis' });
  }

  try {
    const matriculaCriada = await matriculasRepository.criar({
      aluno_id: req.alunoId,
      aula_id: aula.id,
    });

    res
      .status(201)
      .location(`/aulas/${aula.id}/matriculas/${matriculaCriada.id}`)
      .json(matriculaCriada);
  } catch (err) {
    if (err.code === '23505') {
      return res.status(409).json({ erro: 'Aluno já matriculado nesta aula' });
    }
    next(err);
  }
});
O que sumiu desta rota

Repare que a checagem alunosRepository.buscarPorId(aluno_id) → 422 (parte 6, seção 7) não existe mais aqui. Antes, aluno_id vinha do body — qualquer número, precisava validar se existia. Agora aluno_id vem de req.alunoId, que só existe porque o middleware já validou um token assinado pelo próprio servidor pra um aluno que existia no momento do login. A validação de "existência do aluno" foi substituída por uma garantia mais forte: autenticação.

Cancelamento (PATCH .../matriculas/:matriculaId) ganha uma checagem de autorização nova — não basta a matrícula existir, ela precisa pertencer ao aluno autenticado:

// routes/aulas.js
router.patch('/:id/matriculas/:matriculaId', autenticar, async (req, res) => {
  const { status } = req.body;

  if (status !== 'cancelada') {
    return res.status(400).json({ erro: "status precisa ser 'cancelada'" });
  }

  const matricula = await matriculasRepository.buscarPorIdEAula(
    req.params.matriculaId,
    req.params.id,
  );

  if (!matricula) {
    return res.status(404).json({ erro: 'Matrícula não encontrada' });
  }

  if (matricula.aluno_id !== req.alunoId) {
    return res.status(403).json({
      erro: 'Você não pode cancelar a matrícula de outro aluno',
    });
  }

  const matriculaCancelada = await matriculasRepository.cancelar(matricula.id);
  res.json(matriculaCancelada);
});
404 vs. 403, e por que essa ordem

Primeiro confere se a matrícula existe (404), só depois se pertence a quem está pedindo (403). Fazer na ordem inversa vazaria informação: um 403 pra um matriculaId que nem existe confirmaria pro atacante que aquele ID é válido (só não é dele). Confirmar existência antes de checar posse é o mesmo raciocínio de "não vazar informação" da seção 11 — só que aqui é sobre IDs, não sobre emails.

E a consulta "em que aulas o aluno X está matriculado" (routes/alunos.js) também exige o próprio aluno — req.params.id (da URI) precisa bater com req.alunoId (do token):

// routes/alunos.js
const autenticar = require('../middlewares/autenticar');

router.get('/:id/matriculas', autenticar, async (req, res) => {
  if (Number(req.params.id) !== req.alunoId) {
    return res.status(403).json({
      erro: 'Você não pode ver as matrículas de outro aluno',
    });
  }

  const aluno = await alunosRepository.buscarPorId(req.params.id);
  if (!aluno) {
    return res.status(404).json({ erro: 'Aluno não encontrado' });
  }

  const matriculas = await matriculasRepository.listarPorAluno(req.params.id);
  res.json(matriculas);
});

req.params.id é sempre string (tudo que vem da URI é texto). req.alunoId é number (veio do payload do JWT, que preserva o tipo original do jwt.sign). Comparar com !== sem converter (Number(req.params.id) !== req.alunoId) faria "3" !== 3 ser sempre true — a checagem de autorização bloquearia até o dono da própria matrícula. Erro fácil de escrever, fácil de não notar em teste manual se você sempre testar só com o próprio ID.

Já GET /aulas/:id/matriculas (lista quem está matriculado numa aula, parte 6 seção 9) fica sem proteção por enquanto — não identifica um aluno específico fazendo a pergunta, é mais uma visão de "lista de chamada" da aula, que neste escopo não tem dono (não existe papel de instrutor autenticado ou admin ainda, seção 1). Registrado aqui como decisão consciente, não esquecimento — do mesmo jeito que a condição de corrida da Regra 1 (parte 6) e o soft-delete de instrutor ficaram documentados como próximos passos em vez de resolvidos "de qualquer jeito".

    return res.status(401).json({ erro: 'Token inválido ou expirado' });
  }
}

module.exports = autenticar;

    'INSERT INTO alunos (nome, email, data_nascimento, senha_hash) VALUES ($1, $2, $3, $4) RETURNING *';
  const resultado = await pool.query(query, [nome, email, data_nascimento, senha_hash]);

}

  return resultado.rows[0];

Por que listar não usa SELECT *

GET /alunos devolve o resultado de listar() pra qualquer um que chamar a rota — nenhuma desestruturação depois, como fizemos no criar da seção 9. Se a query fosse SELECT *, o senha_hash (hash bcrypt de verdade, uma vez que existirem alunos cadastrados com senha) apareceria na lista pública. Listar só as colunas necessárias na própria query resolve na raiz — o hash nem sai do banco, não depende de lembrar de filtrar depois em cada lugar que usa esse resultado. buscarPorId e buscarPorEmail continuam com SELECT * de propósito: o primeiro nunca é devolvido direto numa resposta (só usado pra checar existência), o segundo precisa do senha_hash pra comparar no login (seção 11).

routes/alunos.js — completo, com senha no cadastro, senha_hash removido da resposta (ver seção 9), e a rota de matrículas protegida:

// routes/alunos.js — arquivo completo
const express = require('express');
const { hashSenha } = require('../services/senhaService');

const alunosRepository = require('../repositories/alunosRepository');
const matriculasRepository = require('../repositories/matriculasRepository');
const autenticar = require('../middlewares/autenticar');

const router = express.Router();

router.get('/', async (req, res) => {
  const alunos = await alunosRepository.listar();
  res.json(alunos);
});

router.post('/', async (req, res) => {
  const { nome, email, data_nascimento, senha } = req.body;

  if (!nome || !email || !data_nascimento || !senha) {
    return res.status(400).json({
      erro: 'nome, email, data_nascimento e senha são obrigatórios',
    });
  }

  const senha_hash = await hashSenha(senha);

  const alunoCriado = await alunosRepository.criar({
    nome,
    email,
    data_nascimento,
    senha_hash,
  });

  const { senha_hash: _senhaHash, ...alunoSemSenha } = alunoCriado;

  res.status(201).location(`/alunos/${alunoCriado.id}`).json(alunoSemSenha);
});

router.get('/:id/matriculas', autenticar, async (req, res) => {
  if (Number(req.params.id) !== req.alunoId) {
    return res.status(403).json({
      erro: 'Você não pode ver as matrículas de outro aluno',
    });
  }

  const aluno = await alunosRepository.buscarPorId(req.params.id);
  if (!aluno) {
    return res.status(404).json({ erro: 'Aluno não encontrado' });
  }

  const matriculas = await matriculasRepository.listarPorAluno(req.params.id);
  res.json(matriculas);
});

module.exports = router;
O truque do _senhaHash

const { senha_hash: _senhaHash, ...alunoSemSenha } = alunoCriado; usa desestruturação pra separar senha_hash do resto do objeto — alunoSemSenha fica com todo o resto (id, nome, email...), sem o hash. A variável _senhaHash é descartada de propósito (o prefixo _ já é reconhecido pelo ESLint configurado na parte 4/5, mesmo padrão usado pro _next do middleware de erro).

16. Erros comuns

  1. Esquecer o prefixo Bearer no header — mandar só o token cru faz authHeader.split(' ') devolver [token, undefined], cai no 400/401 de "Formato de token inválido".
  2. Comparar req.params.id com req.alunoId sem Number() — string nunca é === number em JS; checagem de autorização bloqueia até o dono correto (ver aviso da seção 13).
  3. Continuar confiando em aluno_id do body nas rotas de matrícula — reabre exatamente a brecha de segurança que esta parte veio fechar. Depois do autenticar, a única fonte confiável de "quem é o aluno" é req.alunoId.
  4. Esquecer await em bcrypt.hash/bcrypt.compare — as duas são funções assíncronas; sem await, você grava/compara uma Promise em vez do valor real (bug silencioso: nenhum erro é lançado, só nada nunca bate).
  5. JWT_SECRET ausente do .env — jwt.sign/jwt.verify recebem undefined como segredo; funciona "por acidente" (token válido contra undefined), mas qualquer um sem o segredo real também consegue forjar tokens. Confira com console.log(process.env.JWT_SECRET) se desconfiar.
  6. Achar que o payload do JWT é secreto — não é (seção 3). Não é bug de código, é erro de modelo mental que leva a colocar dado sensível onde não devia.

17. O que vem a seguir

Com login, token e autorização básica funcionando, o núcleo do projeto Studio Fit definido na parte 2 está completo — as 4 entidades, as 4 regras de negócio, e a proteção das rotas de matrícula. Itens que ficam registrados como possíveis próximos passos, sem compromisso de ordem:

  1. Refresh token: hoje o aluno precisa logar de novo a cada 2 horas; um fluxo de refresh evitaria isso sem aumentar a validade do token original.
  2. Testes automatizados: até aqui, todo teste foi manual via curl — uma suíte automatizada (ex: Jest + supertest) passaria a pegar regressões sem depender de reproduzir o fluxo na mão.
  3. Deploy em produção: rodar essa API fora da máquina local — variáveis de ambiente de produção, banco gerenciado, HTTPS.

Quando terminar de testar o fluxo (cadastro com senha, login, matricular com token, tentar sem token, tentar mexer na matrícula de outro aluno), volta com dúvidas — principalmente se algum 401/403 aparecer onde você não esperava, ou se ficar em dúvida sobre por que o payload do JWT não é considerado seguro.
