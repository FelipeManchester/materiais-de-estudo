Projeto Studio Fit — Trilha Node + Express — Parte 3

Schema do banco de dados

A parte 2 definiu as entidades do projeto (Aluno, Instrutor, Aula, Matrícula) e como se relacionam. Agora essas entidades viram tabelas de verdade no Postgres, com os tipos de dado e as restrições certas — antes de qualquer linha de Express ser escrita.

1. Por que o schema vem antes do código

Um endpoint como GET /alunos precisa consultar uma tabela alunos que já existe. Sem o schema criado, não tem o que consultar — o código do Express ficaria tentando conversar com uma tabela inexistente. Por isso a ordem: modelo do negócio (parte 2) → schema no banco (aqui) → código que usa esse schema (próxima parte).

Vale também entender uma distinção: o schema é a estrutura (quais tabelas, quais colunas, quais regras o banco garante sozinho). Os dados são o conteúdo que vai entrar nessas tabelas depois, através da API. Este documento cria só a estrutura — tabelas vão nascer vazias.

2. Conceitos de SQL que vamos usar

Antes do script completo, vale entender cada peça isoladamente — é isso que faz o SQL parecer menos "mágico" depois.

CREATE TABLE

Comando que cria uma tabela nova, declarando cada coluna com seu tipo:

CREATE TABLE nome_da_tabela (
  coluna1 TIPO restrições,
  coluna2 TIPO restrições
);

Tipos de dado principais que vamos usar

TipoGuarda
SERIALNúmero inteiro que o próprio banco gera automaticamente, incrementando a cada linha nova (1, 2, 3...). Uso clássico: chave primária.
VARCHAR(n)Texto curto, com limite máximo de n caracteres (ex: VARCHAR(120) pra nome).
INTEGERNúmero inteiro comum (sem geração automática).
DATESó data (ano-mês-dia), sem hora.
TIMESó hora (hora:minuto:segundo), sem data.
TIMESTAMPData e hora juntas — usado pra "quando esse registro foi criado".

PRIMARY KEY — chave primária

Marca a coluna que identifica unicamente cada linha da tabela — equivalente ao id que você já vem usando nas URIs desde a parte 3 da trilha API REST (/alunos/42 — esse 42 é a chave primária do aluno).

NOT NULL

Impede que a coluna fique vazia. Sem isso, o Postgres aceita gravar a linha mesmo faltando aquele dado — e "esquecer" de validar isso no código vira um bug silencioso. Colocar NOT NULL no schema é uma segunda linha de defesa, além da validação de forma que a API vai fazer (parte 5 da trilha API REST).

UNIQUE

Garante que nenhuma outra linha da tabela pode repetir aquele valor. Vamos usar em email do aluno — duas contas com o mesmo e-mail não deveriam existir.

FOREIGN KEY / REFERENCES — chave estrangeira

É como o banco representa o relacionamento entre tabelas (seção 4 da parte 2 do projeto). Uma coluna que guarda o id de uma linha de outra tabela, com uma trava: o banco não deixa você gravar um instrutor_id que não existe na tabela instrutores.

instrutor_id INTEGER NOT NULL REFERENCES instrutores(id)

E o que acontece se alguém tentar apagar um instrutor que já tem aulas vinculadas? É isso que a cláusula ON DELETE decide:

OpçãoComportamento
ON DELETE CASCADEApaga também todas as linhas dependentes automaticamente
ON DELETE RESTRICTBloqueia a exclusão enquanto existir algo dependente — erro, não deixa apagar

Vamos usar as duas, com intenção diferente em cada relação — detalhe explicado tabela por tabela adiante.

CHECK

Restrição customizada — uma condição que precisa ser verdadeira pra linha ser aceita. Exemplo: capacidade de uma aula não faz sentido ser zero ou negativa:

capacidade_maxima INTEGER NOT NULL CHECK (capacidade_maxima > 0)

DEFAULT

Valor usado automaticamente quando a coluna não é informada. Vamos usar pra data de criação (NOW(), a hora atual do banco) e pro status inicial de uma matrícula ('confirmada').

3. Ordem de criação importa

Uma FOREIGN KEY só pode apontar pra uma tabela que já existe. Como aulas referencia instrutores, e matriculas referencia tanto alunos quanto aulas, a ordem de criação segue a dependência:

1. instrutores   (não depende de ninguém)
2. alunos        (não depende de ninguém)
3. aulas         (depende de instrutores)
4. matriculas    (depende de alunos e aulas)

4. Tabela instrutores

instrutores

CREATE TABLE IF NOT EXISTS instrutores (
  id SERIAL PRIMARY KEY,
  nome VARCHAR(120) NOT NULL,
  especialidade VARCHAR(80) NOT NULL
);

Tabela mais simples do projeto — nenhuma chave estrangeira, nenhuma regra especial. id gerado automaticamente pelo SERIAL.

5. Tabela alunos

alunos

CREATE TABLE IF NOT EXISTS alunos (
  id SERIAL PRIMARY KEY,
  nome VARCHAR(120) NOT NULL,
  email VARCHAR(160) NOT NULL UNIQUE,
  data_nascimento DATE NOT NULL,
  criado_em TIMESTAMP NOT NULL DEFAULT NOW()
);

email UNIQUE aplica a regra "não pode ter duas contas com o mesmo e-mail" direto no banco — mesmo que a validação de forma da API (parte 5) falhe por algum bug, o banco recusa a segunda linha duplicada. Duas camadas de defesa pro mesmo problema, uma nunca substitui a outra.

6. Tabela aulas

aulas

CREATE TABLE IF NOT EXISTS aulas (
  id SERIAL PRIMARY KEY,
  nome VARCHAR(120) NOT NULL,
  instrutor_id INTEGER NOT NULL REFERENCES instrutores(id) ON DELETE RESTRICT,
  dia_semana VARCHAR(10) NOT NULL
    CHECK (dia_semana IN ('segunda','terca','quarta','quinta','sexta','sabado','domingo')),
  hora_inicio TIME NOT NULL,
  duracao_minutos INTEGER NOT NULL CHECK (duracao_minutos > 0),
  capacidade_maxima INTEGER NOT NULL CHECK (capacidade_maxima > 0)
);
Por que ON DELETE RESTRICT aqui

Se alguém tentar apagar um instrutor que ainda dá aulas, o banco recusa a exclusão. Decisão intencional: apagar o instrutor não deveria fazer as aulas dele desaparecerem silenciosamente (isso afetaria alunos matriculados sem aviso). Forçar um erro aqui obriga quem estiver operando o sistema a decidir explicitamente o que fazer com as aulas primeiro — reatribuir a outro instrutor, cancelar, etc. Isso é uma decisão de negócio sendo expressa como restrição de banco.

O CHECK em dia_semana funciona como uma lista fixa de valores permitidos — o banco recusa qualquer string que não esteja nessa lista, similar a um enum em outras linguagens (Postgres tem um tipo ENUM nativo também, mas CHECK com lista é mais simples de ler e alterar pra quem está começando).

7. Tabela matriculas

matriculas

CREATE TABLE IF NOT EXISTS matriculas (
  id SERIAL PRIMARY KEY,
  aluno_id INTEGER NOT NULL REFERENCES alunos(id) ON DELETE CASCADE,
  aula_id INTEGER NOT NULL REFERENCES aulas(id) ON DELETE CASCADE,
  status VARCHAR(10) NOT NULL DEFAULT 'confirmada'
    CHECK (status IN ('confirmada','cancelada')),
  criado_em TIMESTAMP NOT NULL DEFAULT NOW()
);
Por que ON DELETE CASCADE aqui, diferente de aulas

Uma matrícula não tem sentido nenhum sem o aluno ou a aula que ela liga — ao contrário do instrutor (que continua existindo/fazendo sentido mesmo se uma aula for removida), uma matrícula órfã é só lixo no banco. Por isso aqui a exclusão em cascata é o comportamento certo: apagar um aluno remove as matrículas dele junto, sem precisar de um passo manual extra.

status com DEFAULT 'confirmada': toda matrícula nasce confirmada; vira 'cancelada' só através de um PATCH explícito (Regra 4 do projeto, parte 2) — nunca apagada de verdade, o que preserva o histórico.

8. A Regra 2 e o índice único parcial

A Regra 2 do projeto diz: "um aluno não pode ter duas matrículas confirmada na mesma aula ao mesmo tempo". Primeira tentação: um UNIQUE simples nas duas colunas:

-- NÃO faz isso:
UNIQUE (aluno_id, aula_id)

Problema: isso bloquearia até o cenário válido de "aluno se matriculou, cancelou, e quer se matricular de novo na mesma aula depois". Com UNIQUE simples, a segunda matrícula (mesmo sendo uma tentativa legítima, depois do cancelamento) seria rejeitada só por já existir uma linha antiga com esse par aluno_id/aula_id — mesmo essa linha antiga estando cancelada.

A solução é um índice único parcial (partial unique index) — um UNIQUE que só se aplica às linhas que passam numa condição WHERE:

CREATE UNIQUE INDEX matriculas_aluno_aula_confirmada_idx
  ON matriculas (aluno_id, aula_id)
  WHERE status = 'confirmada';

Com isso, o banco garante unicidade só entre as linhas confirmada. Duas linhas cancelada com o mesmo par podem coexistir sem problema (histórico de tentativas antigas), mas nunca duas confirmada ao mesmo tempo. A Regra 2 inteira, garantida pelo banco, sem precisar de uma consulta extra no código pra checar duplicidade antes de inserir.

Isso é diferente das Regras 1 e 3 (capacidade máxima da aula, conflito de agenda do instrutor) — ver seção 9. A diferença é o que torna esse índice parcial um caso interessante de estudar: nem toda regra de negócio vira restrição de banco tão elegante quanto essa.

9. O que o banco não garante sozinho

Vale deixar explícito, pra não achar que o schema resolve tudo:

Regra (parte 2 do projeto)O banco garante sozinho?Onde vai ser aplicada
Regra 1 — Capacidade máxima da aulaNãoCódigo da API: contar matrículas confirmada da aula antes de inserir uma nova
Regra 2 — Matrícula duplicadaSimÍndice único parcial, seção 8
Regra 3 — Conflito de agenda do instrutorNãoCódigo da API: comparar dia_semana/hora_inicio/duracao_minutos das aulas do mesmo instrutor
Regra 4 — Cancelamento não apaga registroParcialmenteCHECK garante que status só aceita os dois valores válidos; a lógica de "usar PATCH, nunca DELETE" é responsabilidade do código da API

Regras 1 e 3 exigem contar ou comparar várias linhas — coisa que dá pra fazer em SQL puro (com sub-consultas ou triggers), mas nesse estágio de aprendizado fica mais claro implementar na camada de lógica de negócio (parte 5 da trilha API REST, seção 2) do próximo material. O schema faz a parte que faz sentido pra ele: estrutura, tipos, e as restrições simples o bastante pra não precisar de lógica de aplicação.

10. Script completo

Junta tudo, na ordem certa, num arquivo db/schema.sql dentro da pasta do projeto (a mesma minha-api/ do guia de ambiente):

-- db/schema.sql

CREATE TABLE IF NOT EXISTS instrutores (
  id SERIAL PRIMARY KEY,
  nome VARCHAR(120) NOT NULL,
  especialidade VARCHAR(80) NOT NULL
);

CREATE TABLE IF NOT EXISTS alunos (
  id SERIAL PRIMARY KEY,
  nome VARCHAR(120) NOT NULL,
  email VARCHAR(160) NOT NULL UNIQUE,
  data_nascimento DATE NOT NULL,
  criado_em TIMESTAMP NOT NULL DEFAULT NOW()
);

CREATE TABLE IF NOT EXISTS aulas (
  id SERIAL PRIMARY KEY,
  nome VARCHAR(120) NOT NULL,
  instrutor_id INTEGER NOT NULL REFERENCES instrutores(id) ON DELETE RESTRICT,
  dia_semana VARCHAR(10) NOT NULL
    CHECK (dia_semana IN ('segunda','terca','quarta','quinta','sexta','sabado','domingo')),
  hora_inicio TIME NOT NULL,
  duracao_minutos INTEGER NOT NULL CHECK (duracao_minutos > 0),
  capacidade_maxima INTEGER NOT NULL CHECK (capacidade_maxima > 0)
);

CREATE TABLE IF NOT EXISTS matriculas (
  id SERIAL PRIMARY KEY,
  aluno_id INTEGER NOT NULL REFERENCES alunos(id) ON DELETE CASCADE,
  aula_id INTEGER NOT NULL REFERENCES aulas(id) ON DELETE CASCADE,
  status VARCHAR(10) NOT NULL DEFAULT 'confirmada'
    CHECK (status IN ('confirmada','cancelada')),
  criado_em TIMESTAMP NOT NULL DEFAULT NOW()
);

CREATE UNIQUE INDEX IF NOT EXISTS matriculas_aluno_aula_confirmada_idx
  ON matriculas (aluno_id, aula_id)
  WHERE status = 'confirmada';

O IF NOT EXISTS em cada CREATE torna o script seguro de rodar mais de uma vez — se a tabela já existir, o comando é ignorado em vez de dar erro. Útil enquanto o schema ainda está em desenvolvimento e você roda o script várias vezes testando ajustes.

11. Executando o script

Com o Postgres já no ar (docker compose up -d, do guia de ambiente), duas formas de rodar:

Via terminal, direto no container

docker compose exec -T db psql -U postgres -d estudo < db/schema.sql

O -T desativa alocação de terminal interativo — necessário porque estamos redirecionando um arquivo (<) pra dentro do comando, não digitando na hora.

Via DBeaver

Abre a conexão estudo configurada anteriormente, cria um novo editor SQL (SQL Editor → New SQL Script), cola o conteúdo do schema.sql, e executa o script inteiro (Execute SQL Script, ou Alt+X) — diferente de "executar só a linha atual" (Ctrl+Enter), que rodaria apenas o primeiro comando.

12. Verificando o resultado

Pelo terminal:

docker compose exec db psql -U postgres -d estudo

-- dentro do psql:
\dt              -- lista todas as tabelas
\d alunos        -- mostra colunas, tipos e restrições da tabela alunos
\d matriculas    -- mostra colunas, tipos, restrições E os índices (inclusive o parcial)

Pelo DBeaver: atualiza a conexão (botão de refresh ou F5 na árvore lateral), expande estudo → Schemas → public → Tables — as 4 tabelas devem aparecer, todas vazias.

13. Erros comuns

  1. "relation does not exist" ao criar aulas — normalmente significa que instrutores ainda não existe. Confirma a ordem de execução (seção 3).
  2. Rodar o script mais de uma vez sem IF NOT EXISTS — dá erro "relation already exists" na segunda vez. O script deste guia já vem protegido, mas vale entender o motivo se aparecer em outro contexto.
  3. Confundir UNIQUE simples com o índice único parcial — ver seção 8. Sintoma do erro: sistema recusa uma matrícula legítima depois de um cancelamento anterior.
  4. Esquecer NOT NULL num campo obrigatório — a tabela aceita a linha mesmo faltando dado, e o problema só aparece bem depois, quando o código tentar usar aquele campo e encontrar null onde não esperava.

14. O que vem a seguir

Com as 4 tabelas criadas e verificadas, o próximo material sai do SQL puro e volta pro Express — a primeira conexão de verdade entre código e banco.

  1. Primeiro endpoint funcional: servidor Express de pé, conexão com Postgres via pg, implementando GET /alunos e POST /alunos contra as tabelas criadas aqui.
  2. CRUD completo das demais entidades, aplicando as Regras 1 e 3 no código (a parte que o schema não resolveu sozinho, seção 9).

Quando terminar de rodar e verificar o script, volte com dúvidas — principalmente se algum CHECK ou REFERENCES se comportar diferente do esperado ao testar inserções manuais no psql ou DBeaver antes de ir pro código.
