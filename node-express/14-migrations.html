Migrations

Desde a parte 7, toda alteração de banco foi digitada à mão no psql, com o db/schema.sql atualizado depois — quando dava. Esta parte mostra por que esse arranjo já falhou no seu projeto (com prova), e troca ele por arquivos versionados que rodam sozinhos.

1. O arquivo que mente

O db/schema.sql nasceu na parte 3 como a descrição do banco. Desde então, três partes mandaram alterar tabelas direto no psql:

ParteAlteração
7ALTER TABLE alunos ADD COLUMN senha_hash
8CREATE TABLE refresh_tokens + índice
10ALTER TABLE instrutores (três colunas), ALTER TABLE refresh_tokens (nullable, instrutor_id, CHECK)

Em cada uma, o material pediu para refletir a mudança no schema.sql logo depois. Rode este comando e compare com o que está no arquivo:

docker compose exec -T db psql -U postgres -d estudo -c \
  "SELECT column_name FROM information_schema.columns
   WHERE table_name = 'instrutores' ORDER BY ordinal_position;"

db/schema.sql diz

CREATE TABLE instrutores (
  id SERIAL PRIMARY KEY,
  nome VARCHAR(120) NOT NULL,
  especialidade VARCHAR(80) NOT NULL
);

O banco tem

id
nome
especialidade
email        ← parte 10
senha_hash   ← parte 10
papel        ← parte 10

Se o seu projeto estiver assim, não é descuido isolado — é o resultado previsível do processo. Manter dois lugares sincronizados na lembrança sempre falha, e falha em silêncio: o banco da sua máquina funciona, os testes passam, e o arquivo versionado — o único que outra pessoa vai ler — descreve um banco que não existe mais.

A consequência aparece quando alguém clona o projeto e monta o banco pelo schema.sql: cria a tabela instrutores sem email nem senha_hash, e a rota POST /auth/instrutores/login quebra. O erro vai apontar pra parte 10, escrita semanas atrás, e não pro arquivo desatualizado.

Existe outro problema, menos visível: não há como saber o que já foi aplicado. Você lembra de ter rodado o ALTER TABLE da parte 10 no banco de desenvolvimento. E no banco de teste? E no de produção, quando existir? A única forma de responder é ir olhar cada um.

2. O que é uma migration

Uma migration é um arquivo que descreve uma alteração no banco, com nome que define a ordem, guardado no repositório junto do código. Uma ferramenta lê esses arquivos, compara com uma tabela de controle dentro do próprio banco, e aplica só o que falta.

schema.sql na mãoMigrations
O que descreveO estado final desejado.A sequência de mudanças que leva até ele.
Quem aplicaVocê, no psql, lembrando de fazer.Um comando, que sabe o que já rodou.
Banco novoRoda o arquivo inteiro.Roda tudo em ordem.
Banco existenteNão serve — recriar apagaria dados.Roda só o que falta.
HistóricoSó o git log do arquivo.Cada mudança é um arquivo datado, com o motivo no nome.
ReversãoManual.Um down por migration.

A diferença que resolve o problema da seção 1 é a linha "banco existente". CREATE TABLE IF NOT EXISTS não ajuda quando a tabela existe mas está desatualizada — e é exatamente esse o caso toda vez que você adiciona uma coluna.

4. Instalando e configurando

Rodar na raiz do projeto. Aqui é --save-dev: a ferramenta roda no seu terminal e no deploy, nunca dentro da API:

npm install --save-dev node-pg-migrate

Alterar package.json — na seção "scripts", junto do dev e do lint que já existem:

"scripts": {
  "dev": "nodemon index.js",
  "lint": "eslint .",
  "migrate": "node-pg-migrate",
  "migrate:up": "node-pg-migrate up",
  "migrate:down": "node-pg-migrate down"
}

A ferramenta lê a variável de ambiente DATABASE_URL — a mesma que o db/pool.js usa desde a parte 4, já no seu .env. Só falta carregá-la: o index.js chama require('dotenv').config(), mas o comando de migration não passa pelo index.js.

Criar .node-pg-migraterc — arquivo de configuração na raiz, em JSON. Ele diz onde ficam as migrations e manda carregar o .env:

{
  "migrations-dir": "migrations",
  "envPath": ".env"
}

Se preferir não criar o arquivo de configuração, dá pra passar tudo na linha de comando: node-pg-migrate up -m migrations --envPath .env. O arquivo existe pra você não precisar lembrar disso toda vez — e pra que o comando seja idêntico na sua máquina e no servidor.

5. A tabela pgmigrations

Na primeira execução, a ferramenta cria uma tabela no seu banco:

          name          |           run_on
------------------------+----------------------------
 1700000000000_baseline | 2026-08-14 10:32:11.284
 1700000000001_indice   | 2026-08-14 10:32:11.301

É só isso: o nome de cada migration já aplicada e quando. Ao rodar up, a ferramenta lista os arquivos da pasta, compara com essa tabela, e executa em ordem os que não estão lá.

Por que o controle mora no banco, e não num arquivo

Porque a pergunta que ele responde é "este banco está atualizado?", e cada banco tem uma resposta diferente: o seu de desenvolvimento, o de testes, o de produção. Um arquivo no repositório responderia "o código está atualizado", que é outra pergunta — a que o git já responde.

É o mesmo raciocínio do refresh token da parte 8: o estado que precisa sobreviver a restart e ser compartilhado entre instâncias mora no único lugar que os dois lados enxergam.

6. Baseline: começar com o banco já existente

Aqui está a parte que confunde. Seu banco já tem as cinco tabelas, com dados. Se a primeira migration for "criar tudo", ela vai falhar no seu banco (as tabelas existem) — mas precisa funcionar num banco vazio, senão ninguém consegue montar o projeto do zero.

A saída é uma migration baseline: ela representa todo o estado atual, escrita de forma que rodar num banco que já está assim seja inofensivo. O schema.sql já usa CREATE TABLE IF NOT EXISTS desde a parte 3, o que faz metade do trabalho — falta incluir o que foi adicionado por ALTER TABLE depois.

Rodar para gerar o arquivo com o nome e o timestamp corretos. A ferramenta cria o arquivo vazio; o conteúdo é o próximo passo:

npm run migrate create baseline

Alterar o arquivo recém-criado em migrations/<timestamp>_baseline.js — apague o conteúdo gerado e cole este. É o schema completo, agora incluindo as colunas que as partes 7, 8 e 10 adicionaram por ALTER TABLE:

export const up = (pgm) => {
  pgm.sql(`
    CREATE TABLE IF NOT EXISTS instrutores (
      id SERIAL PRIMARY KEY,
      nome VARCHAR(120) NOT NULL,
      especialidade VARCHAR(80) NOT NULL,
      email VARCHAR(160) UNIQUE,
      senha_hash VARCHAR(60),
      papel VARCHAR(10) NOT NULL DEFAULT 'instrutor'
        CHECK (papel IN ('instrutor', 'admin'))
    );

    CREATE TABLE IF NOT EXISTS alunos (
      id SERIAL PRIMARY KEY,
      nome VARCHAR(120) NOT NULL,
      email VARCHAR(160) NOT NULL UNIQUE,
      data_nascimento DATE NOT NULL,
      senha_hash VARCHAR(60),
      criado_em TIMESTAMP NOT NULL DEFAULT NOW()
    );

    CREATE TABLE IF NOT EXISTS aulas (
      id SERIAL PRIMARY KEY,
      nome VARCHAR(120) NOT NULL,
      instrutor_id INTEGER NOT NULL REFERENCES instrutores(id) ON DELETE RESTRICT,
      dia_semana VARCHAR(10) NOT NULL
        CHECK (dia_semana IN ('segunda', 'terca', 'quarta', 'quinta', 'sexta', 'sabado', 'domingo')),
      hora_inicio TIME NOT NULL,
      duracao_minutos INTEGER NOT NULL CHECK (duracao_minutos > 0),
      capacidade_maxima INTEGER NOT NULL CHECK (capacidade_maxima > 0)
    );

    CREATE TABLE IF NOT EXISTS matriculas (
      id SERIAL PRIMARY KEY,
      aluno_id INTEGER NOT NULL REFERENCES alunos(id) ON DELETE CASCADE,
      aula_id INTEGER NOT NULL REFERENCES aulas(id) ON DELETE CASCADE,
      status VARCHAR(10) NOT NULL DEFAULT 'confirmada'
        CHECK (status IN ('confirmada', 'cancelada')),
      criado_em TIMESTAMP NOT NULL DEFAULT NOW()
    );

    CREATE UNIQUE INDEX IF NOT EXISTS matriculas_aluno_aula_confirmada_idx
      ON matriculas (aluno_id, aula_id)
      WHERE status = 'confirmada';

    CREATE TABLE IF NOT EXISTS refresh_tokens (
      id SERIAL PRIMARY KEY,
      aluno_id INTEGER REFERENCES alunos(id) ON DELETE CASCADE,
      instrutor_id INTEGER REFERENCES instrutores(id) ON DELETE CASCADE,
      CHECK ((aluno_id IS NOT NULL)::int + (instrutor_id IS NOT NULL)::int = 1),
      token_hash CHAR(64) NOT NULL UNIQUE,
      expira_em TIMESTAMP NOT NULL,
      revogado_em TIMESTAMP,
      criado_em TIMESTAMP NOT NULL DEFAULT NOW()
    );

    CREATE INDEX IF NOT EXISTS refresh_tokens_aluno_id_idx
      ON refresh_tokens (aluno_id);
  `);
};

export const down = () => {
  throw new Error('A migration baseline não é reversível.');
};

O baseline precisa refletir o banco, não o schema.sql. Como a seção 1 mostrou, os dois divergiram. Copiar o schema.sql como está congelaria a mentira: quem montasse o projeto do zero continuaria sem email em instrutores. As três colunas estão incluídas acima justamente por isso — e a seção 7 mostra como conferir se sobrou alguma diferença no seu banco.

Por que o arquivo usa "export const" num projeto CommonJS

O projeto inteiro usa require/module.exports, e o arquivo gerado pela ferramenta usa export const. Não é engano nem exige mudar o package.json: o node-pg-migrate carrega os arquivos de migration por conta própria, com suporte aos dois formatos. Mantenha como veio.

Quem não sabe disso é o ESLint. A configuração da parte 4 declara sourceType: "commonjs" para todo .js, então o npm run lint passa a falhar assim que a primeira migration existe:

migrations/..._baseline.js
  1:1  error  Parsing error: 'import' and 'export' may appear
              only with 'sourceType: module'

Alterar eslint.config.mjs — adicione um bloco depois da linha que define sourceType: "commonjs". Configuração de ESLint é aplicada em cascata: o bloco mais específico vence para os arquivos que ele casa, e o resto do projeto continua CommonJS:

export default defineConfig([
  { files: ["**/*.{js,mjs,cjs}"], plugins: { js }, extends: ["js/recommended"], languageOptions: { globals: globals.node } },
  { files: ["**/*.js"], languageOptions: { sourceType: "commonjs" } },
  // node-pg-migrate gera migrations em ESM (export const up/down) e as carrega
  // por conta própria — o resto do projeto continua CommonJS.
  { files: ["migrations/**/*.js"], languageOptions: { sourceType: "module" } },
  { rules: { "no-unused-vars": ["error", { argsIgnorePattern: "^_", varsIgnorePattern: "^_" }] } },
]);

Rodar — no seu banco de desenvolvimento, que já tem tudo, isso não deve alterar nada. É o teste de que o baseline é seguro:

npm run migrate:up
> Migrating files:
> - 1786660195208_baseline
### MIGRATION 1786660195208_baseline (UP) ###
...
Migrations complete!

As tabelas já existiam, então cada CREATE TABLE IF NOT EXISTS foi ignorado pelo Postgres. O que mudou foi só a linha nova em pgmigrations, marcando o ponto de partida. Daqui pra frente, toda alteração é uma migration.

7. Conferindo o baseline contra o banco

O baseline foi escrito à mão, então vale conferir se ele descreve mesmo o seu banco. O pg_dump mostra o estado real:

docker compose exec -T db pg_dump -U postgres -d estudo \
  --schema-only --no-owner --no-privileges > /tmp/banco-real.sql

grep -A 10 "CREATE TABLE public.instrutores" /tmp/banco-real.sql

Compare coluna por coluna com o baseline. O pg_dump escreve de um jeito mais verboso (separa SEQUENCE de CREATE TABLE, nomeia todas as constraints), então não espere texto idêntico — o que importa é que não falte nem sobre nada.

O teste definitivo é montar um banco do zero e comparar. A seção 14 faz isso.

Você pode se perguntar por que não usar direto a saída do pg_dump como baseline. É uma opção legítima e mais garantida — a desvantagem é legibilidade: o dump traz ALTER TABLE ONLY ... ADD CONSTRAINT separado de cada tabela, nomes gerados automaticamente e detalhes de sequência. Como este é material de estudo, o baseline legível vale mais. Em projeto grande, com dezenas de tabelas, use o dump.

8. A primeira migration de verdade

Tem uma pendência real esperando desde a parte 10: refresh_tokens ganhou a coluna instrutor_id, mas só aluno_id tem índice. Toda vez que um instrutor renova o token, o Postgres varre a tabela.

Rodar — o nome vira parte do arquivo, então descreva a mudança, não o arquivo:

npm run migrate create indice-refresh-tokens-instrutor

Alterar o arquivo criado em migrations/<timestamp>_indice-refresh-tokens-instrutor.js — substitua o conteúdo gerado:

export const up = (pgm) => {
  pgm.createIndex('refresh_tokens', 'instrutor_id', {
    name: 'refresh_tokens_instrutor_id_idx',
    ifNotExists: true,
  });
};

export const down = (pgm) => {
  pgm.dropIndex('refresh_tokens', 'instrutor_id', {
    name: 'refresh_tokens_instrutor_id_idx',
    ifExists: true,
  });
};
npm run migrate:up

### MIGRATION ..._indice-refresh-tokens-instrutor (UP) ###
CREATE INDEX IF NOT EXISTS "refresh_tokens_instrutor_id_idx"
  ON "refresh_tokens" ("instrutor_id");
Migrations complete!

Repare no que aconteceu: a ferramenta rodou só a migration nova. O baseline já estava na tabela de controle e foi pulado sem você precisar dizer nada. É essa a diferença prática do schema.sql.

9. API do pgm ou SQL cru?

As duas migrations acima usaram estilos diferentes de propósito. pgm tem métodos para as operações comuns (createTable, addColumns, createIndex, addConstraint...), e tem o pgm.sql(), que aceita qualquer SQL.

Use a API do pgmUse pgm.sql()
Operações comuns — coluna, índice, tabela simples.SQL específico do Postgres que a API não cobre bem.
Ganha o down quase de graça, com a operação inversa óbvia.Quando escrever em SQL é mais claro do que traduzir pra chamadas.
Ex: pgm.addColumns('alunos', { telefone: { type: 'varchar(20)' } })Ex: o CHECK do arco exclusivo da parte 10, ou o índice único parcial da parte 3.

Não existe resposta certa universal. A regra prática: comece pela API, e caia pro pgm.sql() quando perceber que está lutando contra ela. Migration que ninguém entende é pior do que migration verbosa.

10. down: reversibilidade e quando abrir mão

Todo arquivo tem up e down. O down desfaz — e npm run migrate:down reverte a última aplicada.

npm run migrate:down

### MIGRATION ..._indice-refresh-tokens-instrutor (DOWN) ###
DROP INDEX IF EXISTS "refresh_tokens_instrutor_id_idx";
Migrations complete!

A linha some de pgmigrations, e um up aplica de novo. Útil quando você percebe um erro na migration que acabou de rodar em desenvolvimento.

Nem todo down é possível, e fingir que é dá pior resultado. Uma migration que apaga uma coluna não consegue trazer os dados de volta — o down recria a coluna vazia, que parece reversão e não é. O baseline desta parte declara isso explicitamente com um throw: melhor falhar com mensagem clara do que executar um DROP TABLE em cascata achando que está desfazendo algo.

Em produção, down quase nunca é a resposta certa. Corrigir um erro com uma migration nova preserva o histórico e não depende de o down ter sido escrito com cuidado. down é ferramenta de desenvolvimento.

11. O fluxo do dia a dia

1

Precisou mudar o banco

npm run migrate create nome-que-descreve. Nunca mais abra o psql pra ALTER TABLE.

2

Escreva up e down

Uma mudança lógica por arquivo. Duas alterações não relacionadas são duas migrations.

3

Rode e teste

npm run migrate:up, verifique, e — se der — migrate:down seguido de up pra confirmar que o down funciona. É o único momento em que testar o down é barato.

4

Commit junto do código

A migration e o código que depende dela vão no mesmo commit. Separados, existe um commit no meio da história em que o código espera uma coluna que não existe.

E o db/schema.sql, morre?

Ele perde a função de fonte da verdade — quem monta o banco agora é migrate:up. Duas saídas defensáveis: apagar o arquivo (o baseline o substitui) ou mantê-lo como documentação legível do estado atual, com um comentário no topo dizendo que ele é gerado/informativo e que as migrations mandam.

Recomendo apagar. Um arquivo que não é executado por ninguém volta a divergir na primeira semana — é exatamente a história da seção 1. Se quiser uma visão do schema atual, pg_dump --schema-only gera na hora, sempre correta.

12. Migrations e deploy

Até aqui, migration é conveniência. No deploy, vira necessidade: ninguém abre psql em servidor de produção pra rodar ALTER TABLE na mão — é lento, não tem registro e cada ambiente vira um floco de neve.

O padrão é rodar as migrations antes de subir a versão nova do código, como passo do processo de deploy:

npm ci
npm run migrate:up
npm start

A ordem importa e tem uma consequência que vale entender desde já: por um instante, o banco novo convive com o código velho. Se a migration remove uma coluna que o código atual ainda lê, esse instante vira erro. Por isso mudanças destrutivas costumam ser feitas em duas etapas, separadas por um deploy: primeiro para de usar, depois remove.

Isso conecta com o que a parte de produção vai tratar. Por ora, o que importa é a decisão de arquitetura: migration não roda dentro do index.js. Se a API aplicasse migrations ao subir, duas instâncias subindo ao mesmo tempo tentariam migrar em paralelo — e um erro de migration derrubaria a aplicação inteira em vez de falhar num passo isolado do deploy.

13. O que não fazer numa migration

  • Editar migration já aplicada. A tabela de controle guarda o nome: alterar o conteúdo não faz ela rodar de novo no seu banco, mas roda a versão nova em quem ainda não aplicou. Os bancos divergem em silêncio. Migration aplicada é imutável; correção é migration nova.
  • Migração de dados pesada junto com mudança de estrutura. Um UPDATE em milhões de linhas dentro da migration segura lock e trava o deploy. Estrutura na migration, dados num script separado que dá pra rodar e acompanhar.
  • Depender do código da aplicação. Nada de importar seus repositories ou services dentro de uma migration. Ela precisa rodar igual daqui a dois anos, quando aquele arquivo tiver mudado de forma — ou deixado de existir.
  • Uma migration gigante com dez mudanças. Se uma falhar no meio, você fica num estado difícil de descrever. Uma mudança lógica por arquivo.
  • Renomear arquivo de migration. O nome é a chave na tabela de controle. Renomear faz a ferramenta achar que é migration nova e tentar aplicar de novo.

14. Testando

O teste que importa é o que a seção 1 descreveu: alguém clona o projeto e monta o banco do zero. Dá pra simular sem tocar no seu banco de desenvolvimento, criando um banco descartável:

# cria um banco vazio só pro teste
docker compose exec -T db psql -U postgres -c "CREATE DATABASE estudo_teste_migrations;"

# roda as migrations apontando pra ele (variável só nesta linha)
DATABASE_URL="postgresql://postgres:SUA_SENHA@localhost:5432/estudo_teste_migrations" \
  npx node-pg-migrate up
# as tabelas nasceram?
docker compose exec -T db psql -U postgres -d estudo_teste_migrations -c "\dt"

# e as colunas que faltavam no schema.sql?
docker compose exec -T db psql -U postgres -d estudo_teste_migrations -c \
  "SELECT column_name FROM information_schema.columns
   WHERE table_name = 'instrutores' ORDER BY ordinal_position;"
# deve listar 6: id, nome, especialidade, email, senha_hash, papel

Se as seis colunas aparecerem, o baseline está correto e o problema da seção 1 acabou. Confirme também o índice novo e o arco exclusivo da parte 10:

docker compose exec -T db psql -U postgres -d estudo_teste_migrations \
  -c "SELECT indexname FROM pg_indexes WHERE tablename = 'refresh_tokens';" \
  -c "SELECT conname FROM pg_constraint
      WHERE conrelid = 'refresh_tokens'::regclass AND contype = 'c';"

Apagar o banco de teste quando terminar — ele não serve pra mais nada:

docker compose exec -T db psql -U postgres -c "DROP DATABASE estudo_teste_migrations;"

Por fim, o teste de que a API continua funcionando: rode npm run dev e repita um fluxo qualquer das partes anteriores — login, matrícula, refresh. O banco de desenvolvimento não mudou nada além de ganhar o índice novo e a tabela pgmigrations.

15. Erros comuns

  1. Rodar ALTER TABLE no psql "só dessa vez" — o banco fica à frente das migrations, e a próxima migration que mexer naquela tabela falha em ambiente limpo e funciona no seu. Todo o problema da seção 1, de volta com outro nome.
  2. Editar uma migration já aplicada — divergência silenciosa entre bancos (seção 13).
  3. Esquecer o envPath — a ferramenta não passa pelo index.js, então não carrega o .env sozinha. O sintoma é erro de conexão dizendo que faltou DATABASE_URL.
  4. Commitar o código sem a migration — o colega puxa, roda, e a API quebra procurando uma coluna que não existe no banco dele.
  5. Baseline copiado do schema.sql desatualizado — congela a divergência em vez de corrigi-la, e o teste da seção 14 passa a "provar" um banco errado.
  6. down que finge reverter — recriar coluna apagada não traz os dados. Ou escreva um down honesto, ou declare que não há (seção 10).
  7. Rodar migration dentro da aplicação — duas instâncias subindo migram em paralelo (seção 12).
  8. Migration que importa código do projeto — ela precisa continuar rodando quando aquele arquivo mudar.

16. O que vem a seguir

O banco agora tem histórico versionado, e montar o projeto do zero virou um comando. Ainda dentro da categoria banco e dados, faltam duas mudanças — e as duas são, agora, migrations:

  1. Limpeza dos refresh tokens expirados — a tabela só cresce: cada login e cada renovação deixam uma linha revogada pra sempre. Entra um DELETE periódico dos expirados há mais de X dias, e a discussão de onde esse tipo de rotina roda (script agendado, cron, ou dentro da aplicação — e por que a última opção é a pior).
  2. Soft-delete de instrutor — anotado desde a parte 6 e mais urgente depois da parte 10: hoje DELETE /instrutores/:id apaga a linha, e com ela o email e o senha_hash. Além disso, o ON DELETE RESTRICT de aulas impede apagar quem já deu aula — então na prática a rota falha com 409 pra qualquer instrutor real. Marcar como inativo resolve os dois problemas e preserva o histórico.

Depois disso: qualidade (Jest + supertest, CI — e migrations facilitam, porque a suíte pode montar um banco limpo com um comando) → contrato da API (paginação, OpenAPI) → produção (logging, health check, Dockerfile, deploy com HTTPS, e o passo de migration no processo de deploy da seção 12).

O momento que vale observar é o teste da seção 14: um banco vazio virando o schema completo com um comando, incluindo as três colunas que estavam faltando no schema.sql. Volta com dúvidas, principalmente se o migrate:up reclamar de algo que você jurava já existir — quase sempre é o baseline descrevendo um banco diferente do seu, e o pg_dump da seção 7 responde qual dos dois está certo.
