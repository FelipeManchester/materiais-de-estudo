Projeto Studio Fit — Trilha Node + Express — Parte 16

Testes automatizados

Quinze partes, todas testadas com curl na mão. Funcionou enquanto o projeto era pequeno — hoje conferir tudo depois de uma mudança é meia hora de terminal, e é por isso que ninguém confere. Esta parte troca isso por um comando.

1. O custo de testar na mão

Faça a conta do que a trilha acumulou de comportamento que precisa continuar funcionando:

OrigemCasos
4 regras de negócio (partes 5 e 6)capacidade, duplicidade, conflito de agenda, cancelamento
Matriz de permissões (parte 10)10 linhas × 4 papéis, mais posse de recurso
Fluxo de autenticação (partes 7, 8, 11)login, refresh, logout, reuso, expiração, cookie
Validação (parte 12)cada campo de cada schema
Concorrência (parte 13)capacidade sob requisições simultâneas

São dezenas de comportamentos. Você conferiu todos eles, várias vezes, colando comandos no terminal. E mesmo assim, três coisas escaparam ao longo da trilha e só foram descobertas depois: o login de instrutor que devolvia 400 sempre, o PATCH/DELETE de aulas respondendo 500, e o filtro ?instrutor_id= que parou de funcionar em silêncio.

Repare no padrão dos três: nenhum deles estava na parte que você tinha acabado de escrever. Eram comportamentos antigos, que funcionavam, e quebraram por causa de uma mudança em outro lugar. É exatamente o que teste automatizado pega e teste manual não: você reconfere o que mexeu, não o que já estava pronto.

O objetivo aqui não é cobrir 100% do código — é transformar aquela meia hora de terminal em npm test, para que reconferir tudo deixe de ser uma decisão e passe a ser o padrão.

2. Que tipo de teste vamos escrever

A divisão clássica separa testes por escopo:

TipoO que testaAqui
UnitárioUma função isolada, sem banco nem rede.Pouco a ganhar: nossas funções puras são poucas (hashRefreshToken, calcularExpiracao). A lógica de verdade está na conversa entre rota, repository e banco.
Integração / API escolhidoUma requisição HTTP de verdade, atravessando middlewares, rota, repository e Postgres.É o que descreve o comportamento que importa: "aluno não matricula em aula lotada" é uma frase sobre a API, não sobre uma função.
End-to-endNavegador + front-end + API.Não existe front-end neste projeto.

A escolha tem uma consequência importante: os testes vão usar banco de verdade, não simulado. Isso é deliberado — metade das garantias do projeto está no banco (o UNIQUE parcial da parte 3, o CHECK da parte 10, o FOR UPDATE da parte 13). Testar contra um banco falso testaria uma aplicação que não existe.

O custo dessa escolha

Testes com banco são mais lentos (segundos, não milissegundos) e exigem infraestrutura — o Postgres precisa estar de pé pra suíte rodar, inclusive no CI. Em troca, quando eles passam, você sabe que a API funciona de verdade. Um teste unitário que simula o Postgres passa mesmo quando a query está errada.

Como nosso Postgres já roda em Docker desde a parte 1, o custo aqui é baixo.

3. Jest e supertest

Rodar na raiz do projeto — as duas são de desenvolvimento, não vão pra produção:

npm install --save-dev jest supertest
PacotePapel
JestO executor: encontra os arquivos de teste, roda, isola cada arquivo num processo próprio e reporta o resultado. Traz junto as funções describe, it e expect.
supertestFaz requisições HTTP contra o seu app Express sem subir servidor. Ele mesmo sobe a aplicação numa porta efêmera, faz a chamada e devolve a resposta.

Esse "sem subir servidor" é o que torna a suíte rápida e independente: nada de precisar do npm run dev rodando em outro terminal, nada de porta ocupada, nada de teste falhando porque você esqueceu de reiniciar depois de editar.

Falta um ajuste antes de escrever o primeiro teste. O Jest injeta describe, it, expect e afterAll em tempo de execução — o ESLint não sabe disso e vai acusar cada um deles como variável inexistente:

tests/alunos.test.js

  17:1  error  'describe' is not defined  no-undef
  18:3  error  'it' is not defined        no-undef
  ...dezenas de linhas iguais

Alterar eslint.config.mjs — mais um bloco específico, como o que a parte 14 acrescentou para as migrations. O globals.jest vem do pacote globals, já importado no topo do arquivo desde a parte 4:

4. O obstáculo: separar app de index

Para o supertest fazer isso, ele precisa receber o objeto app do Express. E o index.js hoje faz duas coisas no mesmo arquivo: monta o app e chama app.listen(). Importar esse arquivo num teste subiria um servidor na porta 3000 — que provavelmente já está ocupada pelo seu npm run dev.

A separação é mecânica: o app vai pra um arquivo, o listen fica no outro.

Criar app.js na raiz — recorte todo o conteúdo atual do index.js, da linha const express = require('express') até o middleware de erro (inclusive), sem o require('dotenv').config() do topo e sem o bloco do PORT/listen do fim. Depois acrescente a exportação na última linha:

const express = require('express');

const alunosRouter = require('./routes/alunos');
// ...todos os requires que já estavam no index.js

const app = express();

app.use(helmet());
app.use(corsConfigurado);
app.use(limitadorGlobal);
app.use(express.json({ limit: '10kb' }));
app.use(cookieParser());

app.use('/alunos', alunosRouter);
app.use('/instrutores', instrutoresRouter);
app.use('/aulas', aulasRouter);
app.use('/auth', limitadorLogin, authRouter);

app.use((err, req, res, _next) => {
  // ...o middleware de erro continua exatamente igual
});

module.exports = app;

Alterar index.js — o arquivo inteiro passa a ser só isto. Ele volta a ter uma responsabilidade só: subir o servidor:

require('dotenv').config();

const app = require('./app');

const PORT = process.env.PORT || 3000;

app.listen(PORT, () => {
  console.log(`Servidor rodando em http://localhost:${PORT}`);
});

O require('dotenv').config() fica no index.js, não no app.js. Motivo: quem decide de onde vêm as variáveis de ambiente é quem inicia o processo. Em produção é o index.js lendo o .env; nos testes é o Jest lendo o .env.test (seção 8). Se o app.js carregasse o .env por conta própria, ele sobrescreveria a configuração de teste toda vez.

Confirme que nada quebrou: npm run dev deve subir igual a antes.

5. Um banco só pros testes

Teste que cria aluno, matricula e cancela precisa de um banco onde isso não incomode ninguém. Rodar contra o banco de desenvolvimento tem dois problemas: os testes sujam seus dados, e seus dados quebram os testes (um teste que espera "3 alunos" falha quando você cadastra o quarto na mão).

A solução é um banco separado, recriado do zero a cada execução da suíte. E "recriado do zero" agora é barato, porque a parte 14 deu o mecanismo: node-pg-migrate up monta o schema inteiro num banco vazio.

Sem banco separado

Teste depende do que já existe. Passa hoje, falha amanhã porque você cadastrou um instrutor. Ou pior: passa sempre, porque o dado que ele precisava já estava lá por acidente.

Banco recriado por execução

Toda execução parte do mesmo estado: schema completo, zero linhas. O teste cria o que precisa e não depende de nada anterior.

6. A guarda que evita o desastre

Antes de escrever o código que apaga e recria o banco, pare um segundo: esse código roda DROP DATABASE. Se a variável de ambiente estiver errada — um .env.test mal copiado, uma variável exportada no terminal, um comando rodado na pasta errada — ele apaga o banco que encontrar.

Este é o único ponto desta trilha inteira em que um erro de configuração destrói dados sem volta. Todo o resto responde erro HTTP; aqui o estrago é silencioso e permanente. Por isso a primeira coisa que vamos escrever não é o DROP, é a recusa a rodar quando o nome do banco não termina em _test.

A convenção é simples e funciona: banco de teste tem nome terminando em _test. Qualquer outro nome, a suíte se recusa a rodar antes de tocar em nada.

7. globalSetup: banco limpo por execução

Jest tem um gancho que roda uma vez, antes de qualquer arquivo de teste: é onde o banco é preparado.

Criar tests/globalSetup.js — diretório novo:

const { execSync } = require('node:child_process');
const { Client } = require('pg');

module.exports = async () => {
  require('dotenv').config({ path: '.env.test', override: true, quiet: true });

  const url = new URL(process.env.DATABASE_URL);
  const nomeDoBanco = url.pathname.slice(1);

  if (!nomeDoBanco.endsWith('_test')) {
    throw new Error(
      `Recusando rodar testes contra o banco "${nomeDoBanco}": o nome precisa terminar em _test.`,
    );
  }

  // conecta no banco administrativo pra poder dropar/criar o de teste
  const urlAdmin = new URL(process.env.DATABASE_URL);
  urlAdmin.pathname = '/postgres';

  const client = new Client({ connectionString: urlAdmin.toString() });
  await client.connect();
  await client.query(`DROP DATABASE IF EXISTS ${nomeDoBanco}`);
  await client.query(`CREATE DATABASE ${nomeDoBanco}`);
  await client.end();

  execSync('npx node-pg-migrate up', {
    env: { ...process.env, DATABASE_URL: process.env.DATABASE_URL },
    stdio: 'ignore',
  });
};

Três coisas acontecem aqui, na ordem:

  1. Guarda. Nome sem _test, erro antes de qualquer comando destrutivo.
  2. Banco zerado. DROP + CREATE a partir de uma conexão com o banco postgres — não dá pra dropar o banco em que você está conectado.
  3. Schema. As migrations da parte 14 montam tudo. Se você criar uma migration nova amanhã, a suíte já a considera — sem ninguém precisar lembrar.

Criar jest.config.js na raiz:

module.exports = {
  testEnvironment: 'node',
  globalSetup: './tests/globalSetup.js',
  setupFilesAfterEnv: ['./tests/setup.js'],
  testMatch: ['**/tests/**/*.test.js'],
};

testEnvironment: 'node' importa: o padrão do Jest simula um navegador, o que aqui só atrapalha. E testMatch restringe a busca a tests/*.test.js, para o Jest não tentar rodar as migrations ou o testar-corrida.js da parte 13.

8. .env.test e a ordem de carregamento

Criar .env.test na raiz. Diferente do .env, este pode ser commitado: não há segredo de verdade aqui, e o CI vai precisar dele (parte 17):

DATABASE_URL=postgresql://postgres:SUA_SENHA@localhost:5432/estudo_test
JWT_SECRET=segredo_de_teste_nao_usar_em_producao
CORS_ORIGINS=http://localhost:5173
NODE_ENV=test

Criar tests/setup.js — o globalSetup roda num processo separado, então cada arquivo de teste precisa carregar as variáveis de novo:

require('dotenv').config({ path: '.env.test', override: true, quiet: true });

override: true é o detalhe que decide tudo. Sem ele, o dotenv respeita variáveis já definidas no ambiente — então se você tiver um DATABASE_URL exportado no terminal, ou o CI definir um, o .env.test é ignorado e os testes rodam contra o banco errado. Com override, o arquivo de teste sempre vence dentro da suíte.

Combinado com a guarda da seção 6, são duas barreiras independentes: uma garante que o valor certo é usado, a outra recusa valores perigosos.

Duas linhas que evitam dor de cabeça

afterAll(() => pool.end()): sem fechar o pool, o Jest termina os testes e fica pendurado, porque ainda há conexões abertas. A mensagem é "Jest did not exit one second after the test run has completed", e a causa é sempre essa.

--runInBand: manda o Jest rodar os arquivos em série, não em paralelo. Como todos compartilham o mesmo banco, testes paralelos podem interferir entre si — um apagando dado que o outro acabou de criar. Serial é mais lento e previsível; previsível vale mais numa suíte que você quer confiar.

10. Ajudantes: chegar rápido no que importa

Testar autorização exige um aluno logado, um instrutor, um admin, uma aula. Repetir esse preparo em cada teste enterraria a intenção debaixo de dez linhas de setup.

Criar tests/ajudantes.js — repare que ele não termina em .test.js, então o Jest não tenta rodá-lo como suíte:

const request = require('supertest');
const app = require('../app');
const pool = require('../db/pool');
const { hashSenha } = require('../services/senhaService');

let contador = 0;
const unico = () => `${Date.now()}_${contador++}`;

async function criarAlunoLogado() {
  const email = `aluno_${unico()}@example.com`;

  await request(app).post('/alunos').send({
    nome: 'Aluno Teste',
    email,
    data_nascimento: '1990-01-01',
    senha: 'senha123',
  });

  const login = await request(app)
    .post('/auth/login')
    .send({ email, senha: 'senha123' });

  return {
    email,
    token: login.body.access_token,
    cookie: login.headers['set-cookie'],
  };
}

async function criarInstrutorLogado(papel = 'instrutor') {
  const email = `instrutor_${unico()}@studiofit.com`;
  const senha_hash = await hashSenha('senha123');

  const { rows } = await pool.query(
    `INSERT INTO instrutores (nome, especialidade, email, senha_hash, papel)
     VALUES ($1, 'testes', $2, $3, $4) RETURNING id`,
    [`Instrutor ${unico()}`, email, senha_hash, papel],
  );

  const login = await request(app)
    .post('/auth/instrutores/login')
    .send({ email, senha: 'senha123' });

  return {
    id: rows[0].id,
    token: login.body.access_token,
    cookie: login.headers['set-cookie'],
  };
}

async function criarAula(admin, dados = {}) {
  const instrutor = await criarInstrutorLogado();

  const resposta = await request(app)
    .post('/aulas')
    .set('Authorization', `Bearer ${admin.token}`)
    .send({
      nome: `Aula ${unico()}`,
      instrutor_id: instrutor.id,
      dia_semana: 'segunda',
      hora_inicio: '07:00',
      duracao_minutos: 60,
      capacidade_maxima: 10,
      ...dados,
    });

  return { aula: resposta.body, instrutor };
}

module.exports = { criarAlunoLogado, criarInstrutorLogado, criarAula };

Duas decisões nesse arquivo:

  • O instrutor é criado direto no banco, não pela API. Criar instrutor exige um admin, e criar o primeiro admin exigiria outro admin — o problema circular da parte 10, seção 12. No teste, a saída é a mesma de lá: INSERT direto.
  • Emails únicos por chamada. O unico() combina timestamp e contador porque duas chamadas no mesmo milissegundo dariam o mesmo email, e o UNIQUE da parte 3 recusaria a segunda.

11. Testando a matriz de permissões

Agora a parte que compensa o trabalho: a matriz da parte 10 vira código que se verifica sozinho.

Criar tests/autorizacao.test.js:

const request = require('supertest');
const app = require('../app');
const pool = require('../db/pool');
const {
  criarAlunoLogado,
  criarInstrutorLogado,
  criarAula,
} = require('./ajudantes');

afterAll(() => pool.end());

describe('matriz de permissões', () => {
  it('GET /alunos: 401 sem token, 403 como aluno, 200 como admin', async () => {
    const aluno = await criarAlunoLogado();
    const admin = await criarInstrutorLogado('admin');

    expect((await request(app).get('/alunos')).status).toBe(401);

    expect(
      (
        await request(app)
          .get('/alunos')
          .set('Authorization', `Bearer ${aluno.token}`)
      ).status,
    ).toBe(403);

    expect(
      (
        await request(app)
          .get('/alunos')
          .set('Authorization', `Bearer ${admin.token}`)
      ).status,
    ).toBe(200);
  });

  it('instrutor só edita as próprias aulas', async () => {
    const admin = await criarInstrutorLogado('admin');
    const { aula } = await criarAula(admin);
    const outro = await criarInstrutorLogado();

    const resposta = await request(app)
      .patch(`/aulas/${aula.id}`)
      .set('Authorization', `Bearer ${outro.token}`)
      .send({ nome: 'Roubada' });

    expect(resposta.status).toBe(403);
  });
});

O primeiro teste é o que teria pego o bug do PATCH/DELETE sem middleware da parte 10 — aquele que respondia 500 com ou sem token. Um teste que espera 401 teria falhado no minuto seguinte à mudança.

12. Testando as regras de negócio

Alterar tests/autorizacao.test.js — acrescente este bloco no fim do arquivo, depois do describe anterior:

describe('regras de negócio', () => {
  it('respeita a capacidade máxima', async () => {
    const admin = await criarInstrutorLogado('admin');
    const { aula } = await criarAula(admin, {
      capacidade_maxima: 1,
      hora_inicio: '08:00',
    });

    const primeiro = await criarAlunoLogado();
    const segundo = await criarAlunoLogado();

    const r1 = await request(app)
      .post(`/aulas/${aula.id}/matriculas`)
      .set('Authorization', `Bearer ${primeiro.token}`);

    const r2 = await request(app)
      .post(`/aulas/${aula.id}/matriculas`)
      .set('Authorization', `Bearer ${segundo.token}`);

    expect(r1.status).toBe(201);
    expect(r2.status).toBe(409);
  });

  it('recusa matrícula duplicada', async () => {
    const admin = await criarInstrutorLogado('admin');
    const { aula } = await criarAula(admin, { hora_inicio: '09:00' });
    const aluno = await criarAlunoLogado();

    await request(app)
      .post(`/aulas/${aula.id}/matriculas`)
      .set('Authorization', `Bearer ${aluno.token}`);

    const segunda = await request(app)
      .post(`/aulas/${aula.id}/matriculas`)
      .set('Authorization', `Bearer ${aluno.token}`);

    expect(segunda.status).toBe(409);
  });
});

O hora_inicio diferente em cada teste não é decoração: criarAula cria um instrutor novo a cada chamada, mas se dois testes usassem o mesmo instrutor no mesmo horário, a Regra 3 (conflito de agenda) recusaria a segunda aula com 422 — e o teste falharia por um motivo que não tem nada a ver com o que ele quer verificar. É a mesma armadilha que apareceu no script da parte 13.

13. Testando o fluxo de refresh

O fluxo da parte 8 com o cookie da parte 11 é o mais difícil de testar na mão — e o que mais ganha com automação.

Alterar tests/autorizacao.test.js — mais um bloco no fim:

describe('fluxo de refresh', () => {
  it('renova com cookie e detecta reuso', async () => {
    const aluno = await criarAlunoLogado();

    const primeira = await request(app)
      .post('/auth/refresh')
      .set('Cookie', aluno.cookie);

    expect(primeira.status).toBe(200);
    expect(primeira.body).toHaveProperty('access_token');
    expect(primeira.body).not.toHaveProperty('refresh_token');

    // reapresentar o mesmo cookie: rotação já revogou (parte 8)
    const reuso = await request(app)
      .post('/auth/refresh')
      .set('Cookie', aluno.cookie);

    expect(reuso.status).toBe(401);
  });

  it('recusa refresh sem cookie', async () => {
    expect((await request(app).post('/auth/refresh')).status).toBe(401);
  });
});

O expect(...).not.toHaveProperty('refresh_token') é pequeno e vale ouro: ele trava a decisão da parte 11 de que o refresh token não volta no corpo. Se alguém, um dia, "simplificar" o responderComTokens devolvendo os dois de novo, o teste falha — e o motivo é uma regressão de segurança que ninguém notaria olhando a resposta.

14. Obstáculos que a própria API cria

Algumas defesas construídas nas partes anteriores atrapalham os testes. Vale saber onde elas aparecem antes de perder tempo depurando.

DefesaComo atrapalhaO que fazer
Rate limit (parte 9)300 requisições por 15 min no limite global. Uma suíte grande passa disso, e testes começam a falhar com 429 sem motivo aparente.Desligar em teste, com a opção skip do express-rate-limit (abaixo).
bcrypt (parte 7)Deliberadamente lento. Cada aluno criado no teste custa ~100 ms.Aceitar. Reduzir o custo em teste esconderia diferença de comportamento; a suíte inteira ainda roda em poucos segundos.
Regra 3 (parte 5)Conflito de agenda derruba testes que criam aulas parecidas (seção 12).Variar horário ou instrutor entre testes.
Access token de 15 min (parte 8)Nenhum problema numa suíte que roda em segundos — mas impede testar expiração de forma direta.Testar expiração exigiria forjar um token vencido, como foi feito na mão na parte 8.

Alterar middlewares/limitadores.js — adicione a mesma opção skip nos dois limitadores, junto das opções que já existem:

const limitadorGlobal = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 300,
  standardHeaders: 'draft-7',
  legacyHeaders: false,
  skip: () => process.env.NODE_ENV === 'test',
  message: { erro: 'Muitas requisições. Tente novamente em alguns minutos.' },
});

Desligar uma proteção em ambiente de teste é sempre uma troca. O ganho é uma suíte que não falha por motivo alheio ao que testa; a perda é que o rate limit deixa de ser exercitado. Se quiser testá-lo, o caminho é um arquivo de teste dedicado que ligue o limitador explicitamente — não deixar ele ligado para todos os outros e conviver com falhas intermitentes.

Perceba que isso só é seguro porque NODE_ENV vem do .env.test e o globalSetup recusa banco sem _test. Uma configuração que desliga segurança precisa de uma condição que não possa valer em produção por acidente.

15. Erros comuns

  1. Rodar testes contra o banco de desenvolvimento — apaga tudo no DROP DATABASE do globalSetup. A guarda da seção 6 existe só por isso, e é a linha mais importante desta parte.
  2. Esquecer override: true no dotenv — uma variável exportada no terminal vence o .env.test, e os testes rodam onde não deviam (seção 8).
  3. Esquecer pool.end() — Jest não encerra e o processo fica pendurado. Em CI, isso vira build travado até o timeout.
  4. Importar index.js em vez de app.js — o teste sobe um servidor de verdade na porta 3000 e falha com EADDRINUSE se o npm run dev estiver rodando.
  5. Testes que dependem de ordem — "o teste 2 usa o aluno criado pelo teste 1" quebra quando alguém roda um teste isolado. Cada teste cria o que precisa.
  6. Dados fixos que colidem — email teste@example.com em dois testes viola o UNIQUE. Gere valores únicos (seção 10).
  7. Testar implementação em vez de comportamento — verificar que bcrypt.hash foi chamado é frágil; verificar que a resposta não traz senha_hash descreve a garantia real.
  8. Colocar ajudantes em arquivo .test.js — o Jest tenta rodar e reclama que não há testes no arquivo.

16. O que vem a seguir

A suíte cobre hoje o cadastro de aluno com validação, a matriz de permissões, duas regras de negócio e o fluxo de refresh com cookie. É pouco perto de tudo que a API faz — e já é infinitamente mais do que zero, porque a partir de agora cada parte nova pode adicionar seus testes em vez de recomeçar do curl.

  1. CI — a próxima parte. Os testes rodando sozinhos a cada push, no GitHub Actions: Postgres como serviço do workflow, migrations aplicadas, npm test e npm run lint. É o que transforma a suíte de "coisa que eu rodo quando lembro" em portão que barra código quebrado antes de virar problema.
  2. Cobertura — jest --coverage mostra quais linhas nenhum teste exercita. Útil como mapa do que falta, péssimo como meta: perseguir 100% leva a testes que existem só pra subir o número.

Depois: contrato da API (paginação, filtro, ordenação, OpenAPI) → produção (logging estruturado, health check, Dockerfile e deploy com HTTPS).

Fica registrado o que a suíte ainda não cobre e vale acrescentar quando você mexer nessas áreas: as regras 3 e 4 (conflito de agenda e cancelamento), o soft-delete da parte 15, os limites de validação de cada schema, e o comportamento sob concorrência da parte 13 — este último cabe melhor como teste próprio, porque exige disparar requisições em paralelo, o oposto do --runInBand.

Ao terminar, rode npm test duas vezes seguidas: o resultado precisa ser idêntico. Suíte que passa na primeira e falha na segunda tem dado sobrando entre execuções — e o globalSetup desta parte existe justamente pra isso não acontecer. Volta com dúvidas, principalmente se o Jest não encerrar sozinho (é o pool.end()) ou se algum teste falhar com 429 (é o rate limit da seção 14).
