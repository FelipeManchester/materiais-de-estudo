Projeto — Trilha Node + Express

Projeto: API de uma academia

Domínio fictício pra dar contexto real aos próximos materiais da trilha. Em vez de rotas soltas sem propósito, toda implementação daqui pra frente serve pra construir a API de uma academia: alunos se matriculando em aulas, com regras de negócio de verdade — mas de propósito mantidas pequenas, pra não competir com o foco real, que é aprender REST + Node, não desenhar um sistema de gestão de academia completo.

1. O negócio: Studio Fit

Studio Fit é uma academia fictícia de porte pequeno/médio, que oferece aulas em turma (não musculação livre) — tipo spinning, yoga, funcional. Cada aula tem um instrutor responsável, um horário fixo e um número limitado de vagas. Alunos se matriculam nas aulas que quiserem, respeitando a vaga disponível.

Esse recorte (aula em turma com vaga limitada) foi escolhido de propósito: gera regras de negócio reais — conflito de horário, capacidade máxima, matrícula duplicada — sem precisar entrar em assunto complexo como plano de assinatura, cobrança ou múltiplas unidades.

2. Escopo: o que entra e o que fica de fora

Delimitar isso agora evita que o domínio cresça sozinho no meio da implementação — o problema descrito no início da conversa que gerou este documento.

Entra

  • Cadastro de alunos e instrutores
  • Cadastro de aulas (horário, capacidade, instrutor responsável)
  • Matrícula de aluno numa aula, com limite de vaga
  • Cancelamento de matrícula
  • Consulta: aulas de um aluno, alunos de uma aula
  • Autenticação básica (prevista pra próxima parte da trilha)

Fica de fora

  • Pagamento, mensalidade, plano de assinatura
  • Múltiplas unidades/filiais
  • Avaliação física, histórico de evolução do aluno
  • Folha de pagamento / contrato de instrutor
  • Notificação (e-mail, SMS, push)
  • Musculação livre / check-in de catraca

Se em algum momento bater vontade de adicionar algo da lista "fica de fora": resista. Esses itens não ensinam nenhum conceito novo de REST que os itens já incluídos não ensinem — só aumentam a superfície de modelagem de negócio.

3. Entidades (recursos)

Aluno

Recurso de topo — /alunos

Campos: id, nome, email (único), data_nascimento, criado_em.

Instrutor

Recurso de topo — /instrutores

Campos: id, nome, especialidade (ex: "yoga", "spinning").

Aula

Recurso de topo — /aulas

Campos: id, nome (ex: "Spinning matinal"), instrutor_id, horario (dia da semana + hora), duracao_minutos, capacidade_maxima.

Matrícula

Recurso aninhado — só existe no contexto de uma aula, ver seção 4 da parte 3 da trilha API REST

Campos: id, aluno_id, aula_id, status (confirmada ou cancelada), criado_em. Representa o vínculo entre um aluno e uma aula — a entidade que só existe porque as outras duas existem.

4. Como as entidades se relacionam

                        N

  • Um instrutor dá várias aulas; cada aula tem um único instrutor responsável.
  • Uma aula tem várias matrículas (até o limite da capacidade); cada matrícula pertence a uma única aula.
  • Um aluno tem várias matrículas (em aulas diferentes); cada matrícula pertence a um único aluno.

Matrícula é o que se costuma chamar de tabela de associação: existe pra representar a relação muitos-pra-muitos entre aluno e aula (um aluno em várias aulas, uma aula com vários alunos), carregando informação própria (o status).

5. Regras de negócio

Só as regras necessárias pra gerar casos reais de validação/erro HTTP — nada além disso, de propósito.

Regra 1 — Capacidade máxima

Uma matrícula só pode ser criada se o número de matrículas confirmada na aula for menor que capacidade_maxima. Se a aula estiver lotada, a tentativa de matrícula deve falhar com 409 Conflict (a requisição conflita com o estado atual do recurso — visto na parte 2 da trilha API REST).

Regra 2 — Matrícula duplicada

Um aluno não pode ter duas matrículas confirmada na mesma aula ao mesmo tempo. Tentar matricular de novo devolve 409 Conflict.

Regra 3 — Conflito de agenda do instrutor

Um instrutor não pode ter duas aulas cadastradas no mesmo horário. Validação acontece na criação/edição da aula, devolve 422 Unprocessable Entity (dado sintaticamente válido, mas semanticamente inconsistente com o resto do sistema).

Regra 4 — Cancelamento é mudança de status, não exclusão

Cancelar uma matrícula não apaga o registro do banco — muda status para cancelada. Isso preserva histórico (quem já foi matriculado em quê) e é o que abre vaga de novo na aula pra Regra 1. Na prática de API, isso é feito com PATCH no recurso de matrícula, não DELETE.

6. Mapa de endpoints

Aplicando as convenções da parte 3 da trilha API REST (recursos no plural, aninhamento de 1 nível, ações via sub-recurso quando necessário):

MétodoURIO que faz
GET/alunosLista alunos
POST/alunosCria aluno
GET/alunos/:idBusca um aluno
PATCH/alunos/:idAtualiza dados do aluno
DELETE/alunos/:idRemove aluno
GET/alunos/:id/matriculasLista as aulas em que o aluno está matriculado
GET/instrutoresLista instrutores
POST/instrutoresCria instrutor
GET/instrutores/:idBusca um instrutor
GET/aulasLista aulas (filtros: ?instrutor_id=, parte 3 da trilha API REST)
POST/aulasCria aula (valida Regra 3)
GET/aulas/:idBusca uma aula
PATCH/aulas/:idAtualiza aula (valida Regra 3 de novo, se horário mudar)
DELETE/aulas/:idRemove aula
GET/aulas/:id/matriculasLista alunos matriculados nessa aula
POST/aulas/:id/matriculasMatricula um aluno (body: aluno_id) — valida Regras 1 e 2
PATCH/aulas/:id/matriculas/:matriculaIdCancela a matrícula (Regra 4) — body: {"status": "cancelada"}

7. Validações por entidade

Retomando a distinção da parte 5 da trilha API REST — validação de forma (schema) acontece antes de qualquer regra de negócio da seção 5:

EntidadeValidação de forma esperada
Alunonome obrigatório; email obrigatório, formato válido, único no sistema; data_nascimento data válida
Instrutornome obrigatório; especialidade obrigatória
Aulanome obrigatório; instrutor_id obrigatório e precisa existir; capacidade_maxima inteiro positivo; duracao_minutos inteiro positivo
Matrículaaluno_id obrigatório e precisa existir; status, quando enviado, só pode ser confirmada ou cancelada

Erro de validação de forma → 400 Bad Request. Regra de negócio da seção 5 quebrada → 409 ou 422, conforme já especificado em cada regra.

8. Autenticação (prevista, não agora)

Ainda não implementada nesta fase — fica planejada aqui só pra próxima parte da trilha já ter contexto pronto:

  • Aluno se autentica pra ver/cancelar as próprias matrículas.
  • Instrutor não precisa de login neste escopo (cadastro de instrutor é feito por quem administra o sistema).
  • Sem "papéis" complexos por enquanto — só "autenticado" vs "não autenticado" pra rotas que exigem identificar o aluno.

9. Como usar este documento

Este arquivo é a especificação que os próximos materiais da trilha `node-express/` vão implementar, endpoint por endpoint. Ele não muda conforme a implementação avança — se durante a implementação surgir necessidade de mudar uma regra ou adicionar uma entidade, volte aqui primeiro e atualize a especificação, antes de mudar o código. Mantém spec e código alinhados, e evita "regra escondida só no código" que ninguém documentou.

10. O que vem a seguir

  1. Schema do banco de dados: as 4 entidades viram tabelas de verdade no Postgres, com tipos, chaves estrangeiras e restrições.
  2. Primeiro endpoint funcional: servidor Express de pé, conexão com Postgres testada, implementando GET /alunos e POST /alunos como primeiro recorte real deste projeto.
  3. CRUD completo das demais entidades (Instrutor, Aula), aplicando as regras 1-3.
  4. Matrícula e suas regras: o endpoint mais rico do projeto — capacidade máxima, duplicidade, cancelamento.
  5. Autenticação: login de aluno, proteção das rotas de matrícula.

Com o domínio fechado, o próximo material já parte direto pra código — sem precisar mais decidir "o que é o negócio", só "como expor isso via HTTP direito".
