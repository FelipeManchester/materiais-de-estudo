Projeto Studio Fit — Trilha Node + Express — Parte 22

Deploy com HTTPS

A imagem está pronta e sobe com um comando. Falta ela existir num endereço que outra pessoa consiga digitar. Esta parte publica a API — e liga três coisas que a trilha construiu e nunca chegaram a funcionar, porque em localhost elas não fazem sentido.

1. O que muda ao sair do localhost

Em localhost, três coisas são verdade e deixam de ser em produção: você é o único usuário, ninguém está no meio do caminho, e tudo mora no mesmo endereço. Cada uma dessas quebras já tem código escrito na trilha esperando para entrar em ação.

Em localhostEm produçãoConstruído na
Cada requisição vem de um IPTodas chegam pelo proxy, com o mesmo IPParte 9 — rate limit
http://, sem criptografiahttps://, e o cookie pode exigir issoParte 11 — Secure
Front e API no mesmo endereçoDomínios diferentesPartes 9 e 11 — CORS e SameSite
Você olha o terminalVocê lê o log depoisParte 20 — X-Request-Id

Nenhuma dessas mudanças é grande. O que torna esta parte difícil é que as falhas são silenciosas: o rate limit continua "funcionando" contando errado, o cookie simplesmente não é gravado, e a doc continua abrindo apontando para o lugar errado. Nada quebra alto.

2. Onde hospedar de graça

Plano gratuito é assunto que muda todo ano, então vale o critério em vez da lista: você precisa de dois serviços — algo que rode o container e algo que guarde o banco —, e a armadilha comum é uma plataforma que dá os dois de graça só por um tempo.

PlataformaSituação
Render (aplicação)Plano gratuito sem cartão. A API hiberna quando fica ociosa; a primeira requisição depois disso leva cerca de um minuto.
Neon (banco)Postgres gratuito por tempo indeterminado, sem cartão. Escala a zero quando ninguém usa.
Postgres do Rendercuidado A instância gratuita é apagada depois de 30 dias. Por isso o banco vai para o Neon.
RailwayÓtima experiência e nativa em Docker, mas US$ 5 de crédito por 30 dias e depois ~US$ 5/mês. Serve para experimentar, não para deixar no ar.

Separar aplicação e banco em plataformas diferentes não é gambiarra de plano gratuito — é como funciona na maioria das empresas. O banco tem ciclo de vida próprio: ele sobrevive a deploys, precisa de backup e de janela de manutenção. O docker-compose.yml da parte 21 continua sendo a forma de rodar tudo junto na sua máquina; em produção, os dois se separam.

3. O banco primeiro: Neon

O banco vem antes porque a aplicação não sobe sem a DATABASE_URL dele.

  1. Crie a conta e um projeto. Escolha a região mais perto de onde a API vai rodar — cada ida ao banco atravessa essa distância.
  2. Copie a connection string. Ela tem o formato postgresql://usuario:senha@ep-alguma-coisa.regiao.aws.neon.tech/nomedobanco?sslmode=require.
  3. Guarde essa string. Ela é uma credencial — vale a mesma regra do .env: não vai para o repositório.

Repare que o banco do Neon é alcançável pela internet, diferente do seu Postgres em container, que a parte 21 fechou dentro da rede do compose. É isso que permite rodar as migrations da sua máquina (seção 12) — e é também por isso que a senha dele importa muito mais.

4. SSL na string de conexão

O ?sslmode=require no fim da URL não é decoração: o Neon recusa conexão sem TLS. A boa notícia é que o pg já entende esse parâmetro sozinho — não é preciso mexer em db/pool.js.

const { parse } = require('pg-connection-string');
parse('postgresql://u:s@ep-abc.neon.tech/estudo?sslmode=require').ssl
// {}   <- objeto vazio significa "SSL ligado, com verificação"

Só que o pg avisa que isso vai mudar:

SECURITY WARNING: The SSL modes 'prefer', 'require', and 'verify-ca' are
treated as aliases for 'verify-full'. In the next major version
(pg-connection-string v3.0.0 and pg v9.0.0), these modes will adopt
standard libpq semantics, which have weaker security guarantees.

Hoje require valida o certificado; na próxima versão maior, deixará de validar — e a sua conexão ficaria vulnerável a interceptação sem nenhum aviso. Troque para sslmode=verify-full na URL que você colar no Render. É o comportamento atual, dito de forma explícita, e imune à mudança.

Você vai ver por aí a receita ssl: { rejectUnauthorized: false }. Ela desliga a verificação do certificado — ou seja, resolve o erro escondendo o problema. O Neon tem certificado válido; não há motivo para isso aqui.

5. O rate limit que contava errado

Na parte 21, ao olhar o log do container, apareceu isto:

"ip":"::ffff:172.18.0.1"

Esse não é o IP de ninguém — é o gateway da rede Docker. Em produção acontece o mesmo com o proxy da hospedagem: todas as requisições chegam ao seu processo vindas do mesmo endereço, e o IP verdadeiro fica no header X-Forwarded-For.

O Express ignora esse header por padrão, e com razão: qualquer cliente pode forjá-lo. Confiar nele só é seguro quando existe um proxy conhecido na frente — que é exatamente o caso em produção.

Alterar app.js — logo depois do const app = express(), antes de qualquer app.use:

const app = express();

// Atrás do proxy da hospedagem, o IP de quem chega vem no X-Forwarded-For.
// Sem isto, req.ip é sempre o do proxy — e o rate limit conta o mundo
// inteiro como um usuário só.
app.set('trust proxy', 1);

app.use(registrarRequisicoes);

O 1 quer dizer "confie em um proxy à minha frente" — o da hospedagem. Não use true: isso mandaria confiar na cadeia inteira, e aí qualquer um poderia forjar o próprio IP mandando o header, que é o cenário que o rate limit tenta impedir.

A diferença é mensurável. Duas requisições, de dois IPs diferentes, olhando o contador do express-rate-limit:

Sem trust proxy

RateLimit: limit=300, remaining=299
RateLimit: limit=300, remaining=298

O contador desceu. Os dois caíram no mesmo balde — para a API, é tudo o mesmo usuário. Um cliente abusivo esgota a cota de todo mundo.

Com trust proxy

RateLimit: limit=300, remaining=299
RateLimit: limit=300, remaining=299

Cada IP tem o próprio balde. É o que a parte 9 sempre quis fazer, e nunca teve como.

6. O IP que o log não mostrava

Com o trust proxy ligado, req.ip passa a valer o IP real dentro das rotas. Mas o log da parte 20 continua mostrando o do proxy — e isso é fácil de não perceber.

O motivo: o serializer do pino-http não recebe o request do Express diretamente. Ele recebe um invólucro, onde remoteAddress é o IP do socket — o do proxy, sempre. O request do Express fica em req.raw. Medindo os três campos ao mesmo tempo, com X-Forwarded-For: 203.0.113.77:

{ "remoteAddress": "::1",
  "req.ip":         undefined,
  "req.raw.ip":     "203.0.113.77" }

Alterar middlewares/registrarRequisicoes.js — no serializers.req, a linha do ip:

    req: (req) => ({
      id: req.id,
      metodo: req.method,
      url: req.originalUrl || req.url,
      ip: req.remoteAddress,
      // req.raw é o request do Express; req.remoteAddress é o IP do socket,
      // que atrás de um proxy é sempre o do proxy.
      ip: (req.raw && req.raw.ip) || req.remoteAddress,
    }),

Sem essa correção, todo log de produção registraria o mesmo IP para todo mundo — e a primeira vez que você precisasse investigar um abuso, descobriria que o dado não está lá.

7. O cookie entre domínios

O refresh token mora num cookie desde a parte 11, com secure ligado só em produção e sameSite: 'lax'. Os dois valores precisam de atenção agora.

O secure resolve sozinho: em produção é true, e como o Render serve HTTPS, o cookie passa a trafegar criptografado. Era isso que a parte 11 estava esperando.

O sameSite é o problema. Ele quer dizer "só mande este cookie em requisições vindas do mesmo site" — e o seu front-end vai estar em outro domínio (algo como studio-fit.vercel.app, com a API em studio-fit-api.onrender.com). Para o navegador, são sites diferentes. Com lax, o cookie de refresh nunca é enviado, e a renovação de sessão simplesmente não funciona — sem erro, sem log, sem nada.

Alterar services/tokenService.js — a função opcoesCookieRefresh inteira:

function opcoesCookieRefresh() {
  const emProducao = process.env.NODE_ENV === 'production';

  // Front e API em domínios diferentes exigem SameSite=None — e o
  // navegador só aceita None junto com Secure.
  const entreSites = process.env.COOKIE_CROSS_SITE === 'true';

  return {
    httpOnly: true,
    secure: emProducao || entreSites,
    sameSite: entreSites ? 'none' : 'lax',
    path: '/auth',
    maxAge: DIAS_DE_VALIDADE * 24 * 60 * 60 * 1000,
  };
}

Os três cenários, medidos:

dev local                          secure=false | sameSite=lax
produção, mesmo site               secure=true  | sameSite=lax
produção, front em outro domínio   secure=true  | sameSite=none

SameSite=None só é aceito pelo navegador junto com Secure — por isso secure também liga quando COOKIE_CROSS_SITE está ativo. Um cookie None sem Secure é descartado em silêncio, e você fica olhando um login que "não guarda a sessão".

E vale ter claro o que se perde: SameSite=None desliga a proteção contra CSRF que o lax dava de graça. A parte 11 já explicava que essa defesa era parcial aqui; agora ela some. Se um dia o front e a API ficarem sob o mesmo domínio (com a API em /api), volte para lax — é estritamente melhor.

8. CORS com a origem real

O middleware da parte 9 lê CORS_ORIGINS do ambiente, então não há código a mudar — só configuração. Duas coisas precisam estar certas:

CORS_ORIGINS=https://studio-fit.vercel.app
  • Com https://, sem barra no fim. Origem é o trio esquema + host + porta. https://site.com/ com barra não casa com https://site.com.
  • Nunca *. O cors está com credentials: true desde a parte 11, e o navegador recusa a combinação de curinga com credenciais — a requisição falha inteira.

Enquanto o front não existir, deixe a variável com a URL da própria API. Ela some do caminho do Swagger UI (que é mesma origem) e não libera ninguém.

9. A spec que ainda diz localhost

A documentação da parte 19 declara onde a API responde. Publicada como está, o botão Try it out dispararia contra a máquina de quem abriu a página:

servers: [{ url: 'http://localhost:3000', description: 'Desenvolvimento' }],

Alterar docs/openapi.js — o servers:

  servers: [
    {
      url: process.env.PUBLIC_URL || 'http://localhost:3000',
      description: process.env.PUBLIC_URL ? 'Produção' : 'Desenvolvimento',
    },
  ],

Sem PUBLIC_URL definida, tudo continua como antes na sua máquina. Com ela, a doc publicada aponta para o endereço certo:

curl -s https://studio-fit-api.onrender.com/docs.json | jq .servers
# [{"url":"https://studio-fit-api.onrender.com","description":"Produção"}]

Se um dia isso mudar, o corte é uma linha em app.js, envolvendo as duas rotas num if (process.env.NODE_ENV !== 'production'). Registre a decisão conscientemente, é só isso que esta seção pede.

11. render.yaml

Dá para configurar tudo clicando no painel do Render. O problema é o mesmo do schema.sql da parte 14: configuração que só existe numa interface não tem histórico, não tem revisão e não sobrevive a "alguém mudou e não avisou".

Criar render.yaml — arquivo novo, na raiz:

services:
  - type: web
    name: studio-fit-api
    runtime: docker
    dockerfilePath: ./Dockerfile
    plan: free
    region: oregon
    healthCheckPath: /health

    envVars:
      - key: NODE_ENV
        value: production

      # sync: false = o Render pergunta o valor na primeira vez e guarda
      # cifrado. Não fica no repositório.
      - key: DATABASE_URL
        sync: false
      - key: CORS_ORIGINS
        sync: false
      - key: PUBLIC_URL
        sync: false

      # Gerado pelo Render, forte, e que ninguém precisa ver.
      - key: JWT_SECRET
        generateValue: true

      # Front e API em domínios diferentes: o cookie de refresh precisa
      # de SameSite=None (parte 11).
      - key: COOKIE_CROSS_SITE
        value: 'true'

Duas linhas merecem destaque.

healthCheckPath: /health aponta para a rota de liveness da parte 20 — a que não consulta o banco. Apontar para /health/ready aqui repetiria o erro que aquela parte inteira existe para evitar: um soluço no Neon viraria reinício da aplicação.

sync: false quer dizer "este valor não está no arquivo". O Render pergunta na primeira vez e guarda cifrado. É o que permite versionar a configuração sem versionar segredo — a mesma separação do .env.example.

generateValue: true no JWT_SECRET faz o Render sortear um valor forte que nem você precisa ver. Bom motivo para usar: um segredo que ninguém digitou é um segredo que ninguém vaza. Só lembre que trocá-lo invalida todos os access tokens em circulação.

12. Migrations no plano gratuito

A parte 21 avisou: migration é passo de deploy, não de boot. Colocá-la no CMD quebra assim que existir mais de uma réplica.

O lugar certo no Render seria o preDeployCommand, que roda uma vez por deploy, antes de a versão nova receber tráfego. Só que ele é exclusivo dos planos pagos. No plano gratuito, o passo de deploy é você:

DATABASE_URL='postgresql://...@ep-abc.neon.tech/estudo?sslmode=verify-full' \
  npm run migrate:up

Roda da sua máquina, apontando para o Neon — que é alcançável pela internet (seção 3). Funciona porque o node-pg-migrate só precisa de uma conexão; não importa de onde ela sai.

A ordem importa e não é a intuitiva: migre antes de publicar o código novo. Se o código novo subir esperando uma coluna que ainda não existe, ele quebra até você migrar. O contrário — banco com uma coluna a mais que o código antigo ignora — é inofensivo.

É a mesma razão pela qual, em times, migrations precisam ser compatíveis com a versão anterior do código: durante um deploy existe um intervalo em que as duas versões rodam ao mesmo tempo.

13. O primeiro deploy

  1. Suba as mudanças desta parte para o GitHub. O Render lê do repositório, então nada existe para ele antes disso.
  2. No Render, escolha New → Blueprint e aponte para o repositório. Ele acha o render.yaml e pergunta os valores marcados com sync: false.
  3. Responda as três variáveis:
    • DATABASE_URL — a string do Neon, com sslmode=verify-full
    • PUBLIC_URL — a URL que o Render acabou de te dar
    • CORS_ORIGINS — a origem do front, ou a própria URL da API por enquanto
  4. Rode as migrations (seção 12) enquanto a primeira build acontece.
  5. Acompanhe o build. Ele executa o mesmo Dockerfile da parte 21 — se funcionou na sua máquina, funciona ali.

O primeiro deploy demora alguns minutos, porque nenhuma camada está em cache no servidor do Render. Os seguintes aproveitam o cache do npm ci exatamente como a seção 4 daquela parte descreveu.

14. Deploy sem downtime

Esta seção não tem nada para fazer — é uma conferência do que já está pronto. Quando o Render publica uma versão nova, a sequência é:

  1. Sobe o container novo e espera o healthCheckPath responder 200. É o /health da parte 20.
  2. Passa a mandar tráfego para o novo.
  3. Manda SIGTERM para o antigo.
  4. O antigo marca a readiness como 503, termina as requisições em andamento, fecha o pool e sai — em torno de 0,2 s, como medido na parte 21.
  5. Se demorar demais, SIGKILL.

Os quatro pontos que a plataforma toca são código que você escreveu nas partes 20 e 21: a rota de liveness, a de readiness, o handler de SIGTERM e o CMD em forma exec. Nenhum deles fazia diferença visível em localhost. Todos fazem agora.

15. Testando

Troque SUA_URL pelo endereço que o Render deu.

# 1) está no ar, e em HTTPS
curl -s https://SUA_URL/health
# {"status":"ok","uptime_segundos":42,"timestamp":"..."}

# 2) o banco do Neon respondeu
curl -s https://SUA_URL/health/ready
# {"status":"ok","banco":"ok"}     <- 503 aqui = DATABASE_URL errada

# 3) as migrations rodaram
curl -s -o /dev/null -w "%{http_code}\n" https://SUA_URL/aulas
# 200   (500 = tabela não existe: faltou a seção 12)

# 4) a doc aponta para o lugar certo
curl -s https://SUA_URL/docs.json | grep -o '"servers":\[[^]]*\]'
# "servers":[{"url":"https://SUA_URL","description":"Produção"}]

Os dois testes que só existem em produção:

# 5) o certificado é válido (sem -k, e sem erro)
curl -sI https://SUA_URL/health | head -1
# HTTP/2 200

# 6) o cookie de refresh saiu com Secure e SameSite=None
curl -s -D - -o /dev/null -X POST https://SUA_URL/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"seu@email.com","senha":"suasenha"}' | grep -i set-cookie
# set-cookie: refresh_token=...; Path=/auth; HttpOnly; Secure; SameSite=None

Se o Secure ou o SameSite=None não aparecerem, o front vai logar e perder a sessão na primeira renovação — e sem nenhuma mensagem de erro.

No plano gratuito, a primeira requisição depois de um tempo parada leva cerca de um minuto: o container estava hibernando. Não é erro. Se estiver testando e achar que travou, espere e repita.

16. Erros comuns

  1. Esquecer o trust proxy — o rate limit passa a contar todos os usuários como um só, e nada avisa (seção 5).
  2. trust proxy com true — confia na cadeia inteira, e aí qualquer um forja o próprio IP mandando X-Forwarded-For.
  3. Corrigir o trust proxy e esquecer o serializer do log — req.ip fica certo nas rotas e o log continua registrando o proxy (seção 6).
  4. SameSite=Lax com front em outro domínio — o cookie de refresh nunca é enviado. Login funciona, sessão não sobrevive (seção 7).
  5. SameSite=None sem Secure — o navegador descarta o cookie sem dizer nada.
  6. CORS_ORIGINS com barra no fim ou com * — o primeiro não casa; o segundo é recusado por causa do credentials: true (seção 8).
  7. ssl: { rejectUnauthorized: false } — resolve o erro de conexão desligando a verificação do certificado. O Neon tem certificado válido: use sslmode=verify-full (seção 4).
  8. Migration depois de publicar o código novo — a versão nova quebra até você migrar. Migre antes (seção 12).
  9. healthCheckPath apontando para /health/ready — um problema no banco vira reinício da aplicação (seção 11).
  10. Deixar o Postgres gratuito do Render — some depois de 30 dias, com os dados (seção 2).
  11. Confundir hibernação com erro — o primeiro acesso depois de horas parado demora um minuto no plano gratuito.

17. Fim do projeto

Acabou. A API que começou como um GET /alunos devolvendo uma lista fixa na parte 4 agora está publicada, com HTTPS, autenticação por papel, transações, testes, CI, documentação navegável, log estruturado e deploy sem downtime.

O próximo projeto natural é o front-end que consome esta API. A parte 19 já deixou o contrato pronto para isso: abra /docs, teste a rota, veja a resposta real e só então escreva o cliente. E os pontos desta parte que ficaram provisórios — CORS_ORIGINS e COOKIE_CROSS_SITE — passam a ter valores de verdade no dia em que o front existir.

O momento que vale a pena é o primeiro curl https://.../health respondendo de um endereço que não é o seu computador. Depois disso, vale reler a parte 1 da trilha de API REST: as seis restrições do Fielding vão significar coisas concretas agora, porque cada uma delas virou código que você escreveu. Volta com dúvidas quando o front começar — a conversa entre os dois é onde aparecem os problemas que nenhuma das duas pontas mostra sozinha.
