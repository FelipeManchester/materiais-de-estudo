Refresh token

Na parte 7 o token do aluno vale 2 horas. Passou disso, ele digita email e senha de novo. Diminuir esse prazo melhora a segurança e piora a experiência; aumentar faz o contrário. Esta parte quebra esse dilema com um segundo token — e, de quebra, resolve uma limitação que ficou em aberto: hoje não existe logout de verdade.

1. O problema: 2 horas, e o dilema da expiração

Volta na seção 11 da parte 7, na linha que assina o token:

const token = jwt.sign({ aluno_id: aluno.id }, process.env.JWT_SECRET, {
  expiresIn: '2h',
});

Esse '2h' é um número escolhido no olho, equilibrando duas forças que puxam em direções opostas:

Se o prazo for curto (ex: 15 min)Se o prazo for longo (ex: 30 dias)
Token vazado tem pouco tempo de uso — o estrago é limitado.Token vazado serve por um mês inteiro pro atacante.
O aluno digita a senha várias vezes por dia. Experiência ruim.O aluno praticamente nunca reloga. Experiência boa.

E não dá pra "cancelar" um JWT vazado no meio do caminho. Isso é consequência direta do que a parte 7 explicou na seção 3: o servidor não guarda nada sobre os tokens que emitiu. Ele recebe a string, confere a assinatura contra o JWT_SECRET, e pronto — não existe lista de tokens válidos pra remover uma entrada. O token é válido porque a matemática fecha, não porque alguém autorizou.

Consequência prática que talvez tenha passado batido na parte 7: a API de hoje não tem logout. Você pode apagar o token no cliente (o front-end esquece a string), mas quem tiver copiado aquele token continua entrando até o prazo vencer. "Sair" hoje é um teatro do lado do cliente — o servidor não fica sabendo de nada.

A saída padrão da indústria não é escolher melhor o prazo. É usar dois tokens, com prazos e papéis diferentes.

2. Dois tokens, dois papéis

O token que você já tem passa a se chamar access token e fica curto. Um segundo token, o refresh token, fica longo e serve pra uma coisa só: pedir um access token novo sem digitar senha.

Access tokenRefresh token
Pra que serveProvar quem é você em cada requisição protegida.Trocar por um access token novo quando o atual expira.
ValidadeCurta — vamos usar 15 minutos.Longa — vamos usar 7 dias.
FormatoJWT assinado (igual à parte 7).String aleatória opaca (seção 4).
Vai em quais requisiçõesEm todas as rotas protegidas, no header Authorization.Só em POST /auth/refresh e POST /auth/logout, no body.
Servidor guarda?Não guarda nada.Guarda o hash dele no banco.
Dá pra revogar?Não — só esperar os 15 min.Sim — é o que torna o logout real.

Repare no ganho: o token que trafega o tempo todo (e portanto tem mais chance de vazar em log, histórico de proxy, extensão de navegador) agora vale 15 minutos. O token que vale 7 dias trafega raramente, e esse pode ser cancelado no banco a qualquer momento.

3. Isso quebra o stateless (e tudo bem)

Vale ser honesto sobre o custo, porque a parte 7 vendeu JWT justamente como a forma de aplicar a restrição stateless de Fielding (parte 1 da trilha API REST): guardar refresh token no banco é, literalmente, o servidor mantendo estado sobre sessões.

A diferença é onde esse estado é consultado:

Continua stateless

Todas as rotas protegidas (POST /aulas/:id/matriculas, GET /alunos/:id/matriculas, ...) seguem só verificando a assinatura do access token. Zero consulta ao banco pra saber quem é o aluno.

Vira stateful

Só POST /auth/refresh e POST /auth/logout vão ao banco. Uma vez a cada 15 minutos, contra todas as outras requisições do período.

É um trade-off consciente, do mesmo tipo que a parte 6 fez ao aceitar a condição de corrida da Regra 1: você abre mão de pureza arquitetural num ponto pequeno e localizado, em troca de uma capacidade concreta (revogar sessão) que não existe de outro jeito. O modelo clássico de sessão consulta o banco em toda requisição; aqui, numa a cada 15 minutos.

4. Por que o refresh não é um JWT

Seria tentador emitir o refresh token também com jwt.sign, só que com expiresIn: '7d'. Não vamos, por um motivo direto: a única vantagem do JWT é não precisar consultar o banco — e o refresh token vai ser consultado no banco de qualquer jeito, pra saber se foi revogado. Um JWT que exige ida ao banco é um JWT que perdeu o motivo de existir, e ainda carrega o peso extra (string comprida, payload legível em Base64, risco de alguém achar que pode confiar nele sem checar).

Então o refresh token vai ser opaco: 32 bytes aleatórios em hexadecimal, uma string de 64 caracteres sem nenhum significado interno. Quem olha não extrai nada dela; o servidor não "lê" o token, ele procura o token.

De onde vem a aleatoriedade

Do módulo crypto do próprio Node — crypto.randomBytes(32), o mesmo comando que a parte 7 usou pra gerar o JWT_SECRET. É um gerador criptograficamente seguro, diferente de Math.random() (previsível, jamais use pra nada de segurança). 32 bytes = 256 bits de entropia: adivinhar um token válido por tentativa é inviável.

5. Rotação e detecção de reuso

Um refresh token de 7 dias que pode ser usado várias vezes é um alvo gordo. A prática padrão é rotação: cada vez que o refresh é usado, ele é revogado e um novo é emitido junto com o access token. Cada refresh token vale um uso.

Isso traz de brinde um detector de vazamento. Pensa no que acontece se um atacante copiar o refresh token do aluno:

1

Os dois têm a mesma string

Aluno legítimo e atacante seguram o mesmo refresh token R1.

2

Um dos dois usa primeiro

Digamos o atacante. R1 é revogado, ele recebe R2. Até aqui, nada parece errado pro servidor.

3

O outro tenta usar

O aluno legítimo manda R1 — um token que existe no banco mas já está revogado. Isso nunca acontece num fluxo normal: cliente honesto joga fora o token usado.

4

Servidor reage

Token revogado sendo reapresentado = a string está em duas mãos. O servidor revoga todos os refresh tokens daquele aluno, incluindo o R2 que o atacante acabou de ganhar. Os dois são obrigados a logar de novo — e só o legítimo sabe a senha.

Repare que o servidor não sabe qual dos dois é o impostor, e nem precisa saber. Derrubar a sessão dos dois já resolve, porque a senha é o desempate.

Esse mecanismo depende de conseguir distinguir três situações diferentes: token inexistente (lixo, ou de outro sistema), token expirado (passou dos 7 dias, normal) e token revogado (suspeito). Guarda isso — é o motivo de a busca no banco, na seção 9, trazer a linha inteira em vez de já filtrar WHERE revogado_em IS NULL.

6. O fluxo completo, passo a passo

1

Login

POST /auth/login com email e senha, igual à parte 7. A resposta agora traz dois tokens: access_token (15 min) e refresh_token (7 dias).

2

Uso normal

Cliente manda o access token no header Authorization: Bearer <token>, exatamente como na parte 7. Nada muda nas rotas protegidas — o middleware autenticar continua igual.

3

Access token expira

Depois de 15 minutos, a rota protegida responde 401 com "Token inválido ou expirado". É o sinal pro cliente ir renovar — não é erro do usuário.

4

Renovação

POST /auth/refresh com o refresh token no body. Servidor confere no banco, revoga o token usado e devolve um par novo (access + refresh). Sem senha, sem tela de login.

5

Logout

POST /auth/logout com o refresh token. Servidor marca como revogado. O aluno não consegue mais renovar — e em no máximo 15 minutos o access token dele também morre.

7. Schema: tabela refresh_tokens

Criar tabela nova no banco. Rode no psql (docker compose exec -T db psql -U postgres -d estudo) ou no DBeaver, igual você fez com a coluna senha_hash na parte 7.

CREATE TABLE IF NOT EXISTS refresh_tokens (
  id SERIAL PRIMARY KEY,
  aluno_id INTEGER NOT NULL REFERENCES alunos(id) ON DELETE CASCADE,
  token_hash CHAR(64) NOT NULL UNIQUE,
  expira_em TIMESTAMP NOT NULL,
  revogado_em TIMESTAMP,
  criado_em TIMESTAMP NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS refresh_tokens_aluno_id_idx
  ON refresh_tokens (aluno_id);

Alterar db/schema.sql — cole o mesmo CREATE TABLE acima no fim do arquivo, depois do índice de matriculas. O arquivo é a documentação do schema completo (parte 3); se ele não acompanhar as alterações, quem clonar o projeto do zero monta um banco diferente do seu.

Coluna por coluna, o que cada uma resolve:

ColunaPor que existe
aluno_idDe quem é a sessão. O ON DELETE CASCADE faz os tokens sumirem junto com o aluno — token órfão apontando pra aluno inexistente não faria sentido nenhum.
token_hashO hash SHA-256 do token, em hexadecimal — sempre 64 caracteres, por isso CHAR(64). Nunca o token em si (seção 8). O UNIQUE garante a busca por igualdade e serve de índice.
expira_emQuando o token deixa de valer. Gravado como data absoluta, calculada no momento da criação — mais simples de consultar do que guardar "duração" e somar depois.
revogado_emNULL = ativo. Preenchido = revogado (por uso, por logout ou por suspeita de vazamento). Guardar quando em vez de um booleano revogado não custa nada e ajuda a investigar depois.
Por que a linha não é simplesmente apagada

Rotação poderia dar DELETE no token usado. Só que aí a detecção de reuso da seção 5 morre: um token deletado é indistinguível de um token que nunca existiu, e a reapresentação de R1 viraria só mais um 401 silencioso, sem alarme. Marcar em vez de apagar é o mesmo raciocínio do soft-delete que a parte 6 deixou anotado pra instrutor.

8. Gerar e guardar: services/tokenService.js

Guardar o refresh token em texto puro no banco seria repetir, com outro nome, o erro de guardar senha em texto puro (parte 7, seção 5): quem vazar a tabela sai logado como qualquer aluno. Então guardamos o hash, e o token puro só existe em dois lugares — na resposta HTTP e na mão do cliente.

Mas aqui usamos SHA-256, não bcrypt. Isso parece contradizer a parte 7, e não contradiz — os dois casos são diferentes:

Senha (parte 7 → bcrypt)Refresh token (aqui → SHA-256)
EntropiaBaixa. Gente escolhe senha123, aniversário, nome do cachorro. Dá pra chutar.256 bits vindos de randomBytes. Não dá pra chutar, nem com força bruta.
Por que lento ajudaLentidão é a defesa contra quem testa milhões de senhas prováveis por segundo.Não há lista de "tokens prováveis" pra testar. Lentidão só custa CPU sem comprar nada.
Como é verificadoVocê já sabe qual aluno é (buscou por email) e compara um hash só.Você não sabe de quem é o token — precisa achá-lo no banco.

Essa última linha é a que decide: bcrypt gera um salt aleatório por hash (parte 7, seção 5), então o mesmo token hasheado duas vezes dá resultados diferentes. Ótimo pra senha, inviável aqui — não existiria WHERE token_hash = $1, você teria que ler a tabela inteira e rodar bcrypt.compare linha por linha. SHA-256 é determinístico: mesmo token, mesmo hash, busca direta pelo índice.

Criar services/tokenService.js — arquivo novo, ao lado do senhaService.js da parte 7. Duas funções, nenhuma delas sabe o que é um "aluno":

const crypto = require('node:crypto');

const DIAS_DE_VALIDADE = 7;

function gerarRefreshToken() {
  return crypto.randomBytes(32).toString('hex');
}

function hashRefreshToken(token) {
  return crypto.createHash('sha256').update(token).digest('hex');
}

function calcularExpiracao() {
  const agora = new Date();
  agora.setDate(agora.getDate() + DIAS_DE_VALIDADE);
  return agora;
}

module.exports = { gerarRefreshToken, hashRefreshToken, calcularExpiracao };

node:crypto é módulo nativo — não tem npm install nesta parte, nenhuma dependência nova entra no projeto. O prefixo node: deixa explícito que é built-in do Node, não um pacote do node_modules com esse nome (convenção recente, mas já é o estilo recomendado).

hashRefreshToken é síncrona de propósito: SHA-256 de 64 caracteres é instantâneo, não faz sentido o async/await que o senhaService precisa ter. Se você escrever await hashRefreshToken(...) por hábito, funciona igual (await em valor não-Promise é inofensivo) — mas é ruído.

9. Repository: refreshTokensRepository.js

Criar repositories/refreshTokensRepository.js — arquivo novo, seguindo o mesmo padrão dos outros repositories (só SQL, nenhuma regra de negócio):

const pool = require('../db/pool');

async function criar({ aluno_id, token_hash, expira_em }) {
  const query = /* sql */ `
    INSERT INTO refresh_tokens (aluno_id, token_hash, expira_em)
    VALUES ($1, $2, $3)
    RETURNING *
  `;
  const resultado = await pool.query(query, [aluno_id, token_hash, expira_em]);
  return resultado.rows[0];
}

async function buscarPorHash(token_hash) {
  const query = 'SELECT * FROM refresh_tokens WHERE token_hash = $1';
  const resultado = await pool.query(query, [token_hash]);
  return resultado.rows[0];
}

async function revogar(id) {
  const query = /* sql */ `
    UPDATE refresh_tokens
    SET revogado_em = NOW()
    WHERE id = $1 AND revogado_em IS NULL
    RETURNING *
  `;
  const resultado = await pool.query(query, [id]);
  return resultado.rows[0];
}

async function revogarTodosDoAluno(aluno_id) {
  const query = /* sql */ `
    UPDATE refresh_tokens
    SET revogado_em = NOW()
    WHERE aluno_id = $1 AND revogado_em IS NULL
  `;
  await pool.query(query, [aluno_id]);
}

module.exports = { criar, buscarPorHash, revogar, revogarTodosDoAluno };
Por que buscarPorHash não filtra revogado nem expirado

Seria natural escrever WHERE token_hash = $1 AND revogado_em IS NULL AND expira_em > NOW() e devolver só tokens usáveis. Aí a rota receberia undefined nos três casos — token inexistente, expirado e revogado viram a mesma coisa — e a detecção de reuso da seção 5 fica impossível. O repository traz a linha crua; quem decide o que cada estado significa é a rota (seção 12).

O AND revogado_em IS NULL no revogar tem outra função: garante que revogar duas vezes não sobrescreve o timestamp original, e faz a função devolver undefined se o token já estava revogado.

10. Um lugar só pra emitir o par

Duas rotas vão precisar emitir o mesmo par de tokens: o login (seção 11) e o refresh (seção 12). Escrever o mesmo bloco nas duas convida a alterar uma e esquecer a outra — exatamente o tipo de divergência que vira bug de segurança silencioso.

Alterar routes/auth.js — no topo do arquivo, adicione os imports novos junto dos que já existem:

const express = require('express');
const jwt = require('jsonwebtoken');

const { compararSenha } = require('../services/senhaService');
const {
  gerarRefreshToken,
  hashRefreshToken,
  calcularExpiracao,
} = require('../services/tokenService');
const alunosRepository = require('../repositories/alunosRepository');
const refreshTokensRepository = require('../repositories/refreshTokensRepository');

const router = express.Router();

Adicionar routes/auth.js — logo depois do const router = express.Router(); e antes do router.post('/login', ...), uma função auxiliar:

async function emitirTokens(aluno) {
  const accessToken = jwt.sign({ aluno_id: aluno.id }, process.env.JWT_SECRET, {
    expiresIn: '15m',
  });

  const refreshToken = gerarRefreshToken();

  await refreshTokensRepository.criar({
    aluno_id: aluno.id,
    token_hash: hashRefreshToken(refreshToken),
    expira_em: calcularExpiracao(),
  });

  return { access_token: accessToken, refresh_token: refreshToken };
}
Por que uma função no arquivo, e não um authService.js

Mesmo raciocínio da parte 7, seção 8: senhaService.js nasceu porque hash de senha é operação genérica, que outra entidade com login usaria igual. Já emitirTokens é específico do fluxo de autenticação de aluno deste projeto, e é usada por duas rotas do mesmo arquivo. Criar authService.js agora seria uma camada com um cliente só, adivinhando um futuro que ainda não chegou. Se um dia instrutor ganhar login, aí sim a função sai daqui.

Note o expiresIn: '15m' — o access token encurtou aqui dentro, e essa é a única linha do projeto que define esse prazo. O login não assina mais token nenhum por conta própria (próxima seção).

11. Login passa a devolver os dois tokens

Alterar routes/auth.js — dentro de router.post('/login', ...), no fim do handler. Apague as linhas do jwt.sign e o res.json({ token }), e troque pelas duas linhas destacadas. Todo o resto da rota (validação de campos, busca por email, compararSenha, os dois 401) fica exatamente igual:

  // ...validações e checagem de senha continuam iguais

  const token = jwt.sign({ aluno_id: aluno.id }, process.env.JWT_SECRET, {
    expiresIn: '2h',
  });
  res.json({ token });
  const tokens = await emitirTokens(aluno);
  res.json(tokens);
});

A resposta do login muda de formato:

Antes (parte 7)

{ "token": "eyJhbGci..." }

Agora

{
  "access_token": "eyJhbGci...",
  "refresh_token": "9f2c...64 chars"
}

Isso é uma quebra de contrato. Qualquer cliente que lia resposta.token passa a receber undefined. Num projeto com front-end em produção, mudar o nome de um campo assim exige versionamento ou um período com os dois campos convivendo — é o tipo de decisão que a parte 3 da trilha API REST discute em "URIs são contrato". Aqui, com o único cliente sendo o seu curl, a troca é livre.

12. Rota nova: POST /auth/refresh

É a rota que concentra tudo que foi discutido nas seções 5 e 9. Ela recebe um refresh token e responde uma de quatro coisas: par novo, token desconhecido, token expirado, ou alarme de reuso.

Adicionar routes/auth.js — depois do router.post('/login', ...), antes do module.exports:

router.post('/refresh', async (req, res) => {
  const { refresh_token } = req.body;

  if (!refresh_token) {
    return res.status(400).json({ erro: 'refresh_token é obrigatório' });
  }

  const registro = await refreshTokensRepository.buscarPorHash(
    hashRefreshToken(refresh_token),
  );

  if (!registro) {
    return res.status(401).json({ erro: 'Refresh token inválido' });
  }

  if (registro.revogado_em) {
    // Token já usado sendo reapresentado: sinal de vazamento (seção 5).
    await refreshTokensRepository.revogarTodosDoAluno(registro.aluno_id);
    return res.status(401).json({ erro: 'Refresh token inválido' });
  }

  if (registro.expira_em < new Date()) {
    return res.status(401).json({ erro: 'Refresh token expirado' });
  }

  const aluno = await alunosRepository.buscarPorId(registro.aluno_id);
  if (!aluno) {
    return res.status(401).json({ erro: 'Refresh token inválido' });
  }

  await refreshTokensRepository.revogar(registro.id);

  const tokens = await emitirTokens(aluno);
  res.json(tokens);
});

A ordem das checagens não é arbitrária — cada uma depende da anterior ter passado:

SituaçãoRespostaEfeito colateral
Hash não existe no banco401 "Refresh token inválido"Nenhum. Pode ser lixo, token de outro ambiente, ou chute.
Existe, mas revogado_em preenchido401 "Refresh token inválido"Revoga todos os tokens ativos do aluno.
Ativo, mas passou de expira_em401 "Refresh token expirado"Nenhum. Ficou 7 dias sem usar, precisa logar de novo.
Ativo e no prazo200 com o par novoRevoga o token usado (rotação).
Por que "inválido" e "expirado" têm mensagens diferentes

Parece contradizer a parte 7, seção 11, onde os dois erros de login viraram a mesma mensagem genérica. A diferença é o que cada mensagem entrega pra quem está do outro lado: no login, distinguir "email não existe" de "senha errada" permite descobrir quem está cadastrado testando emails. Aqui, "expirado" só é dito a quem já apresentou um token válido que o servidor emitiu — não vaza a existência de ninguém, e ajuda o cliente a mostrar "sua sessão terminou" em vez de "erro". O reuso, por outro lado, responde a mensagem genérica de propósito: se um atacante souber que foi detectado, ele age antes de você.

A busca por alunosRepository.buscarPorId parece redundante — o token já diz o aluno_id. Ela existe pro caso do aluno ter sido apagado depois da emissão: sem ela, emitirTokens tentaria inserir um refresh_tokens.aluno_id apontando pra ninguém, e o REFERENCES alunos(id) do banco derrubaria a requisição com 500 em vez de um 401 honesto.

Limitação conhecida, registrada de propósito: entre o buscarPorHash e o revogar existe uma janela em que duas requisições simultâneas com o mesmo refresh token passariam as duas. É a mesma condição de corrida da Regra 1 na parte 6, e a solução também seria a mesma (transação com SELECT ... FOR UPDATE, ou fazer da própria revogação a checagem: UPDATE ... WHERE revogado_em IS NULL RETURNING * e desistir se não voltar linha). Fica anotado, não resolvido aqui.

13. Rota nova: POST /auth/logout

Adicionar routes/auth.js — depois da rota de refresh, ainda antes do module.exports:

router.post('/logout', async (req, res) => {
  const { refresh_token } = req.body;

  if (!refresh_token) {
    return res.status(400).json({ erro: 'refresh_token é obrigatório' });
  }

  const registro = await refreshTokensRepository.buscarPorHash(
    hashRefreshToken(refresh_token),
  );

  if (registro) {
    await refreshTokensRepository.revogar(registro.id);
  }

  res.status(204).send();
});
Por que 204 mesmo quando o token não existe

Logout é idempotente (conceito da parte 2 da trilha API REST): o resultado desejado é "essa sessão não vale mais", e isso já é verdade se o token nunca existiu ou já estava revogado. Responder 404 a um logout obrigaria todo cliente a tratar um erro que não é erro — e ainda contaria pra quem estivesse chutando strings quais delas existem no banco. Chamar duas vezes seguidas dá 204 nas duas.

O access token sobrevive ao logout — por até 15 minutos. Não é bug, é a consequência direta do stateless (seção 1): não existe lista de tokens válidos pra remover uma entrada. Quem precisa de corte instantâneo (banco, saúde) tem que consultar uma denylist a cada requisição, o que joga fora boa parte do ganho do JWT. Encurtar o access token é o meio-termo que a indústria adotou, e é por isso que 15 minutos é um número comum.

Repare que /auth/logout não usa o middleware autenticar. Exigir access token válido pra sair seria impedir logout justamente de quem está com o access expirado — a hora em que sair é mais provável. A prova de posse aqui é o próprio refresh token.

# reusa o refresh ANTIGO: dispara a detecção da seção 5
curl -X POST http://localhost:3000/auth/refresh \
  -H "Content-Type: application/json" \
  -d '{"refresh_token":"REFRESH_ANTIGO"}'
# 401, "Refresh token inválido"

# e agora o refresh NOVO também morreu (foi revogado junto)
curl -X POST http://localhost:3000/auth/refresh \
  -H "Content-Type: application/json" \
  -d '{"refresh_token":"REFRESH_NOVO"}'
# 401 — prova de que revogarTodosDoAluno rodou

# refresh inexistente
curl -X POST http://localhost:3000/auth/refresh \
  -H "Content-Type: application/json" \
  -d '{"refresh_token":"nao_existe"}'
# 401, "Refresh token inválido"

# logout (logue de novo antes, pra ter um refresh válido)
curl -X POST http://localhost:3000/auth/logout \
  -H "Content-Type: application/json" \
  -d '{"refresh_token":"REFRESH_AQUI"}'
# 204, sem corpo

# logout de novo, mesmo token: continua 204 (idempotente)
curl -X POST http://localhost:3000/auth/logout \
  -H "Content-Type: application/json" \
  -d '{"refresh_token":"REFRESH_AQUI"}'
# 204

Pra conferir o efeito no banco depois de brincar um pouco:

docker compose exec -T db psql -U postgres -d estudo \
  -c "SELECT id, aluno_id, LEFT(token_hash, 12) AS hash, revogado_em, expira_em FROM refresh_tokens ORDER BY id;"

Você deve ver uma linha por token emitido, com revogado_em preenchido em todos os que já foram usados ou revogados em cascata, e a coluna hash mostrando que o token puro não está lá.

Pra ver o access token expirar sem esperar 15 minutos: troque temporariamente o expiresIn: '15m' do emitirTokens por '10s', faça login, espere passar, e chame uma rota protegida — deve dar 401 "Token inválido ou expirado". Aí use o refresh pra pegar um access novo e repita a chamada: 200. Esse é o ciclo inteiro que o front-end automatiza. Depois devolve pra '15m'.

15. Erros comuns

  1. Guardar o refresh token em texto puro no banco — vazou a tabela, vazaram todas as sessões ativas. É o mesmo erro da senha em texto puro, com outro nome.
  2. Usar bcrypt no refresh token — o salt por hash impede o WHERE token_hash = $1, e você acaba varrendo a tabela inteira a cada renovação (seção 8).
  3. Filtrar revogado_em IS NULL direto no SELECT — some com a diferença entre "não existe" e "já foi usado", e a detecção de reuso deixa de existir sem nenhum erro aparecer.
  4. Não rotacionar — devolver o mesmo refresh token na renovação transforma um vazamento único em acesso permanente por 7 dias, sem alarme nenhum.
  5. Mandar o access token no /auth/refresh — são tokens diferentes, com formatos diferentes. O hash de um JWT nunca vai bater com nenhum token_hash da tabela: 401.
  6. Esperar que o logout mate o access token na hora — não mata, e nenhum ajuste de código muda isso sem abandonar o stateless (seção 13).
  7. Comparar expira_em com string — o driver pg devolve TIMESTAMP como objeto Date do JavaScript. Comparar com new Date() funciona; comparar com Date.now() (número) dá resultado sem sentido, sem lançar erro.
  8. Esquecer de atualizar o db/schema.sql — o banco da sua máquina fica certo e o arquivo versionado fica mentindo. Quem clonar o projeto monta um schema sem refresh_tokens e só descobre no primeiro login.

16. O que vem a seguir

O ciclo de autenticação está fechado: login, uso, renovação sem senha, logout de verdade e reação a vazamento. Com isso, o que estava previsto na parte 2 para o Studio Fit acabou — as 4 entidades, as 4 regras de negócio e a proteção das rotas de matrícula.

O que vem daqui em diante não é mais "funcionalidade que falta", é o que separa um projeto que roda na sua máquina de um que aguenta ser usado por outras pessoas. São muitos itens, então ficam agrupados por natureza, e as partes seguintes da trilha atacam uma categoria por vez, nesta ordem:

  1. Segurança de borda e autorização — a próxima parte. Depois de todo cuidado das partes 7 e 8, o POST /auth/login ainda aceita quantas tentativas o atacante quiser: bcrypt segura força bruta offline, não online. Entram rate limit, headers de segurança (helmet), CORS e limite de tamanho de body — e depois papéis (instrutor/admin), que fecham o GET /aulas/:id/matriculas deixado aberto de propósito na parte 7, e o cookie httpOnly pro refresh token (tira ele do alcance de um XSS, mas traz CSRF pra mesa e exige HTTPS).
  2. Corretude e robustez — hoje toda validação é if (!nome || !email). Mande data_nascimento: "banana" e o erro vira 500 do Postgres, não 400. Validação de schema (Zod ou Joi) num middleware, mais uma classe de erro de domínio pra 409/422 pararem de virar 500. Junto vêm as transações: a condição de corrida da Regra 1 (parte 6) e a da rotação de refresh (seção 12 desta parte) são o mesmo problema, e se resolvem com SELECT ... FOR UPDATE e afins.
  3. Banco e dados — tudo que hoje é feito na mão no psql: migrations versionadas (o ALTER TABLE da parte 7 e o CREATE TABLE desta viram arquivos que rodam sozinhos), limpeza periódica dos refresh tokens expirados (a tabela só cresce), e o soft-delete de instrutor anotado na parte 6.
  4. Qualidade — testes automatizados (Jest + supertest), começando pelos quatro caminhos do /auth/refresh e pelas quatro regras de negócio, e CI rodando lint + testes a cada push.
  5. Contrato da API — paginação, filtro e ordenação (a parte 3 da trilha API REST ensina, a nossa API ainda devolve a tabela inteira em GET /alunos) e documentação OpenAPI com Swagger UI, pra outra pessoa conseguir consumir sem ler o código.
  6. Produção — logging estruturado e health check, Dockerfile do app (hoje só o banco está em container) e o deploy de verdade: env de produção, banco gerenciado e HTTPS. Sem HTTPS, todo o cuidado desta parte vai por água abaixo — o token trafega em texto puro na rede.

Deploy fica por último de propósito: cada categoria acima muda o que você empacota. Ficam fora de escopo desta trilha, por não serem necessidade do Studio Fit: HATEOAS, cache com Redis, WebSocket, fila e microserviços — coisas que entram se você quiser estudar a tecnologia em si, não porque o projeto pediu.

Quando testar, presta atenção especial no passo do reuso — logue, renove, e tente usar o refresh antigo de novo. Ver os dois tokens morrerem de uma vez é o momento em que a seção 5 sai do papel. Volta com dúvidas, principalmente se algum 401 aparecer onde você esperava 200, ou se ficar em dúvida sobre por que o access token continua vivo depois do logout.
