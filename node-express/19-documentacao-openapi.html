Documentação com OpenAPI

A API está completa e testada, e ainda assim ninguém além de você consegue usá-la sem abrir o código. Esta parte descreve o contrato num formato que ferramentas entendem — e transforma essa descrição numa página onde dá para testar cada rota pelo navegador.

1. A API que só o código descreve

Responda sem olhar o projeto: o que POST /alunos exige no corpo? Quantos caracteres o nome pode ter? GET /alunos aceita quais parâmetros de query? Quem pode chamar? O que volta em caso de erro?

Tudo isso existe, escrito com precisão — espalhado entre schemas/alunoSchema.js, routes/alunos.js e a matriz da parte 10. Um consumidor da sua API precisaria ler os três, em JavaScript, para montar uma requisição.

Sem documentaçãoCom OpenAPI
"Manda um curl de exemplo pra mim?"Uma página com todas as rotas, campos e formatos.
Descobrir os erros possíveis testando até quebrar.Cada resposta documentada, com o formato do corpo.
Cliente escrito na mão, campo por campo.Cliente gerado a partir da especificação.
A documentação é o código.A documentação nasce do código (seções 4 e 17).

Isso importa especialmente no seu caso: você mencionou querer construir um front-end para esta API. A especificação é exatamente o contrato que o front vai consumir — e a página do Swagger UI é onde você testa uma rota e vê a resposta real antes de escrever a primeira linha do cliente.

2. O que é OpenAPI

OpenAPI é um formato padronizado para descrever uma API HTTP: quais caminhos existem, que métodos aceitam, o formato de entrada e saída, os códigos de status, e como autenticar. A descrição é um documento JSON ou YAML — não é código, não roda, é dado.

Isso é o que a torna útil: sendo dado num formato conhecido, ferramentas fazem coisas com ela.

FerramentaO que faz com a spec
Swagger UIGera uma página navegável, com formulário para testar cada rota. É o que vamos servir.
Geradores de clienteProduzem código de cliente em várias linguagens a partir da spec.
Postman / InsomniaImportam a spec e criam a coleção de requisições pronta.
Validadores de contratoConferem se a API responde o que a spec promete.
Swagger ou OpenAPI?

Os dois nomes aparecem misturados por motivo histórico. "Swagger" era a especificação original; em 2015 ela foi doada para a OpenAPI Initiative e renomeada para OpenAPI a partir da versão 3. "Swagger" hoje é o nome das ferramentas (Swagger UI, Swagger Editor), mantidas pela SmartBear.

Na prática: o documento é OpenAPI, a página que o exibe é Swagger UI.

3. Escrever à mão ou derivar

Duas abordagens, e a escolha define se a documentação vai envelhecer bem:

Escrever à mão

Um arquivo YAML descrevendo tudo. Controle total sobre o texto, e duas fontes da verdade: o schema Zod valida, o YAML documenta, e na primeira mudança em um deles os dois divergem em silêncio.

Derivar dos schemas

Os schemas Zod das partes 12 e 18 já descrevem cada entrada com precisão — tipo, tamanho, formato, valores aceitos. Converter isso em OpenAPI mantém uma fonte só: mudou o schema, mudou a doc.

Vamos derivar. Não dá para derivar tudo — descrição em prosa, exemplos e códigos de resposta continuam sendo escritos à mão —, mas a parte que mais muda e mais erra quando desatualiza (o formato dos dados) sai de graça.

4. Zod vira JSON Schema

OpenAPI descreve dados usando JSON Schema. E o Zod 4 converte para JSON Schema nativamente, sem nenhuma biblioteca extra:

const { z } = require('zod');
const { criarAlunoSchema } = require('./schemas');

console.log(z.toJSONSchema(criarAlunoSchema));
{
  "type": "object",
  "properties": {
    "nome":  { "type": "string", "minLength": 2, "maxLength": 120 },
    "email": { "type": "string", "maxLength": 160, "format": "email", "pattern": "..." },
    "data_nascimento": { "type": "string", "format": "date", "pattern": "..." },
    "senha": { "type": "string", "minLength": 8, "maxLength": 72 }
  },
  "required": ["nome", "email", "data_nascimento", "senha"],
  "additionalProperties": false
}

Repare no que veio junto: os limites de tamanho da parte 12, o formato de email, e o additionalProperties: false que corresponde ao z.strictObject. A documentação herda cada decisão de validação sem ninguém redigitar nada.

Se o seu projeto usasse Zod 3, isso exigiria a biblioteca @asteasolutions/zod-to-openapi. A conversão nativa chegou no Zod 4 — e é mais um motivo para a escolha da parte 12 ter envelhecido bem.

5. io: input, e por que importa

Um schema Zod descreve duas coisas diferentes: o que entra e o que sai depois das transformações. Para .default() e .trim(), essas duas coisas divergem — e a documentação precisa da entrada, que é o que o cliente manda.

Compare o mesmo schema de paginação convertido nos dois modos:

ModorequiredSignificado
io: 'output' (padrão)["pagina","limite","ordenar_por","ordem"]Depois do parse, esses campos sempre existem — o default preencheu. Verdade sobre a saída, mentira sobre o que o cliente precisa enviar.
io: 'input'[]Nenhum é obrigatório na requisição. É isto que a documentação deve dizer.

Documentar com o padrão faria a página do Swagger marcar pagina e limite como obrigatórios em GET /alunos — e quem lesse a doc mandaria os dois sempre, achando que a rota exige. A doc estaria descrevendo com precisão um comportamento que não existe.

Junto vai target: 'openapi-3.0', que ajusta detalhes de compatibilidade (o OpenAPI 3.0 usa um dialeto ligeiramente diferente de JSON Schema) e remove o campo $schema, que não pertence a uma spec OpenAPI.

7. Componentes reaproveitáveis

Todo erro da API tem o mesmo formato desde a parte 12 — { erro }, com detalhes nos casos de validação. Repetir esse objeto em cada resposta de cada rota seria dezenas de cópias. components/schemas guarda uma vez, e as rotas referenciam com $ref.

Adicionar docs/openapi.js — um atalho para as respostas de erro, antes do objeto openapi:

Com isso, documentar um 401 vira 401: erro('Não autenticado') em vez de seis linhas repetidas.

8. Descrevendo a autenticação

O securitySchemes da seção anterior declara como autenticar; cada rota declara se exige. O bearerAuth descreve exatamente o que a parte 7 construiu: um token JWT no header Authorization.

get: {
  tags: ['Alunos'],
  summary: 'Lista alunos (somente admin)',
  security: [{ bearerAuth: [] }],
  // ...
}

Duas consequências práticas na página do Swagger UI: as rotas protegidas ganham um cadeado, e aparece um botão Authorize onde você cola um access token uma vez — todas as requisições de teste passam a mandá-lo.

Rotas sem security são públicas. Vale conferir essa lista contra a matriz da parte 10 enquanto escreve: é a segunda vez que você declara as mesmas permissões, e a doc que discorda do código é pior do que doc nenhuma. Um dia isso pode ser derivado do próprio autorizar(...) — mas aí é infraestrutura, não documentação.

9. Query params a partir do schema

OpenAPI descreve parâmetro de query num formato próprio — um objeto por parâmetro, com name, in e schema. O schema de paginação da parte 18 tem cinco; escrever os cinco à mão em cada rota que lista seria repetir o que o Zod já sabe.

Adicionar docs/openapi.js — uma função que converte um schema de objeto na lista de parâmetros, logo abaixo do paraJsonSchema:

function parametrosDeQuery(schema) {
  const jsonSchema = paraJsonSchema(schema);
  const obrigatorios = jsonSchema.required ?? [];

  return Object.entries(jsonSchema.properties).map(([nome, definicao]) => ({
    name: nome,
    in: 'query',
    required: obrigatorios.includes(nome),
    schema: definicao,
  }));
}

O resultado, para a listagem de alunos, é a lista completa com tipos, limites e valores aceitos:

parametros de query gerados: pagina, limite, ordenar_por, ordem, nome

{
  "name": "pagina",
  "in": "query",
  "required": false,
  "schema": { "default": 1, "type": "integer", "minimum": 0, "exclusiveMinimum": true }
}

O ordenar_por vira um enum na página — quem lê a doc vê exatamente as três colunas aceitas, sem precisar descobrir por tentativa e erro.

Só que listarAlunosQuerySchema e listarInstrutoresQuerySchema estão declarados dentro das rotas (parte 18), e a spec não alcança nenhum dos dois. Duas saídas: repetir a construção no docs/ — que recria a divergência que a seção 3 quer evitar — ou mover os schemas para schemas/ e importá-los nos dois lugares.

A segunda é a correta. Schema que precisa ser conhecido por mais de um módulo pertence a schemas/, que é justamente o lugar criado na parte 12 para isso. listarAulasQuerySchema já mora lá — os outros dois ficaram para trás por acaso, não por decisão.

10. Uma rota vira um path item

Até aqui a spec descreve tipos e não descreve nenhuma rota. O paths é o mapa: cada chave é um caminho, cada chave interna é um método HTTP, e o objeto de dentro é uma operação.

paths: {
  '/alunos': {
    get:  { /* operação: GET /alunos  */ },
    post: { /* operação: POST /alunos */ },
  },
  '/alunos/{id}/matriculas': {
    get: { /* ... */ },
  },
}

Repare no {id}: OpenAPI usa chaves para parâmetro de caminho, não os dois-pontos do Express. /alunos/:id vira /alunos/{id}.

Uma operação aceita estas chaves:

ChaveO que é
tagsEm qual grupo da página a rota aparece. Usa os nomes declarados em tags (seção 6).
summaryUma linha, mostrada ao lado da rota na lista fechada.
descriptionTexto longo, mostrado quando a rota é expandida. É onde cabe a regra de negócio.
securityExige autenticação (seção 8). Ausente = rota pública.
parametersParâmetros de caminho (in: 'path') e de query (in: 'query', seção 9).
requestBodyO corpo esperado. Só faz sentido em POST, PUT e PATCH.
responsesUm objeto por código de status. É a metade do contrato que ninguém documenta e todo mundo precisa.

Escrita sem nenhum atalho, a operação mais simples do projeto — POST /alunos — fica assim:

post: {
  tags: ['Alunos'],
  summary: 'Cadastra um aluno',
  requestBody: {
    required: true,
    content: {
      'application/json': {
        schema: { $ref: '#/components/schemas/CriarAluno' },
      },
    },
  },
  responses: {
    201: {
      description: 'Aluno criado',
      content: {
        'application/json': {
          schema: { $ref: '#/components/schemas/Aluno' },
        },
      },
    },
    400: {
      description: 'Corpo inválido',
      content: {
        'application/json': {
          schema: { $ref: '#/components/schemas/Erro' },
        },
      },
    },
  },
}

Trinta linhas para uma rota, e o projeto tem vinte operações. Quase tudo aí é a mesma casca de cinco linhas em volta de um $ref — exatamente o tipo de repetição que uma função elimina. O erro() da seção 7 já fez isso para um caso; faltam os outros.

11. Os schemas de saída

Os responses da seção anterior referenciam Aluno, e esse schema não existe. A seção 7 criou os de entrada, derivados do Zod; o projeto não tem schema nenhum do que a API devolve — o repository faz SELECT e a rota manda as linhas para o res.json. Esses vão escritos à mão.

O components também cresce demais para continuar dentro do openapi.js. É a mesma divisão que a parte 5 fez com routes/: quando um arquivo passa a ter dois assuntos, ele vira dois arquivos.

Três nomes para a mesma entidade. Escrever esses schemas obriga a olhar o que cada rota realmente devolve, e aí aparece isto: matriculas sai da API em três formatos diferentes.

RotaCampos devolvidos
POST /aulas/{id}/matriculasid, aluno_id, aula_id, status, criado_em (a linha crua)

Não é bug — cada listagem devolve o que é útil no contexto dela. Mas é uma inconsistência que ninguém tinha notado, porque nunca alguém precisou escrever o contrato. Documentar é a primeira vez que a API é lida de fora.

O .refine() some na conversão. atualizarAulaSchema e atualizarInstrutorSchema terminam com um .refine() exigindo ao menos um campo (parte 12). JSON Schema não tem como expressar isso, e o z.toJSONSchema descarta a regra em silêncio — sem aviso, sem erro. Por isso os dois ganham um description escrito à mão dizendo o que a conversão perdeu. Toda validação em .refine() tem esse mesmo destino.

Isso deve ficar público?

Do jeito que está, qualquer um que alcance a API vê a documentação inteira. Para uma API pública, é o objetivo. Para uma API interna, é entregar o mapa da casa — inclusive os nomes dos campos e as regras de validação, que ajudam quem quer sondar.

As saídas usuais: servir /docs só fora de produção (if (process.env.NODE_ENV !== 'production')), ou protegê-la com autenticação. Nenhuma das duas cabe aqui como decisão definitiva, mas vale escolher conscientemente antes do deploy.

15. O Swagger e o helmet

A parte 9 avisou que o CSP do helmet costuma bloquear a interface do Swagger, porque ela dependeria de script e estilo inline. Vale corrigir esse aviso com o que realmente acontece na versão atual.

O swagger-ui-express 5 serve todos os assets como arquivos do mesmo domínio:

src="./swagger-ui-bundle.js"
src="./swagger-ui-standalone-preset.js"
src="./swagger-ui-init.js"
href="./swagger-ui.css"

Não há <script> inline. Como o CSP padrão do helmet permite script-src 'self', os arquivos carregam; e style-src já inclui 'unsafe-inline' por padrão, o que cobre os estilos que a interface aplica em tempo de execução. Na prática, a página funciona sem mexer no helmet.

Se em alguma versão isso mudar, o sintoma é claro: a página abre em branco e o console do navegador mostra qual diretiva bloqueou. A correção é afrouxar o CSP só na rota da documentação — nunca desligar o helmet globalmente:

app.use(
  '/docs',
  helmet({ contentSecurityPolicy: false }),
  swaggerUi.serve,
  swaggerUi.setup(openapi),
);

Aplicar helmet de novo numa rota específica sobrescreve os headers só ali. O resto da API continua com a política da parte 9.

16. Expondo a spec crua

A rota /docs.json da seção 14 parece redundante — a página já mostra tudo. Ela existe porque a página é para humanos e o JSON é para ferramentas:

  • Importar no Postman ou Insomnia — cole a URL e a coleção inteira é criada.
  • Gerar cliente — geradores consomem a spec para produzir código de cliente.
  • Testes de contrato — uma ferramenta pode comparar as respostas reais com o que a spec promete.
  • Versionar a spec — salvar o JSON num arquivo a cada release deixa o histórico de mudanças de contrato visível no git diff.

17. O risco de a doc mentir

Documentação errada é pior que documentação ausente: sem doc, a pessoa lê o código; com doc errada, ela confia e erra. Derivar dos schemas resolve metade do problema — a metade dos formatos de entrada. O que continua escrito à mão pode divergir:

Parte da specDeriva do código?Risco
Formato do corpo da requisiçãosimNenhum — mudou o schema, mudou a doc.
Parâmetros de querysimNenhum, desde que o schema seja o mesmo objeto (seção 9).

Listar os códigos revelou um bug

A seção 12 mandou conferir cada responses contra o que a rota faz. Fazendo isso em POST /alunos, aparece um buraco: a tabela alunos tem índice único em email (parte 3), o repository não trata o erro, e o catch genérico do app.js transforma tudo em 500.

curl -X POST localhost:3000/alunos -H 'Content-Type: application/json' \
  -d '{"nome":"Dup","email":"ja@existe.com","data_nascimento":"1990-01-01","senha":"senha123"}'

# 2ª vez: 500 — deveria ser 409

O código certo é 409 Conflict: o pedido é válido, o estado atual do servidor é que impede. É o mesmo tratamento que POST /aulas/{id}/matriculas já faz para matrícula duplicada (parte 6), capturando o 23505 do Postgres.

Alterar routes/alunos.js — na rota POST /, envolva a criação num try/catch que traduz o 23505:

    res.status(201).location(`/alunos/${alunoCriado.id}`).json(alunoSemSenha);

    if (err.code === '23505') {

    throw err;
  }                                                // NOVO
});

O ErroDeDominio vem da parte 12 e precisa do require no topo do arquivo, se ainda não estiver lá. Feito isso, o 409 entra no responses de POST /alunos em docs/paths/alunos.js:

      responses: {
        201: json('Aluno', 'Aluno criado (header Location aponta para ele)'),
        400: erro('Corpo inválido'),

Esse é o ganho menos anunciado de documentar: escrever o contrato obriga a ler a API de fora, e coisas que ninguém tinha exercitado aparecem. O bug estava lá desde a parte 4.

A defesa contra isso não é disciplina, é teste — e a parte 16 deixou o mecanismo pronto. Um teste que compara a resposta real com o que a spec declara transforma "doc desatualizada" em build vermelho. É o passo natural depois desta parte, e o mesmo raciocínio de todas as automações da trilha: o que depende de alguém lembrar, uma hora é esquecido.

# spec válida: Studio Fit API

É a diferença entre "o Swagger UI abriu" e "a spec está correta". Um $ref com nome errado, por exemplo, passa despercebido na página (o campo simplesmente não aparece) e aqui vira Missing $ref pointer "#/components/schemas/NaoExiste".

Rode isso num processo separado, como acima, e não dentro do app.js: o validador resolve os $ref no próprio objeto, substituindo cada referência pelo schema inteiro. Numa spec já servida, isso mudaria o que o /docs.json devolve.

Mas o teste que importa é no navegador. Abra http://localhost:3000/docs e:

  1. Confira se os cinco grupos aparecem — Autenticação, Alunos, Instrutores, Aulas, Matrículas — e se as rotas protegidas estão com cadeado.
  2. Expanda POST /alunos e confira se os quatro campos aparecem com os limites da parte 12.
  3. Clique em Try it out, preencha e execute — deve criar um aluno de verdade e devolver 201.
  4. Expanda GET /alunos: os cinco parâmetros de query devem estar lá, com ordenar_por como lista de opções.
  5. Chame GET /alunos sem autorizar: 401. Depois clique em Authorize, cole um access token de admin, e chame de novo: 200.
  6. Expanda POST /aulas/{id}/matriculas e confira que não há corpo — o aluno vem do token (parte 10). Se aparecer um campo aluno_id, a doc está descrevendo a API de antes da parte 7.

O passo 4 é o que fecha a história das partes 7 a 11: a mesma sequência que você fazia com três comandos curl e uma variável de shell, agora num formulário. E o cadeado fechado nas rotas protegidas é a matriz de permissões da parte 10 virando interface.

Vale também rodar npm test e confirmar que a suíte continua verde — a spec não deveria afetar nenhuma rota, e é bom ter certeza de que o middleware novo não mudou a ordem de nada.

19. Erros comuns

  1. Escrever open: em vez de openapi: — a página abre e mostra "Unable to render this definition: The provided definition does not specify a valid version field". O Swagger UI procura a chave openapi na raiz para saber que versão da spec está lendo; sem ela, não renderiza nada. O /docs.json continua respondendo normalmente, o que faz o erro parecer ser da interface.
  2. Converter sem io: 'input' — campos com .default() aparecem como obrigatórios, e a doc descreve uma exigência que não existe (seção 5).
  3. Redeclarar o schema de query dentro do docs/ — recria a divergência que derivar do Zod veio evitar. Mova o schema para schemas/ e importe nos dois lugares (seção 9).
  4. Documentar rota protegida sem security — o Swagger não manda o token, a chamada volta 401, e parece bug da API.
  5. Desligar o helmet inteiro por causa do Swagger — se um dia precisar afrouxar, afrouxe só na rota da doc (seção 15).
  6. Deixar servers apontando para localhost em produção — o Try it out dispara contra a máquina de quem abriu a página, e a doc "não funciona" sem explicação.
  7. Expor /docs em produção sem pensar — pode ser o objetivo, ou pode ser entregar o mapa da API (seção 14).
  8. Confiar que .refine() foi convertido — regras que não cabem em JSON Schema são descartadas em silêncio na conversão (seção 11). Nenhum aviso, nenhum erro: a regra simplesmente não está na doc.
  9. Documentar só o caminho feliz — os erros são metade do contrato. Quem escreve o cliente precisa saber que existe 409 em matrícula duplicada.
  10. Confiar que a doc continua verdadeira — sem teste de contrato, ela envelhece igual ao schema.sql da parte 14 (seção 17).

20. O que vem a seguir

A categoria contrato da API fecha aqui. A API agora é consumível por quem não escreveu o código: paginação e filtros para lidar com volume (parte 18), e uma descrição navegável do contrato inteiro (esta).

Falta a última categoria, produção — e ela é a que transforma o projeto em algo que existe fora do seu computador:

  1. Logging estruturado e health check — hoje o único registro é console.error no middleware de erro. Em produção, log precisa ser pesquisável (JSON, com request id) e o orquestrador precisa de uma rota que responda "estou vivo".
  2. Dockerfile do app — o Postgres roda em container desde a parte 1; a API, não. Empacotá-la é o que torna o deploy reproduzível.
  3. Deploy com HTTPS — variáveis de produção, banco gerenciado, migrations no processo de deploy (parte 14), e o momento em que trust proxy (parte 9) e Secure no cookie (parte 11) finalmente entram em ação.

Se a última parte ficar densa demais, ela se divide em duas — empacotar e publicar são problemas diferentes.

O momento que vale a pena nesta parte é o passo 4 da seção 18: autorizar com um token e ver o 401 virar 200 dentro da página. É a primeira vez que a API tem uma interface — e é a mesma que você vai usar para conferir cada resposta quando começar o front-end. Volta com dúvidas, principalmente se a página abrir em branco (olhe o console do navegador) ou se algum campo aparecer como obrigatório sem ser.
