Matrícula e suas regras

Última peça do projeto: a entidade que liga aluno e aula. É também a mais rica em regra de negócio — as 3 que faltavam do documento de projeto (parte 2) se resolvem aqui: capacidade máxima, matrícula duplicada e cancelamento.

1. O que vamos construir

Retomando o mapa de endpoints da parte 2 do projeto, os que faltavam implementar:

RotaO que fazRegra aplicada

Repara que cada regra já tem "dono" definido desde antes: a Regra 2 (parte 3, seção 8) já é garantida pelo banco, via índice único parcial — aqui só precisamos capturar o erro que o banco lança e transformar em resposta HTTP correta. A Regra 1 não tem como o banco resolver sozinho (precisa contar linhas) — fica 100% no código, como já antecipado na parte 3, seção 9.

2. O que é JOIN, antes de usar um

Até agora, toda consulta deste projeto olhou pra uma tabela só (SELECT * FROM alunos, SELECT * FROM aulas WHERE id = $1). Mas "listar os alunos matriculados numa aula" precisa de dado de duas tabelas ao mesmo tempo: o `id`/`nome`/`email` que está em alunos, e o vínculo que está em matriculas.

JOIN é o comando SQL que combina linhas de duas tabelas com base numa condição de igualdade — geralmente a chave estrangeira batendo com a chave primária:

SELECT matriculas.id, matriculas.status, alunos.nome
FROM matriculas
JOIN alunos ON alunos.id = matriculas.aluno_id
WHERE matriculas.aula_id = 1;

Passo a passo: FROM matriculas começa pela tabela de matrículas. JOIN alunos ON alunos.id = matriculas.aluno_id diz "pra cada matrícula, gruda a linha de alunos cujo id bate com o aluno_id dessa matrícula". O resultado é uma tabela "achatada", com colunas das duas tabelas juntas numa linha só por matrícula.

Sem JOIN, a alternativa seria fazer 2 consultas separadas (uma em matriculas, outra em alunos) e juntar os dados no JavaScript na mão. Funciona, mas é mais lento (duas viagens ao banco) e mais código. JOIN deixa o banco — que é otimizado pra isso — fazer a junção de uma vez.

4. Repository de matrículas

// repositories/matriculasRepository.js
const pool = require('../db/pool');

async function contarConfirmadas(aula_id) {
  const resultado = await pool.query(
    /* sql */ `SELECT COUNT(*)::int AS total
               FROM matriculas
               WHERE aula_id = $1 AND status = 'confirmada'`,
    [aula_id]
  );
  return resultado.rows[0].total;
}

async function criar({ aluno_id, aula_id }) {
  const resultado = await pool.query(
    /* sql */ `INSERT INTO matriculas (aluno_id, aula_id)
               VALUES ($1, $2)
               RETURNING *`,
    [aluno_id, aula_id]
  );
  return resultado.rows[0];
}

async function listarPorAula(aula_id) {
  const resultado = await pool.query(
    /* sql */ `SELECT matriculas.id, matriculas.status, matriculas.criado_em,
                      alunos.id AS aluno_id, alunos.nome AS aluno_nome, alunos.email AS aluno_email
               FROM matriculas
               JOIN alunos ON alunos.id = matriculas.aluno_id
               WHERE matriculas.aula_id = $1
               ORDER BY matriculas.id`,
    [aula_id]
  );
  return resultado.rows;
}

async function listarPorAluno(aluno_id) {
  const resultado = await pool.query(
    /* sql */ `SELECT matriculas.id, matriculas.status, matriculas.criado_em,
                      aulas.id AS aula_id, aulas.nome AS aula_nome,
                      aulas.dia_semana, aulas.hora_inicio
               FROM matriculas
               JOIN aulas ON aulas.id = matriculas.aula_id
               WHERE matriculas.aluno_id = $1
               ORDER BY matriculas.id`,
    [aluno_id]
  );
  return resultado.rows;
}

async function buscarPorIdEAula(id, aula_id) {
  const resultado = await pool.query(
    'SELECT * FROM matriculas WHERE id = $1 AND aula_id = $2',
    [id, aula_id]
  );
  return resultado.rows[0];
}

async function cancelar(id) {
  const resultado = await pool.query(
    "UPDATE matriculas SET status = 'cancelada' WHERE id = $1 RETURNING *",
    [id]
  );
  return resultado.rows[0];
}

module.exports = {
  contarConfirmadas,
  criar,
  listarPorAula,
  listarPorAluno,
  buscarPorIdEAula,
  cancelar,
};

Repara o AS aluno_nome, AS aula_nome: como as duas tabelas do JOIN têm coluna nome (uma é nome do aluno, outra é nome da aula), sem apelidar ficaria ambíguo qual é qual no resultado. AS renomeia a coluna na resposta, deixando explícito.

5. Regra 1: capacidade máxima

Do documento de projeto (parte 2): "uma matrícula só pode ser criada se o número de matrículas confirmadas na aula for menor que a capacidade máxima". Isso exige contar linhas — não dá pra expressar como restrição simples de coluna, por isso ficou no código desde o começo (parte 3, seção 9).

contarConfirmadas (seção 4) faz a contagem; a rota compara com capacidade_maxima da aula antes de inserir — ver seção 7.

6. Regra 2: matrícula duplicada

Essa já está resolvida — pelo banco, desde a parte 3 (seção 8), pelo índice único parcial matriculas_aluno_aula_confirmada_idx. O que falta é só o lado da API: capturar o erro que o Postgres lança quando a restrição barra o INSERT, e devolver status certo em vez de 500.

Mesma mecânica do err.code === '23503' que já usamos pro DELETE de instrutor (parte 5) — só que o código muda, porque o tipo de violação é outro:

7. Rota: matricular um aluno

// routes/aulas.js (adicionar)
router.post('/:id/matriculas', async (req, res, next) => {
  const aula = await aulasRepository.buscarPorId(req.params.id);
  if (!aula) {
    return res.status(404).json({ erro: 'Aula não encontrada' });
  }

  const { aluno_id } = req.body;
  if (!aluno_id) {
    return res.status(400).json({ erro: 'aluno_id é obrigatório' });
  }

  const aluno = await alunosRepository.buscarPorId(aluno_id);
  if (!aluno) {
    return res.status(422).json({ erro: 'aluno_id não corresponde a nenhum aluno existente' });
  }

  const totalConfirmadas = await matriculasRepository.contarConfirmadas(aula.id);
  if (totalConfirmadas >= aula.capacidade_maxima) {
    return res.status(409).json({ erro: 'Aula sem vagas disponíveis' });
  }

  try {
    const matriculaCriada = await matriculasRepository.criar({ aluno_id, aula_id: aula.id });
    res
      .status(201)
      .location(`/aulas/${aula.id}/matriculas/${matriculaCriada.id}`)
      .json(matriculaCriada);
  } catch (err) {
    if (err.code === '23505') {
      return res.status(409).json({ erro: 'Aluno já matriculado nesta aula' });
    }
    next(err);
  }
});

Ordem das checagens importa, cada uma "mais barata" que a próxima: primeiro confere se a aula existe (404, sem nem olhar o body). Depois valida forma do que veio (400, campo ausente). Depois confere se o aluno existe (422, regra de referência). Depois a Regra 1 (409, capacidade). Só se passar por tudo isso tenta o INSERT, que ainda pode falhar na Regra 2 (409, capturado no catch). Validar do mais simples/barato pro mais caro evita bater no banco sem necessidade quando um erro simples já explica o problema.

8. Regra 4: cancelamento via PATCH

Do documento de projeto: "cancelar uma matrícula não apaga o registro — muda status para cancelada". Por isso a rota é PATCH, nunca DELETE:

// routes/aulas.js (adicionar)
router.patch('/:id/matriculas/:matriculaId', async (req, res) => {
  const { status } = req.body;

  if (status !== 'cancelada') {
    return res.status(400).json({ erro: "status precisa ser 'cancelada'" });
  }

  const matricula = await matriculasRepository.buscarPorIdEAula(
    req.params.matriculaId,
    req.params.id
  );

  if (!matricula) {
    return res.status(404).json({ erro: 'Matrícula não encontrada' });
  }

  const matriculaCancelada = await matriculasRepository.cancelar(matricula.id);
  res.json(matriculaCancelada);
});
Por que buscarPorIdEAula, não só buscarPorId

A URI é /aulas/:id/matriculas/:matriculaId — o :id da aula faz parte do endereço, então a matrícula precisa pertencer aquela aula, não só existir em algum lugar do banco. Sem essa checagem dupla (id = $1 AND aula_id = $2), alguém poderia cancelar a matrícula 5 chamando /aulas/999/matriculas/5 — URI mentindo sobre o contexto, mas funcionando do mesmo jeito. Validar os dois IDs juntos mantém a URI honesta com o que ela promete.

Depois de cancelada, a matrícula continua existindo no banco (histórico preservado) e libera a vaga — porque contarConfirmadas (Regra 1) só conta status = 'confirmada', e essa matrícula não é mais isso.

12. Ponto de atenção: condição de corrida

A Regra 1, do jeito que está, tem uma brecha: se duas requisições POST /aulas/1/matriculas chegarem ao mesmo tempo pra uma aula com 1 vaga sobrando, as duas podem rodar contarConfirmadas antes de qualquer uma inserir — as duas veem "tem vaga", as duas inserem, a aula fica com 1 vaga a mais que o permitido. Diferente da Regra 2, que o banco garante mesmo sob concorrência (o índice único é atômico), a Regra 1 não tem proteção equivalente aqui.

Postgres resolveria isso com um EXCLUDE constraint ou um controle de concorrência mais explícito (SELECT ... FOR UPDATE, travando a linha da aula durante a checagem) — fora do escopo deste material por ora, registrado como melhoria futura, do mesmo jeito que decidimos deixar o DELETE de instrutor sem soft-delete por enquanto.

13. Erros comuns

  1. Usar DELETE pra cancelar matrícula — quebra a Regra 4 direto. Cancelamento é sempre PATCH mudando status, nunca remoção da linha.
  2. Esquecer o AS nas colunas repetidas do JOIN — alunos.nome e aulas.nome colidiriam no resultado (as duas virariam só nome, uma sobrescrevendo a outra no objeto JS).
  3. Checar capacidade depois de inserir, não antes — inverteria a ordem da seção 7, permitindo estourar a capacidade e só descobrir depois (ou pior, teria que desfazer o INSERT manualmente).
  4. Confundir 23503 com 23505 — são violações diferentes (chave estrangeira vs. unicidade); usar o código errado no catch faz o if nunca bater, e o erro cai no 500 genérico em vez do 409 esperado.

14. O que vem a seguir

Com Aluno, Instrutor, Aula e Matrícula todos funcionando — CRUD completo e as 4 regras de negócio do projeto implementadas — falta proteger quem pode fazer o quê.

  1. Autenticação e autorização: login de aluno (JWT), proteger rotas de matrícula pra só o próprio aluno (ou um admin) poder matricular/cancelar em seu nome.

Quando terminar de testar o fluxo completo (matricular, tentar duplicar, lotar a aula, cancelar, rematricular), volta com dúvidas — principalmente se o JOIN devolver algo diferente do esperado, ou se ficar em dúvida sobre quando usar 404 vs 422 nas checagens em cadeia da seção 7.
