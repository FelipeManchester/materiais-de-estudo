Paginação, filtro e ordenação

A parte 3 da trilha API REST ensinou as convenções; a API nunca as implementou. GET /alunos devolve a tabela inteira, sem exceção — hoje são 111 linhas e funciona, o que é exatamente o que torna o problema fácil de adiar.

1. A tabela inteira na resposta

curl -s http://localhost:3000/alunos -H "Authorization: Bearer TOKEN_ADMIN" | wc -c
# dezenas de milhares de caracteres, e crescendo

O tamanho é o sintoma óbvio. Os problemas reais são três, e nenhum aparece enquanto a tabela é pequena:

ProblemaQuando aparece
Memória do servidorO Node carrega todas as linhas num array antes de responder. 100 mil alunos viram centenas de MB por requisição — e duas requisições simultâneas dobram isso.
Tempo de respostaO cliente espera o banco varrer tudo, a API serializar tudo e a rede transportar tudo, para exibir os 20 primeiros.
Impossível de usarSem filtro nem ordenação, achar um aluno específico exige baixar todos e procurar no cliente. É a API empurrando trabalho para quem a consome.

As três coisas desta parte resolvem juntas o mesmo problema — "quero um pedaço, não tudo" —, e é por isso que costumam aparecer na mesma conversa: paginação escolhe o tamanho do pedaço, ordenação escolhe qual pedaço vem primeiro, e filtro diminui o universo antes de cortar.

2. Duas formas de paginar

Offset escolhidoCursor
Como o cliente pede?pagina=3&limite=20?depois_de=abc123&limite=20
SQLLIMIT 20 OFFSET 40WHERE id > 123 LIMIT 20
Ir direto à página 50SimNão — só avançar de um em um
Custo em tabela grandeCresce: o banco precisa percorrer e descartar as linhas puladasConstante, se houver índice
Se alguém inserir enquanto você navegaUma linha pode repetir ou sumir entre páginasEstável

Offset é o escolhido aqui pelo mesmo critério das outras escolhas da trilha: resolve o problema que existe, com a menor complexidade. Ele permite a interface que as pessoas esperam — números de página, "ir para a última" — e o custo só incomoda em tabelas realmente grandes, navegadas até páginas profundas.

Quando trocar por cursor

Dois sinais: páginas profundas ficando lentas (OFFSET 100000 obriga o Postgres a ler e jogar fora cem mil linhas), ou uma lista que muda o tempo todo, onde repetir/pular item entre páginas é inaceitável — feed, notificação, log. Redes sociais usam cursor por causa do segundo motivo, não do primeiro.

Para uma listagem administrativa de alunos, que muda algumas vezes por dia e é navegada nas primeiras páginas, offset é adequado por muitos anos.

3. Onde colocar o total

Quem recebe uma página precisa saber quantas existem — senão não dá para desenhar a navegação. Duas convenções:

Headers

X-Total-Count: 111
Link: <...?pagina=2>; rel="next"

[ {...}, {...} ]

O corpo continua um array puro. Elegante, e o Link é padronizado (RFC 8288) — mas metadado em header é fácil de ignorar, e o CORS da parte 9 precisaria expor os headers explicitamente.

Envelope no corpo

{
  "dados": [ {...}, {...} ],
  "paginacao": {
    "pagina": 1, "limite": 20,
    "total": 111, "total_paginas": 6
  }
}

Tudo num lugar só, visível para quem abrir a resposta. É o que a maioria das APIs faz hoje.

Terceira quebra de contrato da trilha (depois do token na parte 8 e do refresh saindo do corpo na parte 11). Quem lia resposta[0].nome passa a precisar de resposta.dados[0].nome. Em API com clientes reais, isso exigiria versionamento — /v2/alunos — ou um período devolvendo os dois formatos. Aqui, o único cliente é o seu curl e a sua suíte de testes, que vamos atualizar na seção 12.

4. O schema da query

Os parâmetros chegam pela query string, e a parte 12 já deixou o middleware validar pronto para recebê-los. Todos são opcionais — GET /alunos sem nada precisa continuar funcionando.

Criar schemas/paginacaoSchema.js — uma função que monta o schema, porque cada rota tem colunas ordenáveis diferentes:

const { z } = require('zod');

const LIMITE_PADRAO = 20;
const LIMITE_MAXIMO = 100;

function paginacaoSchema(colunasOrdenaveis) {
  return z.object({
    pagina: z.coerce.number().int().positive().default(1),
    limite: z.coerce
      .number()
      .int()
      .positive()
      .max(LIMITE_MAXIMO)
      .default(LIMITE_PADRAO),
    ordenar_por: z.enum(colunasOrdenaveis).default(colunasOrdenaveis[0]),
    ordem: z.enum(['asc', 'desc']).default('asc'),
  });
}

module.exports = { paginacaoSchema, LIMITE_PADRAO, LIMITE_MAXIMO };

Três detalhes que a parte 12 tornou possíveis:

  • z.coerce.number() — query string é sempre texto; "3" chega como 3 no handler.
  • .default(...) — o middleware escreve o resultado validado de volta em req.query (com Object.defineProperty, pelo motivo explicado na parte 12, seção 7), então o handler recebe pagina: 1 mesmo quando o cliente não mandou nada. Nada de ?? 1 espalhado pelo código. Se pagina ou limite chegarem undefined no handler — e total_paginas vier null no JSON —, é essa escrita de volta que não está funcionando.
  • z.enum(colunasOrdenaveis) — é aqui que a segurança da seção 5 acontece. Um valor fora da lista vira 400 antes de chegar perto do SQL.

E continua z.object, não z.strictObject, pelo motivo da parte 12: um ?utm_source= colado na URL não pode derrubar a requisição.

5. Ordenação não pode ser parametrizada

Desde a parte 4, toda entrada do usuário vai pro SQL como parâmetro ($1), nunca concatenada. Ordenação é a exceção — e entender por quê evita um bug silencioso e uma falha de segurança.

A tentativa natural:

SELECT nome FROM alunos ORDER BY $1 LIMIT 5

Isso não dá erro. Roda, devolve linhas, e parece funcionar. Rode com dois valores diferentes e compare:

ORDER BY $1 com "nome": Ana Silva, João Pereira, Maria Costa, Carla Souza, Bruno Lima
ORDER BY $1 com "id"  : Ana Silva, João Pereira, Maria Costa, Carla Souza, Bruno Lima
sem ORDER BY nenhum   : Ana Silva, João Pereira, Maria Costa, Carla Souza, Bruno Lima
ORDER BY nome de fato : Aluno Corrida 1, Aluno Corrida 2, Aluno Corrida 3, Ana Silva, ...

As três primeiras linhas são idênticas. O motivo: um parâmetro é sempre um valor, nunca um identificador. O Postgres recebe a string 'nome' e entende "ordene por esta constante" — e ordenar todas as linhas pela mesma constante não reordena nada.

É o pior tipo de bug: sem erro, sem aviso, e a resposta tem a cara de estar certa. Você testaria a ordenação, veria uma lista de alunos, e seguiria em frente.

Como o nome da coluna precisa ser interpolado direto na string SQL, ele volta a ser o vetor de SQL injection que a parte 4 fechou:

// se ordenar_por vier do usuário sem controle:
`ORDER BY ${ordenar_por}`
// com ordenar_por = "id; DROP TABLE alunos--"

6. A whitelist

A saída é nunca deixar o valor do usuário chegar ao SQL — só um valor seu, escolhido a partir do que ele pediu. Isso é uma whitelist: um mapa de valores aceitos, com tudo que não está nele caindo num padrão.

const COLUNAS_ORDENAVEIS = {
  id: 'id',
  nome: 'nome',
  criado_em: 'criado_em',
};

const coluna = COLUNAS_ORDENAVEIS[ordenar_por] ?? 'id';
const direcao = ordem === 'desc' ? 'DESC' : 'ASC';

O que entra no SQL é coluna, que só pode ser uma das três strings escritas por você. "id; DROP TABLE alunos--" não é chave do objeto, então vira 'id'.

Repare que isso é defesa em duas camadas, e as duas são intencionais: o z.enum do schema (seção 4) já recusa valor fora da lista com 400, então a whitelist do repository nunca deveria receber lixo. Ela existe para o caso de alguém chamar o repository de outro lugar — de um script, de um teste, de uma rota futura que esqueça o validar. A camada que protege o SQL fica colada no SQL.

Mesma lógica no ordem: em vez de interpolar o que veio, comparar e escolher entre duas constantes suas.

7. Filtro com ILIKE

Buscar aluno por nome parcial, sem diferenciar maiúsculas: o Postgres tem ILIKE, a versão de LIKE que ignora caixa.

WHERE nome ILIKE '%' || $1 || '%'

Repare onde estão os %: concatenados no SQL, não dentro do parâmetro. As duas formas funcionam — ILIKE $1 com o valor '%ana%' daria o mesmo resultado — mas concatenar no SQL deixa explícito que a busca é "contém", em vez de esconder isso na montagem do valor. O conteúdo digitado pelo usuário continua sendo só $1, parametrizado.

# filtro normal
?nome=ana  →  Ana Silva | Joana Prado

# tentativa de injection no filtro
?nome='; DROP TABLE alunos; --  →  0 linhas, tabela intacta

O segundo caso é o esperado: o texto malicioso é tratado como texto, e a API responde que ninguém tem esse nome.

O custo do % no começo

ILIKE '%ana%' não usa índice comum — o Postgres precisa varrer a tabela, porque um índice B-tree organiza por prefixo e a busca não tem prefixo fixo. Com 111 alunos é irrelevante; com milhões, vira lento.

As saídas, quando chegar lá: índice trigram (extensão pg_trgm, que indexa trechos de três letras e acelera ILIKE com % dos dois lados) ou busca textual de verdade (tsvector). Nenhuma das duas cabe agora — mas saber o nome ajuda quando o problema aparecer.

8. O repository completo

Agora juntando tudo. A função monta a query em pedaços porque o filtro é opcional — e isso muda a numeração dos parâmetros.

Alterar repositories/alunosRepository.js — a função listar, que hoje não recebe nada e devolve tudo. Adicione também a constante de colunas antes dela:

const COLUNAS_ORDENAVEIS = {
  id: 'id',
  nome: 'nome',
  criado_em: 'criado_em',
};

async function listar() {
  const query =
    'SELECT id, nome, email, data_nascimento, criado_em FROM alunos ORDER BY id';
  const resultado = await pool.query(query);
  return resultado.rows;
}
async function listar({
  pagina = 1,
  limite = 20,
  ordenar_por = 'id',
  ordem = 'asc',
  nome,
} = {}) {
  const coluna = COLUNAS_ORDENAVEIS[ordenar_por] ?? 'id';
  const direcao = ordem === 'desc' ? 'DESC' : 'ASC';

  const valores = [];
  let where = '';

  if (nome) {
    valores.push(nome);
    where = `WHERE nome ILIKE '%' || $${valores.length} || '%'`;
  }

  valores.push(limite, (pagina - 1) * limite);

  const query = /* sql */ `
    SELECT id, nome, email, data_nascimento, criado_em,
           COUNT(*) OVER() AS total
    FROM alunos
    ${where}
    ORDER BY ${coluna} ${direcao}
    LIMIT $${valores.length - 1} OFFSET $${valores.length}
  `;

  const resultado = await pool.query(query, valores);

  const total = resultado.rows.length
    ? Number(resultado.rows[0].total)
    : 0;

  return {
    dados: resultado.rows.map(({ total: _total, ...aluno }) => aluno),
    total,
  };
}

Três pontos que merecem atenção:

TrechoPor quê
COUNT(*) OVER()Devolve o total de linhas que satisfazem o filtro, ignorando o LIMIT, na mesma consulta. A alternativa seria uma segunda query SELECT COUNT(*) — que exigiria repetir o WHERE e poderia ver um estado diferente do banco.
Number(...total)COUNT devolve bigint, e o driver pg entrega bigint como string (para não perder precisão em números gigantes). Sem o Number, o JSON sairia com "total": "111", entre aspas.
valores.length - 1A posição de $ muda conforme o filtro existir ou não: sem filtro, LIMIT $1 OFFSET $2; com filtro, LIMIT $2 OFFSET $3. Contar o array em vez de escrever o número fixo é o que mantém isso correto.

Quando nenhuma linha bate no filtro, não há linha nenhuma para carregar o COUNT(*) OVER() — por isso o resultado.rows.length ? ... : 0. Sem essa guarda, resultado.rows[0].total seria erro de leitura em undefined, e a busca por um nome inexistente responderia 500.

9. A rota

Alterar schemas/index.js — reexporte o schema novo junto dos que já existem:

const { paginacaoSchema } = require('./paginacaoSchema');

module.exports = {
  // ...os schemas que já estão aqui

};

Alterar routes/alunos.js — no topo, acrescente o schema à desestruturação existente; depois a rota GET /, que ganha o validar na assinatura e passa a devolver o envelope:

const { criarAlunoSchema, idParamSchema } = require('../schemas');
const {
  criarAlunoSchema,
  idParamSchema,
  paginacaoSchema,
} = require('../schemas');

const listarAlunosQuerySchema = paginacaoSchema([
  'id',
  'nome',
  'criado_em',
]).extend({
  nome: z.string().trim().min(1).optional(),
});

router.get('/', autenticar, autorizar('admin'), async (req, res) => {
  const alunos = await alunosRepository.listar();

  res.json(alunos);
});
router.get(
  '/',
  autenticar,
  autorizar('admin'),
  validar({ query: listarAlunosQuerySchema }),
  async (req, res) => {
    const { pagina, limite } = req.query;

    const { dados, total } = await alunosRepository.listar(req.query);

    res.json({
      dados,
      paginacao: {
        pagina,
        limite,
        total,
        total_paginas: Math.ceil(total / limite),
      },
    });
  },
);

O .extend(...) acrescenta o filtro específico desta rota ao schema genérico de paginação. Como ele usa z diretamente, o arquivo precisa importar o Zod:

Alterar routes/alunos.js — mais um import no topo:

const { z } = require('zod');

Repare que alunosRepository.listar(req.query) passa o objeto inteiro. Isso funciona porque os nomes dos parâmetros da query e os da função coincidem — e coincidem porque foram escolhidos assim. Quando divergirem, é melhor mapear explicitamente do que renomear um dos lados só para manter o atalho.

10. Replicando nas outras listagens

Três rotas listam coleções. As outras duas seguem o mesmo padrão, com colunas e filtros próprios:

RotaOrdenar porFiltros
GET /alunos feitoid, nome, criado_emnome
GET /instrutoresid, nome, especialidadenome, especialidade
GET /aulasid, nome, hora_inicioinstrutor_id (já existe), dia_semana

GET /aulas tem uma diferença que importa: ela já tem um filtro (instrutor_id, da parte 5) e um schema de query (listarAulasQuerySchema, da parte 12). O caminho ali é estender o que existe, não criar outro schema em paralelo — dois schemas para a mesma rota é a receita para um deles ser esquecido na próxima alteração.

E o filtro por dia_semana deve reusar a constante DIAS que o aulaSchema.js já exporta desde a parte 12, em vez de repetir a lista dos sete dias. Lista de valores válidos duplicada é lista que vai divergir.

Como listar muda de assinatura nas três, todo lugar que chama essas funções precisa acompanhar — inclusive o GET /aulas que hoje faz aulasRepository.listar({ instrutor_id: req.query.instrutor_id }).

11. Índices para ordenar e filtrar

Ordenar por uma coluna sem índice obriga o Postgres a carregar tudo e ordenar em memória a cada requisição. Com índice, ele lê na ordem certa e para quando completa a página.

Das colunas que abrimos para ordenação, id já tem índice (é a chave primária) e nome não tem em nenhuma das tabelas. Seguindo o fluxo da parte 14:

Rodar:

npm run migrate create indices-para-ordenacao

Alterar o arquivo gerado em migrations/<timestamp>_indices-para-ordenacao.js:

export const up = (pgm) => {
  pgm.createIndex('alunos', 'nome', { ifNotExists: true });
  pgm.createIndex('instrutores', 'nome', { ifNotExists: true });
  pgm.createIndex('aulas', 'nome', { ifNotExists: true });
};

export const down = (pgm) => {
  pgm.dropIndex('alunos', 'nome', { ifExists: true });
  pgm.dropIndex('instrutores', 'nome', { ifExists: true });
  pgm.dropIndex('aulas', 'nome', { ifExists: true });
};

Índice não é de graça: cada um ocupa espaço e torna INSERT/UPDATE um pouco mais lentos, porque a estrutura precisa ser atualizada junto. Criar índice "por precaução" em toda coluna é um antipadrão comum. A regra prática: indexe o que você sabe que vai ordenar ou filtrar com frequência — e aqui você sabe, porque acabou de decidir quais colunas a API aceita nesses papéis.

12. Testando de verdade

Esta é a primeira parte escrita depois da suíte existir (parte 16) e do CI rodar sozinho (parte 17). Aproveite: os testes de paginação são fáceis de escrever e teriam pego pelo menos dois dos erros da seção 14.

Criar tests/paginacao.test.js:

const request = require('supertest');
const app = require('../app');
const pool = require('../db/pool');
const { criarAlunoLogado, criarInstrutorLogado } = require('./ajudantes');

afterAll(() => pool.end());

describe('GET /alunos paginado', () => {

    await criarAlunoLogado();

    expect(p2.body.dados).toHaveLength(2);

    expect(resposta.status).toBe(400);
  });

  it('recusa limite acima do máximo', async () => {
    const admin = await criarInstrutorLogado('admin');

    const resposta = await request(app)

    expect(resposta.status).toBe(400);

});
O teste que prova o bug da seção 5

O terceiro teste — "ordena de verdade" — é o mais importante do arquivo, e o mais fácil de escrever errado. Verificar só que a resposta tem 200 e traz alunos passaria com o ORDER BY $1 quebrado, porque a lista existe, ela só não está ordenada.

O que ele faz em vez disso: pega os nomes devolvidos e confirma que estão em ordem alfabética de fato, e que desc começa por outro nome que asc. Um teste de ordenação que não compara a ordem não testa ordenação.

Você vai precisar atualizar os testes existentes: qualquer um que trate a resposta de GET /alunos como array puro quebra com o envelope. É a quebra de contrato da seção 3 cobrando o preço — e é bom que cobre agora, na sua máquina, em vez de num cliente.

13. Limites e defaults

DecisãoValorMotivo
Limite padrão20Cabe numa tela, resposta pequena. Cliente que quer mais, pede.
Limite máximo100Não é conveniência, é proteção. Sem teto, ?limite=10000000 devolve a tabela inteira — e aí toda esta parte não serviu para nada. É a mesma família do limite de body da parte 9.
Página padrão1Páginas contadas a partir de 1, não de 0: é o que o usuário final vê na interface.
Ordenação padrãoid ascPrecisa existir uma. Sem ORDER BY, o Postgres não garante ordem nenhuma — e a mesma consulta pode devolver ordens diferentes, fazendo item pular entre páginas.

Esse último ponto é sutil e vale insistir: banco relacional não tem ordem "natural". A ordem que você observa hoje é consequência de como as linhas foram gravadas, e muda depois de um UPDATE, um VACUUM ou uma mudança de plano de execução. Paginação sem ORDER BY determinístico é paginação que repete e pula itens sem nenhuma alteração nos dados.

14. Erros comuns

  1. ORDER BY $1 — não ordena e não avisa (seção 5). Só whitelist resolve.
  2. Interpolar ordenar_por direto no SQL — reabre o SQL injection que a parte 4 fechou, agora por um caminho que $1 não protege.
  3. Esquecer o teto do limite — ?limite=99999999 anula a paginação inteira.
  4. Total como string — COUNT é bigint, o driver devolve string. Sem Number(), o JSON sai com "total": "111" e o cálculo de páginas vira concatenação de texto.
  5. Ler rows[0].total sem checar se há linhas — busca sem resultado vira 500 (seção 8).
  6. Paginar sem ORDER BY — itens repetem ou somem entre páginas, sem nada ter mudado (seção 13).
  7. Contar com uma segunda query sem repetir o WHERE — o total ignora o filtro, e a interface mostra "6 páginas" para um resultado de 2 linhas.
  8. Testar ordenação só pelo status — 200 não diz nada sobre ordem (seção 12).
  9. Esquecer de atualizar os testes e clientes existentes — o envelope quebra quem esperava array.

15. O que vem a seguir

As listagens agora devolvem pedaços em vez de tabelas inteiras, com filtro e ordenação controlados por uma lista de valores que você definiu. Falta um item da categoria contrato da API:

  1. Documentação OpenAPI — a próxima parte. Hoje, a única forma de descobrir que GET /alunos aceita ?pagina, ?limite, ?ordenar_por, ?ordem e ?nome é lendo o código. OpenAPI é o formato padrão para descrever isso de forma que ferramentas entendam — e o Swagger UI transforma a especificação numa página onde dá para testar cada rota pelo navegador. Boa parte do trabalho já existe: os schemas Zod da parte 12 e desta parte descrevem a entrada de cada rota, e há como derivar a documentação deles em vez de escrever tudo de novo.

Depois disso, só falta produção: logging estruturado e health check, Dockerfile do app, e o deploy com HTTPS — onde o trust proxy da parte 9, o Secure do cookie da parte 11 e o passo de migrations da parte 14 finalmente entram em ação.

Fica registrado como dívida consciente: a paginação por offset não é estável sob inserções concorrentes (seção 2), e o filtro por ILIKE '%...%' não usa índice (seção 7). As duas só passam a incomodar em escala que este projeto não tem — e agora você sabe o nome da solução de cada uma.

Ao testar, o caso que vale prestar atenção é a ordenação: compare ?ordenar_por=nome&ordem=asc com &ordem=desc e confirme que a primeira linha muda. Se as duas devolverem a mesma coisa, a whitelist não está sendo aplicada — e esse é exatamente o bug que não dá erro. Volta com dúvidas, principalmente se o total vier entre aspas no JSON ou se alguma listagem começar a repetir itens entre páginas.
