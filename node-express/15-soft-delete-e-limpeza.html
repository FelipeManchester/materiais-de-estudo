Soft-delete e limpeza

Duas pendências de dados fecham a categoria: uma tabela que cresce pra sempre e nunca é limpa, e uma rota de exclusão que apaga credenciais de login — quando consegue apagar alguma coisa. As duas viram migrations, agora que a parte 14 deu o mecanismo.

1. A tabela que só cresce

Desde a parte 8, cada login e cada renovação inserem uma linha em refresh_tokens. Nenhuma linha jamais sai. Rode no seu banco:

docker compose exec -T db psql -U postgres -d estudo -c "
SELECT COUNT(*) AS total,
       COUNT(*) FILTER (WHERE revogado_em IS NOT NULL) AS revogados,
       COUNT(*) FILTER (WHERE expira_em < NOW()) AS expirados,
       MIN(criado_em)::date AS mais_antigo
FROM refresh_tokens;"

Num projeto de estudo, com um punhado de usuários de teste e poucos dias de uso, o resultado costuma passar de cem linhas. Extrapole: um usuário ativo renova o token a cada 15 minutos enquanto usa o sistema, o que dá umas 30 linhas por dia de uso. Mil usuários assim são 30 mil linhas por dia — 11 milhões por ano, das quais 99,99% não servem pra nada.

Por que isso importa antes de virar problema

Tabela grande não é problema por ocupar disco — disco é barato. O custo aparece em outros lugares: buscarPorHash continua rápido porque usa o índice único, mas backup e restauração ficam lentos, o VACUUM do Postgres trabalha mais, e qualquer consulta analítica que alguém escreva sem índice varre milhões de linhas mortas.

É também um problema de privacidade: guardar registro de sessão de um usuário que saiu do sistema há dois anos é dado pessoal retido sem propósito. Legislações de proteção de dados tratam retenção indefinida como problema, não como neutralidade.

2. O que dá pra apagar (e a armadilha)

A resposta óbvia — "apaga tudo que está expirado ou revogado" — está errada, e o motivo conecta direto com a parte 8.

Lembre da detecção de reuso: quando um refresh token revogado é reapresentado, o servidor entende que a string vazou e derruba todas as sessões daquele dono. Isso só funciona porque a linha revogada continua no banco. Se ela tiver sido apagada, o mesmo ataque cai em outro caminho:

Linha apagada

buscarPorHash não acha nada → 401 "Refresh token inválido" e nada mais acontece. O atacante continua com a sessão que roubou, e ninguém foi avisado.

Linha preservada

buscarPorHash acha a linha com revogado_em preenchido → todas as sessões do dono são revogadas. O ataque é interrompido.

A regra que sai daí: a retenção precisa ser confortavelmente maior que a validade do refresh token. Com 7 dias de validade (parte 8), apagar linhas com 30 dias é seguro: qualquer token que ainda pudesse ser reapresentado por um atacante já expirou há mais de três semanas, e um token expirado é recusado antes mesmo de a detecção de reuso importar.

Apagar com 3 dias, por outro lado, abriria um buraco silencioso na defesa da parte 8 — sem nenhum erro, sem nenhum teste falhando.

O critério vai no expira_em, não no criado_em: é a data de expiração que diz quando o token deixou de ter qualquer utilidade.

DELETE FROM refresh_tokens
WHERE expira_em < NOW() - INTERVAL '30 days';

Note que isso pega tanto os revogados quanto os que simplesmente venceram sem uso — depois de 30 dias da expiração, a distinção não interessa mais.

3. Onde uma rotina dessas roda

Tendo o comando, falta decidir quem o executa periodicamente. Quatro opções, em ordem crescente de acerto:

OndeProblema
setInterval dentro do index.jspior opção Some no restart, e com duas instâncias da API os dois processos limpam ao mesmo tempo. Além disso, mistura responsabilidades: um erro na limpeza pode derrubar a API inteira.
Rota HTTP secreta chamada de foraVira um endpoint que precisa ser protegido, e alguém sempre acaba chamando pelo navegador. Se demorar, estoura timeout do proxy no meio do DELETE.
pg_cron (agendador dentro do Postgres)Ótimo, e mantém a lógica perto do dado — mas é uma extensão a instalar e configurar, e a regra de negócio some do repositório.
Script separado + agendador do sistemaescolhido Um arquivo que roda, faz o trabalho e termina. Testável na mão, versionado junto do código, e o agendamento é responsabilidade de quem opera (cron, systemd timer, CronJob do Kubernetes, agendador do provedor).

É o mesmo raciocínio da parte 14 sobre migrations não rodarem dentro do index.js: tarefa que não é atender requisição não deve morar no processo que atende requisições.

4. Migration: índice para a limpeza

O DELETE da seção 2 filtra por expira_em, e não existe índice nessa coluna — o Postgres varreria a tabela inteira toda vez. Primeira migration da parte, seguindo o fluxo da 14.

Rodar na raiz do projeto:

npm run migrate create indice-refresh-tokens-expira-em

Alterar o arquivo gerado em migrations/<timestamp>_indice-refresh-tokens-expira-em.js — substitua o conteúdo:

export const up = (pgm) => {
  pgm.createIndex('refresh_tokens', 'expira_em', {
    name: 'refresh_tokens_expira_em_idx',
    ifNotExists: true,
  });
};

export const down = (pgm) => {
  pgm.dropIndex('refresh_tokens', 'expira_em', {
    name: 'refresh_tokens_expira_em_idx',

5. Repository: removerExpirados

Adicionar repositories/refreshTokensRepository.js — função nova antes do module.exports, e inclua o nome na exportação:

async function removerExpirados(diasDeRetencao = 30) {
  const query = /* sql */ `
    DELETE FROM refresh_tokens
    WHERE expira_em < NOW() - ($1 || ' days')::interval
  `;

  const resultado = await pool.query(query, [diasDeRetencao]);
  return resultado.rowCount;
}

module.exports = { criar, buscarPorHash, revogar, revogarTodosDoDono };
module.exports = {
  criar,
  buscarPorHash,
  revogar,
  revogarTodosDoDono,
  removerExpirados,
};

O detalhe estranho é o ($1 || ' days')::interval. Seria natural escrever NOW() - INTERVAL '$1 days', mas isso não funciona: dentro de uma string literal do SQL, $1 é texto, não placeholder. Concatenar o número com ' days' e converter para interval resolve mantendo a query parametrizada — nada de montar SQL com template string, que é exatamente o buraco de SQL injection que a parte 4 fechou.

resultado.rowCount devolve quantas linhas foram apagadas, que é o que o script vai reportar.

Em tabela realmente grande (milhões de linhas), um DELETE único segura lock e transação por muito tempo — o mesmo problema que a parte 13 discutiu. A versão robusta apaga em lotes, num laço: DELETE FROM refresh_tokens WHERE id IN (SELECT id FROM refresh_tokens WHERE expira_em < ... LIMIT 1000), repetido até rowCount voltar zero. Não vamos precisar disso aqui, mas é a evolução natural quando a tabela crescer.

6. O script de limpeza

Criar scripts/limpar-tokens.js — diretório novo. É um programa completo: carrega o .env sozinho (não passa pelo index.js), faz o trabalho e encerra:

require('dotenv').config();

const pool = require('../db/pool');
const refreshTokensRepository = require('../repositories/refreshTokensRepository');

const DIAS_DE_RETENCAO = Number(process.env.RETENCAO_TOKENS_DIAS || 30);

async function main() {
  const removidos =
    await refreshTokensRepository.removerExpirados(DIAS_DE_RETENCAO);

  console.log(
    `[limpar-tokens] ${new Date().toISOString()} | retenção: ${DIAS_DE_RETENCAO} dias | removidos: ${removidos}`,
  );
}

main()
  .catch((erro) => {
    console.error('[limpar-tokens] falhou:', erro.message);
    process.exitCode = 1;
  })
  .finally(() => pool.end());

Três detalhes que fazem diferença num script agendado:

  • pool.end() no finally. Sem fechar o pool, o processo fica vivo esperando conexões ociosas e o cron acumula processos pendurados. Script termina; servidor é que fica de pé.
  • process.exitCode = 1 em caso de erro. É assim que o agendador sabe que falhou — sem isso, o cron considera sucesso e você nunca fica sabendo.
  • Log com data e número. A saída vai pro arquivo de log do agendador, e "removidos: 0" por semanas seguidas é sinal de que algo parou de funcionar.

Alterar package.json — mais um script, junto dos de migration:

"scripts": {
  "dev": "nodemon index.js",
  "lint": "eslint .",
  "migrate": "node-pg-migrate",
  "migrate:up": "node-pg-migrate up",
  "migrate:down": "node-pg-migrate down"
  "migrate:down": "node-pg-migrate down",
  "limpar-tokens": "node scripts/limpar-tokens.js"
}

7. Agendando

Rodando na mão, o script já funciona:

npm run limpar-tokens
# [limpar-tokens] 2026-08-14T03:00:00.000Z | retenção: 30 dias | removidos: 0

Em produção, quem chama é o agendador do sistema. Com cron, uma linha no crontab -e:

0 3 * * * cd /caminho/do/projeto && /usr/bin/node scripts/limpar-tokens.js >> /var/log/limpar-tokens.log 2>&1
PedaçoO que faz
0 3 * * *Todo dia às 3h. Horário de baixo movimento, porque o DELETE compete por recursos com o uso normal.
cd /caminho && ...O cron roda a partir do diretório do usuário, não do projeto — sem o cd, o require('../db/pool') e o .env não são encontrados.
/usr/bin/nodeCaminho absoluto. O PATH do cron é mínimo e frequentemente não inclui o Node — principalmente com nvm. Descubra o seu com which node.
>> log 2>&1Guarda saída e erros. Sem isso, o cron tenta mandar email pro usuário local e a mensagem se perde.

Em ambiente gerenciado, o formato muda mas a ideia é a mesma: CronJob no Kubernetes, Scheduled Job no Render/Railway, EventBridge + Lambda na AWS. O script continua igual — é essa a vantagem de ele não depender de onde roda.

8. O que o DELETE de instrutor faz hoje

Segunda pendência, anotada desde a parte 6. Teste o comportamento atual com dois instrutores diferentes:

# instrutor SEM aulas
curl -s -w "\n%{http_code}\n" -X DELETE http://localhost:3000/instrutores/ID_SEM_AULAS \
  -H "Authorization: Bearer TOKEN_ADMIN"
# 204 — a linha foi apagada

# instrutor COM aulas
curl -s -w "\n%{http_code}\n" -X DELETE http://localhost:3000/instrutores/ID_COM_AULAS \
  -H "Authorization: Bearer TOKEN_ADMIN"
# 409 "Não é possível remover: Existem aulas cadastradas com este instrutor"

Os dois resultados são problemáticos, por motivos opostos:

CasoO que acontecePor que é ruim
Instrutor com aulas409, nada é removidoO ON DELETE RESTRICT da parte 3 impede. Como todo instrutor real dá aula, a rota na prática não funciona pra ninguém que importa.
Instrutor sem aulas204, linha apagadaVão junto o email, o senha_hash e o papel criados na parte 10 — e o ON DELETE CASCADE leva os refresh_tokens dele. Se esse instrutor for o único admin, você acabou de perder o acesso administrativo do sistema, sem confirmação nenhuma.

E existe o problema histórico: um instrutor que deu 200 aulas ao longo de dois anos e saiu da academia não deveria desaparecer. As aulas dele aconteceram; a matrícula dos alunos naquelas aulas aconteceu. Apagar a linha destrói o histórico ou trava na FK — que é exatamente o dilema que o 409 expressa.

9. Soft-delete: a coluna ativo

Soft-delete é marcar como removido em vez de apagar. A linha continua lá, com o histórico intacto, e a aplicação passa a tratá-la como inexistente nos lugares onde faz sentido.

O projeto já usa essa ideia desde a parte 6, sem esse nome: a Regra 4 diz que cancelar matrícula nunca é DELETE — é status = 'cancelada'. Aqui é o mesmo padrão, aplicado a instrutor.

Rodar:

npm run migrate create adicionar-ativo-em-instrutores

Alterar o arquivo gerado em migrations/<timestamp>_adicionar-ativo-em-instrutores.js:

export const up = (pgm) => {
  pgm.addColumns('instrutores', {
    ativo: { type: 'boolean', notNull: true, default: true },
  });
};

export const down = (pgm) => {
  pgm.dropColumns('instrutores', ['ativo']);
};

O default: true é o que permite notNull numa tabela com dados: todo instrutor existente vira ativo na hora do ALTER. Mesma lógica do papel na parte 10.

npm run migrate:up
Booleano ou timestamp?

Muitos projetos usam desativado_em TIMESTAMP (nulo = ativo) em vez de ativo BOOLEAN — é o que a própria tabela refresh_tokens faz com revogado_em, pelo motivo explicado na parte 8: guardar quando não custa nada e ajuda a investigar depois.

Aqui o booleano é escolha deliberada porque o estado é reversível: instrutor pode ser reativado (seção 12), e ativo = true lê melhor do que "voltar desativado_em para NULL". Se você quiser as duas coisas, dá pra ter ativo e desativado_em juntos — só lembre que aí são dois campos que precisam concordar, e campo redundante é campo que uma hora diverge.

10. DELETE vira UPDATE

Alterar repositories/instrutoresRepository.js — a função remover deixa de apagar. O nome fica, porque é o que a rota chama; o que muda é o SQL:

async function remover(id) {
  const query = 'DELETE FROM instrutores WHERE id = $1 RETURNING *';
  const resultado = await pool.query(query, [id]);

  return resultado.rows[0];
}
async function remover(id) {
  const query = /* sql */ `
    UPDATE instrutores
    SET ativo = false
    WHERE id = $1
    RETURNING id, nome, especialidade, email, papel, ativo
  `;
  const resultado = await pool.query(query, [id]);

  return resultado.rows[0];
}

Alterar routes/instrutores.js — na rota DELETE /:id. O try/catch do código 23503 não tem mais função: sem DELETE de verdade, a FK de aulas nunca é violada. O handler fica assim:

router.delete(
  '/:id',
  autenticar,
  autorizar('admin'),
  validar({ params: idParamSchema }),
  async (req, res, next) => {
    try {
      const instrutorRemovido = await instrutoresRepository.remover(
        req.params.id,
      );

      if (!instrutorRemovido) {
        return res.status(404).json({ erro: 'Instrutor não encontrado' });
      }

      res.status(204).send();
    } catch (err) {
      if (err.code === '23503') {
        return res.status(409).json({
          erro: 'Não é possível remover: Existem aulas cadastradas com este instrutor',
        });
      }
      next(err);
    }
  },
);
  async (req, res) => {
    const instrutorRemovido = await instrutoresRepository.remover(
      req.params.id,
    );

    if (!instrutorRemovido) {
      return res.status(404).json({ erro: 'Instrutor não encontrado' });
    }

    res.status(204).send();
  },
);

A rota que "na prática não funcionava pra ninguém que importa" (seção 8) passa a funcionar pra todo mundo — e o instrutor com 200 aulas some da listagem sem que uma única aula desapareça.

Repare que desativar duas vezes seguidas devolve 204 nas duas. O UPDATE encontra a linha e a marca de novo — idempotente, como o logout da parte 8. Se você quisesse recusar a segunda com 409, bastaria AND ativo = true no WHERE e tratar o retorno vazio; a escolha aqui é a mesma de sempre: o resultado desejado já é verdade, então não é erro.

11. Onde mais o "ativo" precisa aparecer

Marcar a coluna é a parte fácil. A parte que erra é lembrar de todos os lugares que precisam respeitá-la. No projeto são três:

Alterar repositories/instrutoresRepository.js — listar devolve só os ativos, e buscarPorEmail (usada no login, parte 10) recusa quem foi desativado:

async function listar() {
  const query =
    'SELECT id, nome, especialidade, papel FROM instrutores ORDER BY id';
  const query = /* sql */ `
    SELECT id, nome, especialidade, papel
    FROM instrutores
    WHERE ativo = true
    ORDER BY id
  `;
  const resultado = await pool.query(query);

  return resultado.rows;
}

async function buscarPorEmail(email) {
  const query = 'SELECT * FROM instrutores WHERE email = $1';
  const query = 'SELECT * FROM instrutores WHERE email = $1 AND ativo = true';
  const resultado = await pool.query(query, [email]);

  return resultado.rows[0];
}

Com isso, um instrutor desativado tentando logar recebe o mesmo 401 "email ou senha inválidos" de quem errou a senha — mensagem genérica, pelo motivo da parte 7: não contar pra ninguém quais contas existem.

buscarPorId continua sem filtro, de propósito. Ela é usada em dois lugares que precisam enxergar inativos: a rota GET /instrutores/:id (um admin consultando quem foi desativado) e o /auth/refresh da parte 10, que relê o papel do dono do token. Filtrar ali faria o refresh de um admin desativado devolver 401 genérico em vez do comportamento previsto — e, pior, esconderia a linha de quem tem legitimidade pra vê-la.

Essa é a decisão mais sutil desta parte: soft-delete não é "sumir de todo lugar", é "sumir de onde faz sentido". Cada consulta precisa dessa decisão tomada explicitamente.

Alterar routes/aulas.js — na rota POST /, a checagem de existência do instrutor. Criar aula para instrutor desativado não pode ser permitido:

    const instrutorExiste = await instrutorRepository.buscarPorId(instrutor_id);
    if (!instrutorExiste) {
    if (!instrutorExiste || !instrutorExiste.ativo) {
      return res.status(422).json({
        erro: 'instrutor_id não corresponde a nenhum instrutor existente',
      });
    }

As aulas antigas do instrutor desativado continuam lá, com todas as matrículas — o que muda é que ninguém agenda aula nova pra ele.

12. Reativar

A vantagem do soft-delete só se realiza se der pra desfazer. Como PATCH /instrutores/:id já existe e já exige admin, basta permitir o campo.

Alterar schemas/instrutorSchema.js — adicione o campo no criarInstrutorSchema. O atualizarInstrutorSchema herda automaticamente, porque é o mesmo schema com .partial() (parte 12):

const criarInstrutorSchema = z.strictObject({
  nome: z.string().trim().min(2).max(120),
  especialidade: z.string().trim().min(2).max(80),
  email: z.email().max(160).optional(),
  senha: z.string().min(8).max(72).optional(),
  papel: z.enum(['instrutor', 'admin']).optional(),
  ativo: z.boolean().optional(),
});

Alterar repositories/instrutoresRepository.js — a função atualizar precisa saber gravar o campo novo. Ela usa COALESCE pra manter o valor antigo quando o campo não vem:

async function atualizar(id, { nome, especialidade }) {
  const query = `
    UPDATE instrutores
    SET nome = COALESCE($1, nome),
        especialidade = COALESCE($2, especialidade)
    WHERE id = $3
    RETURNING *
  `;

  const resultado = await pool.query(query, [nome, especialidade, id]);
async function atualizar(id, { nome, especialidade, ativo }) {
  const query = /* sql */ `
    UPDATE instrutores
    SET nome = COALESCE($1, nome),
        especialidade = COALESCE($2, especialidade),
        ativo = COALESCE($3, ativo)
    WHERE id = $4
    RETURNING id, nome, especialidade, email, papel, ativo
  `;

  const resultado = await pool.query(query, [
    nome,
    especialidade,
    ativo ?? null,
    id,
  ]);

  return resultado.rows[0];
}

Alterar routes/instrutores.js — na rota PATCH /:id, passe o campo novo adiante:

    const { nome, especialidade } = req.body;
    const { nome, especialidade, ativo } = req.body;

    const instrutorAtualizado = await instrutoresRepository.atualizar(
      req.params.id,
      {
        nome: nome ?? null,
        especialidade: especialidade ?? null,
        ativo: ativo ?? null,
      },
    );

Reativar vira PATCH /instrutores/12 com {"ativo": true}. E o RETURNING das duas funções lista colunas em vez de * pelo motivo da parte 10: senha_hash não sai do banco.

13. O risco do soft-delete

Vale nomear o custo, porque ele é real e cresce com o projeto: a partir de agora, toda consulta nova a instrutores precisa decidir se filtra ativo. Esquecer é fácil, e o bug é silencioso — um instrutor desativado reaparecendo num relatório meses depois.

EstratégiaComo funciona
Disciplina nossa escolhaCada query decide explicitamente. Simples e visível — com 5 consultas na tabela, dá pra revisar todas de uma vez.
VIEW de ativosCREATE VIEW instrutores_ativos AS SELECT * FROM instrutores WHERE ativo, e o código consulta a view. O filtro deixa de ser esquecível, mas você passa a ter dois nomes pra mesma entidade.
Filtro automático no ORMFerramentas como Prisma e Sequelize têm escopo padrão. O projeto não usa ORM (parte 4), e o filtro invisível tem o problema inverso: um dia você precisa ver os inativos e não entende por que não aparecem.

Há também o efeito colateral que a seção 11 já mostrou: o UNIQUE de email continua valendo para inativos. Um instrutor desativado com paula@studiofit.com impede cadastrar outro com o mesmo email — o que costuma ser o comportamento certo (é a mesma pessoa voltando, então reative), mas é bom saber que é assim antes de descobrir num 409 confuso.

14. Testando

Comece pela limpeza. Como seus tokens têm poucos dias, 30 não apaga nada — é justamente a prova de que o critério funciona:

npm run limpar-tokens
# removidos: 0 — nenhum token expirou há mais de 30 dias

# force a situação: retenção de 0 dias apaga tudo que já expirou

# removidos: N — os expirados saíram

# rode de novo: já não há mais nada
RETENCAO_TOKENS_DIAS=0 npm run limpar-tokens
# removidos: 0

Confirme que os tokens válidos sobreviveram — se algum login parar de renovar, o critério está errado:

docker compose exec -T db psql -U postgres -d estudo -c \
  "SELECT COUNT(*) FILTER (WHERE revogado_em IS NULL AND expira_em > NOW()) AS ainda_validos,
          COUNT(*) AS total FROM refresh_tokens;"

O teste que resolve a pendência da parte 6 — desativar quem tem aulas, o caso que antes dava 409:

# pegue um instrutor que tenha aulas
curl -s -o /dev/null -w "%{http_code}\n" -X DELETE http://localhost:3000/instrutores/ID_COM_AULAS \
  -H "Authorization: Bearer TOKEN_ADMIN"
# 204 (antes: 409)

# e as aulas dele continuam lá
curl -s "http://localhost:3000/aulas?instrutor_id=ID_COM_AULAS" | head -c 200

Faça esse teste com um instrutor de teste, não com o Admin — desativar o único admin tira o seu próprio acesso administrativo. Se acontecer, dá pra voltar pelo banco: UPDATE instrutores SET ativo = true WHERE papel = 'admin';

15. Erros comuns

  1. Retenção menor que a validade do token — apaga linhas revogadas que ainda serviriam pra detectar reuso, furando em silêncio a defesa da parte 8 (seção 2).
  2. Limpar por criado_em em vez de expira_em — um token criado há 40 dias pode ter sido renovado ontem. O critério é quando ele deixou de valer.
  3. setInterval no index.js — some no restart, duplica com duas instâncias, e um erro na limpeza derruba a API (seção 3).
  4. Esquecer pool.end() no script — o processo não termina, e o agendador vai acumulando processos vivos.
  5. INTERVAL '$1 days' — dentro da string literal, $1 é texto, não parâmetro. Use ($1 || ' days')::interval (seção 5).
  6. Soft-delete sem revisar as consultas existentes — a coluna sozinha não esconde ninguém. Cada SELECT precisa decidir (seção 11).
  7. Filtrar ativo em buscarPorId — quebra o /auth/refresh e esconde a linha de quem tem direito de vê-la.
  8. Esquecer o caminho absoluto do Node no cron — o PATH do cron é mínimo, e o erro só aparece no log que você provavelmente não configurou (seção 7).
  9. Desativar o único admin — sem rota de reativação acessível, sobra o psql (seção 14).

16. O que vem a seguir

A categoria banco e dados fecha aqui: migrations versionadas (parte 14), retenção com prazo definido, e exclusão que preserva histórico. Junto com as anteriores, todas as pendências que a trilha vinha anotando desde a parte 6 saíram do papel.

A próxima categoria é qualidade, e ela é o único item da lista que muda como você trabalha, não o que a API faz:

  1. Testes automatizados — a próxima parte. Todo teste desta trilha foi manual, via curl, e a conta já está alta: o fluxo de refresh tem quatro caminhos, a matriz de papéis tem dez linhas, e existem quatro regras de negócio. Cada parte nova exige reconferir tudo na mão. Jest + supertest transformam isso num comando — e migrations tornam viável montar um banco limpo por execução.
  2. CI — os testes rodando sozinhos a cada push, no GitHub Actions. É o que impede que uma correção de segunda-feira quebre a autorização escrita há três semanas.

Depois: contrato da API (paginação, filtro, ordenação e documentação OpenAPI) → produção (logging estruturado, health check, Dockerfile do app e deploy com HTTPS).

Fica registrado como dívida consciente: GET /instrutores agora esconde inativos de todo mundo, inclusive do admin. Uma listagem administrativa completa precisaria de um filtro na query (?incluir_inativos=true), e isso encaixa naturalmente na parte de paginação e filtros.

Ao testar, o momento que fecha a história da trilha é desativar um instrutor com aulas e receber 204 — a mesma requisição que respondia 409 desde a parte 5, agora funcionando sem que nenhuma aula ou matrícula desapareça. Volta com dúvidas, principalmente se algum instrutor desativado continuar aparecendo em algum lugar: isso é uma consulta que ficou sem o filtro da seção 11.
