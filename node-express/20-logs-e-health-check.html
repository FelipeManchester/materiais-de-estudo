Logs e health check

A API funciona, está testada e documentada. Falta ela saber contar o que aconteceu quando você não estava olhando — e saber responder, para quem a hospeda, se está de pé. São as duas conversas que uma aplicação tem com a plataforma onde roda.

1. O que o console.log não resolve

Hoje o projeto tem exatamente dois registros: um console.log dizendo que o servidor subiu, e um console.error(err) no middleware de erro. Em desenvolvimento isso basta, porque você está olhando o terminal no momento em que a coisa quebra.

Em produção nada disso é verdade. O erro acontece às três da manhã, para um usuário que você não conhece, e você chega depois. A pergunta deixa de ser "o que apareceu no terminal" e passa a ser "o que aconteceu naquele pedido" — e aí o console falha em quatro pontos:

PerguntaCom console.error
Que requisição gerou esse erro?Não dá para saber: a stack não diz a rota, o método nem o usuário.
Quantos 500 aconteceram ontem?Só contando à mão, se você tiver guardado a saída.
Mostre só os erros do aluno 42.Impossível — o texto não tem estrutura para filtrar.
Essa rota ficou lenta?Ninguém mediu.

E tem um problema mais sério que a inconveniência: console.error(err) despeja o objeto inteiro. Se esse objeto carregar um corpo de requisição com senha, ou um header Authorization, a senha vai para o log — que costuma ser copiado, agregado e lido por muito mais gente do que o banco.

2. A linha vira objeto

Log estruturado é uma ideia simples: em vez de escrever uma frase, escreva um objeto JSON por evento. A frase continua lá, no campo msg — mas ao lado dela vão campos nomeados, que uma máquina consegue filtrar.

Texto

Erro ao matricular aluno 42 na aula 7

Para achar "todos os erros da aula 7" só resta grep, e ele quebra no dia em que alguém mudar a frase.

Estruturado

{"level":"error","time":"2026-08-25T18:47:51.286Z",
 "aluno_id":42,"aula_id":7,"msg":"erro ao matricular"}

Vira consulta: level = error AND aula_id = 7. A frase pode mudar sem quebrar nada.

É por isso que praticamente todo agregador de log — Grafana Loki, Datadog, CloudWatch, o que a sua hospedagem oferecer — assume JSON. Você não precisa de nenhum deles hoje: o ganho já aparece localmente, e o dia em que precisar, o formato já está certo.

Log vai para o stdout, não para arquivo

A tentação é abrir um logs/app.log. Não faça. Em container, o processo escreve no stdout e quem coleta é a plataforma — Docker, Kubernetes, a hospedagem. Aplicação que gerencia arquivo de log precisa se preocupar com rotação, permissão e disco cheio, e nada disso é problema dela.

É o mesmo raciocínio da parte 1 com as variáveis de ambiente: a aplicação recebe e entrega pelo canal padrão, e quem a hospeda decide o resto.

3. pino

O pino é a escolha usual em Node para isso: escreve JSON por padrão, é rápido o suficiente para não pesar no caminho da requisição, e tem um complemento — pino-http — que registra requisição e resposta sozinho.

Rodar na raiz do projeto:

npm install pino pino-http
npm install --save-dev pino-pretty

O pino-pretty entra como dependência de desenvolvimento de propósito: ele existe para deixar o log legível no seu terminal, e em produção o que se quer é o JSON cru.

4. O logger do projeto

Criar logger.js — arquivo novo, na raiz, ao lado do app.js:

const pino = require('pino');

const emProducao = process.env.NODE_ENV === 'production';

const logger = pino({
  // Em teste o log só polui a saída do Jest.
  enabled: process.env.NODE_ENV !== 'test',

  level: process.env.LOG_LEVEL || (emProducao ? 'info' : 'debug'),

  // Sem isso, o nível sai como número (30, 50) em vez de nome.
  formatters: {
    level: (rotulo) => ({ level: rotulo }),
  },

  // Padrão do pino é epoch em milissegundos; ISO é legível por humano
  // e entendido por qualquer agregador.
  timestamp: pino.stdTimeFunctions.isoTime,

  // Nada aqui pode chegar ao log, nem por acidente.
  redact: {
    paths: [
      'req.headers.authorization',
      'req.headers.cookie',
      'res.headers["set-cookie"]',
      // '*.campo' cobre um nível de aninhamento, NÃO a raiz do objeto.
      // Por isso cada nome aparece duas vezes.
      'senha',
      '*.senha',
      'senha_hash',
      '*.senha_hash',
      'access_token',
      '*.access_token',
      'refresh_token',
      '*.refresh_token',
    ],
    censor: '[REDIGIDO]',
  },

  base: { servico: 'studio-fit-api' },
});

module.exports = logger;

Quatro decisões que valem explicação:

OpçãoPor quê
enabledDurante os testes (parte 16) o log só atrapalharia a saída do Jest. Desligado, o pino vira no-op — não é preciso mudar nada no código que loga.
leveldebug em desenvolvimento, info em produção. LOG_LEVEL permite subir o detalhe sem alterar código, que é o que você vai querer no meio de um incidente.
formatters.levelSem isso o nível sai como número (30, 50). Com isso sai "info", "error" — pesquisável por quem não decorou a tabela do pino.
baseCarimba servico em todo evento. Quando os logs de várias aplicações caem no mesmo lugar, é o campo que separa os seus.

5. O que nunca pode ir para o log

O redact é a parte que merece atenção. Ele substitui o valor de certos caminhos por [REDIGIDO] antes de escrever — a rede de segurança contra o dia em que alguém logar um objeto grande demais sem olhar o que tem dentro.

E ele tem uma armadilha que só aparece testando. O caminho '*.senha' significa "a propriedade senha de qualquer objeto um nível abaixo da raiz". Ele não cobre a raiz. Veja o resultado antes de a lista estar completa:

logger.info({ usuario: { email: 'a@b.com', senha: 'senha123' } }, 'aninhado');
logger.info({ access_token: 'eyJhbG...', refresh_token: 'deadbeef' }, 'raiz');
{"usuario":{"email":"a@b.com","senha":"[REDIGIDO]"},"msg":"aninhado"}
{"access_token":"eyJhbG...","refresh_token":"deadbeef","msg":"raiz"}

O segundo passou inteiro. O token foi para o log em texto puro, e nada avisou — não há erro, não há warning. Por isso cada nome aparece duas vezes na lista do logger.js: 'senha' e '*.senha'.

A lição maior: redact é rede de segurança, não a defesa principal. A defesa principal é a próxima seção — nomear o que entra no log, em vez de despejar o objeto e confiar que a lista de exclusão cobre tudo.

6. Uma linha por requisição

O pino-http registra automaticamente cada requisição que entra e cada resposta que sai. Sem configurar nada ele já funciona — mas os padrões dele logam os headers inteiros, que é exatamente o que não se quer.

Criar middlewares/registrarRequisicoes.js — arquivo novo:

const crypto = require('node:crypto');
const pinoHttp = require('pino-http');

const logger = require('../logger');

const registrarRequisicoes = pinoHttp({
  logger,

  // Reaproveita o id que veio do proxy, se veio. É isso que permite seguir
  // uma requisição por vários serviços; sem isso cada um inventa o seu.
  genReqId(req, res) {
    const doProxy = req.headers['x-request-id'];
    const id = doProxy || crypto.randomUUID();
    res.setHeader('X-Request-Id', id);
    return id;
  },

  // O orquestrador bate no /health a cada poucos segundos. Sem isso,
  // o log vira uma parede de health check.
  autoLogging: {
    ignore: (req) => req.url.startsWith('/health'),
  },

  customLogLevel(req, res, err) {
    if (err || res.statusCode >= 500) return 'error';
    if (res.statusCode >= 400) return 'warn';
    return 'info';
  },

  customSuccessMessage(req, res) {
    return `${req.method} ${req.originalUrl} ${res.statusCode}`;
  },

  serializers: {
    req: (req) => ({
      id: req.id,
      metodo: req.method,
      url: req.originalUrl || req.url,
      ip: req.remoteAddress,
    }),
    res: (res) => ({ status: res.statusCode }),
  },
});

module.exports = registrarRequisicoes;

Os serializers são o ponto central: eles definem exatamente quais campos de req e res vão para o log. Tudo que não estiver ali simplesmente não é escrito — headers, cookies e corpo inclusive. É a defesa por lista de permissão, e é mais confiável que a lista de exclusão da seção anterior.

O customLogLevel resolve outra coisa: sem ele, um 401 e um 200 saem no mesmo nível. Com ele, dá para filtrar level >= warn e ver só o que deu errado.

autoLogging.ignore existe por um motivo prático que você só descobre em produção: o orquestrador bate no /health a cada poucos segundos, para sempre. Sem o filtro, o log vira uma parede de health check e o evento que importa se perde no meio.

7. Request id

Cada requisição ganha um identificador, e ele aparece em toda linha de log daquela requisição. É o que transforma um log em algo investigável: com um id em mãos, você filtra e vê a história inteira de um pedido só.

O genReqId faz duas coisas de uma vez:

  1. Reaproveita o X-Request-Id que veio do proxy, se veio. Isso é o que permite seguir a mesma requisição por vários serviços — se cada um inventar o próprio id, a trilha quebra na fronteira.
  2. Devolve o id no header da resposta. Quando um usuário reclama de um erro, ele consegue te passar o id, e você vai direto na linha certa.
# sem header: a API gera
curl -s -D - -o /dev/null localhost:3000/aulas | grep -i x-request-id
# X-Request-Id: c5b7af72-4dfa-4006-8468-18e9effa3834

# com header: a API reaproveita
curl -s -D - -o /dev/null -H 'X-Request-Id: trace-123' localhost:3000/aulas | grep -i x-request-id
# X-Request-Id: trace-123

Dentro de qualquer rota, req.log é um logger já carimbado com esse id. Logar de dentro de uma rota vira req.log.warn({ aula_id }, 'aula lotada'), e o id vem junto sem você passar nada.

8. Ligando no app.js

Alterar app.js — dois require a mais, junto dos que já existem:

const corsConfigurado = require('./middlewares/cors');
const registrarRequisicoes = require('./middlewares/registrarRequisicoes');
const { router: healthRouter } = require('./routes/health');

Alterar app.js — o bloco de middlewares logo depois do const app = express(). A ordem importa, e os comentários dizem por quê:

const app = express();

// Primeiro de todos: assim até o que morre no rate limit aparece no log.
app.use(registrarRequisicoes);

app.use(helmet());
app.use(corsConfigurado);

// Antes do rate limit: as sondas do orquestrador batem a cada poucos
// segundos e não podem ser barradas por ele.
app.use('/health', healthRouter);

app.use(limitadorGlobal);

Alterar app.js — no middleware de erro, no fim do arquivo, troque o console.error:

  console.error(err);
  req.log.error({ err }, 'erro não tratado');
  res.status(500).json({ erro: 'Erro interno no servidor' });

Duas coisas mudam aí. O erro passa a sair como JSON com stack em campo próprio, e — o que importa mais — passa a carregar o request id. Um 500 no log agora se liga à requisição que o causou.

10. Vivo não é o mesmo que pronto

Quem hospeda a sua API precisa perguntar como ela está, e a pergunta se divide em duas que têm consequências opostas:

Liveness — "está vivo?"Readiness — "posso mandar tráfego?"
RotaGET /healthGET /health/ready
VerificaNada além do próprio processoAs dependências — aqui, o banco
Se falharO container é reiniciadoPara de receber tráfego, mas continua vivo

A liveness não pode consultar o banco. É o erro mais comum nessa parte, e ele é destrutivo: se o Postgres piscar por trinta segundos, o /health passa a falhar, o orquestrador conclui que a aplicação travou e mata o container — que sobe de novo, tenta o banco, falha de novo, e entra em ciclo de reinício. Um problema de trinta segundos no banco vira uma indisponibilidade total da API.

Reiniciar o processo não conserta um banco fora do ar. Por isso o banco é assunto da readiness: ela tira a instância do balanceador enquanto o problema dura, e devolve quando passa, sem matar ninguém.

11. As duas rotas

Criar routes/health.js — arquivo novo:

const express = require('express');
const pool = require('../db/pool');

const router = express.Router();

// Vira true quando o processo começa a desligar (SIGTERM).
let desligando = false;
const iniciarDesligamento = () => {
  desligando = true;
};

// LIVENESS — "o processo está vivo?"
// Não toca em banco, nem em rede, nem em disco de propósito: se responder
// 503 aqui, o orquestrador MATA o container.
router.get('/', (req, res) => {
  res.json({
    status: 'ok',
    uptime_segundos: Math.floor(process.uptime()),
    timestamp: new Date().toISOString(),
  });
});

// READINESS — "dá para me mandar tráfego?"
// Aqui sim o banco entra: sem banco a API não serve para nada, mas o
// processo continua saudável e não precisa ser reiniciado.
router.get('/ready', async (req, res) => {
  if (desligando) {
    return res.status(503).json({ status: 'desligando' });
  }

  try {
    await pool.query('SELECT 1');
    res.json({ status: 'ok', banco: 'ok' });
  } catch (err) {
    req.log.error({ err }, 'readiness falhou: banco inacessível');
    res.status(503).json({ status: 'indisponivel', banco: 'inacessivel' });
  }
});

module.exports = { router, iniciarDesligamento };

O módulo exporta dois valores em vez de só o router: o iniciarDesligamento é o que a seção 13 vai usar para a readiness começar a recusar tráfego antes de o processo fechar a porta.

Repare também no req.log.error dentro do catch: quando a readiness falha, o motivo fica registrado com request id. Sem isso você teria um 503 sem explicação.

SELECT 1 é de propósito a consulta mais barata possível. A readiness roda a cada poucos segundos, para sempre — qualquer coisa mais pesada aí vira carga constante no banco. E ela responde a "o pool consegue falar com o Postgres", que é tudo que precisa responder.

12. Onde montar, e a armadilha do rate limit

O app.use('/health', healthRouter) da seção 8 está posicionado antes do limitadorGlobal, e isso não é detalhe de estilo.

O limitador da parte 9 permite 300 requisições por IP a cada 15 minutos. A sonda do orquestrador vem sempre do mesmo IP e bate a cada poucos segundos: em 15 minutos são umas 300 chamadas só dela. Montado depois do limitador, o /health começaria a responder 429 — e o orquestrador, que só entende "não respondeu 200", reiniciaria um container perfeitamente saudável.

O padrão por trás disso

É a terceira vez na trilha que a ordem dos middlewares muda o comportamento: o rate limit antes do body parser (parte 9), o log antes do rate limit (seção 8), o health check antes do limitador (aqui). Middleware em Express é uma fila, e o que vem antes decide se o de trás chega a rodar.

Colocar o log em primeiro lugar tem a mesma lógica invertida: você quer que ele rode antes de tudo, para que uma requisição barrada por rate limit também apareça no log. Se ela não aparecer, um ataque de força bruta bem-sucedido em barrar seus usuários fica invisível.

13. Desligar direito

Quando a plataforma precisa parar a sua aplicação — deploy novo, escala para baixo, container movido de máquina — ela não mata o processo de imediato. Ela manda SIGTERM e espera alguns segundos.

O padrão do Node é morrer na hora ao receber SIGTERM. Isso significa: requisições em andamento cortadas no meio, transações abertas abandonadas, conexões do pool derrubadas sem aviso ao Postgres.

Alterar index.js — substitua o arquivo inteiro. Ele é pequeno e muda quase todo:

require('dotenv').config();

const app = require('./app');
const logger = require('./logger');
const pool = require('./db/pool');
const { iniciarDesligamento } = require('./routes/health');

const PORT = process.env.PORT || 3000;

const servidor = app.listen(PORT, () => {
  logger.info({ porta: Number(PORT) }, 'servidor no ar');
});

// O orquestrador manda SIGTERM e espera. Se o processo sair na hora,
// as requisições em andamento morrem no meio.
function desligar(sinal) {
  logger.info({ sinal }, 'desligando');

  // Readiness passa a responder 503: o balanceador para de mandar
  // tráfego novo antes de a porta fechar.
  iniciarDesligamento();

  servidor.close(async () => {
    await pool.end();
    logger.info('conexões encerradas');
    process.exit(0);
  });

  // Rede de segurança: se algo travar, não fica pendurado para sempre.
  setTimeout(() => {
    logger.error('desligamento demorou demais, saindo à força');
    process.exit(1);
  }, 10_000).unref();
}

process.on('SIGTERM', () => desligar('SIGTERM'));
process.on('SIGINT', () => desligar('SIGINT'));

A ordem do desligamento é o que importa:

  1. iniciarDesligamento() — a readiness passa a responder 503. O balanceador para de mandar requisição nova para esta instância antes de ela fechar a porta.
  2. servidor.close() — para de aceitar conexões, mas deixa terminar as que já estão em andamento.
  3. pool.end() — só depois disso as conexões com o banco são devolvidas.
  4. O setTimeout de 10 segundos é a rede de segurança: se alguma requisição travar, o processo sai à força em vez de ficar pendurado até a plataforma perder a paciência e mandar SIGKILL.

O .unref() no timer é o detalhe que faz diferença: sem ele, o próprio setTimeout segura o processo vivo pelos 10 segundos inteiros, mesmo quando tudo já fechou em 50 milissegundos.

15. Erros comuns

  1. Liveness que consulta o banco — um soluço no Postgres vira ciclo de reinício do container (seção 10). É o erro mais caro desta parte.
  2. Health check depois do rate limit — as sondas tomam 429 e o orquestrador reinicia uma aplicação saudável (seção 12).
  3. Confiar só no redact — '*.campo' não cobre a raiz do objeto, e a falha é silenciosa (seção 5). Nomeie o que entra no log em vez de listar o que sai.
  4. Logar o objeto req inteiro — vai junto o header Authorization, o cookie de refresh e o corpo com senha. Use serializers.
  5. Escrever log em arquivo — em container, escreva no stdout e deixe a plataforma coletar (seção 2).
  6. Deixar o pino-pretty em produção — ele é dependência de desenvolvimento; o agregador quer o JSON cru.
  7. Não logar o health check e também não logar o motivo do 503 — filtrar a sonda é certo, mas a falha da readiness precisa aparecer.
  8. Esquecer o .unref() no timer de desligamento — o processo demora os 10 segundos inteiros para sair, sempre.
  9. process.exit() direto no SIGTERM — mata requisição em andamento no meio. É o que o Node já faz sozinho, e é o que a seção 13 veio evitar.

16. O que vem a seguir

A API agora conta o que faz e responde por si. O que falta é ela existir fora do seu computador:

  1. Dockerfile do app — o Postgres roda em container desde a parte 1; a API, não. Empacotá-la é o que torna o deploy reproduzível: imagem multi-stage, usuário sem privilégio, npm ci --omit=dev, e o HEALTHCHECK apontando para a rota que esta parte criou.
  2. Deploy com HTTPS — variáveis de produção, banco gerenciado, migrations no processo de deploy (parte 14), e o momento em que trust proxy (parte 9), Secure no cookie (parte 11) e o X-Request-Id vindo do balanceador (seção 7) finalmente entram em ação.

São dois problemas diferentes — empacotar e publicar —, então viram duas partes.

O momento que vale a pena aqui é o teste do banco derrubado: ver o /health responder 200 enquanto o /health/ready responde 503. Parece contraditório até você lembrar que são perguntas diferentes, com consequências opostas — e é essa distinção que evita que um problema pequeno no banco derrube a API inteira. Volta com dúvidas, principalmente se o log aparecer sem cor no npm run dev (o pipe do pretty) ou se alguma linha trouxer campo que não devia.
