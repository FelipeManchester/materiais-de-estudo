Projeto Studio Fit — Trilha Node + Express — Parte 21

Empacotando com Docker

O Postgres roda em container desde a parte 1. A API, não — ela depende do Node que está instalado na sua máquina, do arquivo .env que só existe aí, e de você lembrar a ordem dos comandos. Esta parte transforma a aplicação em uma imagem que sobe igual em qualquer lugar.

1. "Na minha máquina funciona"

Para outra pessoa rodar esta API hoje, ela precisa: instalar a versão certa do Node, clonar o repositório, rodar npm install, subir o Postgres, criar um .env com quatro variáveis que ela precisa adivinhar, e rodar as migrations na ordem. Cada passo é uma chance de dar errado, e nenhum deles está escrito em lugar nenhum que o computador entenda.

Uma imagem Docker é essa lista virando arquivo. O que ela empacota:

Hoje depende deNa imagem
Node instalado na máquinaVem na imagem base, na versão fixada
npm install rodado à mãoPasso do build, com package-lock.json
O código no diretório certoCopiado para dentro, em /app
Você lembrar o comandoCMD, no fim do arquivo
Imagem e container

Imagem é o pacote parado — o resultado do docker build, imutável, igual em qualquer máquina. Container é uma execução dessa imagem, com variáveis de ambiente e rede próprias.

A distinção importa porque define o que vai dentro e o que vai fora: código e dependências entram na imagem; senha, URL do banco e segredo do JWT ficam de fora e chegam só quando o container sobe. É a mesma separação da parte 1, agora valendo também para a aplicação.

2. O que não entra na imagem

Antes do Dockerfile, o .dockerignore. Ele é o equivalente do .gitignore para o build, e vem primeiro por um motivo de segurança: sem ele, um COPY . . leva o seu .env para dentro da imagem — e imagem é distribuída.

Criar .dockerignore — arquivo novo, na raiz:

# O que NÃO entra na imagem.
node_modules
.git
.github
.gitignore

# Segredo nunca vai para dentro da imagem: as variáveis entram em tempo
# de execução, não em tempo de build.
.env
.env.test
.env.example
.env.test.example

# Só servem no seu computador.
tests
coverage
*.md
testar-corrida.js
Dockerfile
.dockerignore

Repare no que não está na lista: docs/. É tentador ignorar um diretório com esse nome, mas ali mora a especificação OpenAPI da parte 19, que o app.js importa. Sem ela a imagem quebra no boot com Cannot find module './docs/openapi'.

O critério não é o nome do diretório, é se a aplicação precisa dele para rodar. tests/ não precisa. migrations/ precisa — a seção 12 explica por quê.

Ignorar node_modules não é só economia: as dependências são reinstaladas dentro da imagem, para o sistema operacional dela. Copiar as suas leva binários compilados para a plataforma errada.

3. O Dockerfile

Criar Dockerfile — arquivo novo, na raiz:

FROM node:24-alpine

# Muda o comportamento de várias bibliotecas, e é o que o logger da parte 20
# lê para decidir o nível de log.
ENV NODE_ENV=production

WORKDIR /app

# Copiado ANTES do resto do código: esta camada só é refeita quando as
# dependências mudam, não a cada alteração de rota.
COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force

# O código vai como usuário node, não como root.
COPY --chown=node:node . .

USER node

EXPOSE 3000

# Usa a rota de liveness da parte 20. fetch é global no Node 24 — não
# precisa instalar curl nem wget na imagem só para isso.
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD node -e "fetch('http://localhost:3000/health').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"

# Forma exec (lista, não string): o node vira PID 1 e recebe o SIGTERM
# que o desligamento gracioso da parte 20 espera.
CMD ["node", "index.js"]

Vinte linhas, e cada uma resolve um problema específico. As próximas cinco seções destrincham as decisões que não são óbvias.

Por que não multi-stage? É comum ver Dockerfiles de Node com dois FROM: um estágio compila, outro só recebe o resultado. Isso vale quando existe etapa de build — TypeScript a transpilar, bundler a rodar. Esta API é JavaScript puro: não há nada para compilar, e o segundo estágio só receberia os mesmos arquivos. Um estágio só, com as camadas na ordem certa (seção 4), entrega o mesmo tamanho sem a complexidade.

4. A ordem das camadas é cache

Cada instrução do Dockerfile vira uma camada, e o Docker reaproveita as camadas cujas entradas não mudaram. É por isso que o package.json é copiado sozinho, antes do resto do código:

COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force

COPY --chown=node:node . .

Com essa ordem, alterar uma rota invalida só a última camada — o npm ci é reaproveitado. Com a ordem invertida (COPY . . antes), qualquer alteração em qualquer arquivo invalidaria a instalação inteira das dependências, e todo build baixaria tudo de novo.

No build medido aqui, a diferença é entre 20 segundos e menos de 2.

O npm cache clean --force está na mesma instrução RUN de propósito: camada de imagem é imutável, então apagar o cache numa instrução seguinte não diminuiria nada — o cache continuaria dentro da camada anterior, só invisível.

5. --omit=dev, e o que isso deixa de fora

npm ci --omit=dev instala só as dependencies, ignorando as devDependencies. Jest, ESLint, nodemon, supertest e o pino-pretty da parte 20 não têm o que fazer em produção.

E npm ci, não npm install: ele exige o package-lock.json e instala exatamente as versões travadas nele. É a mesma decisão da parte 17 para o CI, pelo mesmo motivo — build reproduzível.

Isso tem uma consequência que só aparece quando você tenta migrar: o node-pg-migrate está em devDependencies, então ele não entra na imagem. Rodar npm run migrate:up dentro do container falha com sh: node-pg-migrate: not found. A seção 12 resolve.

6. Não rode como root

Por padrão, um container Node roda como root. Se alguém conseguir execução de código pela aplicação, herda root dentro do container — e a partir daí a distância até a máquina hospedeira depende só de haver alguma falha de isolamento.

As imagens oficiais do Node já trazem um usuário sem privilégio chamado node (uid 1000). Duas linhas usam ele:

COPY --chown=node:node . .
USER node

A ordem importa: o USER vem depois do npm ci, porque a instalação precisa escrever em /app. E o --chown no COPY entrega o código já com o dono certo, em vez de exigir um chown -R depois — que duplicaria os arquivos numa camada nova.

docker compose exec api id
# uid=1000(node) gid=1000(node) groups=1000(node)

7. PID 1 e o sinal que ninguém escuta

Quando o container sobe, o processo do CMD vira o PID 1 — e PID 1 no Linux tem uma regra especial: os tratamentos padrão de sinal não se aplicam a ele. Um processo comum que recebe SIGTERM morre; o PID 1 que recebe SIGTERM sem ter registrado um handler simplesmente ignora.

É aqui que a parte 20 se paga. Medi docker stop nas duas versões, mesma imagem, mesma aplicação, mudando só o index.js:

Versãodocker stopO que aconteceu
Com o handler da parte 200,19 sSIGTERM tratado, readiness em 503, pool encerrado, saída limpa
Sem o handler10,12 sSIGTERM ignorado; o Docker esperou o timeout e mandou SIGKILL

Dez segundos por container, em todo deploy, com as requisições em andamento cortadas no fim. E nada avisa: o container para, o deploy conclui, ninguém percebe.

Sobre a forma exec. A recomendação de escrever CMD ["node", "index.js"] em vez de CMD node index.js costuma vir acompanhada da história de que a forma shell impede o sinal de chegar. Testei as duas nesta imagem, e também CMD ["npm", "start"]: as três desligaram graciosamente, em torno de 0,1 s. O sh do Alpine faz exec quando o comando é simples, e o npm 11 repassa sinais.

A forma exec continua sendo a certa — menos processos na árvore, o node diretamente como PID 1, sem shell nem npm no meio consumindo memória. Mas o que de fato quebra o desligamento é a aplicação não tratar o sinal, não a sintaxe do CMD.

8. HEALTHCHECK sem instalar curl

A instrução HEALTHCHECK diz ao Docker como perguntar se o container está saudável. Ela aponta para a rota de liveness da parte 20 — a que não consulta o banco, pelo motivo explicado lá.

HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD node -e "fetch('http://localhost:3000/health').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"

A maioria dos exemplos usa curl, que não existe na imagem node:alpine — e instalá-lo só para isso engorda a imagem e aumenta a superfície de ataque. O Node 24 tem fetch global: o binário que já está lá resolve.

O --start-period=10s é o detalhe fácil de esquecer: durante esse tempo, falhas não contam. Sem ele, um container que demora a subir seria marcado como não saudável antes de terminar de iniciar.

docker compose ps
# api  running  Up 10 seconds (healthy)
# db   running  Up 15 seconds (healthy)

9. O .env que não existe mais

Dentro do container não há .env — o .dockerignore o excluiu, de propósito. As variáveis chegam pelo ambiente, colocadas lá pelo compose ou pela hospedagem.

O dotenv continua no index.js e não atrapalha: se não achar o arquivo, segue em frente e usa o que já está no ambiente. Só que ele escreve na saída ao carregar — e isso estraga o log estruturado da parte 20:

◇ injected env (0) from .env // tip: ⌘ override existing { override: true }
{"level":"info","time":"2026-08-25T19:32:29.998Z","servico":"studio-fit-api","porta":3000,"msg":"servidor no ar"}

A primeira linha não é JSON. Um agregador que espera uma linha por evento vai descartá-la ou, pior, registrar um erro de parsing a cada boot.

Alterar index.js — primeira linha do arquivo:

require('dotenv').config();
require('dotenv').config({ quiet: true });

Com isso toda linha da saída volta a ser JSON válido — que era a promessa da parte 20.

10. A API entra no compose

O docker-compose.yml já sobe o Postgres. Agora ele sobe os dois, e passa a ser o único comando necessário para rodar o projeto inteiro.

Alterar docker-compose.yml — o serviço db ganha um healthcheck e perde a publicação de porta; o serviço api é novo:

services:
  db:
    image: postgres:16
    restart: always
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?defina POSTGRES_PASSWORD no .env}
      POSTGRES_DB: estudo
    ports:                                   # REMOVER — vira o comentário abaixo
      - '127.0.0.1:5432:5432'
    # NOVO — sem 'ports', o banco não é publicado no host. Só quem está na
    # rede do compose — a api — o alcança. Se quiser abrir o psql ou o
    # DBeaver da sua máquina, descomente:
    # ports:
    #   - '127.0.0.1:5432:5432'
    volumes:
      - pgdata:/var/lib/postgresql/data
    # NOVO — a api espera este healthcheck antes de subir.
    healthcheck:
      test: ['CMD-SHELL', 'pg_isready -U postgres']
      interval: 5s
      timeout: 3s
      retries: 10

  # NOVO — o serviço inteiro, daqui até o fim do bloco
  api:
    build: .
    restart: always
    depends_on:
      db:
        condition: service_healthy
    environment:
      # 'db' é o nome do serviço: dentro da rede do compose ele resolve
      # para o container do Postgres. 'localhost' aqui seria o próprio
      # container da api.
      DATABASE_URL: postgresql://postgres:${POSTGRES_PASSWORD}@db:5432/estudo
      JWT_SECRET: ${JWT_SECRET:?defina JWT_SECRET no .env}
      CORS_ORIGINS: ${CORS_ORIGINS:-http://localhost:5173}
      PORT: 3000
    ports:
      - '127.0.0.1:3000:3000'

volumes:
  pgdata:

O depends_on com condition: service_healthy é o que evita a corrida clássica: sem ele, o compose considera o banco "pronto" assim que o container inicia, e a API tenta conectar antes de o Postgres aceitar conexão.

O banco saiu do host

O ports do db virou comentário. Com a API dentro da rede do compose, publicar a porta 5432 no host deixou de ser necessário — e porta publicada é superfície exposta. Agora só quem está na rede do compose alcança o banco.

Se você quiser abrir o psql ou um cliente gráfico da sua máquina, descomente. É uma escolha consciente entre conveniência de desenvolvimento e exposição, não um padrão a carregar para produção.

11. A rede do compose muda o endereço do banco

Repare na DATABASE_URL do serviço api:

DATABASE_URL: postgresql://postgres:${POSTGRES_PASSWORD}@db:5432/estudo

O host é db, não localhost. Essa é a troca mental que o container exige: dentro dele, localhost é o próprio container — não a sua máquina, não o Postgres. O compose cria uma rede onde cada serviço é alcançável pelo nome do serviço, e é assim que a API acha o banco.

E a porta é 5432, a porta real do Postgres dentro da rede, mesmo com o ports comentado. Publicação de porta serve para o mundo fora do Docker; entre containers, a rede interna já liga tudo.

Isso também explica por que o .env da sua máquina não serve dentro do container sem ajuste: lá a DATABASE_URL aponta para localhost:5432, que dentro do container não é o banco. É por isso que o compose monta a URL do zero, em vez de repassar a variável.

12. Migrations dentro do container

A parte 14 deixou o esquema do banco versionado em migrations/. Só que, como a seção 5 avisou, o node-pg-migrate está em devDependencies e o --omit=dev o deixa de fora da imagem.

É uma decisão de verdade, com dois caminhos: rodar as migrations de fora (num job separado, com as dev deps instaladas) ou deixar a própria imagem capaz de migrar. Para este projeto, o segundo é mais simples — e é o que a maioria das hospedagens espera, já que o comando de deploy delas roda dentro do container.

Alterar package.json — mova node-pg-migrate de devDependencies para dependencies, e rode npm install depois para o lock refletir a mudança:

  "dependencies": {
    "jsonwebtoken": "^9.0.3",
    "node-pg-migrate": "^9.0.0",
    "pg": "^8.22.0",
    ...
  },
  "devDependencies": {
    "jest": "^30.4.2",
    "node-pg-migrate": "^9.0.0",
    "nodemon": "^3.1.11",
    ...
  }

Com isso, migrar é um comando no container que já está no ar:

docker compose exec api npm run migrate:up
# ...
# INSERT INTO "public"."pgmigrations" (name, run_on) VALUES ('1787666415450_indices-para-ordenacao', NOW());
# Migrations complete!

Resista à tentação de colocar as migrations no CMD (CMD ["sh", "-c", "npm run migrate:up && node index.js"]). Funciona com um container e quebra com dois: subindo três réplicas, as três tentam migrar ao mesmo tempo, no mesmo banco. Migration é passo de deploy, executado uma vez; não é passo de boot, executado por instância.

13. Testando

# 1) constrói e sobe os dois serviços
docker compose up -d --build

# 2) ambos precisam ficar healthy (o do db é o pg_isready, o da api é o HEALTHCHECK)
docker compose ps
# api  running  Up 10 seconds (healthy)
# db   running  Up 15 seconds (healthy)

# 3) migrations num banco novo
docker compose exec api npm run migrate:up
# Migrations complete!

# 4) a API responde de dentro do container
curl -s -o /dev/null -w "%{http_code}\n" localhost:3000/aulas         # 200
curl -s -o /dev/null -w "%{http_code}\n" localhost:3000/instrutores   # 200
curl -s -o /dev/null -w "%{http_code}\n" localhost:3000/docs/         # 200
curl -s localhost:3000/health
# {"status":"ok","uptime_segundos":18,"timestamp":"..."}

Três verificações que valem mais que as outras:

# a) o processo NÃO é root
docker compose exec api id
# uid=1000(node) gid=1000(node) groups=1000(node)

# b) o segredo não vazou para dentro da imagem
docker compose exec api sh -c 'ls -a | grep "^\.env" || echo "nenhum .env na imagem"'
# nenhum .env na imagem

# c) toda linha do log é JSON — nada de banner do dotenv
docker compose logs api --no-log-prefix | head -3

E o desligamento, que é o que amarra esta parte com a anterior:

time docker stop $(docker compose ps -q api)
# real  0m0,19s      <- com o handler da parte 20

docker compose logs api --no-log-prefix | tail -2
# {"level":"info",...,"sinal":"SIGTERM","msg":"desligando"}
# {"level":"info",...,"msg":"conexões encerradas"}

Se esse time der por volta de 10 segundos, o SIGTERM não está sendo tratado — volte na parte 20, seção 13.

14. Erros comuns

  1. COPY . . sem .dockerignore — o .env entra na imagem, e imagem é distribuída. É a versão em container do problema que a auditoria da parte anterior encontrou no git.
  2. Ignorar docs/ ou migrations/ — os dois são código de aplicação aqui. O primeiro quebra o boot; o segundo, o deploy (seção 2).
  3. COPY . . antes do npm ci — joga fora o cache de dependências a cada alteração de código (seção 4).
  4. Rodar como root — é o padrão, e é preciso escrever USER node para sair dele (seção 6).
  5. Aplicação sem handler de SIGTERM — 10 segundos a mais em todo deploy, com requisições cortadas no fim (seção 7).
  6. HEALTHCHECK com curl — não existe na imagem alpine. E apontar o health check do Docker para a rota de readiness repete o erro da parte 20: um soluço do banco vira reinício de container.
  7. localhost na DATABASE_URL dentro do container — localhost é o próprio container. Use o nome do serviço (seção 11).
  8. Migration no CMD — quebra com mais de uma réplica (seção 12).
  9. npm install em vez de npm ci — build deixa de ser reproduzível, exatamente como na parte 17.
  10. Esquecer o quiet: true no dotenv — uma linha não-JSON no começo de todo log (seção 9).

15. O que vem a seguir

A aplicação está empacotada e sobe com um comando. Falta o último passo: ela existir num endereço que não seja o seu computador.

Deploy com HTTPS — escolher onde hospedar, banco gerenciado em vez de container, variáveis de ambiente na plataforma, migrations como passo do deploy (seção 12), e o momento em que três coisas da trilha finalmente entram em ação: trust proxy para o rate limit contar o IP certo (parte 9), Secure no cookie de refresh (parte 11) e o X-Request-Id vindo do balanceador (parte 20).

É a última parte do projeto.

O momento que vale a pena aqui é apagar o node_modules da sua máquina, rodar docker compose up -d --build e ver a API responder do mesmo jeito. É a primeira vez que o projeto não depende de nada que você configurou à mão. Volta com dúvidas, principalmente se o build ficar lento (provável ordem das camadas) ou se a API não achar o banco (provável localhost onde deveria estar db).
